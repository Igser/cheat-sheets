# Лаборатория: транзакции

Отработка темы «транзакции и конкурентность» на живых базах: PostgreSQL и MySQL
из стенда `practice`. Каждый сценарий — это то, что нельзя понять по тексту,
но видно за минуту в двух окнах терминала.

Материал по теме в конспектах: [sql.html](../../../sql.html) — «Транзакции и уровни
изоляции», «Блокировки и deadlock», «Optimistic и pessimistic locking», «Уровни
изоляции и аномалии» (таблица 7), «Обработка ошибок и вложенные транзакции».

## Подготовка

```powershell
cd D:\projects\cheat-sheets\practice
docker compose up -d                       # ядро стенда, если ещё не поднято

# схема лаборатории
Get-Content .\lab\transactions\00-schema.sql -Raw | docker exec -i cs-postgres psql -U practice -d practice
Get-Content .\lab\transactions\mysql\00-schema.sql -Raw | docker exec -i cs-mysql mysql -upractice -psecret
```

Схема `lab` живёт отдельно от `blog` / `shop` / `bench` и не пересекается
с заданиями на проектирование из конспекта.

## Как работать со сценарием

Сценарии рассчитаны на **два окна терминала**. Открываем в каждом:

```powershell
docker exec -it cs-postgres psql -U practice -d practice     # окно A и окно B
docker exec -it cs-mysql mysql -upractice -psecret lab       # для MySQL-части
```

Дальше открываем файл сценария и выполняем блоки строго по номерам: шаги с меткой
`[A]` — в первом окне, `[B]` — во втором. Копипаст целого файла ничего не покажет:
весь смысл в том, что транзакции пересекаются во времени.

Полезно третье окно для наблюдения:

```sql
SELECT * FROM lab.activity;    -- кто в транзакции и сколько уже висит
SELECT * FROM lab.blockers;    -- кто кого блокирует
```

Сброс состояния перед каждым сценарием: `SELECT lab.reset();` (Postgres),
`CALL reset_lab(1);` (MySQL).

| `s4-locks.sql` | `FOR UPDATE`, `NOWAIT`, `SKIP LOCKED`, advisory | Почему воркеры очереди без `SKIP LOCKED` не масштабируются |

| `s7-savepoint.sql` | Ошибки, `SAVEPOINT`, забытые транзакции | Почему после ошибки в Postgres не работает даже `SELECT` |
| `s8-boundaries.sql` | Границы транзакции | Ни одного сетевого вызова между `BEGIN` и `COMMIT` |

это то, что спрашивают на собеседовании и что чаще всего ломается в проде.

## Конкурентность под нагрузкой

Одиночные сессии показывают механику, но не показывают, что происходит на 50 клиентах.
Для этого — `pgbench`, он уже лежит в контейнере с Postgres:

```powershell
.\run-concurrency.ps1                  # оба блока
.\run-concurrency.ps1 -Only oversell   # быстро, секунды
.\run-concurrency.ps1 -Only deadlock   # ~3 минуты: каждый дедлок ждёт deadlock_timeout
```

### Замеры на этом стенде

Оверселл, 50 покупателей на 1 товар:

| Вариант покупки | Остаток | Заказов | Итог | tps |
|---|---|---|---|---|
| наивно: `SELECT`, проверка в коде, `UPDATE qty = :avail - 1` | 0 | **50** | продали 50 штук из одной | 484 |
| `SELECT ... FOR UPDATE` + `UPDATE` | 0 | 1 | корректно | 843 |
| `UPDATE ... WHERE qty > 0` + `INSERT` из `RETURNING` | 0 | 1 | корректно | 1037 |

Наивный вариант не уводит остаток в минус — он делает хуже: каждая транзакция
пишет одно и то же абсолютное значение `0`, и 49 покупателей получают заказ
на несуществующий товар. Именно так выглядит потерянное обновление в проде.

Дедлоки, 10 клиентов × 5 переводов между двумя счетами:

| Вариант | Прошло | Дедлоков | Ретраев | Время |
|---|---|---|---|---|
| случайный порядок захвата | 11/50 | 39 (78%) | — | 27 с |
| то же + `--max-tries 10` | 42/50 | 8 (16%) | 238 | 141 с |
| единый порядок захвата по `id` | 50/50 | **0** | — | **0.1 с** |

Три числа, которые стоит запомнить для собеседования: ретрай снял 78% отказов
до 16%, но заплатил пятикратным временем и 238 повторами. Сортировка строк перед
захватом убрала проблему целиком и бесплатно.

## Чек-лист по теме

Пройденной тему можно считать, когда отвечаете без подготовки:

- [ ] Чем `READ COMMITTED` отличается от `REPEATABLE READ` и что при этом видит клиент.
- [ ] Почему повышение уровня изоляции не спасает от lost update.
- [ ] Три способа защитить остаток на складе и когда какой дороже.
- [ ] Что делает `SKIP LOCKED` и почему без него очередь не масштабируется.
- [ ] Как воспроизвести deadlock и два способа его не допустить.
- [ ] Что такое write skew и почему его ловит только `SERIALIZABLE`.
- [ ] Какие SQLSTATE обязан ретраить код записи (`40001`, `40P01`) и почему целиком.
- [ ] Что нельзя делать между `BEGIN` и `COMMIT`.
- [ ] Чем поведение MySQL отличается от PostgreSQL: грязное чтение, gap-локи,
      транзакция после ошибки, DDL внутри транзакции.

## Проверено на этом стенде

Все утверждения в сценариях прогнаны на живых контейнерах, а не взяты из головы:

- `READ UNCOMMITTED` в PostgreSQL принимается и показывается как запрошенный,
  но грязного чтения не даёт; в MySQL на том же уровне чужие незакоммиченные
  данные видны (проверено: `500.00` при откаченной транзакции).
- `REPEATABLE READ` в PostgreSQL на конкурентной записи даёт
  `could not serialize access due to concurrent update`; MySQL молча применяет
  изменение к текущей версии строки.
- Write skew на `REPEATABLE READ` проходит без ошибок (осталось 0 дежурных),
  на `SERIALIZABLE` ловится с `Reason code: Canceled on identification as a pivot`.
- В PostgreSQL после ошибки транзакция переходит в aborted и не выполняет даже
  `SELECT`; `COMMIT` отвечает `ROLLBACK`. В MySQL следующий `SELECT` работает,
  и `COMMIT` сохраняет первую вставку.
- DDL в PostgreSQL откатывается вместе с транзакцией; в MySQL `ALTER TABLE`
  делает неявный коммит, и `ROLLBACK` уже ничего не отменяет.
- Gap-лок в InnoDB: вставка внутрь заблокированного диапазона падает по
  `Lock wait timeout`, вставка вне диапазона проходит мгновенно.
