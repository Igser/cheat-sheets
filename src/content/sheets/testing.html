Тестирование для PHP-разработчиков

Тесты пишут не ради тестов и не ради процента покрытия. Их пишут ради одной вещи: возможности менять код без страха. Проект без тестов не «работает быстрее» — он просто платит за скорость позже, когда любая правка требует ручной проверки половины системы, а рефакторинг откладывается до бесконечности, потому что никто не знает, что сломается.

Главная ошибка новичка — тестировать реализацию: моки на всё подряд, проверка того, что метод вызвал другой метод. Такие тесты ломаются при каждом рефакторинге и ничего не гарантируют, поэтому команда начинает их ненавидеть и в итоге удаляет. Хороший тест проверяет наблюдаемое поведение и остаётся зелёным, пока поведение не изменилось, — сколько бы раз вы ни переписывали внутренности.

Конспект идёт от первого теста к стратегии: PHPUnit и структура теста → интеграция с базой, HTTP-тесты, внешние сервисы, легаси, TDD → выбор, что покрывать чем, борьба с нестабильными тестами, мутационное тестирование и нагрузка. Смежные темы: PHP, базы данных, инфраструктура и CI, HTTP и API, Symfony, Laravel.

junior / зачем

Зачем тесты и пирамида

База

Тесты решают конкретную задачу: сделать изменение кода дешёвым. Без них каждая правка требует ручной проверки, а рефакторинг превращается в риск, на который никто не идёт. Поэтому проект без тестов со временем костенеет: код становится плохим не потому, что разработчики хуже, а потому что улучшать его страшно.

Пирамида — не догма, а следствие экономики: чем выше уровень, тем тест дороже писать, медленнее выполнять и сложнее диагностировать при падении. Отсюда правило: если поведение можно проверить на уровне ниже — проверяйте там. Но и обратная крайность вредна: тысяча модульных тестов при нуле интеграционных даёт систему, где каждая деталь работает, а вместе ничего не собирается.

ВажноЦена ошибки растёт на порядок с каждым шагом вправо. Баг, пойманный модульным тестом, стоит минуту. Тот же баг на код-ревью — полчаса двоих. В проде — инцидент, откат, разбор и потерянное доверие. Именно поэтому тесты окупаются, хотя на первый взгляд кажутся замедлением.
Типичный вопрос на собеседованииЗачем нужны тесты, если код и так работает?
Он работает сегодня. Тесты нужны для завтра: они позволяют менять код, обновлять зависимости и рефакторить, зная за секунды, что ничего не сломалось. Плюс они документируют ожидаемое поведение точнее комментариев и заставляют делать код тестируемым, а значит менее связанным. Без них цена изменений растёт до момента, когда проще переписать.

junior / инструмент

PHPUnit: первый тест

База

Тест — это обычный класс с методами. Структура любого теста укладывается в три шага: подготовить данные, выполнить действие, проверить результат. Держаться этой структуры полезно даже когда кажется, что можно короче: она делает тест читаемым без разбирательства.

phpСтруктура «подготовка → действие → проверка»
<?php
declare(strict_types=1);

namespace App\Tests\Unit\Order;

use PHPUnit\Framework\TestCase;
use PHPUnit\Framework\Attributes\{Test, DataProvider, CoversClass};

#[CoversClass(Cart::class)]
final class CartTest extends TestCase
{
    #[Test]
    public function итоговая_сумма_учитывает_скидку(): void
    {
        // Arrange — подготовка
        $cart = new Cart();
        $cart->add(new Item('A-100', Money::rub('1000.00'), qty: 2));

        // Act — одно действие, которое тестируем
        $total = $cart->total(new PercentDiscount(10));

        // Assert — проверка наблюдаемого результата
        $this->assertSame('1800.00', $total->amount());
        $this->assertSame('RUB', $total->currency());
    }

    #[Test]
    public function пустая_корзина_не_принимает_скидку(): void
    {
        $this->expectException(EmptyCartException::class);
        $this->expectExceptionMessage('Корзина пуста');

        (new Cart())->total(new PercentDiscount(10));
    }
}

Практический выводРусские имена методов в тестах — не экзотика, а рабочий приём: имя теста читается как утверждение о поведении, и при падении в отчёте видно смысл, а не testTotal2. Если команда предпочитает английский, работает то же правило: имя описывает поведение и условие, а не название метода.
Типичный вопрос на собеседованииИз чего состоит хороший модульный тест?
Из трёх частей: подготовка данных, одно действие, проверка результата. Он не ходит в базу, сеть и файловую систему, выполняется за миллисекунды, не зависит от порядка запуска и от других тестов, а его имя объясняет проверяемое поведение. Если в тесте несколько действий и десяток проверок — это уже сценарий, и его лучше разбить.

Что тестировать, а что нет

База

Самый частый источник бесполезных тестов — попытка покрыть всё подряд. Тест стоит денег дважды: при написании и при каждом изменении кода. Поэтому его пишут там, где он что-то гарантирует.

phpПоведение против реализации — главное различие
<?php
// ПЛОХО: тест знает, КАК устроен код, и ломается при любом рефакторинге
public function testRegister(): void
{
    $repo   = $this->createMock(UserRepository::class);
    $hasher = $this->createMock(Hasher::class);
    $mailer = $this->createMock(Mailer::class);

    $hasher->expects($this->once())->method('hash');        // проверяем вызов метода
    $repo->expects($this->once())->method('save');          // ...и ещё вызов
    $mailer->expects($this->once())->method('send');        // ...и ещё

    (new Registration($repo, $hasher, $mailer))->register('a@b.c', 'pass');
    // Ни одной проверки результата. Переименуете save в persist — тест упадёт,
    // хотя поведение не изменилось. Забудете сохранить пароль — тест пройдёт.
}

// ХОРОШО: тест знает, ЧТО должно произойти, и переживает рефакторинг
public function регистрация_создаёт_пользователя_и_шлёт_письмо(): void
{
    $users  = new InMemoryUserRepository();     // фейк, а не мок
    $mailer = new InMemoryMailer();

    (new Registration($users, new NativeHasher(), $mailer))
        ->register('a@b.c', 'secret123');

    $user = $users->findByEmail('a@b.c');
    $this->assertNotNull($user);
    $this->assertTrue($user->verifyPassword('secret123'));   // пароль реально работает
    $this->assertNotSame('secret123', $user->passwordHash);  // и не хранится как есть
    $this->assertCount(1, $mailer->sentTo('a@b.c'));
}
АнтипаттернТестировать приватные методы, делая их публичными «ради тестируемости». Если приватный метод хочется протестировать отдельно — это сигнал, что в классе прячется отдельная сущность: вынесите её в свой класс с публичным контрактом. Приватные детали проверяются через публичное поведение, иначе тест приколачивает реализацию гвоздями.
Типичный вопрос на собеседованииЧто означает «тестировать поведение, а не реализацию»?
Проверять наблюдаемый результат — возвращаемое значение, изменение состояния, отправленное сообщение, — а не то, какие методы и в каком порядке были вызваны внутри. Практический критерий: если после рефакторинга без изменения поведения тесты покраснели, они тестировали реализацию. Такие тесты не защищают от ошибок, зато мешают менять код — то есть работают ровно против своей цели.

Тестовые двойники

База

Двойник подставляется вместо настоящей зависимости, чтобы тест был быстрым и детерминированным. Их принято различать по назначению, и путаница в терминах — обычная тема уточняющих вопросов на собеседовании.

phpЗаглушка, шпион и фейк на одном примере
<?php
// Stub: просто отдаёт данные, никаких проверок вызовов
$rates = $this->createStub(ExchangeRates::class);
$rates->method('rate')->willReturn('92.50');

// Mock: ожидание задаётся до действия и проверяется автоматически
$gateway = $this->createMock(PaymentGateway::class);
$gateway->expects($this->once())
        ->method('charge')
        ->with($this->equalTo(Money::rub('1990.00')), $this->anything())
        ->willReturn(ChargeResult::success('ch_1'));

// Fake: маленькая настоящая реализация — обычно лучший вариант
final class InMemoryOrderRepository implements OrderRepository
{
    private array $orders = [];

    public function save(Order $order): void { $this->orders[$order->id] = $order; }
    public function find(string $id): ?Order { return $this->orders[$id] ?? null; }

    // Фейк может проверять инварианты не хуже настоящего хранилища
    public function countByCustomer(string $id): int
    {
        return count(array_filter($this->orders, fn ($o) => $o->customerId === $id));
    }
}
ВажноПравило выбора: подменяйте то, что вы не контролируете (внешний API, платёжный шлюз, отправка писем, часы), и не подменяйте то, что контролируете (собственные объекты-значения, чистые функции, простые сущности). Мок на каждую зависимость превращает тест в зеркало реализации: он повторяет структуру кода вместо проверки результата.
Типичный вопрос на собеседованииЧем мок отличается от стаба?
Стаб отдаёт подготовленные данные, чтобы код мог выполниться, и ничего не проверяет. Мок дополнительно задаёт ожидания: был ли метод вызван, сколько раз и с какими аргументами, — и проверяет их автоматически. Практическое правило: моки уместны, когда сам факт взаимодействия и есть проверяемое поведение (письмо отправлено, платёж списан); в остальных случаях лучше стаб или фейк.

junior / качество

Признаки хорошего теста

База

Тесты — такой же код, который придётся читать и поддерживать. Плохие тесты хуже отсутствия тестов: они создают ложное чувство защищённости и тормозят разработку, поэтому команда постепенно начинает их отключать.

phpОдин и тот же тест: до и после
<?php
// ДО: непонятно, что проверяется; при падении неясно, что сломалось
public function testOrder(): void
{
    $o = new Order(1, 'new', 1000, 2, true, null, date('Y-m-d'));  // что за аргументы?
    $o->pay();
    $o->ship();
    $this->assertEquals('shipped', $o->getStatus());
    $this->assertEquals(2000, $o->getTotal());
    $this->assertTrue($o->isPaid());
    $this->assertNotNull($o->getShippedAt());
}

// ПОСЛЕ: два теста, говорящие имена, значимые данные явно, остальное — в билдер
public function оплаченный_заказ_можно_отгрузить(): void
{
    $order = OrderBuilder::new()->paid()->build();   // шум скрыт в билдере

    $order->ship();

    $this->assertSame(OrderStatus::Shipped, $order->status);
}

public function неоплаченный_заказ_отгрузить_нельзя(): void
{
    $order = OrderBuilder::new()->unpaid()->build();

    $this->expectException(OrderNotPaid::class);
    $order->ship();
}
Практический выводБилдеры и фабрики тестовых данных — самая окупаемая инвестиция в тестах. Они убирают шум из подготовки, оставляя в тесте только то, что относится к делу, и позволяют менять конструктор сущности в одном месте вместо ста тестов. Признак того, что билдер нужен: подготовка данных занимает больше строк, чем действие и проверка вместе.
Типичный вопрос на собеседованииСколько проверок должно быть в одном тесте?
Столько, сколько нужно для проверки одного поведения, — иногда это три ассерта об одном результате. Плохой признак другой: несколько независимых действий и проверок в одном методе. Тогда при падении первого ассерта остальные не выполняются, а по имени теста непонятно, что именно сломалось. Правило простое: одно поведение — один тест, а имя описывает это поведение.

ОриентирJunior-секция по тестам почти всегда содержит три вопроса: чем мок отличается от стаба, что тестировать и что нет, зачем вообще тесты. Этот блок закрывает их — но лучший ответ всегда с примером из своего кода: что вы покрыли, что нашли и что после этого поменяли в самом коде.

Уровень 02 · практика

Middle: база, HTTP, интеграции, легаси

Модульные тесты пишут все. Middle отличается тем, что умеет тестировать всё остальное: код, работающий с базой, эндпоинты целиком, интеграции с чужими сервисами, недетерминированные вещи вроде времени и случайности — и умеет заходить с тестами в проект, где их никогда не было.

middle / данные

Тесты с базой данных

Ключевое

Запросы, транзакции, каскады, уникальные индексы и миграции невозможно проверить на моках: моки подтвердят ровно то, что вы в них заложили. Здесь нужна настоящая база — та же СУБД и той же версии, что в проде, иначе тесты пропустят различия в типах, сортировке и блокировках.

Типичный вопрос на собеседованииКак изолировать тесты, работающие с базой?
Обычно транзакцией с откатом: тест начинает транзакцию, в конце она откатывается, база остаётся чистой — это самый быстрый способ. middle / сценарии

HTTP и функциональные тесты

Ключевое

Функциональный тест проходит через весь стек: маршрутизация, аутентификация, валидация, бизнес-логика, база, сериализация. Он ловит то, чего не видят модульные, — забытую регистрацию сервиса, неверный код ответа, отсутствующую проверку прав.

phpТест эндпоинта: контракт, права и побочный эффект
<?php
final class CreateOrderTest extends WebTestCase
{
    public function создание_заказа_возвращает_201_и_location(): void
    {
        $client = static::createClient();
        $client->loginUser(UserFactory::create());

        $client->request('POST', '/api/v1/orders', server: [
            'CONTENT_TYPE'        => 'application/json',
            'HTTP_IDEMPOTENCY_KEY' => '3f8c2b1a',
        ], content: json_encode(['product_id' => 'A-100', 'qty' => 2]));

        $response = $client->getResponse();

        $this->assertSame(201, $response->getStatusCode());
        $this->assertMatchesRegularExpression('#^/api/v1/orders/#',
            $response->headers->get('Location'));

        $body = json_decode($response->getContent(), true, flags: JSON_THROW_ON_ERROR);
        $this->assertArrayHasKey('id', $body);
        $this->assertSame('created', $body['status']);

        // Побочный эффект проверяется тоже: заказ действительно сохранён
        $this->assertNotNull($this->repository(OrderRepository::class)->find($body['id']));
    }

    // Тест на права обязателен для каждого эндпоинта: именно здесь ловятся IDOR
    public function чужой_заказ_недоступен(): void
    {
        $client = static::createClient();
        $client->loginUser(UserFactory::create());
        $foreign = OrderFactory::create(['tenant_id' => 'other-tenant']);

        $client->request('GET', "/api/v1/orders/{$foreign->id}");

        $this->assertSame(404, $client->getResponse()->getStatusCode());
    }
}

Типичный вопрос на собеседованииЧем функциональный тест отличается от модульного и когда какой писать?
Модульный проверяет одну единицу логики в изоляции и выполняется за миллисекунды; функциональный проходит через весь стек и проверяет, что всё собрано вместе правильно: маршруты, права, коды ответа, сериализация. Правило: бизнес-правила и граничные случаи — модульными, по одному сценарию на эндпоинт плюс проверка прав — функциональными.

middle / интеграции

Внешние интеграции

Ключевое

Чужой сервис в тестах — источник медленности и нестабильности: он лежит, меняет ответы, ограничивает частоту и требует денег за каждый вызов. Ходить в него из тестов нельзя, но и полностью выдумывать его ответы опасно: тесты пройдут на фантазии, а прод встретит реальность.

Практический выводРабочая комбинация: быстрые тесты на подменённом клиенте закрывают все сценарии, включая отказы, а один отдельный набор ходит в песочницу провайдера по расписанию — раз в сутки, не в каждом прогоне. Первый набор защищает от собственных регрессий, второй — от изменений на стороне партнёра. Эти задачи разные, и одним набором их не решить.
Типичный вопрос на собеседованииКак тестировать код, работающий с внешним API?
Подменять HTTP-клиент и проверять не только успешный ответ, но и отказы: таймаут, 500, 429, некорректное тело, обрыв соединения. Именно они происходят в проде и почти никогда не покрыты. Отдельно проверяется, что мы не дублируем операцию при повторе — то есть ключ идемпотентности одинаков в обеих попытках. А проверку соответствия реальному API выносят в отдельный набор по расписанию.

middle / детерминизм

Время, случайность, окружение

Ключевое

Тест, зависящий от текущего времени, однажды упадёт — в полночь, в конце месяца, тридцать первого декабря или при переходе на летнее время. Тест, зависящий от случайности, упадёт в одном прогоне из ста. Оба лечатся одинаково: недетерминированное становится явной зависимостью.

phpЧасы как зависимость — самый окупаемый приём в тестах
<?php
// Проблема: время берётся изнутри, зафиксировать его невозможно
final class Subscription
{
    public function isExpired(): bool
    {
        return $this->expiresAt < new DateTimeImmutable();   // ← скрытая зависимость
    }
}

// Решение: часы приходят снаружи (в PHP 8.3+ есть стандартный интерфейс PSR-20)
final class Subscription
{
    public function isExpired(ClockInterface $clock): bool
    {
        return $this->expiresAt < $clock->now();
    }
}

// В тесте время фиксируется, и граничные случаи становятся проверяемыми
public function подписка_истекает_ровно_в_полночь(): void
{
    $clock = new MockClock('2026-03-01 00:00:00');
    $sub   = SubscriptionFactory::create(['expires_at' => '2026-03-01 00:00:00']);

    $this->assertFalse($sub->isExpired($clock));

    $clock->modify('+1 second');                 // перемотка вместо sleep()
    $this->assertTrue($sub->isExpired($clock));
}

Типичный вопрос на собеседованииКак тестировать код, зависящий от текущего времени?
Сделать время явной зависимостью: интерфейс часов, который в проде возвращает реальное время, а в тесте — фиксированное и перематываемое. Тогда становятся проверяемыми ровно те случаи, которые ломаются в проде: граница суток, конец месяца, високосный год, истечение срока ровно в момент проверки. Без этого такие сценарии либо не покрыты, либо тест «мигает».

middle / легаси

Тесты на легаси

Ключевое

Классическая ловушка: чтобы безопасно менять код, нужны тесты, а чтобы написать тесты, нужно менять код — он не тестируем. Выход не в том, чтобы покрыть всё, а в том, чтобы покрывать по мере необходимости, начиная с того, что собираетесь трогать.

phpХарактеризующий тест: фиксируем текущее поведение, даже если оно странное
<?php
// Цель НЕ в том, чтобы проверить правильность. Цель — зафиксировать, как есть,
// чтобы рефакторинг не изменил поведение незаметно.

#[DataProvider('реальные_входы_из_прода')]
public function расчёт_комиссии_сохраняет_текущее_поведение(array $input, string $expected): void
{
    // $expected получен запуском текущего кода на реальных данных, а не выведен из ТЗ
    $this->assertSame($expected, calculate_commission(...$input));
}

public static function реальные_входы_из_прода(): iterable
{
    // Данные собраны логированием на проде: 200 самых частых комбинаций
    yield 'обычный заказ'       => [[1000, 'RUB', false], '50.00'];
    yield 'нулевая сумма'       => [[0, 'RUB', false], '0.00'];

    yield 'валюта неизвестна'   => [[1000, 'XXX', false], '0.00'];   // тоже подозрительно
}

TDD и тестируемость

Ключевое

TDD — это цикл «красный → зелёный → рефакторинг»: сначала падающий тест, затем минимальный код, чтобы он прошёл, затем улучшение кода при зелёных тестах. Спорят о нём много, но одно наблюдение бесспорно: код, написанный тестами вперёд, почти всегда получается менее связанным — просто потому, что нетестируемый код невозможно написать этим способом.

Практический выводДаже если вы не практикуете TDD постоянно, есть один случай, где он окупается всегда: исправление бага. Сначала пишется тест, воспроизводящий баг, — он должен упасть. Это доказывает, что вы поняли причину, а не совпадение. Затем исправление, тест зеленеет, и в наборе навсегда остаётся защита от повторения. Багу без такого теста свойственно возвращаться.
Типичный вопрос на собеседованииПрактикуете ли вы TDD?
Честный и сильный ответ — не «всегда» и не «никогда», а с условиями: на алгоритмах, расчётах и разборе форматов TDD экономит время; при исправлении багов пишу падающий тест первым всегда; на исследовательских задачах и коде, состоящем из вызовов фреймворка, пишу тесты после. Главную ценность вижу не в ритуале, а в том, что при таком подходе невозможно написать код, который нельзя протестировать.

middle / пайплайн

Тесты в CI и флаки

Ключевое

Набор тестов имеет два свойства, определяющих его судьбу: время прогона и стабильность. Медленный набор перестают запускать локально; нестабильный — перестают воспринимать всерьёз, и красная сборка становится нормой. Оба состояния означают, что тесты больше не работают, хотя формально они есть.

АнтипаттернАвтоматический повтор упавших тестов как способ «починить» нестабильность. Повтор скрывает проблему, а не решает: тест, падающий один раз из десяти, точно так же пропустит реальную ошибку один раз из десяти. Повтор допустим только как временная мера вместе с задачей на исправление и учётом частоты — тест, который «мигает» вторую неделю, лучше отключить явно, чем терпеть красную сборку.
Типичный вопрос на собеседованииТесты периодически падают без изменений в коде. Что делать?
Прежде всего не игнорировать: нестабильный тест обесценивает весь набор. Найти причину по типовому списку — время, порядок выполнения, общие данные, ожидание через sleep, сеть, порядок строк без сортировки. Помогает запуск в случайном порядке и повтор одного теста много раз подряд. До исправления тест лучше явно отключить с задачей, чем оставлять красную сборку, к которой команда привыкает.

  • Делаю время и случайность явными зависимостями
  • Не использую sleep для ожидания
  • Начинаю покрытие легаси с того, что меняю
  • Пишу характеризующие тесты перед рефакторингом
  • На каждый баг пишу падающий тест до исправления

ОриентирПроверка зрелости набора тестов одним вопросом: сколько времени проходит от изменения кода до понимания, что оно ничего не сломало. Если ответ «секунды для логики и минуты для всего остального» — набор работает. Если «двадцать минут и потом ещё перезапустить, потому что упало что-то не то» — тесты формально есть, но своей задачи не выполняют.

senior / выбор

Стратегия покрытия

Архитектура

Универсального ответа «сколько процентов покрытия нужно» не существует, потому что вопрос поставлен неверно. Правильный вопрос — какой риск мы снижаем и сколько это стоит. Расчёт комиссии и форма обратной связи заслуживают разного отношения, хотя строк кода в них поровну.

Про форму пирамиды. Классическая пирамида (много модульных, мало сквозных) выросла из времени, когда интеграционные тесты были очень медленными. Сегодня база в контейнере поднимается за секунды, и разумный набор ближе к «трофею»: заметная доля интеграционных тестов, потому что именно они проверяют то, что реально ломается — запросы, транзакции, сборку компонентов. Модульные остаются для логики, где важно перебрать много случаев быстро.

ВажноТребование «покрытие не ниже 80 %» без уточнений порождает предсказуемый результат: тесты на геттеры, тесты без единого ассерта и вызовы методов «чтобы строчка засчиталась». Полезнее задавать порог на изменённый код в pull request и отдельно требовать тест на каждый исправленный баг — это измеримо и не поощряет имитацию.
Типичный вопрос на собеседованииКакой процент покрытия нужен проекту?
Сам по себе процент ничего не значит — покрытие показывает, что строка выполнилась, а не что поведение проверено. Практично другое: обязательное покрытие для кода с высокой ценой ошибки (деньги, права, расчёты), порог на изменённый код в pull request, тест на каждый исправленный баг и осознанный отказ от покрытия обвязки. Числу 80 % я бы предпочёл ответ на вопрос «что мы можем безопасно рефакторить».

# Мутация, которую тесты не заметили, — это дыра в проверках.

#   >  превращается в >=      (граничные случаи)
#   && превращается в ||      (условия)
#   return $x  →  return null  (использование результата)
#   удаление вызова метода     (побочные эффекты)
phpЧто находит мутационное тестирование на практике
<?php
// Код: скидка положена от 1000 рублей
public function isEligible(Money $total): bool
{
    return $total->isGreaterThan(Money::rub('1000.00'));
}

// Тест даёт 100 % покрытия — но не проверяет границу
public function скидка_доступна_для_крупного_заказа(): void
{
    $this->assertTrue($this->discount->isEligible(Money::rub('5000.00')));
}

// Мутация меняет isGreaterThan на isGreaterThanOrEqual — тест остаётся зелёным.
// Значит, поведение ровно на границе 1000.00 никак не зафиксировано:
// его можно случайно изменить, и никто не заметит.

// Добавляем граничные случаи — мутация начинает убиваться:
$this->assertFalse($this->discount->isEligible(Money::rub('1000.00')));   // ровно граница
$this->assertTrue($this->discount->isEligible(Money::rub('1000.01')));   // на копейку выше
Практический выводМутационное тестирование дорого гонять на всём проекте, но отлично работает точечно: на модуле расчётов, на правилах скидок, на конечных автоматах статусов. Один прогон по ключевому модулю обычно находит несколько мест, где тесты были декоративными, — и это самая честная проверка качества набора из доступных.
Типичный вопрос на собеседованииЧто такое мутационное тестирование и зачем оно, если есть покрытие?
Инструмент вносит в код мелкие изменения — меняет знак сравнения, условие, удаляет вызов — и проверяет, упадут ли тесты. Если мутация выжила, значит тесты выполнили эту строку, но не проверили её поведение. Покрытие отвечает на вопрос «код выполнялся?», мутационный балл — на вопрос «а тесты заметили бы ошибку?». Второй вопрос гораздо ближе к тому, ради чего тесты пишут.

<?php
// 1. Тест сервиса: проверяем, что задача поставлена с правильными данными.
//    Транспорт в тестовом окружении — «в память», ничего никуда не уходит.
public function оформление_заказа_ставит_задачу_на_письмо(): void
{
    $this->checkout->complete($order = OrderFactory::create());

    $messages = $this->transport->getSent();
    $this->assertCount(1, $messages);
    $this->assertSame($order->id, $messages[0]->getMessage()->orderId);
}

// 2. Тест обработчика: вызываем напрямую, без очереди вообще
public function обработчик_отправляет_письмо_и_помечает_заказ(): void
{
    (new SendReceiptHandler($this->mailer, $this->orders))(new SendReceipt($order->id));

    $this->assertCount(1, $this->mailer->sentTo($order->customerEmail));
}

// 3. Отдельно — самое важное свойство: повтор не создаёт второго эффекта
public function повторная_обработка_не_шлёт_второе_письмо(): void
{
    $handler = new SendReceiptHandler($this->mailer, $this->orders);
    $message = new SendReceipt($order->id, eventId: 'evt_1');

    $handler($message);
    $handler($message);                      // at-least-once: дубликат неизбежен

    $this->assertCount(1, $this->mailer->sentTo($order->customerEmail));
}

<?php
// Гонки нельзя проверить моками — нужны настоящие параллельные транзакции.

Типичный вопрос на собеседованииКак тестировать асинхронную обработку?
Разделив её на три независимые проверки: сервис ставит задачу с правильными данными (транспорт в памяти), обработчик делает работу при прямом вызове, повторная обработка того же сообщения не создаёт второго эффекта. Полный цикл через реальный брокер стоит проверить одним интеграционным тестом, но строить на нём весь набор нельзя — он медленный и нестабильный. Ожидание через sleep при этом заменяется ожиданием условия с таймаутом.

Нагрузочные тесты

Архитектура

Функциональные тесты отвечают на вопрос «работает ли», нагрузочные — «до какого предела и что происходит за ним». Без них ответ на вопрос «выдержим ли распродажу» остаётся гаданием, а первый настоящий пик становится экспериментом на пользователях.

jsСценарий с целями: тест падает при нарушении SLO
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 100 },   // плавный набор
    { duration: '5m', target: 100 },   // удержание целевой нагрузки
    { duration: '2m', target: 300 },   // пик
    { duration: '2m', target: 0 },
  ],
  // Цели — это и есть SLO. Без них тест просто рисует графики.
  thresholds: {
    http_req_duration: ['p(95)<300', 'p(99)<800'],
    http_req_failed:   ['rate<0.01'],
  },
};

export default function () {
  // Профиль должен повторять реальный: 90 % чтения, 10 % записи
  const res = Math.random() < 0.9
    ? http.get('https://staging.example.com/api/v1/orders?limit=20')
    : http.post('https://staging.example.com/api/v1/orders', payload, params);

  check(res, { 'status ok': (r) => r.status < 400 });
  sleep(1);
}

Что смотреть во время прогона — не только цифры клиента. Задержка и доля ошибок со стороны нагрузки говорят «плохо», а причину показывают метрики системы: занятость пула процессов, число соединений и медленные запросы в базе, попадания в кэш, возраст сообщений в очереди, потребление CPU и памяти. Нагрузочный тест без снятия этих метрик отвечает «не держим», но не отвечает «почему».

ВажноНагрузочный тест на стенде, который вдвое слабее прода и работает на пустой базе, показывает не предел системы, а предел стенда. Минимальные требования к осмысленности: сопоставимая конфигурация, объём данных того же порядка (индексы ведут себя иначе на тысяче и на десяти миллионах строк) и профиль запросов, снятый с реального трафика, а не придуманный.
Типичный вопрос на собеседованииКак проверить, что система выдержит распродажу?
Снять профиль реального трафика, оценить ожидаемый пик, прогнать нагрузочный тест на стенде с сопоставимой конфигурацией и объёмом данных, задав цели по p95, p99 и доле ошибок. Отдельно прогнать стресс до отказа, чтобы увидеть, как система деградирует за пределом: отказывает штатно с 429 и 503 или заваливается целиком. Во время прогона снимать метрики системы, иначе будет известен только факт, а не причина.

Процесс и владение

Архитектура

Набор тестов деградирует так же, как код: обрастает дублированием, замедляется, накапливает отключённые и нестабильные тесты. Разница в том, что за код обычно кто-то отвечает, а за тесты — редко.

Что проверять при ревью тестов. Есть ли вообще ассерт и проверяет ли он результат, а не факт вызова. Читается ли имя как утверждение о поведении. Покрыты ли граничные случаи и ошибочный путь, а не только счастливый. Не появилось ли зависимости от времени, порядка или сети. Не дублирует ли тест то, что уже проверено уровнем ниже. Этих пяти вопросов достаточно — длинный чек-лист на ревью никто не читает.

АнтипаттернОтдельная команда, которая «пишет тесты за разработчиков». Так тесты превращаются во внешний контроль, отстают от кода на спринт и не влияют на дизайн — а разработчики перестают чувствовать ответственность за проверяемость своего кода. Автотесты — часть разработки; отдельная роль в тестировании нужна для другого: исследовательского тестирования, сценариев, приёмки, нагрузки.
Типичный вопрос на собеседованииКак поддерживать набор тестов в рабочем состоянии?
Тремя вещами. Правилами, которые видны в процессе: тест на каждый баг, ревью тестов наравне с кодом, порог на изменённый код. Ограничением времени прогона — набор, который идёт полчаса, перестают запускать. И отношением к нестабильным тестам как к дефектам с задачей и сроком, а не как к погоде. Без этого набор за год превращается в двадцать минут ожидания и привычку перезапускать сборку.

Справочник · собеседование

60 вопросов с эталонными ответами

Ответы короткие — это каркас. Сильный ответ про тесты почти всегда содержит цену: не «покрываем всё», а «покрываем расчёты плотно, обвязку не покрываем, потому что тест стоит дважды — при написании и при каждом изменении».

Junior · 20 вопросов

Junior
  1. Зачем нужны тесты?Чтобы изменения кода были дешёвыми: за секунды узнавать, что ничего не сломалось. Дополнительно они документируют ожидаемое поведение точнее комментариев и заставляют делать код менее связанным. Без них цена изменений растёт до момента, когда рефакторинг откладывается навсегда.
  2. Какие бывают уровни тестов?Модульные проверяют одну единицу логики без внешних зависимостей; интеграционные — связку с базой, кэшем, очередью; функциональные проходят сценарий через весь стек; E2E воспроизводят пользовательский путь через браузер. Чем выше уровень, тем дороже писать, медленнее выполнять и труднее диагностировать падение.
  3. Почему модульных тестов больше, чем E2E?Из-за экономики: модульный тест выполняется миллисекунды и при падении точно показывает место, E2E идёт секунды и падает целиком от любой мелочи. Правило: если поведение можно проверить уровнем ниже — проверяйте там. Но и полный отказ от верхних уровней плох: каждая деталь работает, а вместе не собирается.
  4. Из каких частей состоит тест?Подготовка данных, одно действие, проверка результата. Держаться этой структуры полезно даже в коротких тестах: она делает их читаемыми. Если действий несколько и проверок десяток — это уже сценарий, и его лучше разделить.
  5. Что такое провайдер данных?Способ прогнать один и тот же тест на множестве входов вместо копирования метода. Каждый набор именуется, поэтому при падении сразу видно, какой случай сломался. Идеально подходит для граничных значений: ноль, пусто, максимум, отрицательное.
  6. Что означает «тестировать поведение, а не реализацию»?Проверять наблюдаемый результат — возвращаемое значение, изменение состояния, отправленное сообщение, — а не порядок внутренних вызовов. Критерий простой: если после рефакторинга без изменения поведения тесты покраснели, они тестировали реализацию и работают против своей цели.
  7. Что не стоит покрывать тестами?Геттеры и простые DTO без логики, код фреймворка и библиотек, конфигурационные массивы, приватные методы напрямую, точные тексты сообщений интерфейса. Тест стоит денег дважды — при написании и при каждом изменении кода, поэтому пишется там, где что-то гарантирует.
  8. Почему не стоит тестировать приватные методы?Потому что это фиксирует реализацию: любой рефакторинг ломает тесты. Если приватный метод очень хочется протестировать отдельно, это сигнал, что внутри класса прячется самостоятельная сущность, — её стоит выделить в отдельный класс с публичным контрактом и тестировать его.
  9. Чем мок отличается от стаба?Стаб отдаёт подготовленные данные, чтобы код мог выполниться, и ничего не проверяет. Мок задаёт ожидания заранее — был ли метод вызван, сколько раз, с какими аргументами — и проверяет их автоматически. Моки уместны, когда сам факт взаимодействия и есть поведение: письмо отправлено, платёж списан.
  10. Что такое фейк и чем он лучше мока?Рабочая упрощённая реализация — например, репозиторий в памяти. Он не привязывает тест к порядку вызовов: код работает с ним как с настоящим, а тест проверяет результат. Для зависимостей, которые вы контролируете, фейк почти всегда лучше мока и делает тесты устойчивее к рефакторингу.
  11. Что подменять двойниками, а что нет?Подменять то, что вы не контролируете: внешние API, платёжные шлюзы, отправку писем, часы, файловую систему. Не подменять собственные объекты-значения, чистые функции и простые сущности — их использование в тесте бесплатно и делает проверку честнее. Мок на каждую зависимость превращает тест в зеркало реализации.
  12. Каким должно быть имя теста?Читаться как утверждение о поведении с условием: «неоплаченный заказ отгрузить нельзя». Тогда отчёт о падении сам объясняет проблему, а список тестов превращается в описание поведения модуля. Имена вида test1 или testMethodName лишают отчёт смысла.
  13. Что делает тест недетерминированным?Обращение к текущему времени, случайность, сеть, зависимость от порядка выполнения и общее состояние между тестами. Такие тесты падают «иногда», и команда быстро привыкает перезапускать сборку — после чего набор перестаёт что-либо значить.
  14. Почему тесты должны быть независимыми?Чтобы их можно было запускать по одному, в любом порядке и параллельно. Если тест полагается на данные, оставленные предыдущим, набор ломается при перестановке, при запуске одного теста и при распараллеливании — то есть ровно тогда, когда он нужнее всего.
  15. Сколько проверок должно быть в одном тесте?Столько, сколько нужно для одного поведения, — иногда это три ассерта об одном результате. Проблема не в числе ассертов, а в числе независимых действий: при нескольких сценариях в одном методе падение первого скрывает остальные и по имени непонятно, что сломалось.
  16. Зачем нужны фабрики и билдеры тестовых данных?Они убирают шум из подготовки: в тесте остаётся только то, что важно для сценария, остальное берётся по умолчанию. Плюс при изменении конструктора сущности правка делается в одном месте, а не в сотне тестов. Признак, что билдер нужен: подготовка длиннее, чем действие и проверка вместе.
  17. Как тестировать исключения?Объявить ожидание до вызова: тип исключения и, если важно, сообщение или код. Проверять только тип обычно недостаточно, когда один класс исключения используется для разных ситуаций. Отдельно стоит убедиться, что после исключения состояние не изменилось частично.
  18. Что показывает процент покрытия?Что строка кода выполнялась во время тестов. И только. Он не говорит, была ли проверена корректность: тест без единого ассерта даёт покрытие. Поэтому высокий процент — необходимое, но совсем не достаточное условие; полезнее смотреть, что происходит с непокрытыми участками и есть ли в тестах реальные проверки.
  19. Что такое AAA?Соглашение о структуре теста: Arrange — подготовка данных и зависимостей, Act — одно действие, Assert — проверка результата. Разделение этих частей пустыми строками или комментариями делает тест читаемым за пару секунд, что важно, потому что тесты читают чаще, чем пишут.
  20. Что делать, если тест сложно написать?Обычно это сигнал не о тестах, а о коде: зависимости создаются внутри, метод делает пять дел сразу, логика перемешана с побочными эффектами. Правильная реакция — не изобретать хитрый способ протестировать, а упростить код: вынести зависимости в конструктор, разделить вычисление и запись, выделить отдельную единицу.

  1. Как изолировать тесты, работающие с базой?Чаще всего транзакцией с откатом: тест начинает транзакцию, в конце она откатывается. Это быстрее очистки таблиц, но не работает, если тестируемый код сам управляет транзакциями, — тогда усечение таблиц или отдельная база на параллельный процесс. Схема разворачивается один раз перед набором.
  2. Можно ли заменить боевую СУБД на SQLite в тестах?Не стоит: отличаются типы, приведения, диалект SQL, поведение при конкурентном доступе, поддержка JSON и оконных функций. Тесты станут зелёными, а в проде запрос упадёт или отработает иначе — то есть вы получите ровно ложную уверенность. База поднимается в контейнере за секунды, экономия не окупает риска.
  3. Фикстуры или фабрики?Фабрики: они создают ровно то, что нужно тесту, с осмысленными значениями по умолчанию, и в тесте видно только существенное. Большие общие фикстуры со временем становятся неявной зависимостью — никто не помнит, кто на какие записи полагается, и правка одной строки ломает десяток тестов.
  4. Что проверять в функциональном тесте эндпоинта?Код ответа, форму тела, ключевые заголовки, права доступа, поведение при неверном вводе и побочный эффект — что запись действительно создана. Особенно важна проверка прав: функциональные тесты — единственное место, где системно ловятся IDOR и забытые проверки владения.
  5. Сколько нужно функциональных тестов?Немного: по одному счастливому пути и одному-двум ключевым отказам на эндпоинт, плюс обязательная проверка прав. Всё разнообразие бизнес-правил проверяется уровнем ниже — там это в десятки раз быстрее. Попытка покрыть все комбинации через HTTP даёт набор, который идёт полчаса и падает целиком от одной ошибки в конфигурации.
  6. Как тестировать код, работающий с внешним API?Подменять HTTP-клиент и обязательно проверять отказы: таймаут, 500, 429, некорректное тело, обрыв соединения. Именно эти сценарии происходят в проде и почти никогда не покрыты. Соответствие реальному API проверяется отдельным набором по расписанию или контрактными тестами по спецификации — это другая задача.
  7. Как проверить, что повтор запроса не создаёт дубль?Вызвать операцию дважды с одним ключом идемпотентности и убедиться, что эффект один: одна запись, одно письмо, одно списание. Для внешних вызовов дополнительно проверяется, что во второй попытке уходит тот же ключ, — иначе провайдер посчитает это новой операцией.
  8. Как тестировать код, зависящий от текущего времени?Сделать время явной зависимостью: интерфейс часов, который в проде возвращает реальное время, а в тесте — фиксированное и перематываемое. Тогда проверяемыми становятся именно те случаи, которые ломаются в проде: граница суток, конец месяца, високосный год, истечение срока ровно в момент проверки.
  9. Как тестировать случайность?Либо вынести генератор в зависимость и подставить предсказуемую реализацию, либо не проверять конкретное значение, а проверять свойства результата: длину, формат, диапазон, уникальность в наборе. Ассерт на конкретный сгенерированный идентификатор — классическая причина «мигающего» теста.
  10. Почему нельзя использовать sleep в тестах?Он одновременно замедляет набор и не гарантирует результат: на загруженном агенте CI операция не успеет и за две секунды, а на быстрой машине вы просто теряете время. Правильно — либо синхронная обработка в тестовом режиме, либо ожидание условия с коротким шагом и общим таймаутом.
  11. Как начать покрывать тестами проект без тестов?Не пытаться покрыть всё. Начать с того, что собираетесь менять: характеризующие тесты, фиксирующие текущее поведение на реальных данных, минимальный шов для подмены зависимостей, затем рефакторинг под защитой тестов. Приоритеты — деньги, права доступа, места прошлых инцидентов, сценарии ручной проверки перед релизом.
  12. Что такое характеризующий тест?Тест, фиксирующий текущее поведение как есть, даже если оно выглядит неправильным. Его цель — не проверить корректность, а не дать поведению измениться незаметно при рефакторинге. Найденные странности выписываются отдельно и обсуждаются с бизнесом: молча «исправлять» их по дороге нельзя, на них может держаться отчётность.
  13. Что такое шов и зачем он нужен?Минимальное изменение, позволяющее подменить зависимость без переписывания кода: например, конструктор с необязательными параметрами и значениями по умолчанию. Старый код продолжает работать, а тест получает возможность подставить свои реализации. Это способ зайти в легаси с тестами, не начиная с большого рискованного рефакторинга.
  14. Практикуете ли вы TDD?С условиями. На алгоритмах, расчётах, разборе форматов и конечных автоматах он экономит время. При исправлении бага — всегда: сначала падающий тест, доказывающий, что причина понята. На исследовательских задачах и коде из вызовов фреймворка — тесты после. Главная ценность не в ритуале, а в том, что нетестируемый код так просто не напишешь.
  15. Почему на каждый баг нужен тест?Потому что баг, найденный один раз, склонен возвращаться: тот же участок кода трогают снова. Падающий тест до исправления доказывает, что причина понята правильно, а не совпадение; после исправления он остаётся в наборе как защита. Это самая дешёвая и самая окупаемая практика из всех.
  16. Как узнать нетестируемый код?По признакам: зависимости создаются внутри через new, статические вызовы и синглтоны, обращение ко времени и случайности изнутри, метод на триста строк с десятком ветвлений, логика внутри контроллера, вычисления вперемешку с записью в базу. Все они лечатся одинаково — вынесением зависимостей наружу и разделением ответственности.
  17. Как ускорить прогон тестов?Разделить наборы по скорости и гонять модульные отдельно; параллелить с изоляцией (своя база, свой номер базы Redis, свой префикс кэша на процесс); поднимать базу в памяти контейнера с отключённым fsync; развернуть схему один раз на набор; найти самые медленные тесты — в модульный набор регулярно пробирается поход в базу или сеть.
  18. Тесты падают через раз без изменений в коде. Что делать?Не игнорировать: нестабильный тест обесценивает весь набор. Искать причину по типовому списку — время, порядок выполнения, общие данные, sleep, сеть, порядок строк без сортировки. Помогают запуск в случайном порядке и многократный повтор одного теста. До исправления лучше явно отключить с задачей, чем терпеть красную сборку.
  19. Можно ли просто перезапускать упавшие тесты автоматически?Как временная мера — да, вместе с задачей на исправление и учётом частоты. Как постоянное решение — нет: повтор скрывает проблему. Тест, падающий один раз из десяти, ровно так же пропустит настоящую ошибку один раз из десяти, а команда привыкнет, что красное — это нормально.
  20. Как организованы тесты в вашем проекте?Ожидается конкретика: разделение на наборы по скорости, где живут фабрики и базовые классы, как изолируются данные, что подменяется, сколько идёт прогон, что запускается локально, а что только в CI. Ответ «есть PHPUnit» показывает, что человек тесты писал, но за набор не отвечал.

Senior
  1. Какой процент покрытия нужен?Сам по себе процент ничего не значит: покрытие показывает, что строка выполнилась, а не что поведение проверено. Практично другое — плотное покрытие кода с высокой ценой ошибки, порог на изменённый код в pull request, обязательный тест на каждый исправленный баг и осознанный отказ от покрытия обвязки. Главный критерий — что мы можем безопасно рефакторить.
  2. Как выбирать уровень тестов для конкретного кода?По тому, что реально может сломаться. Доменная логика — модульными, много случаев. Репозитории и сложные запросы — интеграционными, потому что мок ничего не докажет о настоящем SQL. Контроллеры — по одному функциональному сценарию. Права — обязательно функционально. Обвязку и конфигурацию не покрывать вовсе.
  3. Пирамида или трофей?Классическая пирамида выросла из времени, когда интеграционные тесты были очень медленными. Сегодня база в контейнере поднимается за секунды, и разумный набор ближе к трофею: заметная доля интеграционных, потому что именно они проверяют то, что ломается — запросы, транзакции, сборку компонентов. Модульные остаются там, где нужно быстро перебрать много случаев.
  4. Как приоритизировать, что покрывать первым?По произведению вероятности изменения на цену ошибки. Часто меняющийся код с дорогими последствиями — расчёты денег, права, скидки — первым. Редко меняющийся и дешёвый в ошибке — последним или никогда. Отдельно вне очереди: места прошлых инцидентов и сценарии, которые сейчас проверяются вручную перед каждым релизом.
  5. Что такое мутационное тестирование?Инструмент вносит в код мелкие изменения — меняет знак сравнения, условие, удаляет вызов — и проверяет, упадут ли тесты. Выжившая мутация означает, что строка выполнялась, но её поведение не проверено. Покрытие отвечает «код выполнялся?», мутационный балл — «тесты заметили бы ошибку?». Второй вопрос ближе к цели.
  6. Где применять мутационное тестирование на практике?Точечно, а не на всём проекте: прогон дорогой. Лучшие кандидаты — модули расчётов, правила скидок и лимитов, конечные автоматы статусов. Один прогон по такому модулю обычно находит несколько мест, где тесты были декоративными: чаще всего это непроверенные границы условий.
  7. Какие метрики набора тестов вы смотрите?Время прогона — от него зависит, будут ли тесты запускать; долю нестабильных — от неё зависит доверие к красной сборке; мутационный балл на ключевых модулях — он говорит о качестве проверок; и по возможности учёт багов, ушедших в прод, с разбором, каким тестом это ловилось бы. Процент покрытия — вспомогательная, а не целевая метрика.
  8. Как тестировать асинхронную обработку?Разделив на три проверки: сервис ставит задачу с правильными данными (транспорт в памяти), обработчик выполняет работу при прямом вызове, повторная обработка того же сообщения не создаёт второго эффекта. Полный цикл через реальный брокер — один интеграционный тест, не более: он медленный и нестабильный, строить на нём набор нельзя.
  9. Как тестировать конкурентность и гонки?На настоящей базе с двумя независимыми соединениями и параллельными транзакциями: проверяется, что остаток не уходит в минус, а уникальность не нарушается. Такой тест не доказывает отсутствие гонок вообще, но ловит самый частый случай. Моками это принципиально не проверяется — гонка возникает именно в хранилище.
  10. Как тестировать миграции?Отдельным набором: применение на копии боевой схемы, проверка обратимости там, где она заявлена, и проверка, что после миграции работают ключевые запросы. Отдельно оценивается время выполнения на объёме, сопоставимом с продом, — миграция, идущая на тестовой базе секунду, на боевой может блокировать таблицу на полчаса.
  11. Что такое контрактные тесты между сервисами?Проверка, что ответы поставщика соответствуют опубликованной схеме, а потребитель ожидает именно её. Они ловят тихое изменение формы ответа — переименованное поле, число вместо строки, исчезнувший null, — которое не ломает логику ни у кого по отдельности, но ломает интеграцию. Обычная альтернатива — узнать об этом в проде.
  12. Зачем нужны нагрузочные тесты и какие они бывают?Функциональные отвечают «работает ли», нагрузочные — «до какого предела и что за ним». Дымовой проверяет, что всё поднимается; нагрузочный — держим ли целевой трафик в рамках SLO; стресс — где предел и как система деградирует; пиковый — переживём ли всплеск; длительный — нет ли утечек за часы работы.
  13. Что делает нагрузочный тест осмысленным?Три вещи: цели, выраженные как SLO (p95, p99, доля ошибок) — иначе тест просто рисует графики; профиль запросов, снятый с реального трафика, а не придуманный; стенд, сопоставимый с продом по конфигурации и объёму данных — на пустой базе индексы ведут себя иначе. И обязательное снятие метрик системы, иначе будет известен факт, но не причина.
  14. Как убедиться, что система штатно деградирует под перегрузкой?Стресс-тестом с плавным ростом до отказа и наблюдением, что происходит за пределом: отдаются ли 429 и 503 с Retry-After, срабатывают ли лимиты и предохранители, отключается ли некритичное, восстанавливается ли система после снятия нагрузки. Если вместо этого растёт очередь и всё останавливается — деградации нет, есть отказ.
  15. Что проверять при ревью тестов?Пять вопросов: есть ли ассерт и проверяет ли он результат, а не факт вызова; читается ли имя как утверждение о поведении; покрыт ли ошибочный путь, а не только счастливый; нет ли зависимости от времени, порядка и сети; не дублирует ли тест то, что уже проверено уровнем ниже. Длинный чек-лист на ревью не работает.
  16. Почему набор тестов деградирует и как это предотвратить?Потому что за него обычно никто не отвечает: накапливаются дублирование, медленные тесты, отключённые и «мигающие». Помогают правила, видимые в процессе: тест на каждый баг, ревью тестов наравне с кодом, порог на изменённый код, бюджет времени прогона и отношение к нестабильному тесту как к дефекту с задачей и сроком.
  17. Нужна ли отдельная команда, пишущая автотесты?Для автотестов на код — нет: так они отстают от кода, не влияют на дизайн и превращаются во внешний контроль, а разработчики перестают отвечать за тестируемость. Отдельная роль в тестировании ценна для другого: исследовательского тестирования, сложных сценариев, приёмки, нагрузки — того, что разработчик со своим кодом не увидит.
  18. Как убедить команду или бизнес вкладываться в тесты?Через измеримые вещи, а не через принципы: сколько времени уходит на ручную проверку перед релизом, сколько багов вернулось повторно, сколько длится подготовка релиза, как часто откатываем. И начинать с малого — покрыть один модуль с высокой ценой ошибки и показать разницу. Абстрактное «нужны тесты» не согласовывают, конкретную экономию — обычно да.
  19. Когда тесты писать не нужно?Для прототипа, который заведомо выбросят; для разового скрипта; для кода, состоящего из вызовов фреймворка без своей логики. Отказ должен быть осознанным решением с пониманием риска, а не привычкой. Опасность в другом: прототипы имеют свойство уезжать в прод — и тогда решение нужно пересмотреть, а не унаследовать.
  20. Как выглядит зрелый набор тестов?Быстрая обратная связь: логика проверяется за секунды, весь набор — за единицы минут. Нестабильных тестов нет, они чинятся как дефекты. Каждый исправленный баг имеет тест. Уровень тестов выбран по типу кода, а не по привычке. И главный признак: команда спокойно проводит рефакторинг, потому что доверяет зелёной сборке.

15 практических заданий

Тестирование осваивается на своём коде: почти каждое задание выполняется в рабочем репозитории и оставляет артефакт — тесты, замеры, отчёт или настройку пайплайна.

Junior · 5 заданий

Junior

1. Первый набор на доменной логике

Возьмите класс с расчётами — цена, скидка, комиссия — и покройте его модульными тестами: счастливый путь, границы (ноль, максимум, отрицательное), ошибочные входы. Используйте провайдер данных с именованными случаями.

РезультатНабор, который выполняется за миллисекунды, и как минимум один найденный граничный случай, который раньше работал неверно.

2. Переписать плохой тест

Найдите в проекте тест с моками на всё и проверкой вызовов. Перепишите его на проверку результата с фейками. Затем переименуйте что-нибудь в реализации и убедитесь, что новый тест не упал, а старый бы упал.

РезультатНаглядное доказательство разницы между тестированием поведения и реализации.

3. Билдер тестовых данных

Для самой громоздкой сущности проекта напишите билдер с осмысленными значениями по умолчанию и методами вроде paid(), expired(). Перепишите на него пять существующих тестов.

РезультатСокращение подготовки в тестах в несколько раз и одно место для правки при изменении конструктора.

4. Тесты на исключения и ошибки

Покройте ошибочные пути модуля: неверный ввод, нарушение бизнес-правила, отсутствующий объект. Проверьте не только тип исключения, но и то, что состояние не изменилось частично.

РезультатСписок найденных мест, где ошибка оставляла систему в промежуточном состоянии.

5. Разделение наборов

Разложите тесты по каталогам и наборам (модульные, интеграционные, функциональные), настройте отдельный запуск и замерьте время каждого набора.

РезультатКоманда, которая гоняет модульные тесты за секунды, — то, что вы будете запускать при каждом изменении.

Middle · 6 заданий

Middle

6. Интеграционные тесты с базой

Настройте окружение: та же СУБД, что в проде, в контейнере с данными в памяти; схема разворачивается один раз; изоляция откатом транзакции. Покройте самые сложные запросы проекта.

РезультатТесты на реальном SQL и замер: сколько добавилось к времени прогона.

7. Функциональные тесты и права

Для трёх эндпоинтов напишите по одному тесту счастливого пути и обязательный тест доступа: попытка получить чужой объект должна давать 404 или 403.

РезультатСписок эндпоинтов, где проверка владения отсутствовала. Обычно он не пустой.

8. Тесты отказов внешнего сервиса

Подмените HTTP-клиент и покройте сценарии: таймаут, 500, 429 с Retry-After, некорректное тело. Проверьте, что при неизвестном исходе операция не считается неуспешной и что повтор идёт с тем же ключом идемпотентности.

РезультатНайденные места, где таймаут интерпретировался как отказ, — типичный источник двойных списаний.

9. Избавление от зависимости во времени

Найдите код, берущий текущее время изнутри, вынесите часы в зависимость и покройте граничные случаи: полночь, конец месяца, истечение срока ровно в момент проверки.

РезультатТесты, которые раньше было невозможно написать, и один-два найденных бага на границах.

10. Характеризующие тесты для легаси

Выберите непонятный участок кода, соберите реальные входы, зафиксируйте текущее поведение тестами. Отдельно выпишите обнаруженные странности. Затем проведите рефакторинг под защитой этих тестов.

РезультатОтрефакторенный модуль и список странностей для обсуждения с бизнесом.

11. Ускорение и стабилизация прогона

Запустите набор в случайном порядке и найдите зависимости между тестами. Найдите десять самых медленных тестов и разберитесь, почему они медленные. Настройте параллельный прогон с изоляцией баз и ключей кэша.

РезультатВремя прогона до и после плюс список исправленных скрытых зависимостей.

12. Мутационное тестирование ключевого модуля

Прогоните мутационное тестирование по модулю с расчётами. Разберите выжившие мутации: какие означают реальные дыры в проверках, какие — эквивалентные изменения. Доведите балл до осмысленного уровня.

РезультатСписок мест, где тесты были декоративными, и добавленные проверки границ.

Покройте фоновую обработку по трём осям: постановка, обработчик, повтор без дублирования эффекта. Отдельно напишите тест гонки на двух параллельных соединениях к настоящей базе.

РезультатДоказательство идемпотентности обработчика и тест, который падает при снятии защиты от гонки.

14. Нагрузочный тест с целями

Снимите профиль реального трафика, напишите сценарий с целями по p95, p99 и доле ошибок, прогоните нагрузочный и стресс-тесты на стенде с сопоставимым объёмом данных, снимая метрики системы.

РезультатИзвестный предел системы в запросах в секунду и описание того, как она деградирует за ним.

15. Стратегия тестирования проекта

Опишите на двух страницах: что каким уровнем покрывается и почему, какой бюджет времени прогона, какие правила процесса (тест на баг, ревью тестов, порог на изменённый код), что делаем с нестабильными тестами и что осознанно не покрываем.

РезультатДокумент, по которому команда принимает решения без спора в каждом pull request. Лучший артефакт для senior-собеседования.

Как отвечать на вопросы про тесты

Бонус
  • Говорите про экономику, а не про идеологию. «Тесты нужны всегда» — слабо. «Расчёты покрываем плотно, потому что цена ошибки в деньгах; обвязку не покрываем, потому что тест стоит дважды» — сильно.
  • Приводите числа. Сколько идёт прогон, сколько тестов, сколько нестабильных, какой мутационный балл на ключевом модуле, сколько времени занимала ручная проверка до и после. Числа мгновенно отличают опыт от прочитанного.
  • Не защищайте догмы. Ответ «TDD всегда» вызывает уточняющий вопрос, на котором обычно и выясняется, что практики не было. Честный ответ с условиями звучит гораздо убедительнее.
  • Показывайте, что понимаете границы. Покрытие не гарантирует корректности, моки не докажут работу SQL, тест гонки не доказывает её отсутствия. Знание границ — главный признак практика.
  • Держите наготове историю. Баг, который вернулся из-за отсутствия теста; тест, поймавший ошибку перед релизом; набор, который вы ускорили с двадцати минут до четырёх. Такие истории отвечают сразу на несколько вопросов.
  • Не стесняйтесь признавать плохое положение дел. «В проекте покрытие низкое, вот что я успел закрыть и с чего начал бы дальше» — сильный ответ. Он показывает и понимание приоритетов, и реализм.
  • Приносите артефакты. Документ стратегии тестирования, отчёт мутационного тестирования, замеры времени прогона до и после, сценарий нагрузочного теста с целями.
