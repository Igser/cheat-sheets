Что нового в PHP: 7.4 → 8.6

За семь лет PHP превратился из «языка для скриптов с примесью ООП» в статически типизируемый язык с перечислениями, неизменяемыми объектами, хуками свойств и композицией функций. Если вы писали на PHP 7.2 и вернулись к нему в 2026-м — это почти другой язык: половина того, для чего раньше требовались библиотеки, докблоки и кодогенерация, теперь есть в ядре.

Этот конспект — по релизам. Для каждой версии: что реально меняет способ писать код, что просто удобно, что сломается при обновлении и что объявлено устаревшим. Порядок хронологический, потому что возможности наслаиваются друг на друга: readonly не имеет смысла без продвижения свойств из 8.0, а хуки свойств из 8.4 — без типизированных свойств из 7.4.

Смежные темы вынесены отдельно: PHP как язык (модель исполнения, память, внутренности), Laravel, Symfony, базы данных.

Как читать этот конспект

Навигация

У возможностей разный «вес». Одни меняют архитектуру, другие экономят три строки. Поэтому в карточках используются метки:

  • Ключевое — меняет то, как вы пишете код. Стоит внедрять целенаправленно.
  • Удобство — применяется по ходу дела, специально переписывать ради этого не нужно.
  • Deprecated — работает, но выдаёт предупреждение и будет удалено. Чинить до следующего мажора.
  • Ломает — обратно несовместимое изменение. Именно из-за таких пунктов обновление требует тестов.
  • Черновик — RFC принят, но версия ещё не вышла. Детали могут измениться.
ПрактикаПрежде чем читать дальше, выполните в проекте php -v и composer why-not php 8.5. Первая команда скажет, откуда вы стартуете, вторая — какие зависимости держат вас на старой версии. Часто ответ — одна заброшенная библиотека, которую проще заменить, чем ждать.

7.4 / типы / свойства

Типизированные свойства и стрелочные функции

Ключевое

До 7.4 тип свойства можно было объявить только в докблоке — и движок его не проверял. Класс мог сколько угодно обещать @var int, а получить строку. Типизированные свойства перенесли эту проверку в рантайм.

phpТипизированные свойства
<?php
// Было: тип только в комментарии, никто его не проверяет
class User {
    /** @var int */
    private $id;
    /** @var string|null */
    private $email;
}

// Стало: движок гарантирует тип при каждой записи
class User {
    private int $id;
    private ?string $email = null;
    private array $roles = [];
}

$u = new User();
// $u->id = 'abc';  → TypeError
Важно: состояние «uninitialized»Типизированное свойство без значения по умолчанию не равно null — оно находится в особом состоянии uninitialized. Чтение до записи бросит Error: Typed property User::$id must not be accessed before initialization. Это не баг, а именно то, ради чего фича сделана: объект не может существовать в частично заполненном виде незаметно для вас. Обратная сторона — isset() на таком свойстве вернёт false, а get_object_vars() его не покажет.

Стрелочные функции решили другую боль: замыкание в PHP не захватывает область видимости автоматически, поэтому короткий колбэк раздувался до нечитаемого. Стрелочная функция захватывает переменные по значению неявно.

phpfn() вместо function() use ()
<?php
$multiplier = 3;

// Было
$result = array_map(function ($n) use ($multiplier) {
    return $n * $multiplier;
}, $numbers);

// Стало
$result = array_map(fn ($n) => $n * $multiplier, $numbers);

// Ограничения, о которых спрашивают:
//  • ровно одно выражение, никаких фигурных скобок и return;
//  • захват ВСЕГДА по значению — fn () => $x++ не изменит внешний $x;
//  • $this захватывается автоматически, как и в обычном замыкании.
Типичный вопросЧем fn отличается от function?
Тремя вещами: неявный захват внешних переменных (всегда по значению, use (&$x) невозможен), тело — одно выражение с неявным возвратом, и нельзя опустить возвращаемое значение. Всё остальное совпадает: это тот же объект Closure, его можно связать через bindTo, он так же видит $this.
АнтипаттернМногострочная стрелочная функция через вложенные тернарники и &&-цепочки ради того, чтобы уложиться в «одно выражение». Если логика не помещается в строку — это обычное замыкание или приватный метод, а не задача для fn.

7.4 / синтаксис / производительность

Остальное в 7.4: ??=, распаковка, preloading

УдобствоЕсть deprecations
phpСинтаксический минимум 7.4
<?php
// 1. Оператор ??= — присвоить, если не задано
$config['timeout'] ??= 30;
// эквивалент: if (!isset($config['timeout'])) $config['timeout'] = 30;

// 2. Распаковка внутри массива (только списки, без строковых ключей)
$base = ['a', 'b'];
$all  = [...$base, 'c'];        // ['a','b','c']

// 3. Разделитель разрядов в числовых литералах
$price = 1_299_000;             // читается как 1 299 000

// 4. Ковариантность возвращаемых типов
class UserRepository {
    public function find(): ?Entity { /* ... */ }
}
class AdminRepository extends UserRepository {
    // теперь можно сузить возвращаемый тип
    public function find(): ?Admin { /* ... */ }
}

// 5. Слабые ссылки — объект не удерживается от сборки мусора
$ref = WeakReference::create($object);
$ref->get();  // объект или null, если он уже уничтожен

// 6. __serialize / __unserialize вместо Serializable
public function __serialize(): array { return ['id' => $this->id]; }
public function __unserialize(array $data): void { $this->id = $data['id']; }

Preloading: прирост без изменения кода

Preloading — механизм, при котором указанные файлы компилируются один раз при старте FPM и остаются в памяти на всё время жизни мастер-процесса. В отличие от обычного opcache, здесь пропускается ещё и связывание классов: не нужно каждый запрос проверять актуальность файла и заново разрешать наследование.

ini + phpНастройка preloading
; php.ini
opcache.preload=/var/www/preload.php
opcache.preload_user=www-data

<?php // preload.php
$files = new RegexIterator(
    new RecursiveIteratorIterator(
        new RecursiveDirectoryIterator('/var/www/vendor')
    ),
    '/\.php$/'
);
foreach ($files as $file) {
    opcache_compile_file($file->getRealPath());
}

// Цена: любое изменение кода требует перезапуска FPM.
// Выигрыш: обычно 5-13% времени ответа на фреймворковом приложении.
Устарело в 7.4 — и уже удалено
  • $str{0} — фигурные скобки для доступа к символу строки. Удалено в 8.0. Используйте $str[0].
  • Вложенные тернарники без скобок: $a ? $b : $c ? $d : $e. Ошибка в 8.0.
  • (real) и is_real(). Удалены в 8.0. Используйте (float).
  • array_key_exists() для объектов, get_magic_quotes_gpc(), интерфейс Serializable (в пользу магических методов).
  • Конкатенация без скобок рядом с +/-: 'x' . $a + $b — приоритет изменился в 8.0.
ПрактикаВозьмите любой класс-модель из своего проекта и добавьте типы всем свойствам. Прогоните тесты. Каждое падение — это место, где объект жил в неконсистентном состоянии; такие места обычно и оказываются источником «необъяснимых» багов.

8.0 / синтаксис / вызовы

Именованные аргументы и продвижение свойств

КлючевоеСпрашивают всегда

Именованные аргументы позволяют передавать параметры по имени, а не по позиции. Это убирает три вещи сразу: необходимость помнить порядок, необходимость передавать «заглушки» ради последнего параметра и целый класс объектов-конфигураций, существовавших только чтобы избежать функции с восемью аргументами.

phpИменованные аргументы
<?php
htmlspecialchars($string, double_encode: false);
// вместо htmlspecialchars($string, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8', false);

array_slice($array, offset: 0, preserve_keys: true);
// length пропущен — берётся значение по умолчанию

// Позиционные и именованные вместе: именованные только после позиционных
$user = new User('ivan@example.com', role: Role::Admin, active: true);

// Распаковка массива со строковыми ключами (тоже с 8.1 для списков)
$args = ['role' => Role::Admin, 'active' => true];
$user = new User('ivan@example.com', ...$args);
Важно для авторов библиотекС появлением именованных аргументов имя параметра стало частью публичного контракта. Переименование $userId в $id — это ломающее изменение, даже если сигнатура по типам не изменилась. В библиотеках это повод к семантическому версионированию, а в приватном коде — повод не бояться, но помнить.

Продвижение свойств конструктора (constructor property promotion) убирает самый скучный шаблон в PHP: объявить свойство, объявить параметр, присвоить одно другому.

phpБыло / стало
<?php
// Было — 12 строк, три повтора каждого имени
final class Money {
    private int $amount;
    private string $currency;

    public function __construct(int $amount, string $currency) {
        $this->amount = $amount;
        $this->currency = $currency;
    }
}

// Стало — 5 строк, имя встречается один раз
final class Money {
    public function __construct(
        private int $amount,
        private string $currency = 'RUB',
    ) {}
}
АнтипаттернПродвижение свойств в классе, где конструктор делает работу: валидирует, нормализует, вычисляет. Смешивать продвинутые и обычные свойства можно, но если половина полей объявлена в сигнатуре, а половина — в теле класса, читатель теряет карту объекта. Правило простое: продвижение — для DTO, value-объектов и сервисов с чистым внедрением зависимостей.
Типичный вопросЧто делают именованные аргументы с производительностью?
Ничего заметного: сопоставление имени с позицией происходит на этапе компиляции опкода, когда сигнатура известна. Единственный случай накладных расходов — распаковка ассоциативного массива через ...$args, где сопоставление идёт в рантайме. В прикладном коде это не измеряется.

8.0 / типы / поток управления

Union-типы, match и nullsafe

Ключевое

Union-типы позволяют объявить, что значение может быть одного из нескольких типов. До 8.0 это можно было выразить только в докблоке — и статический анализатор верил, а движок нет.

phpUnion-типы и новые псевдотипы
<?php
function parse(string|int $input): Result|false { /* ... */ }

// static как возвращаемый тип — «тот же класс, что и вызванный»
public function withStatus(Status $s): static { /* ... */ }

// mixed — явное «любой тип», в отличие от «тип не указан»
function dump(mixed $value): void {}

// get_debug_type() — правильная замена gettype()
gettype(1.5);           // 'double'   — историческое название
get_debug_type(1.5);    // 'float'    — как в объявлении типа
get_debug_type($obj);   // 'App\User' — вместо 'object'

match — выражение, а не оператор. Отличий от switch четыре, и все они важны.

phpmatch против switch
<?php
// switch: нестрогое сравнение, проваливание, не возвращает значение
switch ($code) {
    case 200:
    case 201: $label = 'ok'; break;
    default: $label = 'error';
}

// match: строгое ===, без break, возвращает значение, без default → ошибка
$label = match(true) {
    $code >= 500 => 'server error',
    $code >= 400 => 'client error',
    $code >= 200 => 'ok',
    default  => 'unknown',
};

// Ловушка switch, которой нет в match:
switch ('foo') { case 0: /* в PHP 7 сюда попадали! */ }

Nullsafe-оператор ?-> прерывает цепочку вызовов, если звено оказалось null, и возвращает null вместо фатальной ошибки.

php?-> и его границы
<?php
// Было
$country = null;
if ($user !== null) {
    $address = $user->getAddress();
    if ($address !== null) { $country = $address->country; }
}

// Стало
$country = $user?->getAddress()?->country;

// Чего ?-> НЕ делает:
//  • не работает с массивами: $arr?['key'] — синтаксическая ошибка;
//  • не работает со статикой: Foo?::bar();
//  • нельзя писать слева от присваивания: $a?->b = 1;
//  • не подавляет ошибку «метода не существует» — только null.
АнтипаттернДлинная цепочка ?-> как способ не думать о том, откуда берётся null. Запись $order?->customer?->address?->city?->name означает, что четыре связи в модели необязательны — и почти всегда это неправда: реальный ответ в том, что метод должен принимать уже гарантированно существующий объект. 8.0 / метаданные / атрибуты

Атрибуты вместо докблоков

Ключевое

До 8.0 метаданные для фреймворков жили в комментариях: Doctrine, Symfony и PHPUnit парсили докблоки регулярками и собственными лексерами. Атрибуты — это те же метаданные, но синтаксис языка: они проверяются на этапе компиляции и читаются через рефлексию.

phpОбъявление и чтение атрибута
<?php
// 1. Атрибут — обычный класс, помеченный #[Attribute]
#[Attribute(Attribute::TARGET_METHOD)]
final class Route {
    public function __construct(
        public string $path,
        public string $method = 'GET',
    ) {}
}

// 2. Применение
final class UserController {
    #[Route('/users/{id}', method: 'GET')]
    public function show(int $id): Response { /* ... */ }
}

// 3. Чтение через рефлексию
$method = new ReflectionMethod(UserController::class, 'show');
foreach ($method->getAttributes(Route::class) as $attr) {
    $route = $attr->newInstance();   // вот здесь создаётся объект Route
    register($route->path, $route->method);
}
ВажноАтрибут не выполняется сам по себе. Пока кто-то не вызовет getAttributes() и newInstance(), это просто запись в структуре класса — нулевая стоимость в рантайме. Именно поэтому фреймворки сканируют атрибуты один раз и кладут результат в кэш: сканирование дорогое, само наличие атрибутов — нет.

JIT: что это на самом деле даёт

JIT компилирует горячий байткод в машинный код. На вычислительных задачах — матрицы, обработка изображений, Mandelbrot из бенчмарков — прирост кратный. На типичном веб-приложении прирост около нуля, и это не разочарование, а следствие того, где приложение проводит время.

текстПочему JIT не ускоряет веб
Профиль обычного запроса Laravel/Symfony:

  ожидание базы данных   ████████████████████████  ~60%
  сеть, кэш, внешние API ██████████                ~20%
  выполнение опкодов PHP ████                      ~12%
  всё остальное          ██                        ~8%

JIT ускоряет только последнюю четверть третьей полоски.
Ускорить 12% на 20% = выиграть 2,4% времени ответа.

Что реально ускоряет веб-приложение:
  • opcache (обязателен: экономит парсинг и компиляцию — десятки процентов)
  • preloading (5-13% сверху)
  • устранение N+1 запросов (десятки процентов, иногда в разы)
  • кэш и правильные индексы
Типичный вопросСтоит ли включать JIT в продакшене?
Для веб-приложения — обычно нет: выигрыш в пределах погрешности, а риск редких багов компилятора и лишнее потребление памяти есть. Для CLI-задач с интенсивными вычислениями (обработка изображений, математика, парсинг больших объёмов) — да, и там измеряется реальный прирост. Правильный ответ всегда включает «зависит от профиля нагрузки» и упоминание, что opcache важнее JIT на порядок.

8.1 / типы / перечисления

Перечисления (enum)

КлючевоеСпрашивают всегда

До 8.1 набор допустимых значений выражали константами класса или строками — и ни то, ни другое не защищало от опечатки и не давало типа. Enum — это тип, у которого конечное число экземпляров, созданных движком один раз.

phpЧистый и типизированный enum
<?php
// Чистый enum: у case нет значения
enum Suit {
    case Hearts;
    case Spades;
}

// Типизированный (backed): у case есть скалярное значение — int или string
enum Status: string {
    case Draft     = 'draft';
    case Published = 'published';
    case Archived  = 'archived';

    // В enum можно объявлять методы, константы и реализовывать интерфейсы
    public function label(): string {
        return match($this) {
            self::Draft     => 'Черновик',
            self::Published => 'Опубликовано',
            self::Archived  => 'В архиве',
        };
    }

    public function isVisible(): bool {
        return $this === self::Published;
    }
}

// Использование
function publish(Status $status): void {}   // тип в сигнатуре

Status::Published->value;              // 'published'
Status::Published->name;               // 'Published'
Status::from('draft');                 // Status::Draft, иначе ValueError
Status::tryFrom('nope');               // null вместо исключения
Status::cases();                      // [Draft, Published, Archived]
Важно: enum — не классEnum-case является объектом, но с ограничениями: нельзя объявлять свойства (состояние запрещено), нельзя наследоваться, нельзя создать через new, нельзя клонировать. Сравнение всегда через === — case-ы синглтоны в пределах процесса. Именно поэтому match($this) внутри enum работает надёжно.

Типичный вопросКак хранить enum в базе и почему backed-enum лучше чистого?

Практическое правило: если значение уходит за пределы процесса (БД, JSON, очередь), берите enum: string и относитесь к значениям как к части контракта — их нельзя менять.

8.1 / иммутабельность

readonly-свойства и тип never

Ключевое

readonly-свойство можно записать ровно один раз — из области видимости объявившего класса. Обычно это происходит в конструкторе. Дальше любая попытка записи, включая запись изнутри класса, бросает Error.

phpreadonly и способ «изменить» значение
<?php
final class Money {
    public function __construct(
        public readonly int $amount,
        public readonly string $currency,
    ) {}

    // Изменение = новый объект (withers)
    public function add(Money $other): static {
        return new self($this->amount + $other->amount, $this->currency);
    }
}

$m = new Money(100, 'RUB');
// $m->amount = 200;  → Error: Cannot modify readonly property

//  • только для типизированных свойств (без типа — Fatal error);
//  • нельзя задать значение по умолчанию (снято только в 8.6);
//  • защищает ССЫЛКУ, а не содержимое:
final class Bag {
    public function __construct(public readonly ArrayObject $items) {}
}
$bag = new Bag(new ArrayObject());
$bag->items[] = 'x';   // работает! readonly не делает объект неизменяемым

Это исправлено в 8.3 (переинициализация внутри __clone) и доведено до удобного вида в 8.5 оператором clone with. 8.1 / асинхронность / прочее

Файберы и остальное в 8.1

Инфраструктура

Fiber — прерываемая функция с собственным стеком. Это низкоуровневый примитив: писать на нём прикладной код не нужно, он существует, чтобы библиотеки вроде AMPHP и ReactPHP могли предоставить асинхронность без «заражения» кода ключевым словом async.

phpFiber: минимальный пример
<?php
$fiber = new Fiber(function (string $start): string {
    echo "начали: {$start}\n";
    $resumed = Fiber::suspend('жду');   // приостановились, отдали значение
    echo "продолжили: {$resumed}\n";
    return 'готово';
});

$value = $fiber->start('A');   // 'жду'  — управление вернулось сюда
$fiber->resume('B');            // продолжили изнутри
$fiber->getReturn();            // 'готово'
ВажноФайбер — это не поток и не параллельность. В процессе по-прежнему выполняется ровно одна вещь одновременно; файбер лишь позволяет прерваться на месте ожидания и отдать управление планировщику. Без цикла событий (который дают библиотеки) сами по себе файберы бесполезны. На собеседовании ключевой момент: файбер решает проблему «цветных функций» — асинхронную операцию можно вызвать из обычной синхронной функции, не переписывая всю цепочку вызовов.

8.4 / классы / свойства

Хуки свойств

КлючевоеГлавное в 8.4

Хуки свойств позволяют объявить логику чтения и записи прямо на свойстве. Внешне это остаётся обычное свойство — $user->fullName, а не $user->getFullName(), — но за обращением стоит код.

phpget и set на свойстве
<?php
class User {
    public function __construct(
        private string $first,
        private string $last,
    ) {}

    // Вычисляемое свойство: только get, места в памяти не занимает
    public string $fullName {
        get => "{$this->first} {$this->last}";
    }

    // Валидация при записи: $value — неявный параметр set
    public string $email {
        set {
            if (!filter_var($value, FILTER_VALIDATE_EMAIL)) {
                throw new InvalidArgumentException('bad email');
            }
            $this->email = strtolower($value);   // запись в backing store
        }
    }
}

$u = new User('Иван', 'Петров');
echo $u->fullName;              // «Иван Петров» — как обычное свойство
$u->email = 'IVAN@EXAMPLE.COM';  // сохранится 'ivan@example.com'
Ключевая деталь: backing storeСвойство с хуком только get не хранит значение вообще — оно вычисляется при каждом обращении. Свойство, у которого хук ссылается на $this->email внутри себя, наоборот, получает реальное хранилище. Отсюда практическое следствие: вычисляемое свойство не кэшируется само по себе, и хук get с тяжёлым вычислением будет выполняться при каждом чтении.

Главное архитектурное следствие — интерфейс может требовать свойство. Раньше контракт «у объекта должно быть имя» выражался только методом getName().

8.4 / классы / инкапсуляция

Асимметричная видимость

Ключевое

Классическая дилемма: свойство должно быть открыто на чтение всем и закрыто на запись всем, кроме самого класса. До 8.4 это стоило приватного свойства плюс публичного геттера — двух сущностей ради одного поля. Асимметричная видимость задаёт разные уровни доступа для чтения и записи.

phppublic private(set)
<?php
// Было
class Order {
    private Status $status;

    public function getStatus(): Status { return $this->status; }

    public function markPaid(): void { $this->status = Status::Paid; }
}

// Стало: читают все, пишет только сам класс
class Order {
    public private(set) Status $status;

    public function markPaid(): void { $this->status = Status::Paid; }
}

$order->status;                // читается снаружи
// $order->status = Status::Paid;  → Error: Cannot modify ... from global scope

// Варианты: public protected(set), protected private(set)
// Работает и в продвижении свойств конструктора:
public function __construct(public protected(set) string $name) {}
Типичный вопросЧем public private(set) отличается от public readonly?
readonly разрешает ровно одну запись за всё время жизни объекта; private(set) разрешает сколько угодно записей, но только изнутри класса. Первое — про неизменяемость значения, второе — про то, кто имеет право его менять. Для value-объекта берут readonly, для сущности с жизненным циклом (заказ меняет статусы) — private(set).

8.5 / синтаксис / композиция

Оператор конвейера |>

Ключевое

Вложенные вызовы читаются справа налево и изнутри наружу — то есть в порядке, обратном тому, в котором происходят действия. Оператор конвейера передаёт результат левой части первым аргументом в правую, восстанавливая порядок чтения.

phpБыло / стало

$t = str_replace(' ', '-', $t);

    |> strtolower(...);

Fluent-интерфейс требует, чтобы каждый шаг был методом одного класса и возвращал $this или новый экземпляр того же типа — это цепочка внутри одного API. Конвейер соединяет произвольные функции, включая встроенные, и не требует от них ничего, кроме одного параметра. Первое — свойство библиотеки, второе — свойство языка.

Ключевое

phpЭволюция wither'а по версиям
<?php
final readonly class Article {
    public function __construct(
        public string $title,
        public string $body,
        public ?DateTimeImmutable $publishedAt = null,
    ) {}

    // нужно вспомнить и поправить КАЖДЫЙ wither

        return new self($title, $this->body, $this->publishedAt);
    }

    // PHP 8.5: одно выражение, остальные поля копируются сами
    public function withTitle(string $title): static {
        return clone($this, ['title' => $title]);
    }

    public function published(DateTimeImmutable $at): static {
        return clone($this, ['publishedAt' => $at]);
    }

Крупные deprecations 8.6
  • Возврат из блока finally — тихо отменяет исключение и возврат из try. Источник багов, которые невозможно объяснить по логам.
  • Возврат значения из конструктора и деструктора.
  • Псевдонимы: is_double(), is_integer(), is_long(), doubleval() — используйте is_float(), is_int(), floatval().

  • Методы сортировки ArrayIterator и CSV-методы SplFileObject.

Типичный вопросПочему возврат из finally решили объявить устаревшим?
Потому что return в finally побеждает всё: он отменяет и значение, возвращённое из try, и исключение, которое там было брошено. Функция, внутри которой произошла ошибка, тихо возвращает нормальное значение — и об ошибке никто не узнаёт. Это ровно тот случай, когда синтаксически корректный код почти никогда не выражает намерение автора.

Было / стало: что переписать в первую очередь

Практика

Это не список «модного синтаксиса», а места, где старая идиома реально хуже: либо не проверяется типами, либо скрывает ошибку, либо стоит лишних строк на каждом использовании.

phpДесять замен, окупающихся сразу
<?php
// 1. Поиск подстроки
if (strpos($s, 'abc') !== false)   →   if (str_contains($s, 'abc'))

// 2. Значение по умолчанию
isset($a['k']) ? $a['k'] : 'd'       →   $a['k'] ?? 'd'
if (!isset($a['k'])) $a['k'] = 'd'   →   $a['k'] ??= 'd'

// 3. Набор допустимых значений
const STATUS_DRAFT = 'draft'            →   enum Status: string { ... }

// 4. Ветвление с возвратом значения
switch + break + $result           →   $result = match(...) { ... }

// 5. DTO и value-объекты
свойства + конструктор + присвоение   →   продвижение свойств + readonly

// 6. Геттер без сеттера
private $x + getX()                   →   public private(set) $x        // 8.4

// 7. Вычисляемый геттер
public function getFullName()        →   public string $fullName { get => ... }

// 8. Колбэк по имени
[$this, 'method']                    →   $this->method(...)

// 9. Поиск в массиве
foreach + if + break                 →   array_find($items, fn ($i) => ...)

// 10. Метаданные для фреймворка
/** @Route("/path") */              →   #[Route('/path')]
Антипаттерн миграцииМассовый рефакторинг «под новый синтаксис» отдельным пул-реквестом на всю кодовую базу. Такой PR невозможно отревьюить, он конфликтует со всем, что делают коллеги, и прячет содержательные изменения среди тысячи механических. Работающий подход: автоматические правки Rector'ом отдельными узкими наборами правил (один набор — один PR) плюс правило «трогаешь файл по задаче — приводишь его к современному виду».
Что действительно стоит делать массовоТри вещи безопасны и окупаются: (1) declare(strict_types=1) в новых файлах, (2) добавление типов свойствам и сигнатурам — их проверит статанализ, (3) устранение deprecations перед обновлением версии. Всё остальное — по мере касания кода.

справочник / собеседование

Вопросы по версиям с короткими ответами

Спрашивают часто
  1. Чем match отличается от switch?Строгое сравнение === вместо ==, это выражение с возвращаемым значением, нет проваливания, а ненайденная ветка бросает UnhandledMatchError вместо тихого пропуска. Обратная сторона: тело ветки — только одно выражение.
  2. Что даёт readonly и от чего он не защищает?Защищает свойство от повторной записи после инициализации. Не защищает содержимое объекта, на который свойство ссылается: readonly array нельзя переприсвоить, а вот у readonly ArrayObject можно добавлять элементы. Настоящая иммутабельность требует, чтобы вложенные объекты тоже были неизменяемыми.
  3. Backed-enum или чистый — что выбрать?Если значение пересекает границу процесса (БД, JSON, очередь) — backed, потому что нужно стабильное скалярное представление. Если enum живёт только внутри кода — чистый. Значения backed-enum становятся частью контракта, менять их так же опасно, как менять схему БД.
  4. Зачем нужны файберы, если есть генераторы?Генератор может приостановиться только на своём уровне: чтобы прокинуть yield сквозь пять вызовов, весь стек должен состоять из генераторов. Файбер приостанавливает произвольно глубокий стек целиком, поэтому асинхронную операцию можно вызвать из обычной функции. Это решение проблемы «цветных функций».
  5. Даёт ли JIT прирост вашему приложению?Веб-приложению — практически нет: время уходит на базу и сеть, а не на выполнение опкодов. CLI-задачам с интенсивными вычислениями — да, там прирост измеримый. Гораздо важнее opcache, который обязателен, и preloading, дающий 5–13%.
  6. Что изменилось в сравнении строк и чисел в 8.0 и почему это важно для безопасности?Нечисловая строка больше не приводится к нулю: 0 == 'foo' стало false. В PHP 7 это порождало уязвимости в проверках токенов: если токен из базы был 0 (или приводился к нему), любая нечисловая строка проходила сравнение. Правильная защита не зависит от версии — строгое === и hash_equals() для секретов.
  7. Чем хуки свойств отличаются от __get/__set?Хуки работают на объявленных свойствах, типизированы, видны IDE и статанализу, их можно потребовать в интерфейсе и они не требуют магии в рантайме. __get/__set срабатывают только на необъявленных свойствах, возвращают mixed и известны анализатору лишь через докблок @property.
  8. Когда public private(set), а когда readonly?readonly — ровно одна запись за жизнь объекта, подходит value-объектам. private(set) — сколько угодно записей, но только изнутри класса, подходит сущностям с жизненным циклом. Их можно комбинировать с хуками, но не друг с другом.
  9. Зачем нужен #[\Override]?Чтобы опечатка в имени переопределяемого метода или переименование метода в базовом классе библиотеки падали на этапе компиляции, а не превращались в тихо неработающий код. IDE проверяет момент написания, атрибут — момент сборки.
  10. Что такое ленивые объекты в 8.4 и зачем они в ядре?Это встроенный механизм прокси: объект создаётся при первом обращении. Раньше то же самое делали DI-контейнеры и ORM через кодогенерацию прокси-классов — медленно, хрупко и с проблемами при отладке. Теперь это умеет рефлексия: newLazyProxy() и newLazyGhost().
  11. Оператор конвейера — зачем он, если есть цепочки методов?Цепочка методов работает только внутри одного API, где каждый шаг возвращает совместимый объект. Конвейер соединяет любые функции с одним параметром, включая встроенные, и восстанавливает порядок чтения: вложенные вызовы читаются изнутри наружу, конвейер — сверху вниз.
  12. На какой версии PHP запускать новый проект в 2026 году?8.4, если важна максимальная совместимость экосистемы, или 8.5, если нужны конвейер и clone with. 8.3 приемлемо только при жёстком ограничении окружения: у неё уже закончилась активная поддержка. Всё, что ниже 8.2, — вне поддержки и небезопасно.
Как отвечатьНа вопросы про версии почти всегда ждут не перечисления возможностей, а понимания зачем они появились: какую проблему решает enum, почему readonly недостаточно для иммутабельности, почему JIT не помогает вебу. Ответ «в 8.1 добавили enum, readonly, файберы и never» показывает, что вы читали список изменений. Ответ «до enum набор значений выражали строковыми константами, и тип не проверялся — опечатка ловилась в рантайме» показывает, что вы им пользовались.

  • wiki.php.net/rfc — все RFC со статусами. Здесь видно, что реально принято в разработку, а что осталось предложением.
  • stitcher.io — разборы «что нового» по каждой версии с примерами; удобно для быстрого обзора ещё до релиза.
  • Rector и PHPStan — инструменты, которые делают миграцию управляемой. Наборы правил в Rector повторяют список изменений версии.
Полезная привычкаКаждый ноябрь, когда выходит минорная версия, потратьте час на чтение раздела UPGRADING — не ради новых возможностей, а ради списка deprecations. Устранённое сразу изменение стоит десять минут; то же изменение через три года, когда оно стало ошибкой и заблокировало обновление, стоит спринт.
