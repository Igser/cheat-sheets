Паттерны и архитектура кода

Архитектура кода отвечает на один вопрос: сколько будет стоить следующее изменение. Не «красиво ли написано» и не «сколько паттернов применено» — а получится ли через год добавить новый способ оплаты, не переписав половину системы, и сможет ли новый человек внести правку, не сломав то, о чём он не знал.

Отсюда две противоположные ошибки. Первая — не проектировать вовсе: логика расползается по контроллерам, один класс знает про всё, любое изменение задевает десяток файлов. Вторая, более обидная, — проектировать про запас: пять уровней абстракции, интерфейсы с единственной реализацией, фабрики фабрик. Обе ошибки дают одинаковый результат — изменения становятся дорогими, только по разным причинам.

Конспект идёт от принципов к границам: связность и связанность, SOLID и повседневные паттерны → композиция, тактический DDD, порты и адаптеры, рефакторинг → модульные границы, технический долг, работа с легаси и, отдельным разделом, когда абстракцию применять не надо. Смежные темы: PHP, System Design, тестирование, Symfony, Laravel.

junior / принципы

Зачем архитектура кода

База

Вся тема сводится к двум свойствам. Связность (cohesion) — насколько части одного модуля относятся к одной задаче: высокая связность хороша. Связанность (coupling) — насколько модули зависят друг от друга: низкая связанность хороша. Всё остальное — SOLID, паттерны, слои — это способы достичь именно этого.

Цена изменения ≈ число мест, которые придётся тронуть × риск в каждомХорошая архитектура уменьшает первый множитель; тесты — второй
phpОдна и та же логика: высокая связанность и низкая
<?php
// Высокая связанность: класс знает про SMTP, про структуру таблицы, про формат письма.
// Чтобы добавить отправку в мессенджер, придётся править этот класс.
final class OrderService
{
    public function complete(int $orderId): void
    {
        $pdo = new PDO(DB_DSN, DB_USER, DB_PASS);
        $pdo->exec("UPDATE orders SET status='done' WHERE id={$orderId}");

        $mailer = new SmtpMailer('smtp.example.com', 587);
        $mailer->send($to, 'Заказ выполнен', "Ваш заказ #{$orderId} готов");
    }
}

// Низкая связанность: класс знает только про интерфейсы.
// Новый канал уведомлений — новый класс, этот файл не меняется.
final class CompleteOrder
{
    public function __construct(
        private readonly OrderRepository $orders,
        private readonly Notifier $notifier,
    ) {}

    public function __invoke(OrderId $id): void
    {
        $order = $this->orders->get($id);
        $order->complete();                 // правило перехода живёт в самом заказе
        $this->orders->save($order);

        $this->notifier->notify(new OrderCompleted($id));
    }
}

Типичный вопрос на собеседованииЧто такое связность и связанность?
Связность — насколько всё внутри модуля относится к одной задаче; её хотят высокой. Связанность — насколько модули зависят друг от друга; её хотят низкой. Практический критерий: при типовом изменении правится один модуль, а не десяток файлов в разных слоях. Все принципы проектирования — по сути разные способы добиться этих двух свойств.

SOLID на практике

База

SOLID спрашивают почти на каждом собеседовании, и почти всегда получают пересказ определений. Ценность ответа появляется, когда вы можете показать нарушение в реальном коде и объяснить, чем оно вредит.

phpОткрытость/закрытость: самый практичный из пяти
<?php
// Нарушение: каждый новый способ доставки — правка этого метода.
// Риск сломать существующее при добавлении нового.
public function cost(Order $order, string $type): Money
{
    return match ($type) {
        'pickup'  => Money::zero(),
        'courier' => Money::rub('300.00'),
        'post'    => Money::rub('150.00')->plus($order->weightFee()),
        // ...и так до пятнадцати вариантов
    };
}

// Решение: поведение выносится в отдельные реализации одного контракта
interface DeliveryMethod
{
    public function supports(Order $order): bool;
    public function cost(Order $order): Money;
}

final class CourierDelivery implements DeliveryMethod
{
    public function supports(Order $order): bool { return $order->isInCity(); }
    public function cost(Order $order): Money { return Money::rub('300.00'); }
}

// Новый способ доставки = новый класс. Существующий код не трогается.
final class DeliveryCalculator
{
    public function __construct(private iterable $methods) {}   // контейнер соберёт все реализации

    public function cost(Order $order, DeliveryType $type): Money
    {
        foreach ($this->methods as $method) {
            if ($method->supports($order)) { return $method->cost($order); }
        }

        throw new NoDeliveryAvailable($order->id);
    }
}
АнтипаттернПрименять принцип открытости/закрытости заранее, «на всякий случай»: интерфейс с единственной реализацией и фабрика к нему для кода, который не менялся два года. Правило практичнее формулируется так: первый вариант пишем прямо, при появлении второго — выделяем абстракцию. Два случая уже показывают, где проходит настоящая граница изменчивости, а один — нет.
Типичный вопрос на собеседованииРасскажите про SOLID с примером нарушения.
Сильный ответ — не пересказ, а живой пример. Например, единственная ответственность: класс, который и достаёт данные из базы, и считает скидку, и формирует письмо, меняется по трём независимым причинам, и правка формата письма способна сломать расчёт. Разделение даёт три класса, каждый с одной причиной меняться и с быстрыми тестами. Хорошо добавить и обратную сторону: делить до бесконечности тоже вредно — критерий в том, меняются ли части независимо.

junior / паттерны

Повседневные паттерны

База

Паттерн — это имя для решения, которое всё равно возникает само. Ценность в общем словаре: «здесь стратегия» короче, чем описание из трёх предложений. Знать наизусть все двадцать три не нужно; нужно уверенно владеть теми семью, что встречаются каждую неделю.

phpДекоратор: кэш и повторы без правки исходного класса
<?php
interface RateProvider { public function rate(string $currency): string; }

// Базовая реализация ничего не знает ни про кэш, ни про повторы
final class HttpRateProvider implements RateProvider { /* ... */ }

// Декоратор реализует тот же интерфейс и оборачивает другой экземпляр
final class CachedRateProvider implements RateProvider
{
    public function __construct(
        private readonly RateProvider $inner,
        private readonly CacheInterface $cache,
    ) {}

    public function rate(string $currency): string
    {
        return $this->cache->get("rate:{$currency}", fn () => $this->inner->rate($currency));
    }
}

// Собирается как матрёшка — порядок обёрток задаёт поведение
$provider = new CachedRateProvider(
    new RetryingRateProvider(
        new LoggingRateProvider(new HttpRateProvider($http), $logger),
        attempts: 3
    ),
    $cache
);

// Выигрыш: базовый класс остаётся простым и тестируется без кэша и логов,
// а каждую обёртку можно включать и выключать конфигурацией.
phpОбъект-значение: самый недооценённый приём
<?php
// Было: email — строка. Проверяется в контроллере, в сервисе, в обработчике очереди.
// Однажды где-нибудь проверить забудут.

final readonly class Email
{
    public function __construct(public string $value)
    {
        // Инвариант проверяется один раз — при создании.
        // Дальше по коду объект корректен по построению.
        if (!filter_var($value, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException("Некорректный email: {$value}");
        }
    }

    public function domain(): string
    {
        return substr(strrchr($this->value, '@'), 1);   // поведение рядом с данными
    }

    public function equals(self $other): bool
    {
        return strtolower($this->value) === strtolower($other->value);
    }
}

Типичный вопрос на собеседованииКакие паттерны вы применяете и зачем?
Отвечать стоит от задачи, а не от списка. Стратегия — когда вариантов алгоритма несколько и они растут: вместо разрастающегося match появляются реализации одного контракта. Декоратор — чтобы навесить кэш, логирование и повторы, не трогая исходный класс. Объект-значение — чтобы проверить инвариант один раз при создании, а не в пяти местах. Ответ вида «использую синглтон, фабрику и наблюдатель» без контекста ценности не имеет.

phpАнемичная модель против богатой: где живут правила
<?php
// Анемичная: сущность — контейнер для данных, правила снаружи
class Order
{
    public string $status;
    public array $items = [];
}

// ...и в каждом сервисе, который меняет заказ, повторяется одна и та же проверка
if ($order->status === 'paid' && count($order->items) > 0) {
    $order->status = 'shipped';      // а где-то проверку забудут
}

// Богатая: правило перехода живёт там же, где состояние.
// Нарушить инвариант снаружи физически нельзя.
final class Order
{
    private OrderStatus $status = OrderStatus::New;
    private array $items = [];

    public function ship(): void
    {
        if ($this->status !== OrderStatus::Paid) {
            throw new OrderNotPaid($this->id);
        }

        if ($this->items === []) {
            throw new EmptyOrder($this->id);
        }

        $this->status = OrderStatus::Shipped;
        $this->record(new OrderShipped($this->id));   // доменное событие
    }
}

// Тест такого правила не требует ни базы, ни контейнера — он мгновенный.
Практический выводАнемичная модель — не всегда ошибка. Для CRUD-раздела, где «правило» состоит в сохранении полей, богатая модель избыточна. Она окупается там, где есть настоящие инварианты и переходы состояний: заказы, платежи, подписки, остатки. Признак, что пора: одна и та же проверка появилась в третьем месте.
Типичный вопрос на собеседованииЧто такое анемичная модель и всегда ли это плохо?
Это сущности без поведения — только данные, а все правила в сервисах. Проблема в том, что инвариант не защищён: один и тот же переход статуса проверяется в нескольких местах, и однажды где-то проверку забудут. Но это не универсальное зло: для простого CRUD она уместна и дешевле. Богатая модель окупается там, где есть реальные бизнес-правила и переходы состояний.

// Сервис приложения — сценарий целиком, без знания об HTTP
final class ShipOrder
{
    public function __invoke(OrderId $id, User $user): Order
    {
        return $this->transaction->run(function () use ($id, $user) {
            $order = $this->orders->getForUser($id, $user);   // права — в слое данных
            $order->ship();                                  // правило — в домене
            $this->orders->save($order);
            $this->events->dispatch(...$order->releaseEvents());

            return $order;
        });
    }
}
АнтипаттернСлой ради слоя: контроллер вызывает сервис, который вызывает другой сервис, который вызывает репозиторий и просто передаёт данные дальше без единого решения. Такой «прослойка-сервис» не добавляет ничего, кроме файла и прыжка при чтении кода. Слой оправдан, только если он принимает решения или скрывает детали — иначе его лучше убрать.
Типичный вопрос на собеседованииГде должна жить бизнес-логика?
Не в контроллере и не в запросах к базе. Правила и инварианты — в доменных объектах: там, где живёт состояние, которое они защищают. Сценарий (получить, вызвать, сохранить, уведомить, транзакция) — в сервисе приложения. Контроллер только разбирает запрос и переводит доменные ошибки в коды ответа. Проверка простая: можно ли выполнить бизнес-правило из консольной команды и из обработчика очереди, не дублируя код.

Типичный вопрос на собеседованииПочему композиция предпочтительнее наследования?
Наследование связывает классы жёстко: наследник зависит от всего родителя, комбинации поведений дают взрыв числа классов, а изменение базового класса задевает всю иерархию. Композиция даёт то же переиспользование через контракт: поведение собирается в любом сочетании, подменяется в тестах и меняется конфигурацией. Наследование остаётся уместным там, где есть настоящее отношение «является», — например, в иерархии исключений.

// Стало: таблица переходов в одном месте — читается как документация
enum OrderStatus: string
{
    case New = 'new';
    case Paid = 'paid';
    case Shipped = 'shipped';
    case Cancelled = 'cancelled';

    public function canTransitionTo(self $target): bool
    {
        return in_array($target, match($this) {
            self::New       => [self::Paid, self::Cancelled],
            self::Paid      => [self::Shipped, self::Cancelled],
            self::Shipped   => [],                       // конечное состояние
            self::Cancelled => [],
        }, true);
    }
}

// В сущности остаётся одна проверка на все переходы
private function transitionTo(OrderStatus $target): void
{
    if (!$this->status->canTransitionTo($target)) {
        throw new InvalidTransition($this->status, $target);
    }

    $this->status = $target;
}

Типичный вопрос на собеседованииКогда паттерн приносит вред?
Когда он введён до появления проблемы. phpАгрегат: граница согласованности и единственная точка входа
<?php
final class Order                       // корень агрегата
{
    private array $items = [];          // часть агрегата: снаружи недоступна напрямую
    private array $events = [];

    // Инвариант агрегата: не более 50 позиций и сумма не превышает лимит.
    // Он может быть проверен только здесь — потому что только здесь видно целое.
    public function addItem(Sku $sku, int $qty, Money $price): void
    {
        if (count($this->items) >= 50) {
            throw new TooManyItems($this->id);
        }

        $item = new OrderItem($sku, $qty, $price);

        if ($this->total()->plus($item->subtotal())->isGreaterThan($this->limit)) {
            throw new OrderLimitExceeded($this->id);
        }

        $this->items[] = $item;
        $this->events[] = new ItemAdded($this->id, $sku, $qty);
    }

    // Наружу отдаём копию: никто не изменит состав в обход правил
    public function items(): array { return array_map(fn ($i) => clone $i, $this->items); }

    public function releaseEvents(): array
    {
        $events = $this->events;
        $this->events = [];

        return $events;                  // сервис приложения опубликует их после сохранения
    }
}

// Правила выбора границы агрегата:
//   1. Внутри агрегата инварианты соблюдаются немедленно и в одной транзакции.
//   2. Между агрегатами — согласованность отложенная, через события.
//   3. Ссылки на другие агрегаты — по идентификатору, а не объектом.
//   4. Одна транзакция меняет один агрегат: иначе граница выбрана неверно.
ВажноСамая частая ошибка — слишком крупный агрегат: «Клиент» со всеми заказами, платежами и адресами внутри. Такой объект невозможно загрузить целиком, он создаёт блокировки и конфликты при параллельной работе. Признак правильного размера: агрегат целиком помещается в памяти без усилий, а его инварианты действительно требуют проверки в одной транзакции. Если сомневаетесь — берите меньший.
Типичный вопрос на собеседованииЧто такое агрегат и как выбрать его границу?
Группа объектов, которая сохраняется и проверяется как целое, с единственной точкой входа — корнем. Граница определяется инвариантами: что обязано быть согласованным немедленно, входит внутрь; остальное связывается по идентификатору и согласуется через события. Практическое правило — одна транзакция меняет один агрегат. Частая ошибка в другую сторону: слишком крупный агрегат, который тяжело грузить и который создаёт конфликты при параллельной работе.

}

// ЧТЕНИЕ: никакого агрегата — плоский запрос ровно под нужды экрана.
// Загружать агрегат ради списка из двадцати строк — верный способ получить N+1.
final class OrderListQuery
{
    public function execute(string $tenantId, ?string $cursor, int $limit): array
    {
        return $this->db->fetchAll(
            'SELECT o.id, o.status, o.total, c.display_name AS customer
               FROM orders o
               JOIN customers c ON c.id = o.customer_id
              WHERE o.tenant_id = :t' . ($cursor ? ' AND o.id < :cursor' : '') . '
              ORDER BY o.created_at DESC, o.id DESC
              LIMIT :limit',
            compact('tenantId', 'cursor', 'limit')
        );
    }
}

// Это «CQRS для бедных»: разные модели для чтения и записи в одной базе,
// без отдельного хранилища и синхронизации. Девяносто процентов пользы
// за десять процентов сложности.

Типичный вопрос на собеседованииЗачем разделять модели чтения и записи?

Техника рефакторинга

Ключевое

ВажноРефакторинг и изменение поведения не смешиваются в одном коммите — и тем более в одном pull request. Иначе ревьюер видит дифф на пятьсот строк, где невозможно отделить перестановку кода от новой логики, и ревью превращается в формальность. Правильный порядок: сначала рефакторинг отдельным PR при зелёных тестах, потом новая функция в чистой структуре.
Типичный вопрос на собеседованииКак вы подходите к рефакторингу большого метода?
Сначала фиксирую поведение тестами — если их нет, пишу характеризующие на реальных данных. Затем маленькими шагами: выделить метод, не меняя содержимое; заменить примитивы типами; вынести в класс с явными зависимостями. Каждый шаг — отдельный коммит с зелёными тестами, поэтому в любой момент можно остановиться и откатиться. Абстракцию ввожу последней, когда появился второй вариант, а не заранее.

Уровень 03 · границы и эволюция

Senior: границы, долг, простота

Senior отвечает не за красоту кода, а за скорость команды через год. Это означает три вещи: правильно нарезать модули, управлять техническим долгом как инженерной величиной, а не как ругательством, и — самое трудное — вовремя отказываться от абстракций, которые кажутся правильными.

senior / модули

Модульные границы

Архитектура

Главный архитектурный вопрос в коде — не «какие паттерны», а «где проходят границы». Правильно нарезанные модули позволяют менять один, не читая остальные. Неправильно нарезанные превращают систему в набор файлов, где любое изменение требует знания всего.

Обратный признак: модуль, который годами меняется независимо от остальных, — кандидат на выделение в отдельный сервис, если для этого появится причина (см. конспект по System Design).
Типичный вопрос на собеседованииКак вы решаете, где провести границу модуля?
По тому, что меняется вместе. Нарезка по техническим слоям выглядит аккуратно, но размазывает каждую функцию по трём каталогам, поэтому я режу по бизнес-возможностям, а слои держу внутри модуля. Между модулями — только публичные контракты, без обращения к чужому домену и чужим таблицам, и без циклов. И обязательно автоматическая проверка правил в CI: без неё границы размываются за полгода.

Технический долг

Архитектура

Технический долг — не синоним плохого кода. Это осознанный компромисс: мы сделали быстрее и хуже, чтобы получить что-то ценное сейчас, и знаем, что позже заплатим процентами в виде замедления. Проблема начинается, когда долг берут неосознанно и не учитывают.

Не аргументом «код плохой» — он ничего не значит для продукта. Через числа: сколько сейчас занимает типовая задача в этом модуле и сколько будет занимать после; сколько инцидентов пришло отсюда за квартал; сколько времени уходит на ручную синхронизацию дублирующихся правил. senior / легаси

Легаси-архитектура

Архитектура

Легаси — это код, который приносит деньги и который страшно менять. Полное переписывание почти всегда проигрывает: новая система догоняет старую по функциональности годами, а старая всё это время продолжает меняться.

phpАнтикоррупционный слой: изоляция от чужой модели
<?php
// Проблема: легаси-модуль оперирует массивами со странными ключами
// и статусами вроде 'N', 'P', 'S'. Тащить это в новый код — значит
// заразить его чужими решениями навсегда.

// Решение: слой перевода на границе. Внутри нового модуля живёт своя модель.
final class LegacyOrderGateway implements OrderRepository
{
    public function get(OrderId $id): Order
    {
        $row = $this->legacy->fetchOrder($id->toInt());   // чужой формат

        // Перевод один раз, в одном месте, с явными правилами
        return Order::restore(
            id:     $id,
            status: match ($row['ord_st']) {
                'N' => OrderStatus::New,
                'P' => OrderStatus::Paid,
                'S' => OrderStatus::Shipped,
                default => throw new UnknownLegacyStatus($row['ord_st']),
            },
            total:  Money::fromMinor((int) $row['sum_kop'], 'RUB'),
        );
    }
}

// Выигрыш: новый модуль пишется на своей модели и не зависит от легаси.
// Когда легаси уйдёт, меняется одна реализация, а не весь новый код.

Типичный вопрос на собеседованииВам достался проект без архитектуры. С чего начнёте?
Не с переписывания. Сначала пойму, где болит на самом деле: какие модули меняются чаще всего, откуда приходят инциденты, что дольше всего делается. Это видно по истории репозитория и по трекеру. Затем в самой болезненной точке — характеризующие тесты, выделение границ и антикоррупционный слой для нового кода. Улучшения привязываю к функциональным задачам, чтобы они шли непрерывно, а не отдельным проектом, который отменят при первом же срочном деле.

Практический выводПолезное правило: дублирование дешевле неверной абстракции. Повторённый код виден и легко правится в двух местах; неверная абстракция расползается по всей системе, обрастает флагами и стоит недель на распутывание. Отсюда практика: первое повторение — копируем, второе — присматриваемся, третье — обобщаем, уже понимая, что именно общего.
Типичный вопрос на собеседованииКак понять, что архитектура переусложнена?
По симптомам: чтобы понять один сценарий, приходится открыть восемь файлов; половина интерфейсов имеет единственную реализацию; есть слои, которые только передают вызов дальше; новый человек не может внести правку без сопровождающего неделю. Проверка простая — попросите коллегу, не знающего модуль, проследить путь одного запроса. Если это занимает больше пятнадцати минут, сложность не оправдана.

Архитектура и команда

Архитектура

Структура кода стремится повторить структуру общения в команде — это наблюдение известно как закон Конвея. Практическое следствие: архитектурные решения, идущие против устройства команды, не приживаются, а изменение структуры команды рано или поздно проявится в коде.

Что реально удерживает архитектуру. Не диаграмма на стене и не документ на сорок страниц, а три вещи: автоматические проверки правил в CI (направление зависимостей, границы модулей); короткие записи принятых решений с отвергнутыми вариантами — они не дают возвращаться к одному спору дважды; и владельцы модулей, назначенные явно, чтобы у каждого куска был человек, отвечающий за целостность. Всё остальное размывается за полгода.

ВажноАрхитектурное решение, которое не могут объяснить в команде, не будет соблюдаться — независимо от того, насколько оно верное. Поэтому часть работы senior — не спроектировать, а донести: показать на примере, зафиксировать письменно, встроить в ревью и в автоматику. Решение живёт ровно столько, сколько существует его объяснение.
Типичный вопрос на собеседованииКак вы внедряете архитектурные решения в команде?
Сначала объясняю проблему, а не решение: пока люди не почувствовали боль, любое правило воспринимается как бюрократия. Затем показываю на одном реальном модуле, что меняется. Фиксирую письменно короткой записью с контекстом и отвергнутыми вариантами. И встраиваю в процесс: проверка правил в CI и пункт в чек-листе ревью. Без последнего шага договорённость держится примерно до первого срочного релиза.

Ответы короткие — это каркас. Вопросы по архитектуре почти всегда проверяют не знание определений, а способность назвать цену решения и условие, при котором вы поступили бы иначе.

Junior · 20 вопросов

Junior
  1. Что такое связность и связанность?Связность — насколько всё внутри модуля относится к одной задаче, её хотят высокой. Связанность — насколько модули зависят друг от друга, её хотят низкой. Практический критерий: при типовом изменении правится один модуль, а не десяток файлов в разных слоях.
  2. Зачем вообще думать об архитектуре кода?Чтобы следующее изменение стоило дёшево. Архитектура не про красоту, а про число мест, которые придётся тронуть, и риск в каждом из них. Проект без структуры костенеет: улучшать становится страшно, и качество падает само собой.
  3. Расскажите про принцип единственной ответственности.У класса должна быть одна причина меняться. Класс, который достаёт данные, считает скидку и формирует письмо, меняется по трём независимым причинам, и правка формата письма способна сломать расчёт. Оговорка: дробить до бесконечности тоже вредно — критерий в том, меняются ли части независимо.
  4. Что такое открытость/закрытость и как её достичь?Новое поведение добавляется новым кодом, а не правкой существующего. Практически это переход от растущего match по типу к набору реализаций одного контракта: новый способ доставки — новый класс, старый код не трогается. Вводить стоит при появлении второго варианта, а не первого.
  5. Что означает принцип подстановки Лисков?Наследник должен работать везде, где ожидается базовый тип, не ломая ожиданий. Классическое нарушение — наследник, который бросает «не поддерживается» там, где база возвращает значение, или ужесточает требования к аргументам. Это обычно признак того, что связь «является» надуманная и нужна композиция.
  6. Что такое инверсия зависимостей?Зависимость от абстракции вместо конкретной реализации, причём интерфейс принадлежит потребителю. Сервис принимает интерфейс отправителя писем, а не создаёт внутри SMTP-клиент. Тогда в проде это SMTP, в тестах — двойник, а код не меняется.
  7. Чем внедрение зависимостей отличается от DI-контейнера?Внедрение — приём: зависимости приходят через конструктор. Контейнер — инструмент, который их собирает. Приём работает и без контейнера, а контейнер без приёма превращается в service locator, когда класс сам достаёт что хочет, и зависимости снова становятся скрытыми.
  8. Что такое паттерн стратегия и когда он нужен?Взаимозаменяемые варианты алгоритма за общим контрактом. Признак, что пора: условие по типу, которое растёт с каждой новой задачей. После выделения новый вариант — это новый класс, а существующий код и его тесты не трогаются.
  9. Зачем нужен декоратор?Чтобы добавить поведение, не меняя исходный класс: кэш, логирование, повторы, замеры. Декоратор реализует тот же интерфейс и оборачивает другой экземпляр, поэтому обёртки собираются в любом порядке и включаются конфигурацией. Базовый класс при этом остаётся простым и легко тестируется.
  10. Что такое объект-значение и зачем он?Небольшой неизменяемый объект, определяемый значением: деньги, email, период. Он переносит инвариант в тип: проверка выполняется один раз при создании, дальше объект корректен по построению. Плюс сигнатура метода начинает документировать контракт и защищать от перепутанных аргументов.
  11. Что такое репозиторий?Контракт доступа к объектам домена, выглядящий как коллекция: получить, сохранить, найти по правилу. Он не даёт SQL расползтись по сервисам и позволяет подменить хранилище в тестах. Важно, что он описан на языке домена, а не хранилища: без limit, offset и join в сигнатурах.
  12. Какие вы знаете запахи кода?Божественный объект, длинный метод, одержимость примитивами, завистливый метод, дробовик (одно изменение задевает десять файлов), анемичная модель, флаги в аргументах, длинные цепочки вызовов. Запах — не ошибка, а сигнал: работает, но скоро станет дорого.
  13. Что такое анемичная модель и всегда ли это плохо?Сущности без поведения, вся логика в сервисах. Проблема в том, что инвариант не защищён: одна и та же проверка повторяется в нескольких местах и однажды будет забыта. Но для простого CRUD анемичная модель уместна и дешевле; богатая окупается там, где есть настоящие правила и переходы состояний.
  14. Почему не стоит писать логику в контроллере?Потому что она становится недоступной из консольной команды, обработчика очереди и другого эндпоинта — и её приходится дублировать. Плюс её нельзя протестировать без HTTP-слоя. Контроллер разбирает запрос, вызывает сценарий и переводит ошибки в коды ответа, не более.
  15. Какие бывают слои и что в каждом?Контроллер — HTTP и формат. Сервис приложения — сценарий: получить, вызвать домен, сохранить, уведомить, транзакция. Домен — правила и инварианты, без знания о фреймворке и базе. Репозиторий — контракт хранения. Инфраструктура — реализации. Слой оправдан, только если он принимает решения или скрывает детали.
  16. Что такое «тонкий контроллер»?Контроллер без бизнес-логики и без SQL: он разбирает вход, вызывает один сценарий и формирует ответ. Проверка простая — можно ли выполнить то же действие из консоли и из очереди, не дублируя код. Если нет, логика застряла в контроллере.
  17. Зачем нужны DTO?Чтобы отделить внутреннюю модель от того, что уходит наружу или приходит внутрь. Без них любое переименование поля сущности ломает клиентов, а новое поле публикуется без ревью. Плюс DTO явно описывает, какие данные нужны конкретному сценарию.
  18. Когда абстракция вредна?Когда введена до появления проблемы: интерфейс с единственной реализацией «на будущее», фабрика для объекта с простым конструктором, слой, который только передаёт вызов дальше. Каждая такая абстракция стоит файла, прыжка при чтении и времени нового человека, не давая взамен гибкости.
  19. Что такое трейт и когда он уместен?Механизм примешивания методов в класс. Выглядит как композиция, но работает как копирование кода: источник поведения не виден, подменить его нельзя, конфликты имён приходится разрешать вручную. Для технической мелочи годится, для бизнес-логики лучше композиция через зависимость.
  20. Как понять, что код плохой?Не по ощущениям, а по признакам: типовое изменение задевает много файлов, класс нельзя протестировать без базы, у класса несколько причин меняться, одна и та же проверка повторяется в разных местах, новый человек не может внести правку без сопровождения. Всё это измеримо и обсуждаемо, в отличие от «мне не нравится».

  1. Почему композиция предпочтительнее наследования?Наследование связывает жёстко: наследник зависит от всего родителя, комбинации поведений дают взрыв числа классов, изменение базового класса задевает иерархию. Композиция даёт переиспользование через контракт, собирается в любом сочетании и подменяется в тестах. Наследование остаётся для настоящего «является» — например, иерархии исключений.
  2. Кому принадлежит интерфейс — потребителю или реализации?Потребителю. Интерфейс репозитория лежит в домене и написан на языке домена, а реализация — в инфраструктуре. Это и есть инверсия зависимостей: инфраструктура знает о домене, домен о ней — нет. Если интерфейс лежит рядом с реализацией и повторяет её методы, инверсии не произошло.
  3. Нужен ли интерфейс, если реализация одна?Только если есть второй потребитель контракта: инверсия зависимости, подстановка двойника в тестах или другой слой. Интерфейс, дублирующий публичные методы класса «для соблюдения принципа», — лишний файл, который придётся править вместе с классом. Критерий практический, а не идеологический.
  4. Что такое агрегат и как выбрать границу?Группа объектов, сохраняемая и проверяемая как целое, с единственной точкой входа — корнем. Границу определяют инварианты: что обязано быть согласованным немедленно, входит внутрь, остальное связывается по идентификатору и согласуется через события. Правило — одна транзакция меняет один агрегат.
  5. Чем сущность отличается от объекта-значения?Сущность имеет идентичность и живёт во времени: два заказа с одинаковыми полями — разные заказы. Объект-значение определяется значением и взаимозаменяем: две суммы по 100 ₽ неразличимы. Отсюда следствия: сущность изменяема и сравнивается по идентификатору, объект-значение неизменяем и сравнивается по содержимому.
  6. Зачем нужны доменные события?Чтобы развязать «что произошло» и «что должно случиться в ответ». Агрегат фиксирует факт, а подписчики реагируют: письмо, обновление отчёта, синхронизация с внешней системой. Без событий эти реакции накапливаются в сервисе, который начинает знать про всю систему. Цена — поток управления становится менее явным, поэтому события не стоит применять там, где хватает прямого вызова.
  7. Что такое доменный сервис?Место для правила, которое не принадлежит ни одной сущности: например, перевод средств между счетами затрагивает два агрегата. Важно не превращать его в свалку: если поведение можно выразить внутри сущности, оно должно жить там, иначе модель снова становится анемичной.
  8. Что даёт гексагональная архитектура и в чём цена?Направление зависимостей внутрь: домен не знает про фреймворк, базу и HTTP, поэтому правила тестируются мгновенно и переживают смену инфраструктуры, а один сценарий вызывается из HTTP, консоли и очереди. Цена — больше файлов, преобразования между слоями и более высокий порог входа. Поэтому применяют её к сложным модулям, а не ко всему проекту.
  9. Как не дать архитектурным границам размыться?Автоматической проверкой в CI: домену запрещено импортировать инфраструктуру, модулю — лезть во внутренности соседа, циклы запрещены. Договорённость без автоматики живёт до первого дедлайна: кто-то подключит ORM-сущность в домене, ревью пропустит, и через полгода границы не будет.
  10. Зачем разделять модели чтения и записи?У них разные требования: записи нужен небольшой агрегат с инвариантами, чтению — плоские данные под конкретный экран, часто из нескольких таблиц. Загрузка агрегатов ради списка даёт N+1 и лишнюю работу. Разделение делается дёшево в одной базе: команды через домен, запросы отдельными классами.
  11. Когда нужен полноценный CQRS с отдельным хранилищем?Когда чтение измеримо упёрлось и разделения моделей внутри одной базы не хватает. Это отдельное хранилище, синхронизация через события, лаг и расхождения — то есть новый класс инцидентов. Начинать всегда стоит с лёгкого варианта: он даёт большую часть пользы почти без сложности.
  12. Что такое рефакторинг и чем он не является?Изменение структуры без изменения поведения. Как только вы попутно чините баг или добавляете функцию — это уже не рефакторинг, и при поломке будет непонятно, что виновато. Отсюда практика: рефакторинг отдельным коммитом и отдельным pull request, при зелёных тестах.
  13. Как рефакторить большой метод?Сначала зафиксировать поведение тестами, при их отсутствии — характеризующими на реальных данных. Затем маленькими шагами: выделить метод, не меняя содержимое; заменить примитивы типами; вынести в класс с явными зависимостями. Каждый шаг — коммит с зелёными тестами. Абстракция вводится последней, при появлении второго варианта.
  14. Что делать, если код невозможно протестировать?Это сигнал о дизайне, а не о тестах. Признаки: зависимости создаются внутри, статические вызовы, обращение ко времени и случайности изнутри, вычисления вперемешку с записью в базу. Лечение — вынести зависимости в конструктор, отделить вычисление от побочного эффекта, при необходимости сделать шов с параметрами по умолчанию.
  15. Когда паттерн приносит вред?Когда введён до появления проблемы. Фабрика для простого конструктора, интерфейс «на будущее», шина сообщений вместо прямого вызова — всё это добавляет файлы и прыжки при чтении, не решая ничего. Паттерн — ответ на проявившуюся боль: третье повторение, растущий switch, невозможность протестировать.
  16. Как заменить разросшиеся условия по статусу?Собрать переходы в одно место: таблица допустимых переходов в перечислении и единственная проверка в сущности. Тогда правила читаются как документация, а добавление статуса — правка в одном месте. Полноценный паттерн «состояние» с классом на каждое состояние нужен реже — когда у состояний много собственного поведения.
  17. Что такое спецификация и когда она оправдана?Правило отбора как объект, применимый и к загруженному объекту, и к запросу в базу. Она решает проблему, когда одно условие описано дважды — в PHP и в SQL — и эти описания расходятся. Оправдана, когда правил много и они комбинируются; для двух-трёх условий проще именованный метод репозитория.
  18. Как правильно работать с ORM-сущностями?Не выпускать их за пределы инфраструктуры и не отдавать наружу как контракт API. Иначе переименование колонки ломает клиентов, ленивая загрузка приводит к N+1 при сериализации, а внутренние поля публикуются без ревью. Наружу отдаётся DTO, а домен в строгих модулях работает со своей моделью.
  19. Что такое единица работы и нужна ли она?Механизм, накапливающий изменения и сохраняющий их одной транзакцией. В PHP-проектах она обычно уже есть в ORM, поэтому писать свою почти никогда не нужно. Понимать её полезно по другой причине: она объясняет, почему изменения сущности сохраняются «сами» и почему важно контролировать границы транзакции в сервисе приложения.
  20. Как выбрать между событиями и прямым вызовом?Прямой вызов, когда результат нужен здесь и сейчас и отправитель обязан знать об исходе. События — когда реакций несколько, они не влияют на основной сценарий и могут выполняться позже. Цена событий — неявный поток управления и сложность отладки, поэтому вводить их стоит с третьего «после этого нужно ещё...», а не сразу.

Нарезка по техническим слоям выглядит аккуратно, но размазывает каждую функцию по трём каталогам, поэтому я режу по бизнес-возможностям, а слои держу внутри модуля. Модуль перестаёт быть единицей понимания: чтобы разобраться в тарификации, нужно обойти всю структуру. При нарезке по возможностям изменение остаётся внутри одного каталога.
  3. Что делать, если два модуля зависят друг от друга?Считать это сигналом об ошибке в границах. Обычно либо это на самом деле один модуль, разрезанный пополам, либо часть общего нужно вынести в третий модуль, либо связь должна стать односторонней через событие. Циклическая зависимость означает, что модули нельзя ни понять, ни изменить по отдельности.

У него должен быть владелец и осознанное правило, что изменение затрагивает всех потребителей. Без этого он быстро становится модулем, который никто не решается менять.
  5. Что такое технический долг и всегда ли он плох?Осознанный компромисс: сделали быстрее и хуже ради ценности сейчас, зная, что заплатим замедлением потом. Разумный осознанный долг — нормальный инженерный инструмент. Плох долг неосознанный и неучтённый: он не виден, не оценён и растёт быстрее, чем выплачивается.
  6. Как вести учёт технического долга?Записями в бэклоге с двумя оценками: стоимость исправления и стоимость бездействия (сколько времени и рисков он съедает в месяц). В коде — комментарий с причиной, риском и ссылкой на задачу, а не безымянное «TODO». Тогда долг обсуждается как обычная работа с приоритетом, а не как просьба «дать время на порядок».

И предлагать не отдельный спринт, а привязку к ближайшей задаче в том же модуле — так согласовывается заметно легче.
  8. Какие есть стратегии выплаты долга?Правило бойскаута — трогаешь файл, оставь чуть лучше, не расширяя объём задачи. Фиксированная доля времени спринта, оформленная договорённостью, а не по остаточному принципу. Целевая выплата, когда долг мешает конкретной задаче — тогда рефакторинг становится её частью. Большие «спринты рефакторинга» без функциональной цели обычно съедаются срочными делами.

Это видно по истории репозитория и трекеру. Затем в самой болезненной точке — характеризующие тесты, выделение границ, антикоррупционный слой для нового кода. Улучшения привязываю к функциональным задачам.

Он не даёт чужим решениям — странным статусам, форматам, структурам — расползтись по новому коду. Когда легаси уходит, меняется одна реализация, а не вся система.

Плюс в старом коде зашиты годы неочевидных правил и исключений, которые обнаруживаются только в проде. Рабочая альтернатива — постепенное замещение по одной функции с возможностью вернуть трафик обратно.

Проверка — попросить коллегу проследить путь запроса: дольше пятнадцати минут означает неоправданную сложность.

Практика: первое повторение копируем, второе — присматриваемся, третье — обобщаем, уже понимая настоящую ось изменчивости.

Единообразие ценно, но платить многословием там, где нет правил, не окупается. Важно только не смешивать подходы внутри одного модуля.

Команды, нарезанные по слоям, дают систему, где каждая функция требует согласования трёх команд. Команды по бизнес-возможностям естественно приводят к модулям с контрактами. Практический вывод: архитектурное решение против устройства команды не приживётся, и менять приходится обе стороны.
  16. Что реально удерживает архитектуру от размывания?Три вещи: автоматические проверки правил в CI, короткие записи решений с отвергнутыми вариантами и явно назначенные владельцы модулей. Диаграммы и документы на сорок страниц не работают: код расходится с ними за месяцы, и никто этого не замечает. Работает то, что ломает сборку или всплывает на ревью.
  17. Как вы внедряете архитектурные решения в команде?Сначала объясняю проблему, а не решение: пока боль не почувствовали, правило воспринимается как бюрократия. Затем показываю на одном реальном модуле. Фиксирую письменно с контекстом и отвергнутыми вариантами. И встраиваю в процесс — проверка в CI и пункт в чек-листе ревью. Без последнего шага договорённость держится до первого срочного релиза.
  18. Как оценить архитектуру незнакомого проекта за час?Взять типовую задачу и проследить, что придётся изменить: один модуль и новый класс — хорошо, правки в пяти местах — граница не там. Посмотреть, зависит ли домен от фреймворка. Посчитать, сколько файлов нужно открыть для понимания одного сценария. И заглянуть в историю: какие файлы меняются чаще всего — там и болит.
  19. Что делать, если команда спорит о подходе на каждом ревью?Спор в комментариях — симптом отсутствия договорённости. Нужно вынести решение из ревью: обсудить один раз голосом, зафиксировать короткой записью с аргументами и отвергнутыми вариантами, где возможно — закрепить автоматикой. Тогда ревью обсуждает конкретный код, а не заново тот же принцип.
  20. Какой архитектурой вы гордитесь и что бы сделали иначе?Вопрос проверяет рефлексию. Сильный ответ содержит конкретное решение с числами (что изменилось в скорости работы или в числе инцидентов) и честное «сделал бы иначе»: обычно это про преждевременные абстракции, слишком крупные агрегаты или строгую схему там, где хватило бы простого CRUD. Ответ без второй части выглядит слабее.

Неделя 4 · Границы, долг, простота

Архитектура

Темы

Нарезка модулей и правила связей, циклы и общий модуль, виды технического долга и стратегии выплаты, легаси и антикоррупционный слой, постепенное замещение, цена абстракции и признаки переусложнения, закон Конвея.

Практика

  • Задания 12–15: карта модулей, реестр технического долга, антикоррупционный слой, ревизия сложности.
  • Сопоставить границы модулей с тем, что меняется вместе по истории репозитория.
  • Проговорить вслух 20 senior-вопросов с таймером: 60–90 секунд, обязательно с ценой решения и с тем, от чего отказались.

Результат недели

Карта модулей с проблемными связями, реестр долга с оценками, работающий слой изоляции от легаси и три удалённые бесполезные абстракции.

Контрольные вопросы

  1. Как решить, где провести границу модуля?
  2. Что делать с циклическими зависимостями между модулями?
  3. Как вести учёт технического долга и аргументировать рефакторинг?
  4. Что такое антикоррупционный слой?
  5. Почему переписывание с нуля обычно плохая идея?
  6. Как понять, что архитектура переусложнена?
  7. Почему дублирование бывает лучше абстракции?
  8. Что удерживает архитектуру от размывания?

Как отвечать на вопросы по архитектуре

Бонус
  • Всегда называйте цену. «Применили порты и адаптеры» — половина ответа. «Применили в биллинге, домен тестируется без базы; заплатили многословием и преобразованиями между слоями; в каталоге не стали — там CRUD» — полный.
  • Говорите об отказах. Сильнее всего звучит ответ, где есть «не стали»: не завели интерфейс, не выделили слой, не стали обобщать до третьего случая. Это отличает человека, который платил за сложность, от того, кто её только добавлял.
  • Приводите пример из своего кода. На вопрос про SOLID выигрышнее всего рассказать про конкретный класс: что смешивалось, чем мешало, что изменилось после разделения.
  • Не путайте уровни. Вопросы про модули, агрегаты и слои — про архитектуру кода; вопросы про сервисы, очереди и базы — про системный дизайн. Полезно уточнить, о каком уровне речь, если формулировка расплывчата.
  • Признавайте контекст. «Для команды из трёх человек и CRUD-проекта я бы не стал вводить строгую структуру» — сильный ответ. Универсальные рецепты без условий выдают отсутствие опыта.
  • Держите наготове историю рефакторинга. Что болело, как измерили, какими шагами шли, что стало. Это отвечает сразу на вопросы про паттерны, тесты, работу с легаси и взаимодействие с бизнесом.
  • Приносите артефакты. Карта модулей, реестр долга с оценками, конфигурация проверки границ, история коммитов пошагового рефакторинга.
