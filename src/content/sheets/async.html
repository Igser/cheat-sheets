Асинхронный PHP и реальное время

Классический PHP устроен предельно просто: процесс рождается на запрос, выполняет код и умирает, ничего после себя не оставляя. Эта модель — причина того, что на PHP легко писать и почти невозможно случайно уронить приложение утечкой памяти: любую грязь убирает смерть процесса. Она же — причина всех ограничений, о которых эта тема: нельзя держать соединение, нельзя ничего накопить между запросами, нельзя делать два дела одновременно.

Выйти за эти рамки можно тремя разными способами, и их постоянно путают. Вынести работу в фоновую задачу — это про то, чтобы пользователь не ждал. Поднять долгоживущий процесс на RoadRunner или Swoole — это про то, чтобы не платить за загрузку фреймворка на каждом запросе. Использовать корутины и конкурентный ввод-вывод — это про то, чтобы ждать несколько внешних сервисов одновременно, а не по очереди. Задачи разные, и решения между собой не заменяются.

Конспект идёт от модели выполнения к эксплуатации: shared-nothing и её цена, фоновые задачи и воркеры, способы доставить данные в браузер → долгоживущие процессы и утечки состояния, Fibers, конкурентные запросы, WebSocket на практике → выбор подхода, масштабирование соединений, надёжность и эксплуатация. Смежные темы: брокеры сообщений, производительность, инфраструктура, HTTP и API, PHP.

Уровень 01 · модель выполнения

Junior: как PHP выполняет запрос и что из этого следует

Почти все особенности темы вытекают из одного факта: обычный процесс PHP живёт ровно один запрос. Понимание этой модели — что она даёт, чего лишает и какими способами её обходят — важнее знания названий конкретных инструментов.

junior / модель

Модель выполнения PHP

База

При каждом запросе PHP-FPM берёт свободный процесс, тот подключает файлы, поднимает контейнер зависимостей, выполняет код, отдаёт ответ и полностью очищает память. Следующий запрос начинается с чистого листа и, скорее всего, попадёт в другой процесс. Такая модель называется shared-nothing — процессы ничего не разделяют между собой.

ВажноПростота этой модели — не недостаток, а причина, по которой на PHP можно писать быстро и относительно безопасно. Утечка памяти, циклическая ссылка, забытый ресурс, глобальная переменная — в обычном запросе всё это не имеет последствий, потому что процесс умрёт через сто миллисекунд. Как только вы переходите к долгоживущим процессам, эта страховка исчезает, и код, который годами работал, может начать съедать память.
Типичный вопрос на собеседованииПочему PHP считают синхронным языком?
Дело не в языке, а в типичной модели запуска: FPM даёт один процесс на один запрос, код выполняется последовательно сверху вниз, а любое ожидание — базы, файла, внешнего API — блокирует процесс целиком. Сам язык давно умеет и генераторы, и файберы, и неблокирующий ввод-вывод; ограничение создаёт окружение. При запуске под RoadRunner или Swoole модель меняется, и тот же код начинает жить по другим правилам.

Три способа уйти от синхронности

Карта

Три подхода решают три разные задачи, и путаница между ними — самая частая ошибка в разговорах на эту тему. Прежде чем выбирать инструмент, стоит понять, какая из трёх проблем у вас на самом деле.

Практический пример на всех трёх. Страница оформления заказа: сохраняет заказ, проверяет промокод во внешнем сервисе, запрашивает три варианта доставки у трёх служб, отправляет письмо и обновляет поисковый индекс. Письмо и индекс — фоновая обработка. Три запроса к службам доставки — конкурентный ввод-вывод: 600 мс превращаются в 200. Загрузка фреймворка на каждый такой запрос — долгоживущий процесс. Три инструмента, три разных выигрыша, и ни один не заменяет другой.

junior / фон

Фоновые задачи и воркеры

Практика

Фоновая задача — это работа, которая выполняется после того, как пользователь получил ответ. Запрос кладёт задание в очередь, отдельный процесс-воркер его забирает и выполняет. Воркер здесь — обычная консольная команда PHP, запущенная в цикле и живущая долго.

PHPДолгоживущий воркер: обязательные детали
// консольная команда, которая живёт часами — уже не обычный скрипт
final class WorkerCommand
{
    private bool $shouldStop = false;

    public function run(): int
    {
        // 1. Мягкая остановка: дорабатываем задачу и выходим,
        //    а не умираем посреди обработки
        pcntl_async_signals(true);
        pcntl_signal(SIGTERM, fn() => $this->shouldStop = true);
        pcntl_signal(SIGINT,  fn() => $this->shouldStop = true);

        $processed = 0;

        while (!$this->shouldStop) {
            $job = $this->queue->pop(timeout: 5);
            if ($job === null) {
                continue;
            }

            try {
                $this->handler->handle($job);
                $this->queue->ack($job);
            } catch (\Throwable $e) {
                $this->logger->error('job.failed', ['id' => $job->id, 'e' => $e]);
                $this->queue->retryOrBury($job);
            } finally {
                // 2. Чистим состояние: иначе ORM накопит все сущности
                $this->entityManager->clear();
            }

            // 3. Плановый перезапуск: страховка от медленных утечек
            if (++$processed >= 500
                || memory_get_usage(true) > 200 * 1024 * 1024) {
                break;   // supervisor поднимет новый процесс
            }
        }

        return 0;
    }
}

Три вещи, без которых воркер рано или поздно ломается: обработка сигнала остановки, очистка состояния между задачами и плановый перезапуск по счётчику или памяти. Первое нужно для деплоя без потерь, второе — против роста памяти, третье — страховка от утечек, которые вы не нашли.

ВажноВоркер должен быть под присмотром процесса-надзирателя — supervisor, systemd или планировщик контейнеров. Он перезапускает упавшие процессы, держит нужное количество и корректно останавливает при деплое. Воркер, запущенный вручную через nohup, обязательно умрёт в пятницу вечером, и никто об этом не узнает до понедельника.
АнтипаттернОбработка задачи, не рассчитанная на повтор. Воркер может упасть между выполнением работы и подтверждением задачи, и она придёт снова. Если обработчик отправляет письмо и не проверяет, отправлял ли уже, пользователь получит два письма. Любая фоновая задача должна быть идемпотентной — по ключу, по признаку в базе или по проверке состояния.

Как данные попадают в браузер

Транспорт

Если данные появились на сервере — завершилась фоновая задача, пришло новое сообщение, изменился статус заказа, — их нужно как-то доставить в открытую вкладку. Способов четыре, и выбор между ними определяется не модой, а требованиями к задержке и направлению обмена.

Начинать почти всегда стоит с опроса. Он не требует ни отдельного сервера, ни изменений в инфраструктуре, ни новых знаний, а для большинства задач задержка в две секунды абсолютно приемлема. WebSocket добавляет постоянные соединения, отдельный процесс, аутентификацию, переподключения и масштабирование — это оправдано, когда задача действительно требует двустороннего обмена, а не когда «хочется по-современному».

Типичный вопрос на собеседованииЧем SSE отличается от WebSocket и когда чего достаточно?
SSE — это обычный HTTP-ответ, который сервер не закрывает и дописывает в него события. Он однонаправленный (только сервер к клиенту), работает через привычные прокси и балансировщики, автоматически переподключается силами браузера и умеет продолжать с последнего идентификатора события. WebSocket — отдельный протокол после апгрейда соединения, двусторонний, но требует своей инфраструктуры и ручной обработки переподключений. Если клиент только получает данные — уведомления, лента, прогресс — достаточно SSE, и это заметно дешевле в эксплуатации.

Уровень 02 · инструменты

Уровень, на котором приходится разбираться, что именно меняется в приложении при переходе на долгоживущий процесс, где в старом коде спрятано состояние, и как поднять реальное время так, чтобы это пережило второй сервер и деплой.

middle / рантаймы

Долгоживущие процессы

Рантайм

Идея всех этих инструментов одна: загрузить приложение один раз, а дальше в цикле принимать запросы и отдавать ответы, не пересоздавая контейнер, конфигурацию, маршруты и соединения. Экономия — это то, что в профиле обычно называется «время до вашего кода».

Утечки состояния

Главный риск

Это самая опасная часть темы, потому что ошибки здесь не падают, а тихо портят данные. Код, который годами работал под FPM, под воркером может начать отдавать одному пользователю данные другого — и обнаружится это не в тестах, а по жалобе.

middle / файберы

Fibers и корутины

Механика

Fibers появились в PHP 8.1 и дают возможность приостановить выполнение функции в произвольном месте и вернуться к нему позже. Сами по себе они ничего не ускоряют: это низкоуровневый механизм, на котором асинхронные библиотеки строят планировщик задач.

Отличие от генераторов в том, что генератор может приостановиться только в собственном теле, и всю цепочку вызовов приходится делать генераторами. Fiber приостанавливает весь стек вызовов из любой глубины, поэтому обычный синхронный на вид код может внутри уступать управление.

PHPFiber: приостановка и возобновление
$fiber = new \Fiber(function (string $url): string {
    $request = startRequest($url);        // отправили, не ждём

    // отдаём управление планировщику: он займётся другими задачами
    $response = \Fiber::suspend($request);

    return 'получено: ' . $response;      // продолжили с того же места
});

$pending = $fiber->start('https://api.example.com/rates');
// здесь планировщик может запустить другие файберы

$fiber->resume(awaitResult($pending));
$result = $fiber->getReturn();

// В реальном коде Fiber напрямую не пишут: этим занимаются
// библиотеки (AMPHP, ReactPHP) и рантаймы. Знать нужно принцип:
// «ожидание уступает управление, а не блокирует процесс».

Генератор приостанавливается только в собственном теле: чтобы уступить управление из глубины вызовов, всю цепочку нужно превратить в генераторы и вручную пробрасывать значения. Практически это означает, что асинхронность перестаёт «протекать» через сигнатуры всех промежуточных методов.

middle / конкурентность

Конкурентные запросы

Выигрыш

Самый практичный вид асинхронности и единственный, который можно применить в обычном приложении под FPM без смены рантайма: несколько независимых внешних вызовов выполняются одновременно, и общее время равно самому долгому, а не сумме.

// ПЛОХО: три службы доставки по очереди = 600 мс
$cdek  = $this->http->request('GET', $cdekUrl)->toArray();

$boxb  = $this->http->request('GET', $boxUrl)->toArray();

// ХОРОШО: отправляем все три, потом собираем = ~200 мс
$responses = [];
foreach ($providers as $name => $url) {
    // request() не блокирует: запрос уходит, ответ не читается
    $responses[$name] = $this->http->request('GET', $url, [
        'timeout' => 2.0,
    ]);
}

$rates = [];
foreach ($this->http->stream($responses) as $response => $chunk) {
    if (!$chunk->isLast()) {
        continue;
    }
    try {
        $rates[] = $response->toArray();

    }
}

Аутентификация в реальном времени устроена иначе, чем в HTTP. Соединение устанавливается один раз и живёт часами, поэтому проверять права на каждое сообщение негде. Стандартная схема: приложение выдаёт клиенту короткоживущий токен с указанием, кто он и к каким каналам допущен; клиент предъявляет токен серверу реального времени при подключении; при истечении токен обновляется без разрыва соединения.

middle / sse

SSE и долгие операции

Простой путь

SSE решает большую часть задач реального времени, оставаясь обычным HTTP. Браузерный клиент состоит из трёх строк, переподключение выполняется автоматически, а сервер может продолжить с того места, где клиент оборвался, — по заголовку с последним полученным идентификатором.

PHP + JSПоток событий и его приём
// Сервер: поток событий. Под FPM занимает процесс целиком —
// поэтому для SSE нужен отдельный пул или отдельный рантайм.
public function stream(Request $request): StreamedResponse
{
    $lastId = (int) $request->headers->get('Last-Event-ID', '0');

    return new StreamedResponse(function () use ($lastId) {
        $deadline = time() + 60;   // живём минуту и просим переподключиться

        while (time() < $deadline) {
            foreach ($this->events->since($lastId) as $event) {
                $lastId = $event->id;
                // id позволяет клиенту продолжить после обрыва
                printf("id: %d\nevent: %s\ndata: %s\n\n",
                    $event->id, $event->type, json_encode($event->payload));
            }
            flush();
            sleep(1);
        }
    }, 200, [
        'Content-Type'      => 'text/event-stream',
        'Cache-Control'     => 'no-cache',
        // критично: иначе прокси будет копить ответ в буфере
        'X-Accel-Buffering' => 'no',
    ]);
}

Архитектура

JSПравильный клиент реального времени
// три обязательные части: переподключение с ростом задержки,
// отбрасывание устаревших событий по версии,
// полная перезагрузка состояния после длинного разрыва

let attempt = 0, lastVersion = 0, lastEventAt = Date.now();

function connect() {
  const socket = new WebSocket(url);

  socket.onopen = () => {
    // разрыв дольше окна истории — состоянию нельзя доверять
    if (Date.now() - lastEventAt > 60_000) {
      reloadFullState();
    }
    attempt = 0;
  };

  socket.onmessage = (e) => {
    const msg = JSON.parse(e.data);
    lastEventAt = Date.now();

    // порядок не гарантирован — сравниваем версии
    if (msg.version <= lastVersion) return;
    lastVersion = msg.version;

    apply(msg);
  };

  socket.onclose = () => {
    // нарастающая задержка + случайный разброс:
    // иначе после перезапуска сервера все придут одновременно
    const delay = Math.min(30_000, 1000 * 2 ** attempt++)
                + Math.random() * 1000;
    setTimeout(connect, delay);
  };
}
ВажноГлавный принцип: событие — это уведомление об изменении, а не источник истины. Интерфейс, который строит состояние исключительно из потока событий, обязательно рассинхронизируется, и пользователь не узнает об этом. Правильная схема — событие говорит «изменилось, версия N», а состояние всегда можно получить обычным запросом, и оно получается при первом открытии, при возвращении фокуса и после долгого разрыва.

senior / эксплуатация

Эксплуатация воркеров

Прод

Долгоживущие процессы меняют не только код, но и процедуру выката. Под FPM новый код начинает работать со следующего запроса; воркер продолжит выполнять старый до тех пор, пока его не перезапустят.

Мягкая перезагрузка — обязательный механизм. При выкате новые задачи перестают выдаваться старым процессам, те дорабатывают текущую и завершаются, а поднятые процессы уже с новым кодом принимают работу. Без этого выкат либо обрывает задачи посередине, либо оставляет часть воркеров на старом коде — а это самый неприятный класс инцидентов, потому что поведение системы становится зависящим от того, какой процесс взял задачу.

final class SendOrderEmailHandler
{
    public function __invoke(SendOrderEmail $message): void
    {
        // 1. Ключ идемпотентности из смысла операции,
        //    а не из идентификатора сообщения
        $key = sprintf('email:order:%d:%s', $message->orderId, $message->type);

        // 2. Атомарная отметка: занял — работаю, не занял — уже сделано
        if (!$this->redis->set($key, '1', ['NX', 'EX' => 86400])) {
            $this->logger->info('email.skipped_duplicate', ['key' => $key]);
            return;
        }

        try {
            $order = $this->orders->find($message->orderId);
            // 3. Проверка актуальности: состояние могло измениться
            if ($order === null || $order->isCancelled()) {
                return;
            }

            $this->mailer->send($this->build($order));
        } catch (\Throwable $e) {
            // 4. Не отправили — снимаем отметку, чтобы повтор сработал
            $this->redis->del($key);
            throw $e;
        }
    }
}
ВажноКлюч идемпотентности строится из смысла операции, а не из идентификатора сообщения. Если брокер переотправит то же самое сообщение, идентификатор совпадёт и защита сработает; но если задачу поставят повторно из другого места кода, идентификатор будет новым, а письмо уйдёт вторым. Ключ вида «письмо такого-то типа по такому-то заказу» защищает в обоих случаях.

Junior · 20 вопросов

База
  1. Что происходит при обычном запросе к PHP-приложению?FPM берёт свободный процесс, тот подключает файлы, поднимает контейнер и конфигурацию, выполняет код, отдаёт ответ и полностью очищает память. Следующий запрос начинается с чистого листа и, скорее всего, попадёт в другой процесс.
  2. Что такое shared-nothing?Модель, при которой процессы ничего не разделяют между собой: у каждого своя память, своё состояние и своя жизнь длиной в один запрос. Отсюда и простота PHP, и все его ограничения в этой теме.
  3. Какие плюсы у модели «процесс умирает после запроса»?Утечки памяти и забытые ресурсы не имеют последствий, ошибка в одном запросе не влияет на другие, состояние не может утечь между пользователями, код всегда актуален сразу после выката. Это делает PHP языком, на котором трудно случайно устроить катастрофу.
  4. Какие минусы у этой модели?Ничего нельзя накопить между запросами, поэтому нужен внешний кэш; фреймворк загружается заново на каждый запрос; нельзя держать открытое соединение с клиентом; одновременных запросов ровно столько, сколько процессов; долгая работа задерживает пользователя.
  5. Правда ли, что PHP синхронный язык?Ограничение создаёт не язык, а типичное окружение: один процесс на запрос и блокирующие вызовы. Сам язык умеет генераторы, файберы и неблокирующий ввод-вывод, а под другими рантаймами модель выполнения меняется.
  6. Какие три подхода существуют для ухода от синхронности?Фоновая обработка — чтобы пользователь не ждал; долгоживущий процесс — чтобы не платить за загрузку фреймворка; конкурентный ввод-вывод — чтобы ждать несколько внешних сервисов одновременно. Задачи разные, и подходы не заменяют друг друга.
  7. Что такое фоновая задача?Работа, выполняемая после того, как пользователь получил ответ: запрос кладёт задание в очередь, отдельный процесс-воркер его забирает и выполняет. Так выносят письма, генерацию документов, индексацию, аналитику и уведомления.
  8. Что такое воркер?Обычная консольная команда PHP, запущенная в цикле и живущая часами: она берёт задачу из очереди, обрабатывает, подтверждает и берёт следующую. От обычного скрипта отличается тем, что должна корректно останавливаться, чистить состояние и планово перезапускаться.
  9. Зачем воркеру обработка сигнала остановки?Чтобы при деплое или перезапуске он дорабатывал текущую задачу и завершался, а не умирал посреди обработки. Без этого часть задач будет прерываться на середине, и последствия зависят от того, что успело выполниться.
  10. Зачем воркер перезапускают по счётчику задач или по памяти?Это страховка от утечек, которые не нашли: процесс живёт долго, и любое накопление превращается в рост памяти. Плановый перезапуск ограничивает ущерб, но не заменяет поиск причины и совершенно не помогает от утечки данных между запросами.
  11. Почему фоновая задача должна быть идемпотентной?Потому что воркер может упасть между выполнением работы и подтверждением задачи, и она придёт снова. Гарантия брокеров — «хотя бы один раз». Без защиты это означает два письма, два списания, две отгрузки.
  12. Зачем воркерам нужен процесс-надзиратель?Он перезапускает упавшие процессы, держит нужное количество, корректно останавливает их при деплое и пишет логи. Воркер, запущенный вручную в фоне, однажды умрёт, и об этом никто не узнает, пока не начнут жаловаться пользователи.
  13. В чём разница между cron и очередью?Cron запускает работу по расписанию с шагом в минуту и не знает о конкретных заданиях; очередь обрабатывает задачи по мере поступления почти мгновенно и умеет повторы, приоритеты и задержки. Cron уместен для регулярной работы, очередь — для реакции на события.
  14. Какие есть способы доставить данные в браузер?Периодический опрос, долгий опрос, SSE и WebSocket. Они различаются задержкой, направлением обмена и стоимостью внедрения — от нулевой у опроса до высокой у WebSocket.
  15. Что такое SSE?Поток событий поверх обычного HTTP: сервер не закрывает ответ и дописывает в него события. Однонаправленный, работает через привычную инфраструктуру, переподключается автоматически силами браузера и умеет продолжать с последнего идентификатора события.
  16. Чем WebSocket отличается от SSE?WebSocket — отдельный протокол после апгрейда соединения, обмен идёт в обе стороны, но требует своей инфраструктуры, настройки прокси и ручной обработки переподключений. SSE проще во всём, но данные идут только от сервера к клиенту.
  17. Когда достаточно обычного опроса?Когда задержка в несколько секунд приемлема и открытых вкладок не слишком много: статус фоновой задачи, счётчик уведомлений, прогресс генерации отчёта. Опрос не требует ни нового компонента, ни новых знаний и переживает перезагрузку страницы.
  18. Почему для показа прогресса не нужен WebSocket?Потому что данные идут в одну сторону, задержка в секунду незаметна, а состояние задачи всё равно хранится на сервере и доступно обычным запросом. Опрос простого эндпоинта решает задачу без единого нового компонента в инфраструктуре.
  19. Что такое долгий опрос?Запрос, который сервер не отвечает сразу, а держит до появления события или до таймаута. Даёт почти мгновенную доставку без нового протокола, но занимает процесс PHP на всё время ожидания — поэтому требует отдельного пула.
  20. С чего начинать, если нужны «уведомления в реальном времени»?С уточнения требований: какая задержка недопустима, сколько одновременных вкладок ожидается, нужен ли обмен в обе стороны и что произойдёт при потере события. Чаще всего выясняется, что достаточно опроса раз в несколько секунд.

Middle · 20 вопросов

Инструменты
  1. За счёт чего экономят долгоживущие процессы?Приложение загружается один раз при старте, а дальше воркер в цикле принимает запросы, не пересоздавая контейнер, конфигурацию и маршруты. Экономия равна времени загрузки — обычно от 20 до 80 мс на запрос.
  2. Когда эта экономия незаметна?Когда время ответа определяется не загрузкой, а ожиданием базы или внешних сервисов. Для страницы, отвечающей за 400 мс с 380 мс в базе, переход даст улучшение на проценты. Для лёгкого API на 40 мс, из которых 25 — загрузка, выигрыш кратный.
  3. Чем различаются RoadRunner, Swoole и FrankenPHP?RoadRunner — сервер на Go с воркерами на PHP, ставится бинарником, расширение не нужно. Swoole — расширение PHP с корутинами и собственной моделью, самый высокий порог входа и наибольшая переделка кода. FrankenPHP — сервер на базе Caddy с долгоживущими воркерами, простой в установке. Все три требуют аудита кода на состояние.
  4. Какая главная опасность при переходе на воркеры?Утечка состояния между запросами. Статическое свойство, хранившее текущего пользователя, под FPM безобидно, а в воркере вернёт пользователя предыдущего запроса. Такие ошибки не падают, а тихо отдают одному пользователю данные другого.
  5. Где искать состояние в существующем коде?Статические свойства с данными, синглтоны с накоплением, глобальные вызовы вроде установки часового пояса и локали, прямое чтение суперглобальных массивов, кэш в свойствах сервисов, открытые дескрипторы и соединения, библиотеки с внутренним состоянием.
  6. Как обнаружить утечку состояния?Двумя разными проверками. Утечка памяти видна на графике памяти по числу обработанных запросов: линейный рост вместо пилы. Утечка данных ловится чередованием запросов от разных пользователей и сравнением ответа на первом и пятисотом запросе процесса.
  7. Почему плановый перезапуск не решает проблему?Он скрывает утечку памяти и ограничивает её ущерб, но от утечки данных между пользователями не помогает вовсе: она проявится на втором запросе, а не на пятисотом. Это страховка, а не лечение.
  8. Что такое Fiber?Механизм, позволяющий приостановить выполнение и вернуться к нему позже, приостановив при этом весь стек вызовов из любой точки. Сам по себе ничего не ускоряет: это низкоуровневая основа, на которой асинхронные библиотеки строят планировщик задач.
  9. Чем Fiber отличается от генератора?Генератор приостанавливается только в собственном теле, поэтому асинхронность приходится протаскивать через всю цепочку вызовов. Fiber приостанавливает весь стек, и промежуточные функции остаются обычными — код выглядит синхронным, читается сверху вниз.
  10. Что конкурентность на файберах не даёт?Параллельных вычислений: поток один, и пока считается тяжёлый цикл, все остальные задачи стоят. Не задействует несколько ядер. Не делает неблокирующим произвольный клиент — нужен клиент, умеющий уступать управление. Выигрыш только в совмещении ожиданий.
  11. Как ускорить страницу, которая ждёт четыре внешних сервиса?Отправить все четыре запроса, не читая ответы, а затем собрать результаты по мере готовности. Общее время станет равно самому долгому вызову вместо суммы. Обязательны таймаут на каждый вызов и деградация: один упавший провайдер не должен ронять страницу.
  12. Что обязательно при конкурентных внешних вызовах?Жёсткий таймаут на каждый — иначе весь выигрыш съедает один зависший сервис — и ограничение числа одновременных запросов, особенно если список формируется из данных. Плюс частичная деградация вместо ошибки при отказе одного участника.
  13. Почему WebSocket обычно выносят в отдельный сервер?Потому что десятки тысяч постоянных соединений — не та нагрузка, под которую устроено PHP-приложение: каждое соединение заняло бы процесс. Специализированный сервер держит соединения, а приложение остаётся обычным и только публикует события по HTTP или через брокер.
  14. Как устроена аутентификация в реальном времени?Приложение выдаёт короткоживущий токен с указанием пользователя и разрешённых каналов; клиент предъявляет его серверу реального времени при подключении; при истечении токен обновляется без разрыва. Проверять права на каждое сообщение негде — соединение живёт часами.
  15. Почему нельзя публиковать событие внутри транзакции?Потому что подписчик может получить уведомление и запросить данные до того, как транзакция зафиксирована, — или вообще после её отката. Публикация делается после коммита, а надёжнее — через outbox, чтобы событие не потерялось при сбое.
  16. Что класть в событие?Минимум: идентификатор объекта, тип изменения и версию. Полный объект отправлять не стоит — это утечка полей, лишний трафик и риск показать данные, на которые у подписчика нет прав. Детали клиент дозагружает обычным запросом с обычной проверкой доступа.
  17. Зачем в событии версия?Потому что порядок доставки не гарантирован, а переподключения приводят к повторам. Версия или метка времени позволяет клиенту отбросить событие, которое старше уже применённого состояния, — иначе устаревшие данные перезапишут свежие.
  18. Какие подводные камни у SSE в PHP?Буферизация на прокси и в самом PHP, из-за которой события приходят пачкой в конце; занятый на всё время соединения процесс FPM; обрыв по таймауту прокси; потеря событий при обрыве, если не отдавать идентификаторы; опрос базы в цикле каждым соединением.
  19. Как правильно организовать SSE-поток?Отдавать идентификатор каждому событию и обрабатывать заголовок с последним полученным идентификатором, отключить буферизацию, жить ограниченное время и просить клиента переподключиться, брать события из подписки на канал брокера, а не опросом базы, и вынести это на отдельный пул или рантайм.
  20. Что проще всего для показа прогресса долгой операции?Опрос раз в секунду обычного эндпоинта, который читает состояние задачи из Redis. Работает под FPM, не занимает процессы надолго, переживает перезагрузку страницы и не требует новых компонентов. SSE и WebSocket выигрывают, когда открытых вкладок становится много.

Решения
  1. Стоит ли переводить приложение на Swoole ради скорости?Сначала смотрим профиль: какую долю ответа занимает загрузка приложения. Если время уходит в базу, выигрыш будет в проценты ценой аудита всего кода, новой модели деплоя и риска утечек данных. Если речь о лёгком API с тяжёлой загрузкой — выигрыш реальный. Ответ начинается с чисел.
  2. Как обосновать отказ от WebSocket?Через требования: если данные идут только от сервера и задержка в несколько секунд приемлема, опрос решает задачу без нового компонента, без аутентификации соединений, без масштабирования и без обработки переподключений. Отказ обосновывается стоимостью эксплуатации, а не нелюбовью к технологии.
  3. Какой вопрос стоит задать перед внедрением любого из этих подходов?Сколько людей в команде смогут починить это в три часа ночи. Отдельный сервер событий, нестандартный рантайм и асинхронный код требуют навыков, которых может не быть. Если чинить умеет один человек, решение либо откладывают, либо выбирают вариант попроще.
  4. Что ломается в реальном времени при появлении второго сервера?События перестают доходить до всех: подписчики распределены по узлам, а публикация попадает на один. Нужна общая шина между узлами через Redis или брокер. Дополнительно появляются неравномерная нагрузка, лавины переподключений при перезапуске и вопрос, куда подключать нового клиента.
  5. Что такое схлопывание событий и зачем оно?Если объект меняется двадцать раз в секунду, отправляется не двадцать сообщений, а одно «изменилось, версия такая-то» с ограничением частоты, а состояние клиент дозагружает сам. Это снижает трафик, снимает вопрос порядка сообщений и делает систему устойчивой к всплескам.
  6. Как считать ресурсы под постоянные соединения?По числу соединений на узел, умноженному на размер буфера отправки, плюс лимиты на дескрипторы и порты. Пятьдесят тысяч соединений с буфером в 64 КБ — это больше трёх гигабайт только на буферы. Отдельно нужен предел на соединения с узла и отключение отстающих клиентов.
  7. Какие есть сценарии потери событий?Кратковременный обрыв сети, вкладка в спящем режиме, перезапуск сервера событий, недоставленная до шины публикация, доставка не по порядку и повторная доставка. Для каждого нужен свой механизм: история канала, полная перезагрузка состояния, outbox, версии и идемпотентная обработка.
  8. Сформулируйте главный принцип надёжного реального времени.Событие — это уведомление об изменении, а не источник истины. Интерфейс, строящий состояние исключительно из потока событий, обязательно рассинхронизируется и не узнает об этом. Состояние всегда доступно обычным запросом и перезагружается при первом открытии, при возвращении фокуса и после долгого разрыва.
  9. Как должен вести себя клиент при обрыве?Переподключаться с нарастающей задержкой и случайным разбросом — иначе после перезапуска сервера все придут одновременно и уронят его повторно. При разрыве дольше окна хранения истории — перезагружать состояние полностью, а не пытаться догнать события.
  10. Что меняется в эксплуатации при переходе на долгоживущие процессы?Выкат требует явной мягкой перезагрузки, остановка — сигнала и времени на дообработку, утечки памяти начинают иметь значение, ошибка может убить процесс вместе со всеми его соединениями, соединения к базе живут долго и рвутся по таймауту, а в наблюдаемость добавляются возраст процесса и память.
  11. Что такое мягкая перезагрузка и почему она обязательна?Новые задачи перестают выдаваться старым процессам, те дорабатывают текущую и завершаются, а поднятые процессы уже с новым кодом принимают работу. Без неё выкат либо обрывает задачи посередине, либо оставляет часть воркеров на старом коде — и поведение системы начинает зависеть от того, какой процесс взял задачу.
  12. На что ставить алерт: на длину очереди или на возраст задачи?На возраст самой старой необработанной задачи. Очередь из десяти тысяч задач, разгребаемая за минуту, — норма; очередь из пяти задач, старейшей из которых сорок минут, — сломанный воркер. Возраст напрямую соответствует тому, что чувствует пользователь.
  13. Как обеспечить деградацию реального времени?При недоступности сервера событий интерфейс переключается на периодический опрос, показывает данные, полученные обычным запросом, и не показывает ошибок. Проверяется учениями: сервер событий отключают в тестовой среде и смотрят, что происходит с интерфейсом.
  14. Как разделять воркеры по типам задач?По длительности и по важности: срочные короткие задачи не должны стоять за длинной выгрузкой. Разные очереди с разными пулами воркеров решают это без изменения кода. Отдельно полезно держать очередь для повторов, чтобы отказы не тормозили основной поток.
  15. Что делать с задачами, которые падают постоянно?Ограничивать число повторов с нарастающей задержкой и переводить в очередь отказов, а не повторять бесконечно. Очередь отказов должна быть под наблюдением: её рост означает системную проблему в обработчике, а не случайный сбой. Разбор и повторная отправка — отдельная процедура.
  16. Как перевести существующее приложение на долгоживущий рантайм?Поэтапно: сначала прогнать полный набор тестов под новым рантаймом, добавить тест на чередование запросов разных пользователей, затем вывести на небольшую долю продового трафика с отдельным мониторингом памяти, и только потом переводить всё. Утечки проявляются после сотен запросов на процессе, а не сразу.
  17. Почему тяжёлые вычисления нельзя класть в асинхронный цикл?Потому что они блокируют планировщик целиком: пока считается, ни одна другая корутина не получит управления, и все соединения на этом процессе замирают. Вычисления выносят в отдельные процессы, а асинхронность оставляют для совмещения ожиданий.
  18. Как связаны эта тема и очереди сообщений?Фоновая обработка целиком построена на брокере: от него зависят гарантии доставки, повторы, задержки, приоритеты и очередь отказов. Реальное время использует брокер как шину между узлами и как источник событий для потоков. Понимание семантики доставки и идемпотентности — общая основа для обеих тем.
  19. Как объяснить бизнесу отказ от реального времени?Через стоимость и риск: отдельный сервер, его эксплуатация, аутентификация соединений, обработка обрывов, новый класс инцидентов — против выигрыша в две секунды задержки уведомления. Если выигрыш не влияет на продуктовые показатели, разговор заканчивается быстро. Если влияет — обсуждают уже конкретную цену.
  20. Какой главный признак зрелого решения в этой теме?Названы задача, подход и цена. Инженер, который говорит «сделаем на WebSocket, это современно», и инженер, который говорит «нужен двусторонний обмен с задержкой ниже секунды, берём отдельный сервер, принимаем общую шину между узлами, восстановление после обрыва и деградацию на опрос при его недоступности», решают разные задачи.

Справочник · практика

15 практических заданий

Задания устроены так, чтобы столкнуть с реальными эффектами — утечкой состояния, лавиной переподключений, потерей событий — в безопасных условиях.

Junior · 5 заданий

Основы

1. Разложить сценарий на три подхода

Возьмите сценарий оформления заказа в своём проекте и распишите, что относится к фоновой обработке, что к конкурентному вводу-выводу и что выиграло бы от долгоживущего процесса. Оцените выигрыш каждого в миллисекундах.

РезультатПонимание, что три подхода решают разные задачи, и приоритет для внедрения.

2. Вынести операцию в фон

Найдите синхронную отправку письма или генерацию документа в запросе, вынесите в очередь и замерьте время ответа до и после.

РезультатПара чисел и первый работающий воркер.

3. Написать правильный воркер

Добавьте в воркер обработку сигнала остановки, очистку состояния между задачами и плановый перезапуск по счётчику и по памяти. Проверьте: отправьте сигнал во время обработки и убедитесь, что задача дорабатывается.

РезультатВоркер, который переживает деплой без потери задач.

4. Сломать идемпотентность и починить

Сделайте так, чтобы воркер падал после выполнения работы, но до подтверждения задачи. Посмотрите на дубли. Добавьте ключ идемпотентности и повторите.

РезультатЛичный опыт двойной отправки — после него об идемпотентности не забывают.

5. Прогресс через опрос

Сделайте показ прогресса долгой задачи: воркер пишет состояние в Redis, эндпоинт отдаёт его, клиент опрашивает раз в секунду. Проверьте, что перезагрузка страницы ничего не ломает.

РезультатРабочее решение задачи, ради которой часто зря поднимают WebSocket.

Инструменты

6. Запустить приложение под другим рантаймом

Поднимите приложение под RoadRunner или FrankenPHP на тестовой среде, прогоните тесты и замерьте время ответа лёгкого и тяжёлого эндпоинта. Сравните выигрыш на обоих.

РезультатСобственные числа вместо обещаний из документации — и понимание, где выигрыш реален.

7. Найти утечку состояния

Найдите в коде статическое свойство, хранящее данные запроса. Под воркером сделайте два последовательных запроса от разных пользователей и убедитесь, что второй видит данные первого. Исправьте.

РезультатВоспроизведённая утечка данных — самое убедительное доказательство необходимости аудита.

8. Тест на чередование пользователей

Напишите тест, который на одном процессе выполняет запросы от разных пользователей вперемешку и проверяет, что ответы не смешиваются. Добавьте его в конвейер.

РезультатАвтоматическая защита от самого опасного класса ошибок при работе с воркерами.

9. График памяти воркера

Прогоните тысячу задач на одном процессе, снимая память каждые сто задач. Постройте график. Если растёт линейно — найдите, что накапливается.

РезультатНавык отличать нормальную «пилу» от утечки и умение локализовать причину.

10. Конкурентные вызовы

Найдите место с несколькими независимыми внешними вызовами подряд, перепишите на одновременные с таймаутами. Замерьте до и после. Отключите один сервис и убедитесь, что страница работает частично.

РезультатКратное ускорение участка и проверенная деградация при отказе провайдера.

11. Поднять реальное время

Поднимите Centrifugo или Mercure, реализуйте токен подключения с ограничением каналов и публикацию события после коммита. Проверьте, что чужой канал недоступен.

РезультатРабочая схема с правами, а не демонстрация, где все подписаны на всё.

12. Устойчивый клиент

Реализуйте клиента с нарастающей задержкой и разбросом при переподключении, отбрасыванием устаревших событий по версии и полной перезагрузкой состояния после долгого разрыва. Проверьте, обрывая соединение вручную.

РезультатВозможность узнать о сломанном воркере раньше пользователей.

Результат недели

Что помогает на собеседовании

Бонус
  • Разделяйте три задачи. Первое, что стоит сделать в ответе, — уточнить, о чём речь: не заставлять пользователя ждать, не платить за загрузку фреймворка или совместить ожидания. Кандидат, который сразу говорит «возьмём Swoole», отвечает не на тот вопрос.
  • Начинайте с простого варианта. Умение сказать «здесь хватит опроса раз в две секунды» ценится выше умения поднять WebSocket. Это показывает, что вы считаете стоимость эксплуатации, а не только элегантность.
  • Помните про утечку данных, а не только памяти. Большинство говорит про рост памяти в воркерах. Упоминание того, что статическое свойство может отдать одному пользователю данные другого, сразу выделяет ответ.
  • Знайте, чего асинхронность не даёт. Корутины не ускоряют вычисления, не задействуют ядра и не делают неблокирующим произвольный клиент. Эти три факта отличают понимание от пересказа.
  • Говорите про обрывы. Любой разговор о реальном времени стоит доводить до вопроса «а что при потере соединения»: история, версии, перезагрузка состояния, разброс переподключений. Здесь видно, работали ли вы с этим в проде.
  • Держите наготове историю деплоя. Случай, когда часть воркеров осталась на старом коде и это дало странное поведение, — узнаваемая и убедительная история, через которую проходят все, кто эксплуатировал фоновую обработку.
  • Приносите артефакты. График памяти воркера, дашборд с возрастом старейшей задачи, схема каналов и прав, тест на чередование пользователей — всё это делает рассказ проверяемым.
