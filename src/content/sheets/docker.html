Docker

Docker решает одну задачу: приложение вместе со своим окружением упаковывается в артефакт, который одинаково запускается на ноутбуке, в CI и на сервере. Всё остальное — слои, кэш сборки, тома, сети — это механика, которая нужна ровно постольку, поскольку она влияет на три вещи: скорость сборки, размер образа и поведение контейнера при остановке.

Основная часть проблем в реальных проектах происходит не от незнания команд, а от неверной модели происходящего. Контейнер считают лёгкой виртуальной машиной — и удивляются, что данные исчезли после пересоздания. Складывают команды в Dockerfile в удобном для чтения порядке — и получают пятиминутную пересборку при правке одной строки кода. Запускают PHP через оболочку — и процесс перестаёт получать сигнал остановки, из-за чего деплой каждый раз убивает воркеры на середине задачи.

Модель: образ, слой, контейнер

Обязательно

Образ — неизменяемый шаблон файловой системы, собранный из слоёв. Контейнер — запущенный процесс, которому этот образ подставлен как корневая файловая система, плюс тонкий записываемый слой сверху. Отсюда следуют почти все практические выводы: контейнеры дёшево создавать и удалять, а всё, что записано внутрь контейнера, исчезает вместе с ним.

ВажноСлои только добавляются. Инструкция, удаляющая файл, создаёт новый слой, где файла нет, но сам файл остаётся в предыдущем слое и продолжает занимать место в образе — и, что важнее, остаётся доступным для извлечения. Отсюда правило: секрет, попавший в один слой, нельзя «удалить» следующей строкой. Он там навсегда, и вычистить его можно только пересборкой без этого шага.
Типичный вопрос на собеседованииЧем контейнер отличается от виртуальной машины?
Контейнер — это процесс на общем с хостом ядре, изолированный пространствами имён и ограниченный контрольными группами. Виртуальная машина запускает собственное ядро поверх гипервизора. Отсюда практическая разница: контейнер стартует за доли секунды и почти ничего не стоит по ресурсам, но изоляция слабее, а запустить систему с другим ядром в нём нельзя.

Dockerfile и его инструкции

Рецепт

Dockerfile — последовательность инструкций, каждая из которых порождает слой или меняет метаданные образа. Инструкций много, но в повседневной работе используется около десяти, и почти у каждой есть ловушка, о которую спотыкаются в первый раз.

DockerfileМинимальный рабочий образ для PHP-приложения
# Точная версия вместо latest: сборка должна быть воспроизводимой
FROM php:8.3-fpm-alpine

# Одна инструкция RUN вместо трёх: меньше слоёв, и кэш пакетного
# менеджера удаляется в том же слое, где создан, — иначе он останется
# в образе, даже если удалить его следующей строкой.
RUN apk add --no-cache icu-dev linux-headers \
 && docker-php-ext-install intl opcache pdo_mysql \
 && apk del linux-headers

WORKDIR /app

# Сначала только манифесты зависимостей: слой с composer install
# переиспользуется, пока не изменились сами зависимости.
COPY composer.json composer.lock ./
RUN composer install --no-dev --no-scripts --no-autoloader --prefer-dist

# И только потом исходники, которые меняются при каждом коммите
COPY . .
RUN composer dump-autoload --optimize --classmap-authoritative

# Запуск не от root: у процесса не должно быть прав, которые ему не нужны
USER www-data

# Форма списка, а не строки: процесс запускается напрямую
# и получает сигналы остановки от Docker.
CMD ["php-fpm"]
ОриентирФайл .dockerignore нужен с первого дня и по важности идёт сразу за самим Dockerfile. Без него в контекст сборки уезжают vendor, node_modules, каталог .git и локальные дампы базы: сборка замедляется на передаче сотен мегабайт, а любое изменение в этих каталогах сбрасывает кэш слоёв. Правильный набор исключений экономит больше времени, чем все остальные оптимизации Dockerfile.
Типичный вопрос на собеседованииЧем CMD отличается от ENTRYPOINT?
ENTRYPOINT задаёт саму исполняемую команду, CMD — аргументы по умолчанию к ней или команду, если ENTRYPOINT не задан. Аргументы docker run заменяют CMD, но не ENTRYPOINT. Практическая связка: ENTRYPOINT — скрипт подготовки окружения, CMD — команда по умолчанию, чтобы тот же образ можно было запустить и как веб-процесс, и как воркер, передав другую команду.

junior / кэш

Слои и кэш сборки

Обязательно

Каждая инструкция сверяется с кэшем: если её входные данные не изменились, слой берётся готовым. Проверка идёт сверху вниз и останавливается на первом несовпадении — всё, что ниже, пересобирается заново. Из этого следует единственное правило порядка: редко меняющееся выше, часто меняющееся ниже.

DockerfileОдин и тот же образ: две минуты против пяти секунд
# ПЛОХО: любое изменение любого файла проекта заставляет
# заново скачивать все зависимости
COPY . .
RUN composer install --no-dev

# ХОРОШО: слой с зависимостями переиспользуется, пока не
# изменились composer.json и composer.lock
COPY composer.json composer.lock ./
RUN composer install --no-dev --no-scripts --no-autoloader
COPY . .
RUN composer dump-autoload --optimize

# Тот же принцип для фронтенда: сначала манифест, потом исходники
COPY package.json package-lock.json ./
RUN npm ci
COPY assets ./assets
RUN npm run build
ВажноУдаление файлов не уменьшает образ, если оно происходит в другом слое. Классическая ошибка — установить пакеты сборки в одном RUN, а удалить их в следующем: итоговый образ содержит и то, и другое. Правильно — устанавливать, использовать и удалять в пределах одной инструкции либо, что надёжнее, выносить сборку в отдельный этап многоступенчатой сборки и копировать в финальный образ только результат.
Типичный вопрос на собеседованииПочему сборка образа занимает пять минут при правке одной строки кода?
Потому что копирование исходников стоит выше установки зависимостей: изменение любого файла сбрасывает кэш этого слоя и всех последующих. Лечится порядком — сначала копируются только манифесты зависимостей и выполняется установка, затем копируется остальной код. Дополнительно проверяется .dockerignore: без него в контекст сборки попадают vendor и .git, и кэш сбрасывается на ровном месте.

junior / запуск

Запуск контейнера

Практика

Контейнер живёт ровно столько, сколько работает его главный процесс. Это объясняет большинство недоумений новичка: контейнер «сразу упал», потому что команда завершилась; контейнер «не видно снаружи», потому что порт не опубликован; изменения «пропали», потому что записывались в слой контейнера, а не в том.

bashКоманды, которые нужны каждый день
# Запуск с публикацией порта, томом и переменной окружения
docker run -d --name app \
  -p 8080:80 \                    # порт хоста : порт контейнера
  -v "$PWD":/app \                # каталог хоста внутрь контейнера
  -e APP_ENV=dev \
  --restart unless-stopped \
  myapp:1.4.2

# Что вообще происходит
docker ps                          # запущенные контейнеры
docker ps -a                       # включая остановленные и упавшие
docker logs -f --tail 100 app      # поток логов главного процесса
docker stats                       # потребление процессора и памяти

# Заглянуть внутрь работающего контейнера
docker exec -it app sh             # оболочка в уже запущенном контейнере
docker inspect app                 # полные метаданные: тома, сети, переменные

# Контейнер падает при старте: логи упавшего никуда не деваются
docker logs app
# и можно запустить образ с другой командой, обойдя entrypoint
docker run --rm -it --entrypoint sh myapp:1.4.2

# Уборка: место кончается почти всегда из-за образов и кэша сборки
docker system df                   # кто именно занял диск
docker system prune -a --volumes   # удалит и неиспользуемые тома: осторожно

Типичный вопрос на собеседованииКонтейнер запускается и сразу останавливается. Почему?
Потому что завершился его главный процесс: команда отработала и вышла, конфигурация оказалась неверной, либо процесс упал с ошибкой. Первое действие — посмотреть docker logs у уже остановленного контейнера, они сохраняются. Если логи пусты, образ запускают с подменённой точкой входа и оболочкой, чтобы посмотреть изнутри, что происходит при старте.

Compose для разработки

Окружение

Compose описывает набор связанных контейнеров одним файлом: приложение, база, кэш, брокер. Его главная ценность для команды — воспроизводимое окружение, которое поднимается одной командой и одинаково устроено у всех, включая нового разработчика в первый день.

compose.yamlТипичное окружение PHP-проекта
services:
  app:
    build:
      context: .
      target: dev          # этап многоступенчатой сборки для разработки
    volumes:
      # Код монтируется внутрь: правка файла видна без пересборки
      - .:/app
      # А vendor остаётся в томе: иначе медленная файловая система хоста
      # и перетирание того, что установлено в образе
      - vendor:/app/vendor
    environment:
      APP_ENV: dev
      DATABASE_URL: mysql://app:secret@db:3306/app
    depends_on:
      db:
        condition: service_healthy   # ждём готовности, а не запуска
    ports:
      - "8080:80"

  db:
    image: mysql:8.4
    environment:
      MYSQL_DATABASE: app
      MYSQL_USER: app
      MYSQL_PASSWORD: secret
      MYSQL_ROOT_PASSWORD: secret
    volumes:
      - db-data:/var/lib/mysql        # данные переживают пересоздание
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 5s
      retries: 10

  worker:
    build: { context: ., target: dev }
    # Тот же образ, другая команда — типичная схема для воркеров
    command: ["php", "bin/console", "messenger:consume", "async"]
    volumes:
      - .:/app
    depends_on:
      - db

volumes:
  db-data:
  vendor:

Типичный вопрос на собеседованииКак контейнеры находят друг друга?
По имени сервиса внутри общей сети: Compose создаёт сеть и регистрирует в её DNS каждый сервис, поэтому приложение обращается к базе по адресу db, а не по IP. Публиковать порт на хост для этого не нужно: ports открывает доступ снаружи, а между собой контейнеры общаются напрямую по внутренней сети.

Уровень, на котором образ перестаёт быть «лишь бы запускалось». Появляются многоступенчатая сборка, осознанный выбор базового образа, корректная остановка процессов, разделение данных и кода, работа с секретами и проверки готовности сервисов.

middle / сборка

Многоступенчатая сборка

Обязательно

Инструменты сборки нужны только во время сборки: компиляторы, Composer, Node, заголовочные файлы. В финальном образе они бесполезны и вредны — увеличивают размер и расширяют поверхность атаки. Многоступенчатая сборка решает это буквально: в одном файле описывается несколько этапов, а в итоговый образ копируется только результат.

DockerfileТри этапа: зависимости, сборка ресурсов, финальный образ
# ---------- Этап 1: PHP-зависимости ----------
FROM composer:2 AS vendor

WORKDIR /app
COPY composer.json composer.lock ./
# --no-dev критично: dev-зависимости в проде не нужны и опасны
RUN composer install --no-dev --no-scripts --no-autoloader --prefer-dist

COPY . .
RUN composer dump-autoload --optimize --classmap-authoritative

# ---------- Этап 2: фронтенд ----------
FROM node:22-alpine AS assets

WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY assets ./assets
RUN npm run build

# ---------- Этап 3: то, что поедет в прод ----------
FROM php:8.3-fpm-alpine AS prod

RUN apk add --no-cache icu \
 && apk add --no-cache --virtual .build-deps icu-dev linux-headers \
 && docker-php-ext-install intl opcache pdo_mysql \
 && apk del .build-deps          # удаление в том же слое, где установка

WORKDIR /app

# Из этапов копируется только результат: ни Composer, ни Node,
# ни исходников фронтенда в финальном образе нет.
COPY --from=vendor --chown=www-data:www-data /app /app
COPY --from=assets --chown=www-data:www-data /app/public/build /app/public/build

COPY docker/php/opcache.ini /usr/local/etc/php/conf.d/
COPY --chmod=755 docker/entrypoint.sh /usr/local/bin/entrypoint

USER www-data
ENTRYPOINT ["entrypoint"]
CMD ["php-fpm"]

# ---------- Этап для разработки ----------
# Наследуется от prod и добавляет то, что в проде не нужно.
# Собирается только при явном указании: --target dev
FROM prod AS dev

USER root
RUN apk add --no-cache $PHPIZE_DEPS linux-headers \
 && pecl install xdebug \
 && docker-php-ext-enable xdebug
USER www-data

Типичный вопрос на собеседованииЗачем нужна многоступенчатая сборка?
Чтобы инструменты сборки не попадали в итоговый образ. Composer, Node, компиляторы и заголовочные файлы нужны только для получения артефакта; в финальный образ копируется результат, а всё остальное остаётся в промежуточных этапах. Выигрыш двойной: размер сокращается в разы, и в проде нет ни одного инструмента, которым можно воспользоваться при взломе.

Стек

Alpine или Debian — вопрос, который возникает в каждом проекте. Alpine даёт меньший образ, но использует другую реализацию стандартной библиотеки, из-за чего часть расширений и сторонних бинарников собирается сложнее, а редкие проблемы с производительностью встречаются на нестандартных нагрузках. Практическое правило: если стек типовой и всё собирается — берите компактный вариант; если начинается борьба с расширениями, время инженера дороже трёхсот мегабайт.

; docker/php/opcache.ini — кэш байткода включён и прогрет.
; В контейнере файлы неизменяемы, поэтому проверку времени
; модификации можно отключить: это заметный выигрыш.
opcache.enable=1
opcache.validate_timestamps=0
opcache.memory_consumption=256
opcache.max_accelerated_files=20000
; Кэш путей: без него каждый include делает системные вызовы
realpath_cache_size=4096k
realpath_cache_ttl=600

; docker/php/php.ini — прод-профиль
display_errors=Off
; Логи идут в поток ошибок: их подхватит драйвер логов Docker
error_log=/dev/stderr
memory_limit=256M
expose_php=Off

# В Dockerfile конфигурация копируется, а не правится на месте:
# изменение настроек — это новый образ и новый деплой.
COPY docker/php/opcache.ini /usr/local/etc/php/conf.d/10-opcache.ini
COPY docker/php/php.ini     /usr/local/etc/php/conf.d/20-app.ini

# Число дочерних процессов FPM подбирается под лимит памяти
# контейнера, а не под память хоста: иначе OOM.
COPY docker/php/pool.conf   /usr/local/etc/php-fpm.d/zz-app.conf
ВажноОдин контейнер — один процесс. Связка nginx и PHP-FPM в одном контейнере под управлением супервизора кажется удобной, но ломает модель: падение одного процесса не видно оркестратору, логи смешиваются, обновлять части по отдельности нельзя, а сигнал остановки получает супервизор, а не приложение. Правильная схема — два контейнера в одной сети, где nginx обращается к FPM по имени сервиса.
Типичный вопрос на собеседованииКак настроить PHP-FPM внутри контейнера?
Число дочерних процессов считается от лимита памяти самого контейнера, а не от памяти хоста: типичное значение — лимит, делённый на реальное потребление одного процесса, с запасом. Настройки кладутся файлами в образ, а не правятся внутри работающего контейнера. Кэш байткода включается с отключённой проверкой времени модификации, поскольку файлы в образе не меняются, а логи направляются в стандартные потоки.

middle / процессы

Entrypoint, PID 1 и сигналы

Обязательно

Главный процесс контейнера получает первый идентификатор процесса, и у этого есть последствия: он обязан корректно реагировать на сигнал завершения и, если порождает дочерние процессы, забирать их после смерти. Ошибки здесь не видны на разработке и стабильно проявляются в проде — воркер убивается на середине задачи при каждом деплое.

bashEntrypoint и почему форма записи имеет значение
#!/bin/sh
# docker/entrypoint.sh — подготовка окружения перед стартом
set -e

# Здесь уместны быстрые и идемпотентные вещи: прогрев кэша,
# проверка обязательных переменных, права на каталоги.
if [ -z "$DATABASE_URL" ]; then
  echo "DATABASE_URL не задан" >&2
  exit 1
fi

php bin/console cache:warmup --no-interaction

# Миграции здесь запускать НЕ нужно: контейнеров несколько,
# и они стартуют одновременно. Миграции — отдельный шаг деплоя.

# exec заменяет процесс оболочки процессом приложения:
# приложение становится PID 1 и получает сигналы напрямую.
# Без exec оболочка остаётся PID 1 и сигналы не передаёт.
exec "$@"

Корректная остановка устроена так: команда остановки посылает главному процессу сигнал завершения и ждёт заданное время, по умолчанию около десяти секунд; если процесс не вышел, он убивается принудительно. Для веб-процесса этого обычно достаточно, а для воркера очереди — нет: длинная задача не успевает доработать. Поэтому воркеры проектируют так, чтобы они завершали текущее сообщение и выходили сами, а таймаут остановки поднимают до разумного предела.

АнтипаттернЗапуск миграций базы данных в точке входа контейнера. При масштабировании в три экземпляра три контейнера стартуют одновременно и выполняют миграции параллельно, что в лучшем случае даёт ошибку блокировки, а в худшем — частично применённую схему. Миграции — отдельный шаг процесса выкладки, выполняемый один раз; подробности — в конспекте по инфраструктуре и деплою.
Типичный вопрос на собеседованииПочему воркер не завершается корректно при остановке контейнера?
Почти всегда потому, что главный процесс — оболочка, а не приложение: команда записана строкой, а не списком, или скрипт точки входа запускает процесс без exec. Сигнал завершения приходит оболочке и до приложения не доходит, поэтому через таймаут процесс убивается принудительно вместе с недоработанной задачей. Лечится формой списка и exec в конце скрипта, а для долгих задач — увеличенным таймаутом остановки.

# Права при монтировании каталога хоста: файлы создаются от
# пользователя контейнера, и снаружи они могут оказаться чужими
docker run --rm -u "$(id -u):$(id -g)" -v "$PWD":/app -w /app \

ВажноИменованный том не входит в резервные копии автоматически и не удаляется вместе с контейнером — это одновременно и защита от потери данных, и источник двух типичных проблем. Первая: диск на сервере заканчивается из-за забытых томов от удалённых окружений. Вторая: команда полной очистки с флагом удаления томов сносит вместе с мусором и рабочую базу. Поэтому у томов с данными должно быть понятное имя и явная процедура копирования.
Типичный вопрос на собеседованииКуда девать данные, если контейнеры пересоздаются?
Наружу: база — в именованный том или во внешнюю управляемую базу, пользовательские файлы — в объектное хранилище, кэш и сессии — в Redis. Внутри контейнера остаются только код и временные файлы. Это условие, без которого не работают ни выкладка без простоя, ни горизонтальное масштабирование: любой экземпляр должен быть заменяем без потерь.

Типичный вопрос на собеседованииКак передать пароль базы в контейнер?

middle / готовность

Healthcheck и порядок запуска

Надёжность

Запущенный контейнер и готовый к работе контейнер — разные вещи. База принимает соединения не сразу, приложение прогревает кэш, воркер подключается к брокеру. Без явной проверки готовности зависящие сервисы стартуют раньше времени и падают, а балансировщик отправляет трафик в ещё не готовый экземпляр.

Dockerfile + compose.yamlПроверка готовности и ожидание зависимостей
# Проверка должна быть дешёвой и проверять реальную готовность,
# а не факт, что процесс жив: подключение к базе, доступность кэша.
HEALTHCHECK --interval=10s --timeout=3s --start-period=30s --retries=3 \
  CMD php bin/console app:health || exit 1

# start-period важен: пока приложение стартует, неудачные
# проверки не считаются отказом и не вызывают перезапуск.

# В compose зависимость ждёт именно готовности:
services:
  app:
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started

# Но полагаться только на порядок запуска нельзя: база может
# упасть и позже. Приложение обязано переживать недоступность
# зависимости и переподключаться, а не падать навсегда.

Живость отвечает только за собственный процесс, а состояние зависимостей — предмет проверки готовности и мониторинга.
Типичный вопрос на собеседованииПриложение стартует раньше базы и падает. Как правильно решить?
Двумя способами одновременно. На уровне запуска — проверкой готовности зависимости и ожиданием её здорового состояния. На уровне приложения — устойчивостью к недоступности: повторные попытки подключения с задержкой вместо падения. Второе важнее: порядок запуска решает проблему только в момент старта, а база может стать недоступной в любой момент работы.

На этом уровне вопросы смещаются от «как собрать» к «как собирать быстро и одинаково», «что именно мы выкатываем» и «что делать, когда контейнер ведёт себя не так». Плюс решение, которое дороже всех остальных: нужен ли вообще оркестратор.

senior / сборка

BuildKit и кэш в CI

Скорость

На локальной машине кэш слоёв есть всегда, на агенте CI — почти никогда: каждая сборка стартует на чистой машине. Отсюда типичная ситуация, когда локально сборка занимает пятнадцать секунд, а в пайплайне — шесть минут, и половина этого времени уходит на повторную загрузку зависимостей.

Dockerfile + bashКэш-монтирование и внешний кэш реестра
# Кэш пакетного менеджера сохраняется между сборками, но не
# попадает в слои образа: и быстро, и без лишнего веса.
RUN --mount=type=cache,target=/root/.composer/cache \
    composer install --no-dev --prefer-dist

RUN --mount=type=cache,target=/root/.npm \
    npm ci

# Сборка в CI с кэшем, который хранится в реестре образов:
# следующий запуск на чистом агенте переиспользует слои.
docker buildx build \
  --tag registry.example.com/app:"$GIT_SHA" \
  --tag registry.example.com/app:latest \
  --cache-from type=registry,ref=registry.example.com/app:buildcache \
  --cache-to   type=registry,ref=registry.example.com/app:buildcache,mode=max \
  --build-arg APP_VERSION="$GIT_SHA" \
  --push .

# Проверка, что кэш действительно сработал: в выводе сборки
# у переиспользованных шагов стоит отметка CACHED.

Воспроизводимость — вторая половина темы. Сборка одного и того же коммита через месяц должна давать функционально тот же образ, а этому мешают три вещи: плавающие теги базовых образов, установка пакетов без фиксации версий и загрузка файлов по внешним ссылкам во время сборки. Первое лечится фиксацией базового образа по дайджесту, второе — файлами блокировки версий, третье — переносом артефактов в свой реестр.

ОриентирТег образа стоит делать из хеша коммита, а не только из номера версии: тогда по любому работающему контейнеру мгновенно восстанавливается, какой именно код внутри. Дополнительно полезно записать хеш коммита и время сборки в метки образа — это стоит одной строки и много раз окупается при разборе инцидента, когда нужно понять, что именно выкачено на конкретном узле.
Типичный вопрос на собеседованииСборка в CI занимает шесть минут, локально — пятнадцать секунд. Что делать?
Причина обычно в отсутствии кэша на чистом агенте. Решается внешним кэшем: слои предыдущей сборки подтягиваются из реестра, а каталоги пакетных менеджеров подключаются кэш-монтированием, чтобы зависимости не скачивались заново. Параллельно проверяются порядок слоёв и содержимое контекста сборки — часто половина времени уходит на передачу того, что должно быть исключено.

Безопасность образов

Обязательно

Контейнер не является границей безопасности сам по себе: ядро общее с хостом, и ошибка в изоляции означает выход наружу. Практическая работа сводится к сокращению того, что находится внутри образа, и того, что процесс внутри вправе делать.

# потому что корневая ФС в проде запускается только на чтение.

# корневая ФС только для чтения, запись — только в тома.

  --tmpfs /tmp \

ВажноМонтирование сокета демона внутрь контейнера — самая недооценённая дыра. Это обычно делают ради сборки образов из пайплайна или ради агента мониторинга, а по факту выдают контейнеру возможность запустить на хосте что угодно с правами root: достаточно попросить демон создать привилегированный контейнер с примонтированной корневой файловой системой. Если такая возможность нужна, вопрос решается отдельным сборщиком без доступа к сокету, а не удобным ярлыком.
Типичный вопрос на собеседованииКак сделать образ безопаснее?
Сократить содержимое и права. Минимальная база и многоступенчатая сборка убирают лишние пакеты; отдельный непривилегированный пользователь и запуск без новых привилегий ограничивают процесс; корневая файловая система монтируется только для чтения, а запись разрешена в конкретные тома. Сверху — сканирование уязвимостей в пайплайне с порогом на критичные и регулярная пересборка ради обновлений базового образа.

Артефакты

Реестр — это хранилище артефактов выкладки, и относиться к нему нужно так же, как к репозиторию кода: с понятной схемой именования, сроком хранения и ответом на вопрос «что именно сейчас работает в проде».

Рабочая комбинация — несколько тегов на один образ: хеш коммита как основной идентификатор, семантическая версия для релизов и плавающий тег окружения для удобства. Разворачивается при этом всегда неизменяемый тег или дайджест, а не плавающий: иначе перезапуск контейнера через неделю может незаметно поднять другую версию кода.

ОриентирЗаведите правило хранения с первого дня: сборки веток удаляются через несколько недель, релизные образы живут долго. Реестр без ротации растёт линейно и однажды упирается в квоту ровно в момент выкладки исправления, а разбираться, что можно удалить, приходится в самое неподходящее время.
Типичный вопрос на собеседованииПочему не стоит выкатывать образ с тегом latest?
Потому что тег — подвижная ссылка. Непонятно, какой код работает в проде; перезапуск контейнера может подтянуть другую версию; откат превращается в угадывание. Развёртывают неизменяемый идентификатор — хеш коммита или дайджест, — а читаемые теги вешают дополнительно, для людей и для внешних потребителей образа.

Ресурсы, лимиты, логи

Продакшен

Лимит памяти и настройки приложения должны быть согласованы. Классическая авария: контейнеру выдали 512 мегабайт, а FPM настроен на двадцать дочерних процессов по сто мегабайт — под нагрузкой ядро убивает контейнер, оркестратор его перезапускает, нагрузка перетекает на соседей, и они падают следом. Число процессов считается от лимита контейнера, а не от объёма памяти сервера, и с запасом на пики.

# контейнера: сбор логов — задача платформы, а не приложения.

# Куда уходит диск

Типичный вопрос на собеседованииКонтейнер периодически перезапускается с кодом 137. Что это значит?
Процесс убит по сигналу принудительного завершения, и почти всегда причина — нехватка памяти: контейнер превысил лимит, и его снял механизм ядра. Проверяется признаком в описании контейнера и записями журнала хоста. Дальше сравниваются лимит и реальное потребление, а настройки приложения — число процессов FPM, размер кэша байткода, объём выборок — приводятся в соответствие с лимитом.

Диагностика

Отладка в контейнере отличается тем, что привычных инструментов внутри обычно нет: минимальный образ не содержит ни сетевых утилит, ни редактора. Это правильно с точки зрения безопасности и неудобно ровно в тот момент, когда что-то сломалось, поэтому набор приёмов стоит освоить заранее.

ОриентирДоговоритесь в команде, что диагностика прода — это отдельный отладочный контейнер, подключаемый к пространствам имён проблемного, а не установка утилит внутрь работающего. Установка пакетов в живой контейнер меняет то, что вы отлаживаете, не переживает перезапуск и создаёт соблазн «оставить, пока работает». Отладочный образ с полным набором инструментов при этом никогда не попадает в прод.
Типичный вопрос на собеседованииКак отладить контейнер, внутри которого нет ни одной утилиты?
Запустить рядом контейнер с инструментами, подключив его к сетевому пространству проблемного: тогда проверки DNS и соединений выполняются ровно в его сетевом окружении. Файлы копируются наружу штатной командой, изменения относительно образа видны отдельной командой, а если контейнер падает при старте, образ запускается с подменённой точкой входа и оболочкой.

Куда дальше: оркестрация

Выбор

Docker решает задачу упаковки и запуска на одной машине. Как только требуются несколько узлов, выкладка без простоя, автоматическое восстановление и распределение нагрузки, нужен слой поверх — и вопрос из технического становится организационным: у оркестратора есть постоянная стоимость владения.

Практический критерий звучит так: оркестратор оправдан, когда его функции нужны постоянно, а не однажды. Если сервисов три, обновления раз в неделю и один сервер держит нагрузку с запасом, Compose и обратный прокси дадут тот же результат в разы дешевле. Разбор Kubernetes и цены его внедрения — в конспекте по инфраструктуре и деплою.

Типичный вопрос на собеседованииМожно ли использовать Compose в проде?
Можно, если понимать ограничения: одна машина, нет автоматического восстановления и распределения нагрузки, выкладка без простоя делается вручную через обратный прокси и параллельный запуск новой версии. Для небольшого проекта это честный и дешёвый вариант. Переходить к оркестратору стоит тогда, когда его возможности требуются регулярно, а не ради галочки в резюме.

Чек-лист прод-образа

Проверка
  • Базовый образ зафиксирован версией, а не тегом latest.
  • Есть .dockerignore, и в контекст не уезжают vendor, node_modules и .git.
  • Манифесты зависимостей копируются отдельно от исходников.
  • Сборка многоступенчатая: Composer и Node не попадают в финальный образ.
  • Зависимости ставятся без dev-пакетов, автозагрузчик оптимизирован.
  • Установка и очистка пакетов происходят в одной инструкции.
  • Процесс запускается не от root, пользователь создан явно.
  • Команда записана формой списка, скрипт точки входа заканчивается exec.
  • Миграции не выполняются при старте контейнера.
  • Секретов нет ни в ENV, ни в ARG, ни в слоях — проверено историей образа.
  • Кэш байткода включён, проверка времени модификации отключена.
  • Число процессов FPM согласовано с лимитом памяти контейнера.
  • Логи идут в стандартные потоки, ротация настроена на уровне драйвера.
  • Есть проверка готовности, отличная от проверки живости.
  • Данные вынесены в тома или внешние хранилища.
  • Образ помечен хешем коммита, выкладка идёт по неизменяемому тегу.

60 вопросов с эталонными ответами

Docker спрашивают почти на каждом собеседовании, и почти всегда — на понимание модели, а не на знание флагов. Сильный ответ объясняет, что происходит и какие из этого следствия.

Junior · 20 вопросов

База
  1. Что такое Docker и какую задачу он решает?Инструмент упаковки приложения вместе с его окружением в образ, который одинаково запускается на любой машине с совместимым ядром. Решает проблему расхождения сред: то, что собрано и протестировано в CI, в проде запускается тем же артефактом, а не собирается заново по инструкции из вики.
  2. Чем образ отличается от контейнера?Образ — неизменяемый шаблон файловой системы из слоёв. Контейнер — запущенный процесс, которому этот образ подставлен как корневая файловая система, плюс тонкий записываемый слой сверху. Из одного образа запускается сколько угодно контейнеров, и все изменения каждого живут в его собственном слое.
  3. Чем контейнер отличается от виртуальной машины?Контейнер — процесс на общем с хостом ядре, изолированный пространствами имён и ограниченный контрольными группами. У виртуальной машины своё ядро поверх гипервизора. Контейнер стартует за доли секунды и почти ничего не стоит, но изоляция слабее и другое ядро в нём не запустить.
  4. Что такое слой образа?Разница файловой системы после одной инструкции сборки. Слои переиспользуются между образами и кэшируются, поэтому повторная сборка быстрая. Важное следствие: слои только добавляются, и файл, удалённый следующей инструкцией, остаётся в предыдущем слое вместе со всем содержимым.
  5. Почему нельзя «удалить» секрет следующей строкой Dockerfile?Потому что он остаётся в слое, где появился, и достаётся из образа любым, кто его скачал. Единственный корректный ответ на такую утечку — сменить сам секрет, а потом пересобрать образ без этого шага и почистить реестр.
  6. Что делает .dockerignore?Исключает файлы из контекста сборки, который целиком передаётся демону. Без него уезжают vendor, node_modules и .git: сборка замедляется на передаче сотен мегабайт, а изменения в этих каталогах сбрасывают кэш слоёв. По влиянию на скорость это второй по важности файл после самого Dockerfile.
  7. Чем COPY отличается от ADD?COPY просто копирует файлы из контекста. ADD дополнительно умеет распаковывать архивы и скачивать по ссылке, и именно неявность этого поведения делает его плохим выбором по умолчанию. Практическое правило: всегда COPY, кроме случая распаковки локального архива.
  8. Чем CMD отличается от ENTRYPOINT?ENTRYPOINT — сама команда, CMD — аргументы к ней по умолчанию. Аргументы запуска заменяют CMD, но не ENTRYPOINT. Типичная связка: точка входа — скрипт подготовки окружения, команда — веб-процесс по умолчанию, чтобы тем же образом запускать и воркер, передав другую команду.
  9. Почему сборка долгая при правке одной строки кода?Потому что копирование исходников стоит выше установки зависимостей, и правка любого файла сбрасывает кэш этого слоя и всех следующих. Лечится порядком: сначала копируются манифесты зависимостей и выполняется установка, потом весь остальной код. Плюс проверяется .dockerignore.
  10. Что делает EXPOSE?Только документирует порт в метаданных образа. Наружу порт не публикуется: для этого нужен флаг публикации при запуске или соответствующий ключ в compose. Внутри общей сети контейнеры и без этого обращаются друг к другу по любому порту.
  11. Как контейнеры находят друг друга?По имени сервиса в общей пользовательской сети: у неё есть встроенное разрешение имён. Публикация порта на хост для этого не нужна и в проде часто вредна — база не должна торчать наружу, если к ней ходит только приложение.
  12. Почему контейнер сразу завершается после запуска?Потому что завершился его главный процесс: команда отработала, конфигурация неверна или процесс упал. Контейнер живёт ровно столько, сколько живёт этот процесс. Первое действие — прочитать логи остановленного контейнера, они сохраняются.
  13. Куда деваются данные при удалении контейнера?Всё, что записано в слой контейнера, исчезает. Переживает удаление только то, что лежит в томе или во внешнем хранилище. Отсюда правило: база, загруженные файлы и всё, что нельзя потерять, живёт вне контейнера.
  14. Чем именованный том отличается от монтирования каталога хоста?Том управляется Docker, лежит в его каталоге и удобен для данных: он не зависит от структуры проекта и переживает пересоздание контейнера. Монтирование каталога хоста показывает контейнеру ваш рабочий каталог — это инструмент разработки, дающий мгновенное отражение правок, но приносящий вопросы прав и скорости.
  15. Зачем нужен Docker Compose?Чтобы описать набор связанных сервисов одним файлом и поднимать окружение одной командой: приложение, база, кэш, брокер, воркеры. Главная ценность — одинаковое окружение у всей команды и у нового человека в первый день.
  16. Что делает depends_on?Задаёт порядок запуска. Сам по себе он дожидается только старта контейнера, а не готовности сервиса, поэтому приложение может обратиться к ещё не поднявшейся базе. Ожидание готовности включается условием на здоровье сервиса, а надёжность всё равно обеспечивается повторными попытками подключения в приложении.
  17. Как посмотреть, что происходит внутри работающего контейнера?Логи главного процесса, выполнение команды внутри с интерактивной оболочкой, полные метаданные с томами и переменными, текущее потребление ресурсов. Если контейнер уже упал, логи всё равно доступны, а образ можно запустить с подменённой точкой входа.
  18. Что такое тег образа?Читаемая ссылка на образ, которую можно переназначить: сегодня она указывает на один образ, завтра на другой. Поэтому в проде разворачивают неизменяемый идентификатор — хеш коммита или дайджест, — а плавающие теги оставляют для удобства.
  19. Где хранятся образы?Локально в хранилище демона и в реестре — публичном или собственном. Реестр играет роль хранилища артефактов выкладки, поэтому у него должны быть схема именования, права доступа и правило хранения, иначе он однажды упирается в квоту в самый неподходящий момент.
  20. Как освободить место, которое занял Docker?Сначала посмотреть, кто именно его занял: образы, тома, кэш сборки. Потом удалять адресно — неиспользуемые образы старше нужного срока и кэш сборки. Массовая очистка с удалением томов опасна: вместе с мусором она снесёт и данные базы, если они лежат в томе.

Middle · 20 вопросов

Механика
  1. Зачем нужна многоступенчатая сборка?Чтобы инструменты сборки не попадали в итоговый образ: Composer, Node, компиляторы нужны только для получения артефакта. В финальный этап копируется результат, остальное остаётся в промежуточных. Выигрыш в размере и в безопасности: в проде нет инструментов, которыми можно воспользоваться при взломе.
  2. Как уменьшить образ?По убыванию эффекта: многоступенчатая сборка, компактная база, установка и очистка в одной инструкции, отказ от dev-зависимостей, правильный .dockerignore. Отдельно полезен общий базовый слой у сервисов: узлы и реестр качают его один раз.
  3. Alpine или образ на Debian?Alpine меньше, но использует другую стандартную библиотеку, из-за чего часть расширений и сторонних бинарников собирается сложнее. Если стек типовой и всё собирается — берите компактный вариант; если начинается борьба с расширениями, время инженера дороже нескольких сотен мегабайт.
  4. Почему nginx и PHP-FPM держат в разных контейнерах?Потому что модель — один процесс на контейнер. В одном контейнере падение одной службы не видно снаружи, логи смешиваются, обновлять части по отдельности нельзя, а сигнал остановки получает супервизор. Два контейнера в общей сети решают это без потерь: nginx обращается к FPM по имени сервиса.
  5. Как настроить число процессов FPM в контейнере?От лимита памяти контейнера, а не от памяти хоста: лимит делится на реальное потребление процесса с запасом на пики. Несогласованность здесь даёт классическую аварию — контейнер убивается ядром под нагрузкой, перезапускается, нагрузка перетекает на соседей.
  6. Почему процесс не получает сигнал остановки?Потому что главный процесс — оболочка: команда записана строкой, а не списком, или скрипт точки входа запускает приложение без exec. Сигнал приходит оболочке и дальше не идёт, поэтому через таймаут процесс убивают принудительно. Лечится формой списка и exec в конце скрипта.
  7. Что такое PID 1 и почему это важно?Главный процесс контейнера получает первый идентификатор и вместе с ним обязанности init: реагировать на сигнал завершения и забирать процессы-сироты. Обычные приложения к этому не готовы, поэтому при порождении дочерних процессов накапливаются зомби; решается запуском с минимальным init.
  8. Как корректно останавливать воркер очереди?Воркер должен доработать текущее сообщение и выйти сам, получив сигнал завершения. Для этого он обязан быть главным процессом, а таймаут остановки — превышать типичное время задачи. Дополнительно помогает ограничение времени жизни воркера: он периодически завершается сам, что заодно снимает вопрос утечек памяти.
  9. Почему миграции не запускают в точке входа?Потому что экземпляров несколько и они стартуют одновременно: миграции пойдут параллельно, дав в лучшем случае ошибку блокировки, в худшем — частично применённую схему. Миграции — отдельный шаг выкладки, выполняемый один раз перед или после переключения трафика.
  10. Где хранить состояние приложения?Вне контейнера: база — во внешней управляемой базе или в томе, пользовательские файлы — в объектном хранилище, сессии и кэш — в Redis. Только при этом условии контейнер можно убить и пересоздать в любой момент, а на этом строятся и выкладка без простоя, и горизонтальное масштабирование.
  11. Как передать секрет в образ при сборке?Механизмом секретов BuildKit: значение монтируется на время выполнения инструкции и в слои не попадает. Аргумент сборки для этого не годится — он остаётся в истории образа. В рантайме секреты приходят из механизма оркестратора или внешнего хранилища.
  12. Чем проверка живости отличается от проверки готовности?Живость отвечает на вопрос, не завис ли процесс, и при отказе контейнер перезапускают. Готовность отвечает, можно ли слать трафик, и при отказе экземпляр убирают из балансировки. Путаница дорого стоит: проверка живости, ходящая в базу, превращает кратковременную недоступность базы в одновременный перезапуск всех экземпляров.
  13. Зачем нужен период прогрева у проверки?Чтобы неудачные проверки во время старта не считались отказом. Без него приложение с медленным запуском попадает в цикл: не успело прогреться — признано мёртвым — перезапущено — снова не успело. Внешне это выглядит как случайные падения на ровном месте.
  14. Как контейнер получает конфигурацию?Снаружи: переменными окружения, файлами переменных или смонтированными конфигурационными файлами. Один и тот же образ должен работать во всех средах — различаться может только конфигурация. Настройки, зашитые в образ на этапе сборки, ломают это свойство и заставляют собирать отдельный образ на каждую среду.
  15. Почему в проде не монтируют код внутрь контейнера?Потому что образ перестаёт быть источником истины: то, что выкачено, отличается от того, что собрано и протестировано. Пропадает воспроизводимость, откат становится непредсказуемым, а правки «прямо на сервере» исчезают при следующем перезапуске. Монтирование кода — приём исключительно для разработки.
  16. Что происходит при docker stop?Главному процессу посылается сигнал завершения, и демон ждёт заданное время, по умолчанию около десяти секунд. Если процесс не вышел, он убивается принудительно. Отсюда требования: приложение должно обрабатывать сигнал, а для долгих задач нужно увеличивать период ожидания.
  17. Как ускорить сборку?Порядком слоёв, чтобы кэш зависимостей переиспользовался; исключением мусора из контекста; кэш-монтированием каталогов пакетных менеджеров; вынесением тяжёлых шагов в отдельные этапы, которые пересобираются реже. В CI дополнительно подключается внешний кэш, потому что на чистом агенте локального кэша нет.
  18. Как отлаживать сборку, которая падает на середине?Запустить контейнер из последнего успешно собранного слоя и повторить шаг руками: так видно реальное окружение, в котором инструкция выполняется. Полезно также временно разбить длинную инструкцию на части, чтобы понять, какая именно команда падает, и посмотреть подробный вывод сборки.
  19. Зачем контейнеру непривилегированный пользователь?Чтобы захват процесса не давал полных прав внутри контейнера, а при ошибке в изоляции — и на хосте. Пользователь создаётся явно с фиксированным идентификатором, каталоги для записи готовятся заранее, а сам запуск идёт с урезанным набором возможностей.
  20. Что не так с образами «всё в одном»?В них несколько служб под супервизором, из-за чего теряется наблюдаемость: падение одной службы не видно, логи смешаны, обновить часть нельзя, остановка обрабатывается супервизором, а не приложением. Такие образы удобны на старте и становятся источником непонятных проблем ровно тогда, когда нагрузка вырастет.

Как ускорить сборку образа в CI?Подключить внешний кэш: слои предыдущей сборки берутся из реестра или из кэша платформы, а каталоги пакетных менеджеров монтируются кэш-монтированием, чтобы зависимости не скачивались заново. Параллельно проверяются порядок слоёв и контекст сборки — часто половина времени уходит на передачу того, что должно быть исключено.
  2. Что делает сборку невоспроизводимой?Плавающие теги базовых образов, установка пакетов без фиксации версий и загрузка файлов по внешним ссылкам во время сборки. Лечится фиксацией базового образа по дайджесту, файлами блокировки версий и переносом внешних артефактов в свой реестр.
  3. Зачем фиксировать базовый образ по дайджесту?Потому что тег подвижен: под тем же именем через месяц окажется другой образ, и сборка того же коммита даст другой результат. Дайджест указывает на конкретное содержимое. Цена — обновления безопасности нужно подтягивать осознанно, отдельным изменением, что как раз и является плюсом: обновление становится видимым в истории.
  4. Является ли контейнер границей безопасности?Сам по себе — нет: ядро общее с хостом, и ошибка в изоляции означает выход наружу. Контейнер уменьшает поверхность атаки, но не заменяет виртуализацию там, где выполняется недоверенный код. Практическая работа сводится к сокращению содержимого образа и прав процесса.
  5. Чем опасно монтирование сокета демона в контейнер?Это фактически выдача прав root на хосте: имея доступ к сокету, можно попросить демон запустить привилегированный контейнер с примонтированной корневой файловой системой. Такое встречается ради сборки из пайплайна или агентов мониторинга, и решать эти задачи нужно иначе — сборщиком без доступа к сокету.
  6. Что даёт запуск с корневой файловой системой только для чтения?Атакующий не может изменить код или положить свой файл в контейнер, а случайная запись мимо томов перестаёт быть незаметной. Требует заранее подготовить каталоги для записи и вынести их в тома или временную файловую систему в памяти — это же полезно и с точки зрения понимания, куда приложение вообще пишет.
  7. Как построить схему тегов?Основной идентификатор — хеш коммита, дополнительно семантическая версия для релизов и плавающий тег окружения для удобства. Развёртывается всегда неизменяемый тег или дайджест. Метаданные с хешем коммита и временем сборки записываются метками образа — это многократно окупается при разборе инцидента.
  8. Зачем реестру правило хранения?Потому что он растёт линейно и однажды упирается в квоту ровно в момент выкладки исправления. Работающая схема: образы веток удаляются через несколько недель, релизные живут долго. Разбираться, что можно удалить, лучше заранее и правилом, а не вручную во время инцидента.
  9. Как согласовать лимиты контейнера с настройками приложения?Считать от лимита: число процессов FPM, размер кэша байткода и пулов соединений выводятся из памяти, доступной контейнеру, с запасом на пики. Иначе контейнер убивается ядром под нагрузкой, перезапускается и перекладывает нагрузку на соседей, порождая каскад.
  10. Контейнер перезапускается с кодом 137. Что это?Принудительное завершение, почти всегда из-за нехватки памяти: превышен лимит, и процесс снят механизмом ядра. Подтверждается признаком в описании контейнера и записями журнала хоста. Дальше сравниваются лимит и реальное потребление и правятся настройки приложения.
  11. Куда должны идти логи из контейнера?В стандартные потоки вывода и ошибок, откуда их забирает драйвер логов и система сбора. Запись в файлы внутри контейнера означает, что логи исчезнут вместе с ним и одновременно займут диск. Ротация настраивается на уровне драйвера, иначе один разговорчивый сервис заполняет узел.
  12. Как диагностировать контейнер без утилит внутри?Запустить рядом отладочный контейнер, подключив его к сетевому пространству проблемного: проверки DNS и соединений выполняются в его сетевом окружении. Файлы копируются наружу штатной командой, изменения относительно образа видны отдельной командой. Устанавливать пакеты в живой контейнер не нужно: это меняет то, что вы отлаживаете.
  13. Работает локально, падает в проде. Как искать?Сравнить три вещи: дайджест образа, переменные окружения и смонтированные тома. В подавляющем большинстве случаев расхождение именно там — другой тег, отсутствующая переменная, конфигурация, которая локально приходит из смонтированного файла, а в проде отсутствует. Одинаковый образ и разное поведение почти всегда означают разное окружение.
  14. Что проверять при ревью чужого Dockerfile?Фиксацию базового образа, порядок слоёв и наличие .dockerignore, многоступенчатую сборку, отсутствие dev-зависимостей и секретов, непривилегированного пользователя, форму записи команды, отсутствие миграций в точке входа, работу с логами. Этих пунктов хватает, чтобы поймать большую часть проблем.
  15. Можно ли использовать Compose в проде?Да, с пониманием ограничений: одна машина, нет автоматического восстановления и распределения нагрузки, выкладка без простоя делается вручную через обратный прокси и параллельный запуск новой версии. Для небольшого проекта это честный дешёвый вариант, который не требует отдельного специалиста.
  16. Когда пора переходить к оркестратору?Когда его функции нужны постоянно: несколько узлов, регулярные выкладки без простоя, автоматическое восстановление, масштабирование под нагрузку, несколько команд с общими ресурсами. Если сервисов три и один сервер держит нагрузку с запасом, оркестратор добавит стоимость владения без соразмерной пользы.
  17. Как организовать выкладку без простоя без Kubernetes?Обратным прокси перед приложением: поднимается новая версия рядом, проходит проверку готовности, трафик переключается, старая версия останавливается с запасом времени на завершение запросов. Миграции при этом выполняются отдельным шагом и должны быть совместимы с обеими версиями кода.
  18. Как тестировать код, зависящий от базы, с помощью контейнеров?Поднимать настоящую базу в контейнере на время тестов, а не подменять её заглушками: поведение транзакций, блокировок и типов данных заглушкой не воспроизводится. Контейнер поднимается на прогон, данные изолируются по тестам, а образ базы фиксируется той же версией, что и в проде.
  19. Чем containerd отличается от Docker?Containerd — среда выполнения нижнего уровня, которая непосредственно запускает контейнеры, Docker — надстройка с интерфейсом командной строки, сборкой и сетевой обвязкой. Kubernetes работает с containerd напрямую, поэтому знание, что образ и рантайм описаны стандартом, помогает не путать инструмент с самой технологией.
  20. Какие антипаттерны вы встречали чаще всего?Несколько служб в одном контейнере, копирование всего проекта первым шагом, тег latest в проде, секреты в слоях, запуск от root, данные в контейнере, миграции в точке входа и правки прямо внутри работающего контейнера. У каждого есть предсказуемое последствие, и на ревью они ловятся за пару минут.

Справочник · практика

15 практических заданий

Задания рассчитаны на реальный проект: почти каждое начинается с того, что вы открываете свой Dockerfile или compose-файл. Если контейнеров в проекте нет, подойдёт любое приложение на PHP с базой.

Junior · 5 заданий

Основы

1. Собрать образ с нуля

Напишите Dockerfile для своего приложения без копирования готового шаблона: база, расширения, зависимости, запуск. Добейтесь, чтобы контейнер стартовал и отвечал на запрос.

РезультатПонимание, из чего состоит образ, вместо копирования чужого файла с непонятными строками.

2. Замерить кэш

Замерьте время пересборки при правке одной строки кода. Переставьте копирование манифестов выше копирования исходников и замерьте снова. Добавьте .dockerignore и замерьте в третий раз.

РезультатЧисла вместо теории: обычно разница между первым и третьим замером десятикратная.

3. Потерять и сохранить данные

Запустите базу без тома, создайте таблицу, удалите контейнер и убедитесь, что данных нет. Повторите с именованным томом. Сделайте резервную копию тома в архив.

РезультатЛичный опыт потери данных в безопасной обстановке и готовая процедура копирования.

4. Поднять окружение

Опишите в compose приложение, базу и кэш, свяжите их по именам сервисов, добавьте проверку готовности базы. Проверьте, что окружение поднимается одной командой на чистой машине.

РезультатРабочее окружение, которое можно отдать новому человеку в первый день.

5. Разобрать падение

Сломайте контейнер намеренно тремя способами: неверная команда запуска, отсутствующая переменная окружения, занятый порт. Для каждого найдите причину по логам и метаданным.

РезультатТри знакомых симптома вместо паники при первом падении в проде.

Middle · 6 заданий

Механика

6. Многоступенчатая сборка

Перепишите образ на несколько этапов: зависимости, сборка фронтенда, финальный образ. Сравните размер до и после и посмотрите историю слоёв, чтобы найти оставшийся мусор.

РезультатОбычно кратное уменьшение размера и понимание, что именно занимало место.

7. Проверить сигналы

Запустите воркер командой в форме строки и остановите контейнер, замерив время. Перепишите в форму списка с exec в точке входа и повторите. Убедитесь, что задача успевает завершиться.

РезультатНаглядная разница между корректной остановкой и убийством процесса по таймауту.

8. Убрать root

Создайте в образе пользователя, переключитесь на него и найдите все места, где приложению не хватает прав. Подготовьте каталоги заранее и запустите контейнер с корневой файловой системой только для чтения.

РезультатТочное знание, куда приложение пишет, и заметно уменьшенные последствия любой уязвимости.

9. Проверки готовности

Добавьте в приложение две проверки: живость без обращения к зависимостям и готовность с их проверкой. Погасите базу и убедитесь, что контейнер не перезапускается, а лишь выходит из балансировки.

РезультатОтказ зависимости перестаёт превращаться в лавину перезапусков.

10. Секрет в слоях

Соберите образ, передав токен аргументом сборки, и найдите его в истории образа. Перепишите на механизм секретов сборки и убедитесь, что след исчез.

РезультатПрактическая демонстрация, почему аргумент сборки не годится для секретов.

11. Лимиты и падение по памяти

Поставьте контейнеру заведомо низкий лимит памяти и добейтесь падения под нагрузкой. Найдите признак нехватки памяти и код завершения, затем подберите согласованные лимит и настройки приложения.

РезультатУзнаваемый симптом и метод подбора лимитов вместо значений наугад.

Инженерия

12. Кэш в пайплайне

Замерьте время сборки в CI на чистом агенте. Подключите внешний кэш и кэш-монтирование зависимостей, замерьте снова. Проверьте по выводу сборки, какие шаги действительно взялись из кэша.

РезультатСокращение времени пайплайна, которое чувствует вся команда каждый день.

13. Аудит образа

Прогоните продовый образ через сканер уязвимостей и анализ слоёв. Проверьте пользователя, историю на следы секретов и наличие инструментов сборки. Составьте список правок и внесите их.

РезультатСписок конкретных проблем вместо общего ощущения, что «с образом всё нормально».

14. Выкладка без простоя

Настройте на одном сервере обновление через обратный прокси: новая версия поднимается рядом, проходит проверку готовности, трафик переключается. Проверьте нагрузочным запросом, что запросы не теряются.

РезультатРаботающая выкладка без простоя без оркестратора и понимание, чего она стоит.

15. Ревью чужого Dockerfile

Возьмите Dockerfile из другого проекта или из открытого репозитория и найдите в нём не менее пяти проблем, объяснив последствие каждой. Предложите исправленный вариант.

РезультатГотовый навык для ревью и убедительный материал для разговора на собеседовании.

Финал · подготовка

План подготовки на 4 недели

Расчёт на час-полтора в будний день. Тема практическая до предела: почти каждый пункт закрывается изменением в собственном Dockerfile или compose-файле, а не чтением документации.

Неделя 1 · Модель и сборка

База

Задачи недели

Построить правильную модель происходящего и научиться собирать образ осознанно, а не копированием чужого файла.

Что сделать

  • Написать Dockerfile для своего приложения с нуля (задание 1).
  • Замерить влияние порядка слоёв и .dockerignore на время сборки (задание 2).
  • Разобрать историю слоёв своего образа и найти, что занимает место.
  • Проверить, что произойдёт при удалении контейнера с данными и без тома (задание 3).
  • Объяснить вслух разницу между образом, слоем и контейнером.

Результат недели

Собственный образ, который собирается за секунды при правке кода, и понимание, почему именно так.

Неделя 2 · Окружение

Практика

Задачи недели

Собрать воспроизводимое окружение и разобраться с тем, как контейнеры связаны и где живут данные.

Что сделать

  • Описать окружение из приложения, базы и кэша с проверкой готовности (задание 4).
  • Сломать контейнер тремя способами и найти причину по логам (задание 5).
  • Перевести образ на многоступенчатую сборку и сравнить размер (задание 6).
  • Разделить nginx и PHP-FPM на два контейнера, если они были вместе.
  • Проверить, что в контейнере не остаётся ничего, что нельзя потерять.

Результат недели

Окружение, которое поднимается одной командой, и образ без инструментов сборки внутри.

Неделя 3 · Поведение в проде

Надёжность

Задачи недели

Закрыть вещи, которые не видны на разработке и стабильно проявляются под нагрузкой: сигналы, права, проверки, лимиты.

Что сделать

  • Проверить корректную остановку воркера и починить форму записи команды (задание 7).
  • Перевести образ на непривилегированного пользователя и режим только для чтения (задание 8).
  • Развести проверки живости и готовности и проверить поведение при падении базы (задание 9).
  • Подобрать лимиты и воспроизвести падение по памяти (задание 11).
  • Настроить ротацию логов и убедиться, что приложение пишет в стандартные потоки.

Результат недели

Контейнер, который корректно останавливается, не работает от root и предсказуемо ведёт себя под нагрузкой.

Неделя 4 · Пайплайн и безопасность

Финиш

Задачи недели

Довести сборку до состояния, в котором её не стыдно показать, и выстроить путь образа от коммита до сервера.

Что сделать

  • Подключить внешний кэш сборки в CI и замерить эффект (задание 12).
  • Проверить, не утёк ли секрет в слои, и перейти на секреты сборки (задание 10).
  • Провести аудит образа сканером и анализом слоёв (задание 13).
  • Настроить схему тегов и правило хранения в реестре.
  • Организовать выкладку без простоя через обратный прокси (задание 14) и провести ревью чужого Dockerfile (задание 15).

Результат недели

Готовность обсуждать не команды, а решения: воспроизводимость, безопасность, стоимость эксплуатации и выбор способа запуска.

Что помогает на собеседовании

Бонус
  • Отвечайте моделью, а не флагами. «Контейнер — это процесс, а не машина» объясняет сразу и эфемерность данных, и скорость старта, и слабую изоляцию. Перечисление ключей командной строки не объясняет ничего.
  • Приводите числа. «Перенесли копирование манифестов выше и сократили сборку с пяти минут до сорока секунд» звучит несопоставимо убедительнее общих слов про кэш слоёв.
  • Знайте, что происходит при остановке. Вопрос про сигналы и корректное завершение воркеров задают часто, и он мгновенно отделяет тех, кто эксплуатировал контейнеры в проде, от тех, кто только запускал их локально.
  • Помните про секреты в слоях. Это самая частая реальная утечка, и правильный ответ включает не только «не класть», но и порядок действий, если уже положили: сначала сменить секрет, потом пересобирать.
  • Не защищайте оркестратор ради оркестратора. Сильный ответ на вопрос про Kubernetes часто звучит как «для этого проекта он не нужен, и вот почему». Умение назвать стоимость владения ценится выше знания манифестов.
  • Различайте живость и готовность. Пример с проверкой живости, ходящей в базу, и последующей лавиной перезапусков — короткая история, которая показывает продовый опыт лучше длинных рассуждений.
  • Будьте готовы к ревью на месте. Часто дают Dockerfile и просят найти проблемы. Порядок разбора простой: база и фиксация версии, порядок слоёв, многоступенчатость, пользователь, секреты, форма команды, данные и логи.
  • Признавайте границы. Docker не решает вопросы отказоустойчивости и балансировки, а контейнер не является границей безопасности сам по себе. Кандидат, который это проговаривает, вызывает больше доверия, чем тот, кто описывает контейнеры как универсальное решение.
