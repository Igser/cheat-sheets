Symfony для PHP-разработчиков

Symfony — фреймворк с другой философией, чем у «быстрых» решений: здесь почти ничего не происходит по волшебству. Запрос проходит через явную цепочку событий, зависимости собираются контейнером, который компилируется в обычный PHP-код, а конфигурация описывает, что именно и куда внедряется. Это дороже на входе и заметно дешевле на дистанции: через три года на большом проекте вы всё ещё можете ответить на вопрос «почему это вызвалось».

Отсюда и характер собеседований. Про Symfony редко спрашивают синтаксис — спрашивают устройство: что делает HttpKernel, чем слушатель отличается от подписчика, как контейнер понимает, что подставить в конструктор, что происходит при flush() в Doctrine, зачем нужен voter, если есть access_control, и почему после деплоя надо прогревать кэш.

Конспект собирает то, что нужно в работе и что действительно спрашивают: от первого контроллера до компиляции контейнера, Messenger в проде, деплоя без простоя и обновления мажорных версий. Смежные темы вынесены отдельно: PHP, базы данных, структуры данных, Laravel, AI и LLM.

Жизненный цикл запроса и HttpKernel

БазаСпрашивают всегда

Вся модель Symfony укладывается в одну формулу: HttpKernel превращает Request в Response, а между ними рассылает события, на которые может подписаться любой код. Понимание этой цепочки отвечает сразу на десяток вопросов — от «где поставить проверку» до «почему мой листенер не сработал».

phpСвой подписчик на события ядра
<?php
declare(strict_types=1);

namespace App\EventSubscriber;

use Symfony\Component\EventDispatcher\EventSubscriberInterface;
use Symfony\Component\HttpKernel\Event\RequestEvent;
use Symfony\Component\HttpKernel\Event\ResponseEvent;
use Symfony\Component\HttpKernel\KernelEvents;

final class RequestIdSubscriber implements EventSubscriberInterface
{
    private string $requestId = '';

    // Подписчик сам объявляет, на что он реагирует и с каким приоритетом.
    // Чем больше приоритет, тем раньше вызов.
    public static function getSubscribedEvents(): array
    {
        return [
            KernelEvents::REQUEST  => ['onRequest', 255],
            KernelEvents::RESPONSE => 'onResponse',
        ];
    }

    public function onRequest(RequestEvent $event): void
    {
        // Вложенные запросы (подзапросы) обычно обрабатывать не нужно
        if (!$event->isMainRequest()) {
            return;
        }

        $this->requestId = $event->getRequest()->headers->get('X-Request-Id')
            ?? bin2hex(random_bytes(8));
    }

    public function onResponse(ResponseEvent $event): void
    {
        $event->getResponse()->headers->set('X-Request-Id', $this->requestId);
    }
}
ВажноСобытие kernel.terminate происходит после отправки ответа пользователю. Туда выносят то, что не должно задерживать ответ, но при этом важно понимать: под FPM это всё ещё тот же процесс, он занят до конца обработки. Для по-настоящему долгих задач место в Messenger, а не в terminate.
Типичный вопрос на собеседованииЧто происходит от запроса до ответа в Symfony?
Единая точка входа создаёт ядро, которое вызывает handle(). Дальше рассылаются события: kernel.request (маршрут, локаль, аутентификация — здесь листенер может сразу вернуть ответ), kernel.controller и разрешение аргументов, вызов контроллера, при необходимости kernel.view, затем kernel.response и отправка. После ответа — kernel.terminate, а при исключении — kernel.exception.
ПрактикаНапишите подписчика, который добавляет в каждый ответ идентификатор запроса и время обработки, а в лог — предупреждение о медленных запросах. Проверьте, что заголовок появляется и на страницах с ошибкой 500.

ВажноФайл .env задаёт значения по умолчанию и коммитится, а .env.local — локальные переопределения и в репозиторий не попадает. На проде значения обычно приходят из настоящих переменных окружения, а секреты — из зашифрованного хранилища секретов. Класть боевые ключи в .env нельзя: он в истории git навсегда.
АнтипаттернДержать в проекте один гигантский services.yaml с перечислением каждого сервиса вручную. Autowiring и autoconfigure закрывают 95% случаев; явное описание нужно только там, где контейнер не может догадаться сам: скаляры, несколько реализаций одного интерфейса, фабрики.
Типичный вопрос на собеседованииЧем отличаются окружения и зачем прогрев кэша?
Окружение определяет набор конфигурации и поведение: в dev контейнер и маршруты пересобираются при изменениях, в prod они компилируются заранее и не проверяются на актуальность ради скорости. Поэтому на проде после выкатки нужно собрать кэш (cache:clear/cache:warmup), иначе первый запрос будет собирать его сам или приложение возьмёт устаревшую версию.
ПрактикаДобавьте свой параметр в services.yaml через bind, прочитайте его в сервисе и переопределите значением из переменной окружения. Затем посмотрите скомпилированный контейнер в var/cache и найдите там свой сервис.

Роутинг и контроллеры

БазаСпрашивают всегда
phpКонтроллер: атрибуты, аргументы, ответы
<?php
namespace App\Controller;

use App\Entity\Post;
use App\Repository\PostRepository;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

#[Route('/posts', name: 'post_')]
final class PostController extends AbstractController
{
    #[Route('', name: 'index', methods: ['GET'])]
    public function index(PostRepository $posts, Request $request): Response
    {
        // Сервисы внедряются прямо в аргументы метода
        return $this->render('post/index.html.twig', [
            'posts' => $posts->findPublished($request->query->getInt('page', 1)),
        ]);
    }

    // Сущность находится по параметру маршрута автоматически;
    // если записи нет — 404 без единой строки кода
    #[Route('/{slug}', name: 'show', methods: ['GET'], requirements: ['slug' => '[a-z0-9-]+'])]
    public function show(Post $post): Response
    {
        // Права проверяются явно: поиск сущности их НЕ проверяет
        $this->denyAccessUnlessGranted('view', $post);

        return $this->render('post/show.html.twig', ['post' => $post]);
    }

    #[Route('/{id}', name: 'delete', methods: ['DELETE'])]
    public function delete(Post $post, PostRepository $posts): Response
    {
        $this->denyAccessUnlessGranted('delete', $post);
        $posts->remove($post, flush: true);

        return $this->redirectToRoute('post_index');
    }
}

ВажноАвтоматический поиск сущности по параметру маршрута отвечает на вопрос «существует ли запись», но не на вопрос «можно ли её этому пользователю». Забытая проверка прав здесь — самая частая уязвимость: достаточно подставить чужой идентификатор в адрес. Проверка делается явно — denyAccessUnlessGranted, атрибут #[IsGranted] или выборка сразу с фильтром по владельцу.
АнтипаттернКонтроллер, который сам ходит в базу через EntityManager, отправляет письма, строит отчёт и содержит бизнес-правила. Контроллер — адаптер HTTP: принять запрос, вызвать сервис, вернуть ответ. Всё остальное должно быть вызываемо и из консольной команды, и из обработчика сообщения.
Типичный вопрос на собеседованииКак в контроллер попадают аргументы?
Их разрешают специальные резолверы на этапе kernel.controller_arguments: сервисы подставляются по типу из контейнера, параметры маршрута — по имени, сущности Doctrine ищутся по параметру, а объекты запроса могут собираться из тела или строки запроса соответствующими атрибутами. Это расширяемый механизм: можно написать собственный резолвер.
ПрактикаСделайте контроллер ресурса с маршрутами через атрибуты, ограничениями параметров и именованными маршрутами. Затем напишите функциональный тест: чужая запись даёт 403, несуществующая — 404.

Контейнер и autowiring

БазаСпрашивают всегда

Контейнер — это то, что делает Symfony Symfony. Он знает, как создать любой сервис, и подставляет зависимости по типам аргументов конструктора. Ключевая деталь: в prod контейнер компилируется в обычный PHP-класс, поэтому во время запроса никакой рефлексии и «поиска» не происходит.

phpСервис и его зависимости
<?php
namespace App\Service;

use Psr\Log\LoggerInterface;
use Symfony\Component\DependencyInjection\Attribute\Autowire;

final class InvoiceGenerator
{
    public function __construct(
        // По типу — контейнер сам найдёт реализацию
        private readonly PdfRenderer $renderer,
        private readonly LoggerInterface $logger,

        // Скаляры по типу подставить нельзя — указываем явно
        #[Autowire('%kernel.project_dir%/var/invoices')]
        private readonly string $storageDir,

        #[Autowire(env: 'INVOICE_TEMPLATE')]
        private readonly string $template,
    ) {}
}

ВажноНе путайте внедрение зависимостей и service locator. Правильно — просить конкретные зависимости в конструкторе: они видны в сигнатуре, их можно подменить в тесте. Получать контейнер целиком и доставать из него что попало ($container->get(...)) значит скрыть зависимости и лишиться проверки на этапе компиляции. В контроллерах Symfony это отчасти есть исторически, но в свои сервисы такое тащить не нужно.
АнтипаттернДелать сервис public: true, чтобы «достать его откуда угодно». По умолчанию сервисы приватные именно для того, чтобы обращения шли через внедрение: тогда компилятор контейнера может выбросить неиспользуемое, встроить зависимости и поймать ошибку на этапе сборки, а не в рантайме.
Типичный вопрос на собеседованииКак контейнер понимает, что подставить в конструктор?
По типам аргументов: тип сопоставляется с идентификатором сервиса или его алиасом. Скалярные значения по типу вывести нельзя — их задают через bind, аргументы сервиса или атрибут внедрения. Если у интерфейса несколько реализаций, нужен алиас по умолчанию либо явное указание для конкретного потребителя. В prod всё это разрешается один раз при компиляции контейнера.
ПрактикаЗаведите интерфейс с двумя реализациями, настройте алиас по умолчанию и подмену для одной консольной команды. Проверьте результат через debug:container и найдите оба сервиса в скомпилированном контейнере.

junior / данные / doctrine

Doctrine: сущности, репозитории, EntityManager

БазаСпрашивают всегда

Doctrine — реализация паттерна Data Mapper: сущность ничего не знает о базе, а за сохранение отвечает EntityManager. Это принципиальное отличие от Active Record и источник большинства вопросов на собеседовании.

phpСущность: обычный PHP-класс с разметкой
<?php
namespace App\Entity;

use Doctrine\DBAL\Types\Types;
use Doctrine\ORM\Mapping as ORM;

#[ORM\Entity(repositoryClass: PostRepository::class)]
#[ORM\Table(name: 'posts')]
#[ORM\Index(columns: ['status', 'published_at'], name: 'idx_posts_feed')]
class Post
{
    #[ORM\Id]
    #[ORM\GeneratedValue]
    #[ORM\Column]
    private ?int $id = null;

    #[ORM\Column(length: 200)]
    private string $title;

    #[ORM\Column(type: Types::TEXT)]
    private string $body;

    #[ORM\Column(length: 20, enumType: PostStatus::class)]
    private PostStatus $status = PostStatus::Draft;

    #[ORM\Column(nullable: true)]
    private ?\DateTimeImmutable $publishedAt = null;

    // Владелец связи: внешний ключ лежит в этой таблице
    #[ORM\ManyToOne(inversedBy: 'posts')]
    #[ORM\JoinColumn(nullable: false)]
    private User $author;

    // Обратная сторона: коллекция комментариев
    #[ORM\OneToMany(mappedBy: 'post', targetEntity: Comment::class, cascade: ['persist'])]
    private Collection $comments;

    public function __construct(string $title, string $body, User $author)
    {
        $this->title = $title;
        $this->body = $body;
        $this->author = $author;
        $this->comments = new ArrayCollection();
    }

    // Поведение живёт в сущности, а не в контроллере
    public function publish(\DateTimeImmutable $at): void
    {
        if ($this->status !== PostStatus::Draft) {
            throw new \DomainException('Публиковать можно только черновик');
        }

        $this->status = PostStatus::Published;
        $this->publishedAt = $at;
    }
}

        private readonly PostRepository $posts,
    ) {}

    public function create(string $title, string $body, User $author): Post
    {
        $post = new Post($title, $body, $author);

        $this->em->persist($post);   // «взять под наблюдение» — SQL ещё НЕ выполняется
        $this->em->flush();          // вот здесь всё накопленное уходит в базу

        return $post;
    }

    public function publish(Post $post): void
    {
        $post->publish(new \DateTimeImmutable());

        // persist не нужен: объект уже под наблюдением,
        // Doctrine сама увидит изменения при flush
        $this->em->flush();
    }
}

// Репозиторий: место для запросов, а не для бизнес-логики
final class PostRepository extends ServiceEntityRepository
{
    public function findPublished(int $limit = 20): array
    {
        return $this->createQueryBuilder('p')
            ->andWhere('p.status = :status')
            ->setParameter('status', PostStatus::Published)
            ->orderBy('p.publishedAt', 'DESC')
            ->setMaxResults($limit)
            ->getQuery()
            ->getResult();
    }
}
ВажноКлючевое отличие от Active Record: сущность не умеет сохранять себя. Doctrine хранит загруженные объекты в единице работы, при flush() сравнивает их с исходным состоянием и генерирует нужные запросы. Отсюда следствия: persist() нужен только для новых объектов; один flush() на всю операцию лучше десяти; а flush() внутри цикла — типичная причина медленного импорта.
АнтипаттернВызывать flush() в цикле на каждой итерации. Каждый вызов — это проход по всем отслеживаемым объектам и отдельная транзакция. Для массовых операций: пачки по несколько сотен объектов, flush() и clear() после каждой пачки — иначе память вырастет вместе с числом отслеживаемых сущностей.
Типичный вопрос на собеседованииЧто делает persist() и чем он отличается от flush()?
persist() сообщает менеджеру, что новый объект нужно отслеживать; запросов при этом не выполняется. flush() синхронизирует все изменения отслеживаемых объектов с базой в одной транзакции. Для уже загруженной сущности persist() не нужен: изменения обнаружатся автоматически при flush().
ПрактикаОпишите сущности блога со связями и перечислением статуса, сгенерируйте миграцию и наполните базу фикстурами. Затем включите панель профайлера и посмотрите, какие запросы порождает страница списка.

ВажноВалидатор в Symfony — самостоятельный компонент: он проверяет объекты по ограничениям и работает не только с формами. Типичный вопрос на собеседованииКак связаны формы и валидация?
Это два независимых компонента. Форма отвечает за преобразование данных запроса в объект и обратно, валидатор — за проверку объекта по ограничениям, объявленным атрибутами. Метод isValid() просто запускает валидатор для связанных данных. Поэтому валидацию можно использовать и без форм: в API, в консольных командах, в обработчиках сообщений.
ПрактикаСделайте форму создания записи через отдельный DTO с ограничениями и проверьте три сценария тестом: успех, ошибки валидации, отсутствие CSRF-токена. Затем переиспользуйте тот же DTO в API-эндпоинте.

#[AsCommand(name: 'app:posts:publish', description: 'Публикует запланированные записи')]
final class PublishScheduledCommand extends Command
{
    public function __construct(private readonly PostService $posts)
    {
        parent::__construct();
    }

    protected function configure(): void
    {
        $this->addOption('dry-run', null, InputOption::VALUE_NONE, 'Только показать');
    }

    protected function execute(InputInterface $input, OutputInterface $output): int
    {
        $io = new SymfonyStyle($input, $output);
        $due = $this->posts->findDueForPublishing();

        if ($due === []) {
            $io->success('Нечего публиковать');

            return Command::SUCCESS;
        }

        $io->progressStart(count($due));

        foreach ($due as $post) {
            if (!$input->getOption('dry-run')) {
                $this->posts->publish($post);
            }
            $io->progressAdvance();
        }

        $io->progressFinish();
        $io->success(sprintf('Опубликовано: %d', count($due)));

        return Command::SUCCESS;
    }
}

Контейнер глубже: теги, компиляция, ленивые сервисы

Ключевая темаСпрашивают всегда

Главный приём расширения в Symfony — теги. Вы объявляете интерфейс-точку расширения, все реализации автоматически получают тег, а потребитель получает их коллекцией. Так устроены сами подписчики событий, voters, нормализаторы сериализатора и команды.

phpТочка расширения на тегах
<?php
// 1. Интерфейс — контракт точки расширения
interface ExportFormatter
{
    public function supports(string $format): bool;
    public function format(iterable $rows): string;
}

// 2. Реализации — просто классы; autoconfigure сам повесит тег
final class CsvFormatter implements ExportFormatter { /* ... */ }
final class XlsxFormatter implements ExportFormatter { /* ... */ }

// 3. Потребитель получает все реализации одним аргументом
use Symfony\Component\DependencyInjection\Attribute\AutowireIterator;

final class Exporter
{
    public function __construct(
        #[AutowireIterator(ExportFormatter::class)]
        private readonly iterable $formatters,
    ) {}

    public function export(iterable $rows, string $format): string
    {
        foreach ($this->formatters as $formatter) {
            if ($formatter->supports($format)) {
                return $formatter->format($rows);
            }
        }

        throw new \InvalidArgumentException("Формат {$format} не поддерживается");
    }
}

phpCompiler pass: вмешательство в сборку контейнера
<?php
// Нужен, когда логику нельзя выразить конфигурацией:
// собрать карту «ключ → сервис», проверить обязательные реализации,
// подменить определение сервиса в зависимости от окружения.
final class RegisterFormattersPass implements CompilerPassInterface
{
    public function process(ContainerBuilder $container): void
    {
        if (!$container->has(Exporter::class)) {
            return;
        }

        $map = [];

        foreach ($container->findTaggedServiceIds('app.export_formatter') as $id => $tags) {
            foreach ($tags as $attributes) {
                $map[$attributes['format']] = new Reference($id);
            }
        }

        $container->findDefinition(Exporter::class)
                  ->setArgument('$formatters', $map);
    }
}

// Регистрируется в Kernel::build()
ВажноКонтейнер собирается один раз и компилируется в PHP-код. Всё, что вы делаете тегами и compiler pass'ами, выполняется на этапе сборки, а не на каждом запросе — поэтому такая расширяемость почти ничего не стоит в рантайме. Обратная сторона: изменения конфигурации требуют пересборки кэша, а в prod это шаг деплоя.
АнтипаттернВнедрять десяток сервисов в конструктор «на всякий случай», когда в конкретном вызове нужен один. Каждый аргумент создаётся при создании сервиса. Решение — коллекция по тегу с выбором нужного, локатор сервисов (создаёт по требованию) или пометка тяжёлых зависимостей как ленивых.
Типичный вопрос на собеседованииКак добавить свою реализацию в существующую точку расширения?
Реализовать нужный интерфейс — при включённом autoconfigure сервис получит соответствующий тег автоматически, и фреймворк подхватит его. Если нужна своя точка расширения, объявляется интерфейс, через _instanceof вешается тег, а потребитель получает коллекцию по тегу. Для сложной логики сборки используется compiler pass, работающий на этапе компиляции контейнера.
ПрактикаСделайте точку расширения «формат экспорта»: интерфейс, две реализации, потребитель с коллекцией по тегу и приоритетами. Проверьте порядок через debug:container --tag=app.export_formatter.

ВажноСобытия Doctrine (postPersist, postUpdate и другие) выполняются внутри flush(), то есть в открытой транзакции. Делать оттуда внешние вызовы, отправлять письма или дополнительно вызывать flush() — источник трудноуловимых проблем. Максимум — заполнение технических полей; всё остальное публикуйте после успешного сохранения.
АнтипаттернПрятать основной сценарий в цепочку событий: заказ создаётся в одном подписчике, оплата в другом, письмо в третьем. Через полгода никто не может ответить, что происходит при оформлении. События — для дополнительных эффектов; основной путь должен читаться сверху вниз в одном классе.
Типичный вопрос на собеседованииЧем слушатель отличается от подписчика?
Технически ничем: оба вызываются диспетчером. Разница в том, где объявлена подписка. У подписчика она внутри класса, поэтому по коду сразу видно, на что он реагирует. У слушателя подписка задаётся снаружи — конфигурацией или атрибутом, что удобно, когда её нужно включать по окружению или менять без правки класса.
ПрактикаРазнесите оформление заказа: основной сценарий в отдельном классе, а уведомление и аналитику — в слушателей события. Убедитесь тестом, что при падении слушателя заказ всё равно сохраняется, и проверьте порядок вызовов через debug:event-dispatcher.

Doctrine: связи, N+1, объёмы

Ключевая темаСпрашивают всегда

Doctrine возвращает не строки, а объекты, и делает это лениво: связь загружается в момент первого обращения. Отсюда главная проблема производительности — N+1.

phpN+1 и жадная загрузка через fetch join
<?php
// ПЛОХО: 1 запрос за постами + по запросу за автором на каждый = 101
$posts = $repo->findBy(['status' => PostStatus::Published], ['publishedAt' => 'DESC'], 100);
foreach ($posts as $post) {
    echo $post->getAuthor()->getName();       // ленивая загрузка — новый запрос
}

// ХОРОШО: один запрос с присоединением и выборкой связанных сущностей
public function findFeed(int $limit): array
{
    return $this->createQueryBuilder('p')
        ->addSelect('a')                  // ← без этого join не заполнит объекты
        ->innerJoin('p.author', 'a')
        ->andWhere('p.status = :s')->setParameter('s', PostStatus::Published)
        ->orderBy('p.publishedAt', 'DESC')
        ->setMaxResults($limit)
        ->getQuery()
        ->getResult();
}

// Счётчик — подзапросом, а не загрузкой коллекции в память
$qb->addSelect('(SELECT COUNT(c.id) FROM App\Entity\Comment c WHERE c.post = p) AS commentsCount');

Типичный вопрос на собеседованииЧто такое N+1 в Doctrine и как его убрать?
Это ленивая загрузка связей: один запрос за списком и по запросу на каждое обращение к связи. Убирается присоединением с выборкой связанной сущности (join плюс addSelect), агрегатами вместо загрузки коллекций и гидрацией в массивы там, где объекты не нужны. Находится через профайлер или лог запросов, а лучше — тестом, считающим их количество.
ПрактикаНайдите страницу с N+1 через профайлер, перепишите запрос с присоединением и сравните число запросов. Затем напишите импорт 500 000 записей с потоковым обходом и очисткой, замерив пиковую память.

phpVoter: права на конкретный объект
<?php
use Symfony\Component\Security\Core\Authorization\Voter\Voter;

/** @extends Voter<string, Post> */
final class PostVoter extends Voter
{
    public const VIEW = 'view';
    public const EDIT = 'edit';
    public const DELETE = 'delete';

    protected function supports(string $attribute, mixed $subject): bool
    {
        return in_array($attribute, [self::VIEW, self::EDIT, self::DELETE], true)
            && $subject instanceof Post;
    }

    protected function voteOnAttribute(string $attribute, mixed $subject, TokenInterface $token): bool
    {
        $user = $token->getUser();

        // Публичное чтение доступно и гостю
        if ($attribute === self::VIEW && $subject->isPublished()) {
            return true;
        }

        if (!$user instanceof User) {
            return false;
        }

        return match($attribute) {
            self::VIEW, self::EDIT => $subject->getAuthor() === $user,
            self::DELETE => $subject->getAuthor() === $user
                && $subject->getCreatedAt() > new \DateTimeImmutable('-24 hours'),
        };
    }
}

// Использование: контроллер, атрибут, шаблон
$this->denyAccessUnlessGranted(PostVoter::EDIT, $post);

#[IsGranted('edit', subject: 'post')]
public function edit(Post $post): Response { /* ... */ }
ВажноПравило access_control работает по URL и роли — это грубый фильтр. Ответ на вопрос «может ли этот пользователь редактировать эту запись» дают voters. И самое надёжное — выбирать из базы сразу только доступные записи: тогда забытая проверка не превращается в утечку данных.
АнтипаттернПроверки вида if ($user->getRole() === 'manager'), разбросанные по контроллерам и шаблонам. Через год ролей пять, условия расползлись по сотне мест, а изменить правило нельзя без полного обхода кода. Правила живут в voters, роль — лишь один из входов в решение.
Типичный вопрос на собеседованииЗачем нужны voters, если есть access_control?
Потому что это разные уровни. access_control закрывает раздел по URL и роли, ничего не зная об объектах. Voter отвечает на вопрос о конкретном объекте: владелец ли пользователь, не истёк ли срок, в каком статусе запись. Voters переиспользуются в контроллере, атрибуте и шаблоне, и правило описано в одном месте.
ПрактикаНапишите voter с правилами просмотра, редактирования и удаления, подключите его в контроллере и шаблоне. Покройте тестами: владелец — 200, чужой — 403, гость — редирект или 401, а список содержит только доступные записи.

API: DTO, сериализация, контракт

Прикладное

Symfony даёт готовые механизмы для API без лишних слоёв: объект запроса собирается из тела и проверяется валидатором, ответ формируется сериализатором с группами. Сущности при этом наружу не отдаются.

Messenger: очереди и фоновая обработка

Ключевая темаСпрашивают всегда

Правило то же, что и в любом веб-приложении: всё, что дольше пары сотен миллисекунд и не нужно пользователю немедленно, уходит в фон. В Symfony это Messenger — шина сообщений с транспортами, повторами и обработкой сбоев.

phpСообщение и обработчик
<?php
// Сообщение — простой объект с данными. Внутрь кладут идентификаторы,
// а не сущности: пока задача ждёт в очереди, данные могут измениться.
final class GenerateInvoice
{
    public function __construct(public readonly int $orderId) {}
}

use Symfony\Component\Messenger\Attribute\AsMessageHandler;

#[AsMessageHandler]
final class GenerateInvoiceHandler
{
    public function __construct(
        private readonly OrderRepository $orders,
        private readonly InvoiceBuilder $builder,
    ) {}

    public function __invoke(GenerateInvoice $message): void
    {
        $order = $this->orders->find($message->orderId);

        // Заказ мог быть удалён, пока сообщение ждало обработки
        if ($order === null) {
            return;
        }

        // Идемпотентность: обработчик может быть вызван повторно
        if ($order->hasInvoice()) {
            return;
        }

        $this->builder->build($order);
    }
}

// Отправка
$bus->dispatch(new GenerateInvoice($order->getId()));
$bus->dispatch(new GenerateInvoice($id), [new DelayStamp(300_000)]);   // через 5 минут

АнтипаттернОтправлять сообщение до flush(). При быстром воркере обработчик стартует раньше, чем данные окажутся в базе, и не находит запись. Отправляйте после успешного сохранения — либо используйте штатное средство отложенной отправки в рамках текущей транзакции.
Типичный вопрос на собеседованииЧто произойдёт, если обработчик упадёт?
Сообщение вернётся в транспорт и будет повторено согласно стратегии: заданное число попыток с растущей задержкой. После исчерпания попыток оно попадёт в транспорт сбоев, откуда его можно посмотреть и перезапустить вручную. Поэтому обработчик обязан быть идемпотентным, а окончательные сбои — попадать в мониторинг, а не только в таблицу.
ПрактикаВынесите генерацию документа в Messenger с повторами и очередью сбоев, разделите очереди по критичности. Сымитируйте падение внешнего сервиса и проследите путь сообщения: повторы, попадание в сбойные, перезапуск. Проверьте, что повторная обработка не создаёт дублей.

Кэш: приложение и HTTP

phpКэш приложения: получить или вычислить
<?php
use Symfony\Contracts\Cache\CacheInterface;
use Symfony\Contracts\Cache\ItemInterface;

final class CategoryTree
{
    public function __construct(
        private readonly CacheInterface $cache,
        private readonly CategoryRepository $categories,
    ) {}

    public function get(): array
    {
        return $this->cache->get('categories.tree', function (ItemInterface $item) {
            $item->expiresAfter(3600);
            $item->tag(['categories']);          // для точечного сброса по тегу

            return $this->categories->buildTree();
        });
    }

    {
        $this->cache->invalidateTags(['categories']);
    }

use Symfony\Component\HttpKernel\Attribute\Cache;

public function show(Post $post, Request $request): Response
{
    $response = new Response();
    $response->setEtag(md5($post->getUpdatedAt()->format('U')));
    $response->setLastModified($post->getUpdatedAt());
    $response->setPublic();

    if ($response->isNotModified($request)) {
        return $response;      // 304: тело не формируется и не передаётся
    }

    return $this->render('post/show.html.twig', ['post' => $post], $response);
}

HTTP-кэш живёт перед приложением: при попадании запрос не доходит до PHP вообще — это самый дешёвый вариант, но подходит только для одинакового для всех содержимого. Кэш приложения работает внутри и сохраняет результаты вычислений и запросов, помогая и на персональных страницах. В реальном проекте используют оба уровня плюс кэш контейнера и opcache.
ПрактикаЗакэшируйте самый тяжёлый участок страницы с TTL и тегами, добавьте сброс по событию изменения. Отдельно включите условные запросы на детальной странице и убедитесь по заголовкам, что повторное обращение возвращает 304.

Долгоживущие рантаймы и состояние сервисов

Архитектура

Symfony умеет работать не только под FPM: компонент рантайма позволяет запустить то же приложение в долгоживущем процессе. Выигрыш в том, что ядро и контейнер поднимаются один раз, а не на каждый запрос. Цена — приложение больше не «обнуляется» после ответа.

текстЧто ломается и как с этим жить
СОСТОЯНИЕ МЕЖДУ ЗАПРОСАМИ
  • сервис, запомнивший текущего пользователя или Request,
    начнёт отдавать чужие данные;
  • статические свойства и накопленные коллекции не очищаются;
  • менеджер сущностей после исключения закрывается — и остаётся
    закрытым для следующих запросов, если его не пересоздать.
  → сервисы с состоянием реализуют сброс и помечаются как сбрасываемые;
    зависимости, связанные с запросом, не сохраняются в свойствах.

УТЕЧКИ ПАМЯТИ
  • раньше их убирал конец запроса, теперь процесс растёт часами.
  → ограничение числа обработанных запросов и времени жизни процесса,
    потолок памяти, наблюдение за графиком.

они долгоживущие с самого начала, просто про это реже помнят.

КОГДА ОКУПАЕТСЯ: когда узкое место — загрузка приложения.
Если 70% времени уходит в базу, выигрыш будет скромным.

<?php
use Symfony\Contracts\Service\ResetInterface;

// Такой сервис безопасен и под FPM, и в долгоживущем процессе:
// фреймворк вызовет reset() между запросами.
final class RequestContext implements ResetInterface
{
    private ?User $currentUser = null;
    private array $collectedEvents = [];

    public function reset(): void
    {
        $this->currentUser = null;
        $this->collectedEvents = [];
    }
}
ВажноСамая частая ловушка в долгоживущих процессах и воркерах — закрытый менеджер сущностей. Любое исключение при работе с базой закрывает его, и все последующие обращения падают, пока процесс не перезапустят. Поэтому воркеры перезапускают по лимитам, а обработчики пишут так, чтобы падение одного сообщения не отравляло остальные.
Типичный вопрос на собеседованииЧто нужно проверить перед переходом на долгоживущий рантайм?
Нет ли сервисов, хранящих данные запроса между вызовами, — они начнут смешивать пользователей. Есть ли сброс состояния у тех, кому он нужен. Как ведёт себя менеджер сущностей после ошибок. Нет ли утечек памяти: процесс теперь живёт часами. И главное — измерить, что узкое место действительно в загрузке приложения, а не в базе.
ПрактикаНайдите в проекте сервисы, хранящие состояние между вызовами, и реализуйте у них сброс. Затем запустите воркер Messenger на сутки с лимитами и постройте график памяти — утечка видна сразу.

phpБлокировка между серверами
<?php
use Symfony\Component\Lock\LockFactory;

// Хранилище блокировок должно быть общим для всех узлов,
// иначе «блокировка» защищает только один сервер от самого себя.
final class ReindexCommand extends Command
{
    public function __construct(private readonly LockFactory $locks)
    {
        parent::__construct();
    }

    protected function execute(InputInterface $in, OutputInterface $out): int
    {
        $lock = $this->locks->createLock('catalog.reindex', ttl: 3600);

        if (!$lock->acquire()) {
            $out->writeln('Переиндексация уже выполняется, выходим');

            return Command::SUCCESS;
        }

        try {
            $this->reindex();
        } finally {
            $lock->release();
        }

        return Command::SUCCESS;
    }
}
ВажноРазделяйте очереди по критичности. Одна общая очередь означает, что ночной пересчёт каталога на 200 000 товаров задержит письмо с кодом подтверждения. Минимум — быстрая очередь для пользовательских сценариев и медленная для массовых операций, с отдельными воркерами и разным числом процессов.
Типичный вопрос на собеседованииЧто нужно изменить, чтобы приложение работало на нескольких серверах?
Убрать локальное состояние: сессии и кэш в общее хранилище, файлы в объектное, очереди в общий брокер, блокировки и счётчики лимитов — тоже в общее хранилище, логи в централизованный сбор. Затем убедиться, что деплой согласованно обновляет все узлы и перезапускает воркеры.
ПрактикаРазверните проект на двух узлах за балансировщиком и найдите всё, что сломается: вход в систему, загрузка файла, кэш, планировщик, ограничение частоты. Исправьте и проверьте, что выключение одного узла не ломает сценарии.

Типичный вопрос на собеседованииКогда стоит выносить часть системы в отдельный сервис?

ПрактикаВыделите один домен в отдельный каталог с доменным слоем без зависимостей от фреймворка и Doctrine. Добавьте в CI проверку, которая падает при появлении запрещённой зависимости.

Минимальный набор для прода:

  • Трекер ошибок с группировкой и оповещением: логи, которые никто не читает, — не мониторинг.
  • Метрики приложения: время ответа по перцентилям, доля ошибок, число запросов к БД на обращение.
  • Метрики очередей: длина, время ожидания, доля сбоев, возраст самого старого сообщения — растущая очередь предвещает инцидент.
  • Health-check для оркестратора: проверка доступности базы и критичных зависимостей.
  • Алерты по симптомам: рост ошибок, деградация времени ответа, очередь выше порога, место на диске.
ВажноОбработчик, придерживающий записи до появления ошибки, очень удобен, но у него есть цена: при массовых ошибках он вываливает огромный объём логов. Исключайте из него шум вроде 404 и следите за объёмом — иначе первый же всплеск ошибок заполнит диск.
Типичный вопрос на собеседованииКак вы узнаёте о поломке на проде?
Из алертов: рост доли ошибок и времени ответа, всплеск сбойных сообщений, рост длины и возраста очереди, ошибки в трекере с группировкой. Дальше — сборка полной картины по сквозному идентификатору запроса в структурированных логах. Если единственный сигнал — обращения пользователей, наблюдаемости нет.
ПрактикаДобавьте сквозной идентификатор запроса во все записи и во внешние вызовы, переведите три ключевых места на структурированные события и настройте алерт на рост доли ошибок. Проверьте срабатывание, сломав фичу на стенде.

Версии, устаревания и обновления

Архитектура

У Symfony предсказуемый график выпусков: минорные версии выходят регулярно и обратно совместимы, мажорные — раз в несколько лет, а отдельные версии получают статус долгосрочной поддержки с более длинным сроком исправлений. Это делает планирование обновлений возможным, если им заниматься заранее.

текстСтратегия, которая работает
ПОСТОЯННО
  • обновлять минорные версии регулярно, а не копить на год;
  • держать тесты зелёными — это единственная страховка при обновлении;
  • следить за журналом устареваний: в dev и test каждое использование
    устаревшего API логируется, и это готовый список работ.

ПЕРЕД МАЖОРНЫМ ОБНОВЛЕНИЕМ
  1. Обновиться до последней минорной версии текущей мажорной ветки.
  2. Свести к нулю предупреждения об устареваниях: в новой мажорной
     версии удалено ровно то, о чём предупреждали.
  3. Поднять версию PHP, если новая ветка требует более свежую.
  4. Проверить сторонние бандлы: часть может не поддерживать
     новую версию — это самая частая причина застрять.
  5. Обновлять в отдельной ветке, выкатывать отдельным релизом
     без функциональных изменений.

ПОЛЕЗНО ЗНАТЬ
  • рецепты Flex обновляются отдельной командой: изменения в конфигурации
    приходят не с обновлением пакета, а с обновлением рецепта;
  • автоматический рефакторинг помогает с типовыми заменами,
    но требует ревью каждого изменения.

ВажноУстаревания в Symfony — не косметика, а спецификация будущего обновления. Всё, о чём предупреждает журнал в текущей мажорной ветке, будет удалено в следующей. Проект, где предупреждения игнорируют годами, обновляется не за неделю, а за квартал — и обычно под давлением окончания поддержки.
Типичный вопрос на собеседованииКак обновить мажорную версию Symfony на большом проекте?
Сначала обновиться до последней минорной версии текущей ветки и убрать все предупреждения об устареваниях — именно это удаляется в новой мажорной. Затем проверить требования по версии PHP и совместимость сторонних бандлов, обновиться в отдельной ветке при зелёных тестах, отдельно обновить рецепты конфигурации и выкатить релизом без функциональных изменений, чтобы при проблемах было понятно, что откатывать.

60 вопросов с эталонными ответами

Ответы намеренно короткие — это каркас, а не пересказ документации. Структура сильного ответа: определение → как работает → пример из практики → компромисс.

Junior · 20 вопросов

Junior
  1. Что происходит от запроса до ответа?Единая точка входа создаёт ядро, оно вызывает обработку запроса и рассылает события: определение маршрута и аутентификация, поиск контроллера, разрешение аргументов, вызов контроллера, при необходимости преобразование результата в ответ, финальная правка ответа. После отправки — событие завершения, при исключении — событие обработки ошибки.
  2. Что такое HttpKernel?Компонент, превращающий объект запроса в объект ответа. Вся структура приложения строится вокруг этого преобразования, а расширение делается подпиской на события, которые ядро рассылает по ходу обработки.
  3. Зачем нужны события ядра?Чтобы добавлять поведение всем запросам, не трогая контроллеры: аутентификация, локаль, заголовки, логирование, обработка исключений. Слушатель может даже вернуть ответ на раннем этапе и оборвать дальнейшую обработку.
  4. Чем окружения отличаются друг от друга?Набором конфигурации и поведением кэша: в разработке контейнер и маршруты пересобираются при изменениях, в продакшене компилируются заранее и не проверяются. Тестовое окружение обычно использует свою базу и отключённые внешние интеграции.
  5. Зачем прогревать кэш на проде?Потому что контейнер, маршруты и шаблоны компилируются в файлы. Без прогрева первый запрос после деплоя будет собирать их сам, а при неверных правах — упадёт. Прогрев в правильном окружении — обязательный шаг выкатки.
  6. Как настраиваются маршруты?Обычно атрибутами над классом и методами контроллера: путь, имя, разрешённые методы, ограничения параметров. Альтернатива — файлы конфигурации, что удобно для маршрутов сторонних бандлов.
  7. Как сущность попадает в аргумент контроллера?Её находит специальный резолвер аргументов по параметру маршрута, при отсутствии записи возвращается 404. Права доступа при этом не проверяются — это отдельный шаг.
  8. Что такое autowiring?Автоматическая подстановка зависимостей по типам аргументов конструктора: контейнер сопоставляет тип с сервисом или его алиасом. Скалярные значения так подставить нельзя — их задают явно.
  9. Что делать, если у интерфейса две реализации?Указать алиас по умолчанию, чтобы контейнер знал, что подставлять при запросе интерфейса, и при необходимости задать другую реализацию конкретному потребителю через аргументы сервиса.
  10. Чем persist() отличается от flush()?Первый берёт новый объект под наблюдение, запросов при этом не выполняется. Второй синхронизирует все изменения отслеживаемых объектов с базой в одной транзакции. Для уже загруженной сущности persist() не нужен.
  11. Чем Doctrine отличается от Active Record?Это Data Mapper: сущность — обычный объект, ничего не знающий о базе, а сохранением занимается менеджер сущностей. В Active Record модель сама умеет себя сохранять. Отсюда разные подходы к тестированию, к доменной логике и к пакетным операциям.
  12. Зачем репозиторий, если есть менеджер сущностей?Репозиторий — место для запросов конкретной сущности: там живут методы выборки с понятными именами. Это избавляет от построения одинаковых запросов по всему коду и делает их тестируемыми.
  13. Как связаны формы и валидация?Это независимые компоненты. Форма преобразует данные запроса в объект и обратно, валидатор проверяет объект по ограничениям, объявленным атрибутами. Поэтому валидацию можно использовать и без форм — в API и консольных командах.
  14. Почему форму лучше связывать с DTO, а не с сущностью?Иначе структура базы становится контрактом формы, а лишние поля в запросе могут попасть в сущность. Отдельный объект под ввод разрывает эту связь и делает набор допустимых полей явным.
  15. Как Twig защищает от XSS?Автоматическим экранированием вывода в HTML-контексте. Защита не работает при явном отключении экранирования, при подстановке значений в JavaScript или атрибуты без соответствующей стратегии и при сборке HTML вручную в коде.
  16. Где хранить настройки и секреты?Значения по умолчанию — в файле окружения, который коммитится; локальные переопределения — в файле, который не коммитится. На проде значения приходят из переменных окружения, а секреты — из зашифрованного хранилища. Боевые ключи в репозитории недопустимы.
  17. Как узнать, какие маршруты и сервисы есть в приложении?Командами отладки: список маршрутов, список сервисов и параметров, список типов, доступных для внедрения, подписчики конкретного события. Это же первый шаг, когда что-то «не подставляется» или «не срабатывает».
  18. Как написать консольную команду?Классом с атрибутом команды: имя, описание, аргументы и опции в настройке, логика в методе выполнения, зависимости — через конструктор. Возвращается код завершения, а вывод оформляется стилевым помощником.
  19. Чем отличается запуск команды в разных окружениях?Окружение задаётся отдельно и определяет конфигурацию и кэш. Команда, запущенная без указания продакшн-окружения, отработает в окружении разработки — со своей базой и своими настройками.
  20. Что такое бандл?Способ упаковать переиспользуемый код с его конфигурацией и точками расширения для распространения между проектами. Для разделения одного приложения бандлы сегодня не нужны — достаточно каталогов и пространств имён.

Middle · 20 вопросов

Middle
  1. Как расширить готовый механизм фреймворка?Реализовать нужный интерфейс: при включённой автоконфигурации сервис получит соответствующий тег и будет подхвачен. Для собственной точки расширения объявляют интерфейс, вешают тег через правило по типу и получают коллекцию в потребителе.
  2. Что такое compiler pass и когда он нужен?Класс, вмешивающийся в сборку контейнера: он видит все определения сервисов и может их менять. Нужен, когда логику нельзя выразить конфигурацией — собрать карту «ключ → сервис», проверить обязательные реализации, подменить определение по условию.
  3. Что даёт компиляция контейнера?Всё разрешение зависимостей происходит один раз при сборке, а в рантайме выполняется обычный сгенерированный PHP-код без рефлексии. Поэтому теги и проходы компилятора почти ничего не стоят на запросе, но изменение конфигурации требует пересборки кэша.
  4. Чем слушатель отличается от подписчика?Только тем, где объявлена подписка: у подписчика — внутри класса, поэтому сразу видно, на что он реагирует; у слушателя — снаружи, конфигурацией или атрибутом, что удобно для включения по окружению.
  5. Зачем приоритеты у слушателей?Они задают порядок вызова для одного события. Это важно, когда один слушатель должен отработать до другого — например, установить контекст до того, как им воспользуются. Порядок смотрится командой отладки диспетчера.
  6. Чем опасны события Doctrine?Они выполняются внутри сохранения, то есть в открытой транзакции. Внешние вызовы, отправка писем или дополнительное сохранение оттуда приводят к долгим транзакциям и трудноуловимым ошибкам. Там уместны только технические поля.
  7. Что такое N+1 и как его убрать в Doctrine?Ленивая загрузка связей: один запрос за списком и по запросу на каждое обращение. Убирается присоединением с явной выборкой связанной сущности, агрегатами вместо загрузки коллекций и гидрацией в массивы там, где объекты не нужны.
  8. Почему join сам по себе не решает N+1?Потому что без добавления связанной сущности в выборку соединение используется только для фильтрации, а объекты всё равно догружаются отдельными запросами. Нужно явно включить связанные данные в результат.
  9. Как обработать миллион записей?Потоковым обходом результата запроса с периодическими сохранением и очисткой менеджера: иначе все загруженные объекты остаются под наблюдением и память растёт линейно. Если объекты не нужны — гидрация в массивы или прямой SQL.
  10. Что происходит при очистке менеджера сущностей?Он перестаёт отслеживать ранее загруженные объекты. Это освобождает память, но делает прежние объекты «отсоединёнными»: изменения в них больше не будут сохранены, а связи не догрузятся. После очистки работают с заново загруженными данными.
  11. Зачем voters, если есть access_control?Это разные уровни. Правила по URL и ролям закрывают раздел целиком и ничего не знают об объектах. Voter отвечает на вопрос про конкретный объект: владелец ли пользователь, в каком статусе запись, не истёк ли срок. И переиспользуется в контроллере, атрибуте и шаблоне.
  12. Что такое firewall и зачем их несколько?Firewall описывает, как аутентифицируются запросы по определённому шаблону пути. Их делают несколько, потому что механизмы разные: веб-часть работает с сессией и формой входа, API — без состояния и по токену. Срабатывает первый подходящий по шаблону.
  13. Как принять и проверить JSON-запрос?Объявить DTO с ограничениями и пометить аргумент контроллера атрибутом отображения тела запроса: фреймворк десериализует тело, прогонит валидацию и вернёт 422 при ошибках. Контроллер получает уже корректный типизированный объект.
  14. Почему нельзя отдавать сущность напрямую в API?Ответ становится зеркалом схемы базы: любое изменение колонок меняет контракт, а служебные поля утекают клиенту. Группы сериализации или отдельные выходные DTO делают контракт явным и независимым от схемы.
  15. Что произойдёт, если обработчик сообщения упадёт?Сообщение вернётся в транспорт и будет повторено по заданной стратегии с растущей задержкой. После исчерпания попыток оно попадёт в транспорт сбоев, откуда его можно посмотреть и перезапустить. Поэтому обработчик обязан быть идемпотентным.
  16. Почему в сообщение нельзя класть сущность?Объект сериализуется при отправке, а обрабатывается позже: данные успеют устареть, а связи корректно не восстановятся. Передают идентификатор и загружают актуальное состояние в обработчике, проверяя, что запись ещё существует.
  17. Почему сообщение стоит отправлять после сохранения?Иначе воркер может начать обработку раньше, чем данные окажутся в базе, и не найдёт запись. Отправка после успешной фиксации транзакции убирает эту гонку.
  18. Чем HTTP-кэш отличается от кэша приложения?HTTP-кэш живёт перед приложением: при попадании запрос вообще не доходит до PHP, но подходит только для одинакового для всех содержимого. Кэш приложения работает внутри и сохраняет результаты вычислений, помогая и на персональных страницах.
  19. Чем отличаются виды тестов в Symfony?Модульные обходятся без ядра и проверяют чистую логику. Интеграционные поднимают ядро и работают с реальными сервисами и базой. Функциональные дополнительно выполняют полноценные запросы через ядро и проверяют маршруты, права, валидацию и формат ответа.
  20. Как подменить внешний сервис в тесте?Заменить его в контейнере тестового окружения заглушкой, для HTTP использовать мок-клиент с заранее заданными ответами, для очереди — транспорт в памяти и проверку факта отправки, для времени — управляемые часы. Тесты не должны ходить в сеть.

  1. Эндпоинт отвечает 3 секунды. Порядок действий?Профайлер: число запросов и их время. Обычно N+1 или запрос без индекса. Дальше — гидрация (нужны ли объекты), вынос синхронных внешних вызовов в фон, кэш тяжёлых участков. Инфраструктура в конце, с замером после каждого шага.
  2. Что даёт прогрев кэша и предзагрузка?Прогрев компилирует контейнер, маршруты и шаблоны заранее, чтобы этого не делал первый запрос. Предзагрузка держит скомпилированные классы в памяти процессов, ускоряя старт запроса. Оба механизма требуют перезапуска процессов при выкатке нового кода.
  3. Почему профайлер не оставляют включённым на проде?Он собирает и хранит подробные данные по каждому запросу — это заметная нагрузка и место на диске, а также потенциальная утечка внутренней информации. На проде нужны лёгкие метрики и лог медленных запросов, а профайлер — точечно и с ограничением доступа.
  4. Что ломается при переходе на долгоживущий рантайм?Всё, что опиралось на смерть процесса после ответа: сервисы с состоянием начинают смешивать данные пользователей, утечки накапливаются, менеджер сущностей после ошибки остаётся закрытым. Решается сбросом состояния, лимитами на процесс и аккуратной обработкой ошибок.
  5. Как сделать сервис безопасным для долгоживущего процесса?Не хранить в нём данные запроса, а если состояние необходимо — реализовать сброс, чтобы фреймворк очищал его между запросами. Зависимости, связанные с запросом, получать в момент обработки, а не запоминать в свойствах.
  6. Что нужно, чтобы приложение работало на нескольких серверах?Убрать локальное состояние: сессии, кэш, блокировки и счётчики лимитов — в общее хранилище, файлы — в объектное, очереди — в общий брокер, логи — в централизованный сбор. Плюс согласованный деплой всех узлов и перезапуск воркеров.
  7. Зачем разделять очереди?Чтобы массовая фоновая работа не задерживала пользовательские сценарии. Минимум — быстрая очередь для писем и уведомлений и медленная для пересчётов, с отдельными воркерами и разным числом процессов.
  8. Как защититься от параллельного запуска задачи на кластере?Блокировкой с общим хранилищем: задача пытается захватить лок и завершается, если он занят. Локальное хранилище блокировок защищает только один сервер от самого себя, что на кластере бесполезно.
  9. Стоит ли изолировать домен от фреймворка?Частично и осознанно: правила предметной области и вычисления имеет смысл держать без зависимостей от HTTP и ORM — они тестируются мгновенно и переживают обновления. Контроллеры, конфигурация и миграции остаются фреймворковыми.
  10. Нужны ли свои бандлы внутри приложения?Обычно нет. Бандл — механизм распространения кода между проектами со своей конфигурацией и точками расширения. Для внутреннего разделения достаточно каталогов, пространств имён и правил в конфигурации сервисов, а границы удерживаются проверкой зависимостей в CI.
  11. Как удержать границы модулей?Сделать их нарушение невозможным незаметно: публичные контракты, запрет обращаться к чужим сущностям напрямую и автоматическая проверка зависимостей в CI. Договорённость без проверки не переживает первый срочный релиз.
  12. Какие уязвимости чаще всего находят в Symfony-проектах?Забытая проверка прав на объект при найденной по маршруту сущности; утечка полей через сериализацию сущностей; инъекции в собранных вручную запросах и в сортировке по полю из запроса; доступный профайлер или включённая отладка на проде; секреты в репозитории; устаревшие зависимости.
  13. Как хранить секреты?В переменных окружения на проде и в зашифрованном хранилище секретов, где в репозиторий попадают только шифротексты, а приватный ключ хранится отдельно. Файлы окружения с боевыми значениями в репозитории недопустимы: они остаются в истории навсегда.
  14. Что должно быть в логах и чего в них быть не должно?Должно: имя события, идентификаторы сущностей и пользователя, длительность, сквозной идентификатор запроса — в структурированном виде. Не должно: паролей, токенов, персональных данных сверх необходимого. Маскирование настраивается централизованно.
  15. Как вы узнаёте о поломке на проде?Из алертов: рост доли ошибок и времени ответа, всплеск сбойных сообщений, рост длины и возраста очереди. Дальше — сборка картины по сквозному идентификатору запроса. Если единственный сигнал — обращения пользователей, наблюдаемости нет.
  16. Опишите деплой без простоя.Сборка релиза отдельно, прогрев кэша для нужного окружения, применение только совместимых миграций, атомарное переключение симлинка, перезагрузка процессов PHP, остановка воркеров для перезапуска на новом коде, проверка health-check и метрик. Откат — обратное переключение симлинка.
  17. Почему после деплоя работает старый код?Три обычные причины: не перезагружены процессы PHP и не сброшен кэш опкодов, не остановлены воркеры очередей, кэш собран не для того релиза или не в том окружении. Проверяются именно в этом порядке.
  18. Что делать с предупреждениями об устареваниях?Считать их спецификацией следующего мажорного обновления: всё, о чём предупреждают сейчас, будет удалено. Их сводят к нулю до обновления, опираясь на журнал в окружениях разработки и тестов и на сводку после прогона тестов.
  19. Как обновить мажорную версию на большом проекте?Сначала до последней минорной версии текущей ветки и обнуление устареваний. Затем проверка требований к версии PHP и совместимости сторонних бандлов, обновление в отдельной ветке при зелёных тестах, отдельное обновление рецептов конфигурации и выкатка релизом без функциональных изменений.
  20. Спроектируйте обработку 200 000 заказов за ночь.Ожидается разговор о компромиссах: потоковый обход и обработка пачками с очисткой менеджера; параллелизм несколькими воркерами с разбиением диапазона по ключу; идемпотентность и возобновляемость с сохранением позиции; массовые операции вместо построчных; контроль нагрузки на базу и лага реплик; лимиты памяти и плановый перезапуск воркеров; логирование прогресса и алерт на остановку.

Как отвечать на собеседовании

Бонус
  • Структура ответа: определение в одну фразу → как работает внутри → пример из вашей практики → компромисс или ограничение. Последний пункт отличает middle от senior.
  • Отвечайте про механизм, а не про название. Вопрос «что такое voter» проверяет понимание модели прав. Ответ «класс для проверки доступа» слабый; «точка расширения, куда система авторизации обращается за решением по конкретному объекту, и её же переиспользуют контроллер, атрибут и шаблон» — сильный.
  • Держите в голове SQL под ORM. Половина вопросов по Doctrine на самом деле про то, какие запросы уйдут в базу и когда.
  • Говорите цифрами: «страница с 200 запросов до 4», «время ответа с 3,1 с до 210 мс», «память импорта с 900 МБ до 40 МБ».
  • Не бойтесь сказать «здесь это лишнее». Отказ от бандла, от лишнего слоя или от смены рантайма с внятным обоснованием — сильный ответ: он показывает, что вы считаете стоимость сложности.
  • Приносите артефакты: отчёт по оптимизации, план обновления версии, документ готовности к проду, набор тестов. Они превращают рассказ в доказательство.
