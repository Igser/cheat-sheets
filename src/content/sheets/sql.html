junior / основы / что такое БД

База данных, СУБД и почему PHP-разработчику это важно

База

База данных — организованное хранилище данных. СУБД (MySQL, PostgreSQL, SQLite) — программа, которая этим хранилищем управляет: обрабатывает запросы, следит за целостностью, обеспечивает параллельный доступ и переживает перезапуск сервера.

PHP-процесс живёт миллисекунды и умирает после ответа — у него нет памяти между запросами. Всё состояние приложения (пользователи, заказы, деньги) живёт в БД. Поэтому качество PHP-приложения на 80% определяется тем, как оно разговаривает с базой.

Реляционная модель строится на трёх идеях: данные лежат в таблицах, между таблицами есть связи по ключам, а доступ идёт через декларативный язык SQL — вы описываете что хотите получить, а планировщик решает как это достать.

sqlПервое знакомство: клиент → сервер → результат
-- Одна строка SQL заменяет десятки строк PHP-цикла:
SELECT id, email, created_at
FROM users
WHERE is_active = 1
ORDER BY created_at DESC
LIMIT 10;
ВажноФильтрация, сортировка и агрегация почти всегда должны происходить в БД, а не в PHP. Выгрузить 100 000 строк в память и отфильтровать array_filter — самый частый способ уронить приложение по памяти и времени.
Типичный вопрос на собеседованииЧем отличается база данных от СУБД?
База данных — это сами данные и их структура. СУБД — программное обеспечение, которое их обслуживает: парсит SQL, строит план выполнения, управляет транзакциями, блокировками, кэшем и хранением на диске.
ПрактикаУстановите MySQL или PostgreSQL локально (лучше через Docker). Создайте базу blog, подключитесь консольным клиентом и выполните SELECT VERSION();. Научитесь смотреть список таблиц: SHOW TABLES; в MySQL, \dt в psql.

junior / основы / структура

Таблицы, строки, колонки, схема

База

Таблица — набор однотипных записей об одной сущности. Колонка задаёт атрибут и его тип, строка (запись, кортеж) — один конкретный объект. Схема — описание всех таблиц, колонок, типов, ключей и ограничений.

Правило именования, которое ждут от вас в команде: таблицы во множественном числе и snake_case (users, order_items), первичный ключ — id, внешний ключ — <сущность>_id (user_id). Единообразие важнее вкусовщины: ORM, генераторы и коллеги на него рассчитывают.

sqlDDL: создание таблицы
CREATE TABLE users (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    email       VARCHAR(255)    NOT NULL,
    password    VARCHAR(255)    NOT NULL,
    name        VARCHAR(120)    NULL,
    is_active   TINYINT(1)      NOT NULL DEFAULT 1,
    created_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uniq_users_email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
ВажноВсегда utf8mb4, а не utf8. Старый utf8 в MySQL хранит максимум 3 байта на символ и не умеет эмодзи и часть иероглифов — на проде это выливается в ошибку «Incorrect string value».
АнтипаттернКолонки-«резинки»: field1, field2, extra, куда складывают всё подряд, и хранение нескольких значений в одной ячейке через запятую (tags = "php,sql,web"). По такой колонке нельзя нормально искать, джойнить и строить индекс.
Типичный вопрос на собеседованииЧто такое схема БД и зачем нужны ограничения (constraints)?
Схема — формальное описание структуры. Ограничения (NOT NULL, UNIQUE, CHECK, FOREIGN KEY) переносят инварианты данных из кода в базу: даже если баг в приложении или ручной SQL попытается записать мусор, БД не даст это сделать.
ПрактикаСоздайте таблицы users, posts, comments для блога. Проверьте, что INSERT с дублирующимся email падает с ошибкой уникальности.

junior / ключи / primary key

Первичный ключ

БазаСпрашивают всегда

Первичный ключ (PK) — колонка или набор колонок, однозначно идентифицирующие строку. Он не может быть NULL, обязан быть уникальным, и таблица без него — почти всегда ошибка проектирования: невозможно адресно обновить или удалить запись, ломается репликация, ORM не может собрать объект.

  • Суррогатный ключ — искусственный id (AUTO_INCREMENT, BIGSERIAL, UUID). Стабилен, компактен, не зависит от бизнес-логики. Дефолтный выбор.
  • Естественный ключ — реальный атрибут (ИНН, ISBN, email). Опасен тем, что бизнес меняет правила: email меняют, «уникальный» артикул внезапно дублируется.
  • Составной ключ — из нескольких колонок, типичен для промежуточных таблиц связи many-to-many.
sqlТри вида первичных ключей
-- 1. Суррогатный автоинкремент (MySQL)
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY

-- 2. UUID (PostgreSQL) — удобен, когда id генерирует клиент или другой сервис
id UUID NOT NULL DEFAULT gen_random_uuid() PRIMARY KEY

-- 3. Составной ключ в таблице связи
CREATE TABLE post_tag (
    post_id BIGINT UNSIGNED NOT NULL,
    tag_id  BIGINT UNSIGNED NOT NULL,
    PRIMARY KEY (post_id, tag_id)
);
ВажноВ InnoDB первичный ключ — это ещё и физический порядок хранения строк (кластерный индекс), а каждый вторичный индекс хранит внутри значение PK. Поэтому «толстый» PK (например, VARCHAR(255)) раздувает все индексы таблицы.
Типичный вопрос на собеседованииЧем PRIMARY KEY отличается от UNIQUE?
PRIMARY KEY — один на таблицу, запрещает NULL и в InnoDB определяет кластерный индекс. UNIQUE-ключей может быть несколько, и они (в MySQL/PostgreSQL) допускают NULL, причём несколько NULL не считаются дубликатами.
ПрактикаСоздайте таблицу post_tag с составным PK и убедитесь, что повторная вставка той же пары падает. Затем попробуйте вставить две строки с NULL в UNIQUE-колонку и объясните результат.

junior / ключи / foreign key

Внешний ключ и ссылочная целостность

База

Внешний ключ (FK) — колонка, которая ссылается на первичный ключ другой таблицы. Он гарантирует ссылочную целостность: нельзя создать комментарий к несуществующему посту и нельзя удалить пост, оставив «висячие» комментарии, — база это запретит или каскадно обработает.

sqlFK и стратегии ON DELETE
CREATE TABLE posts (
    id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    user_id    BIGINT UNSIGNED NOT NULL,
    title      VARCHAR(200) NOT NULL,
    body       TEXT NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_posts_user
        FOREIGN KEY (user_id) REFERENCES users(id)
        ON DELETE CASCADE      -- удалили пользователя → удалились его посты
        ON UPDATE RESTRICT
);

-- Другие стратегии:
-- ON DELETE RESTRICT  — запретить удаление родителя (безопасно по умолчанию)
-- ON DELETE SET NULL  — обнулить ссылку (колонка должна быть NULLABLE)
-- ON DELETE NO ACTION — как RESTRICT, но проверка может откладываться (PostgreSQL)
ВажноТипы колонок в FK и PK должны совпадать точно, включая знаковость: BIGINT UNSIGNED ссылается на BIGINT UNSIGNED. Иначе MySQL выдаст «errno 150». В MySQL под FK автоматически создаётся индекс, в PostgreSQL — нет, его надо создавать руками, иначе удаление родителя вызовет full scan дочерней таблицы.
АнтипаттернON DELETE CASCADE на всё подряд. Каскад по цепочке из пяти таблиц однажды удалит половину базы из-за одного «лишнего» DELETE. Для важных сущностей (заказы, платежи) используйте RESTRICT и мягкое удаление.
Типичный вопрос на собеседованииЗачем нужны внешние ключи, если целостность можно проверять в коде?
Код — не единственный писатель в базу: есть миграции, консольные команды, скрипты аналитиков, второй сервис, ручные правки на проде. FK — последняя линия обороны, которая работает всегда и внутри транзакции.
ПрактикаСвяжите comments → posts → users. Проверьте три сценария: вставка комментария к несуществующему посту, удаление поста с комментариями при RESTRICT и при CASCADE.

SELECT 0.1 + 0.2 = 0.3 AS float_check;      -- 0 (ложь!) для FLOAT/DOUBLE

Типичный вопрос на собеседованииВ каком типе хранить деньги и почему?
В DECIMAL/NUMERIC с фиксированной точностью либо в целых минимальных единицах (копейках). FLOAT — двоичная плавающая точка, десятичные дроби представляются приближённо, и на сумме тысяч операций копейки расходятся.

junior / sql / выборка

SELECT, WHERE, ORDER BY, LIMIT

БазаСпрашивают всегда

Порядок, в котором вы пишете запрос, не совпадает с порядком, в котором СУБД его выполняет. Понимание логического порядка объясняет половину «странностей» SQL:

sqlЛогический порядок выполнения
FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT

Отсюда следует: в WHERE нельзя использовать алиас из SELECT (его ещё не существует), а в ORDER BY — можно; фильтр по агрегату идёт в HAVING, а не в WHERE.

sqlОсновные конструкции выборки
-- Перечисляем колонки явно, а не SELECT *
SELECT id, title, created_at
FROM posts
WHERE user_id = 42
  AND status = 'published'
  AND created_at >= '2026-01-01'
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 0;

-- Диапазоны, списки, шаблоны, NULL
SELECT * FROM posts WHERE views BETWEEN 100 AND 500;
SELECT * FROM posts WHERE status IN ('draft', 'review');
SELECT * FROM users WHERE email LIKE '%@gmail.com';   -- индекс НЕ работает (% слева)
SELECT * FROM users WHERE email LIKE 'ivan%';         -- индекс работает
SELECT * FROM posts WHERE deleted_at IS NULL;

-- Псевдонимы и вычисляемые поля
SELECT p.title AS post_title,
       CONCAT(u.name, ' <', u.email, '>') AS author
FROM posts p
JOIN users u ON u.id = p.user_id;
ВажноORDER BY без уникального «тай-брейкера» недетерминирован: при равных created_at порядок может меняться между запросами, и пагинация начнёт дублировать или терять строки. Всегда добавляйте , id DESC.
АнтипаттернSELECT * в продакшн-коде: тянет ненужные TEXT/BLOB, ломает covering-индексы, а любое добавление колонки в миграции молча меняет объём трафика и поведение кода.
Типичный вопрос на собеседованииПочему WHERE alias = ... для алиаса из SELECT не работает?
Потому что WHERE вычисляется до SELECT в логическом порядке выполнения. Нужно повторить выражение целиком, вынести его в подзапрос/CTE или фильтровать в HAVING.
ПрактикаНапишите запрос: 10 последних опубликованных постов пользователя, с заголовком, датой и числом просмотров, отсортированные по дате убывания с детерминированным порядком.

junior / sql / изменение данных

INSERT, UPDATE, DELETE

База
sqlDML: три операции изменения
-- INSERT: одиночная и пакетная вставка
INSERT INTO posts (user_id, title, body, status)
VALUES (42, 'Первый пост', 'Текст', 'draft');

INSERT INTO posts (user_id, title, body, status) VALUES
    (42, 'Пост 2', 'Текст 2', 'draft'),
    (42, 'Пост 3', 'Текст 3', 'draft');   -- в разы быстрее цикла из INSERT

-- UPSERT: вставить или обновить
INSERT INTO counters (post_id, views) VALUES (10, 1)
ON DUPLICATE KEY UPDATE views = views + 1;              -- MySQL

INSERT INTO counters (post_id, views) VALUES (10, 1)
ON CONFLICT (post_id) DO UPDATE SET views = counters.views + 1;  -- PostgreSQL

-- UPDATE: всегда с WHERE!
UPDATE posts
SET status = 'published', published_at = NOW()
WHERE id = 10 AND status = 'draft';

-- Атомарный инкремент вместо чтения-изменения-записи
UPDATE posts SET views = views + 1 WHERE id = 10;

-- DELETE
DELETE FROM comments WHERE post_id = 10;
ВажноПеред UPDATE/DELETE на проде выполните тот же WHERE в виде SELECT COUNT(*) и убедитесь, что число строк совпадает с ожиданием. Хорошая привычка — запускать в транзакции и делать ROLLBACK, если счётчик удивил.
АнтипаттернИнкремент через приложение: SELECT views → $views + 1 → UPDATE. Два параллельных запроса потеряют одно обновление (lost update). Правильный вариант — SET views = views + 1 одним запросом.
Типичный вопрос на собеседованииЧем отличаются DELETE, TRUNCATE и DROP?
DELETE — DML: удаляет строки по условию, транзакционен, откатывается, срабатывают триггеры и FK. TRUNCATE — DDL: быстро опустошает таблицу целиком, сбрасывает автоинкремент, в MySQL вызывает неявный коммит. DROP удаляет саму таблицу вместе со структурой.
ПрактикаРеализуйте счётчик просмотров поста. Сначала «наивно» (SELECT + UPDATE), затем атомарно. Запустите 100 параллельных обновлений скриптом и сравните итоговое значение.

junior / sql / joins

JOIN: INNER и LEFT

БазаСпрашивают всегда

JOIN соединяет строки двух таблиц по условию. Два типа покрывают 95% задач:

  • INNER JOIN — только те пары строк, для которых условие выполнилось. Нет автора — нет строки.
  • LEFT JOIN — все строки левой таблицы, а из правой — совпадения либо NULL. «Покажи все посты, даже без комментариев».
sqlСравнение INNER и LEFT
-- INNER: посты, у которых есть автор
SELECT p.id, p.title, u.name
FROM posts p
INNER JOIN users u ON u.id = p.user_id;

-- LEFT: все посты + число комментариев (даже 0)
SELECT p.id, p.title, COUNT(c.id) AS comments_count
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
GROUP BY p.id, p.title
ORDER BY comments_count DESC;

-- Поиск "сирот": посты без единого комментария
SELECT p.id, p.title
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
WHERE c.id IS NULL;
ВажноУсловие для правой таблицы в LEFT JOIN должно стоять в ON, а не в WHERE. WHERE c.is_approved = 1 отбросит строки, где c.is_approved IS NULL, и превратит LEFT JOIN обратно в INNER JOIN.
sqlКлассическая ошибка LEFT JOIN + WHERE
-- ПЛОХО: LEFT JOIN превратился в INNER
SELECT p.title, c.body
FROM posts p LEFT JOIN comments c ON c.post_id = p.id
WHERE c.is_approved = 1;

-- ХОРОШО: фильтр правой таблицы внутри ON
SELECT p.title, c.body
FROM posts p LEFT JOIN comments c
     ON c.post_id = p.id AND c.is_approved = 1;
АнтипаттернJOIN без условия (декартово произведение): FROM a, b без WHERE a.id = b.a_id на двух таблицах по 10 000 строк даст 100 000 000 строк.
Типичный вопрос на собеседованииЧем INNER JOIN отличается от LEFT JOIN? Приведите практический пример.
INNER возвращает только совпадения, LEFT — все строки левой таблицы плюс NULL при отсутствии пары. Пример: список всех пользователей с суммой заказов — нужен LEFT JOIN, иначе пользователи без заказов исчезнут из отчёта.
ПрактикаСоберите ленту блога: пост, имя автора, количество одобренных комментариев, отсортированные по дате. Убедитесь, что посты без комментариев остаются в выдаче с нулём.

junior / проектирование / нормализация

Нормализация: 1NF, 2NF, 3NF простыми словами

База

Нормализация — приведение схемы к виду, где каждый факт хранится ровно в одном месте. Цель не академическая: она убирает аномалии вставки, обновления и удаления.

  • 1NF — все значения атомарны. Никаких "php,sql,web" в одной ячейке и никаких phone1, phone2, phone3.
  • 2NF — 1NF плюс: каждый неключевой атрибут зависит от всего составного ключа, а не от его части.
  • 3NF — 2NF плюс: неключевые атрибуты не зависят друг от друга. В таблице заказов не должно быть city_name, если есть city_id.
sqlДенормализованная схема → 3NF
-- ПЛОХО: всё в одной таблице
orders(id, customer_name, customer_email, customer_city,
       product_name, product_price, qty)
-- Аномалии: email клиента продублирован в каждом заказе;
-- смена email требует UPDATE всех строк; цена товара «застревает» в истории.

-- ХОРОШО: 3NF
customers(id, name, email, city_id)
cities(id, name)
products(id, name, price)
orders(id, customer_id, created_at, status)
order_items(id, order_id, product_id, qty, price_at_purchase)
ВажноОбратите внимание на price_at_purchase. Это намеренная денормализация: цена товара меняется, а сумма выданного чека — исторический факт, который обязан остаться неизменным. Нормализация — не догма, а инструмент.
Типичный вопрос на собеседованииЧто такое третья нормальная форма?
Отношение в 3NF, если оно во 2NF и ни один неключевой атрибут не зависит транзитивно от ключа через другой неключевой атрибут. Практически: справочные данные выносим в отдельные таблицы и ссылаемся по id.
ПрактикаВозьмите «плоскую» таблицу заказов из примера и приведите её к 3NF: нарисуйте схему, напишите DDL, перенесите данные запросами INSERT ... SELECT DISTINCT.

Работа с БД через PDO

БазаСпрашивают всегда

PDO (PHP Data Objects) — единый объектный интерфейс к разным СУБД. Даёт подготовленные выражения, транзакции, исключения и настраиваемый режим выборки. Даже если вы работаете через Doctrine или Eloquent, под капотом всё равно PDO — и на собеседовании спросят именно про него.

phpПравильное подключение
<?php
declare(strict_types=1);

$dsn = 'mysql:host=127.0.0.1;port=3306;dbname=blog;charset=utf8mb4';

$pdo = new PDO($dsn, 'app', 'secret', [
    // Ошибки как исключения — иначе они молча игнорируются
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
    // Ассоциативные массивы по умолчанию
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    // Настоящие prepared statements на стороне сервера
    PDO::ATTR_EMULATE_PREPARES   => false,
    // Не превращать все значения в строки (PHP 8.1+ и так корректнее)
    PDO::ATTR_STRINGIFY_FETCHES  => false,
]);
phpВыборка и вставка
<?php
// Именованные параметры — читаемее позиционных
$stmt = $pdo->prepare(
    'SELECT id, title, created_at
       FROM posts
      WHERE user_id = :user_id AND status = :status
      ORDER BY created_at DESC
      LIMIT :limit'
);
// LIMIT требует явного INT при EMULATE_PREPARES = false
$stmt->bindValue(':user_id', 42, PDO::PARAM_INT);
$stmt->bindValue(':status', 'published', PDO::PARAM_STR);
$stmt->bindValue(':limit', 20, PDO::PARAM_INT);
$stmt->execute();

// foreach ($stmt as $row) { ... }  // потоково, без загрузки всего в память

    'INSERT INTO posts (user_id, title, body, status)
     VALUES (:user_id, :title, :body, :status)'

    ':user_id' => 42,

    ':body'    => $body,

]);

ВажноATTR_EMULATE_PREPARES => false — обязательная настройка. При эмуляции PDO сам подставляет значения в строку запроса; это работает, но лишает вас настоящего разделения кода и данных и ломает типы.
Типичный вопрос на собеседованииЧем PDO лучше mysqli?
PDO поддерживает 12+ драйверов и одинаковый API для них, даёт именованные параметры, гибкие режимы fetch и единообразную обработку ошибок исключениями. mysqli умеет только MySQL. Для нового кода стандарт — PDO.
ПрактикаНапишите класс Database с ленивым подключением и методами query(), fetchAll(), fetchOne(). Реализуйте на нём CRUD для постов блога.

junior / безопасность / sql injection

Подготовленные выражения и защита от SQL-инъекций

БазаКритично

SQL-инъекция — подмена структуры запроса пользовательскими данными. Она возможна ровно тогда, когда данные попадают в текст запроса конкатенацией. Подготовленное выражение решает проблему принципиально: сервер сначала парсит шаблон запроса, затем получает значения отдельно — они уже не могут стать частью синтаксиса.

phpУязвимый код
<?php
// НИКОГДА так не делайте
$email = $_GET['email'];
$sql   = "SELECT * FROM users WHERE email = '" . $email . "'";
$user  = $pdo->query($sql)->fetch();

// Вход: email = ' OR '1'='1
// Запрос: SELECT * FROM users WHERE email = '' OR '1'='1'  → вернёт всех
// Вход: email = '; DROP TABLE users; --   → в многозапросном режиме удалит таблицу
phpИсправленная версия
<?php
$stmt = $pdo->prepare('SELECT id, email, name FROM users WHERE email = :email');
$stmt->execute([':email' => $_GET['email'] ?? '']);
$user = $stmt->fetch();

// Имена таблиц и колонок параметризовать НЕЛЬЗЯ — только белый список
$allowedSort = ['created_at', 'title', 'views'];
$sort = in_array($_GET['sort'] ?? '', $allowedSort, true)
    ? $_GET['sort']
    : 'created_at';
$dir  = ($_GET['dir' ] ?? '') === 'asc' ? 'ASC' : 'DESC';

$sql = "SELECT id, title FROM posts ORDER BY {$sort} {$dir} LIMIT 20";

// IN-список: генерируем плейсхолдеры по числу элементов
$ids  = [1, 2, 3, 7];
$in   = implode(',', array_fill(0, count($ids), '?'));
$stmt = $pdo->prepare("SELECT id, title FROM posts WHERE id IN ($in)");
$stmt->execute($ids);
ВажноПараметризовать можно только значения. Имена таблиц, колонок, направление сортировки и LIMIT в некоторых драйверах — не значения. Для них — строгий белый список, никогда не «экранирование».
АнтипаттернЗащита через addslashes(), htmlspecialchars() или самописный «фильтр опасных слов». Это не работает: обходится кодировками, комментариями и числовыми контекстами (WHERE id = $id без кавычек вообще не требует апострофа).
Типичный вопрос на собеседованииПочему prepared statement защищает от инъекции?
Потому что запрос и данные передаются на сервер разными сообщениями протокола. План запроса строится по шаблону с плейсхолдерами до того, как сервер увидит значения, поэтому значение физически не может изменить структуру запроса.
ПрактикаНапишите намеренно уязвимую форму логина, проведите инъекцию ' OR '1'='1' -- , затем перепишите на prepared statements и убедитесь, что атака не проходит.

Двенадцать ошибок, на которых заваливаются новички

middle / sql / сложные соединения

Сложные JOIN: несколько таблиц, self-join, множественность строк

Средний

Главное, что нужно понимать про многотабличный JOIN: он размножает строки. Если у заказа 3 позиции и 2 платежа, соединение всех трёх таблиц даст 6 строк, и SUM(order_items.price) в таком запросе будет завышена вдвое. Это самая частая причина «непонятно откуда взявшихся» цифр в отчётах.

sqlМноготабличное соединение
SELECT o.id,
       u.name              AS customer,
       s.title             AS status,
       COUNT(oi.id)        AS items,
       SUM(oi.qty * oi.price) AS total
FROM orders o
JOIN users u          ON u.id = o.user_id
JOIN order_statuses s ON s.id = o.status_id
LEFT JOIN order_items oi ON oi.order_id = o.id
WHERE o.created_at >= '2026-01-01'
GROUP BY o.id, u.name, s.title
HAVING SUM(oi.qty * oi.price) > 10000
ORDER BY total DESC;
sqlSelf-join и корректная агрегация нескольких веток
-- Self-join: сотрудник и его руководитель из одной таблицы
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;

-- Двойная агрегация: считаем в подзапросах, чтобы строки не размножались
SELECT o.id,
       COALESCE(i.items_total, 0)  AS items_total,
       COALESCE(p.paid_total, 0)   AS paid_total
FROM orders o
LEFT JOIN (SELECT order_id, SUM(qty * price) AS items_total
           FROM order_items GROUP BY order_id) i ON i.order_id = o.id
LEFT JOIN (SELECT order_id, SUM(amount) AS paid_total
           FROM payments WHERE status = 'success' GROUP BY order_id) p ON p.order_id = o.id;
Типичная ошибкаСоединить orders с order_items и payments одновременно и посчитать SUM по обеим — суммы умножатся на количество строк противоположной ветки. Лечится агрегацией в подзапросах, CTE или оконными функциями.
Как диагностироватьУберите агрегаты и посмотрите на сырые строки: SELECT o.id, oi.id, p.id FROM .... Если на один o.id приходится больше строк, чем вы ожидали, — размножение найдено. Быстрая проверка: сравните COUNT(*) и COUNT(DISTINCT o.id).
Типичный вопрос на собеседованииПочему при соединении трёх таблиц суммы «удваиваются» и как это исправить?
Потому что JOIN даёт декартово произведение совпадающих строк по каждой ветке. Исправляется предварительной агрегацией каждой ветки в подзапросе/CTE, либо SUM(DISTINCT ...) в простых случаях, либо оконными функциями.
ПрактикаПостройте отчёт «заказ — сумма позиций — сумма оплат — остаток к оплате» так, чтобы цифры сходились при любом количестве позиций и платежей.

middle / sql / агрегация

Агрегатные функции, GROUP BY, HAVING

Средний

Агрегаты сворачивают группу строк в одно значение: COUNT, SUM, AVG, MIN, MAX, GROUP_CONCAT (MySQL) / STRING_AGG (PostgreSQL). GROUP BY задаёт разбиение на группы, HAVING фильтрует уже готовые группы.

sqlАгрегация с фильтрами до и после группировки
SELECT u.id,
       u.name,
       COUNT(*)                          AS posts_total,
       COUNT(p.published_at)             AS published,   -- COUNT игнорирует NULL
       SUM(CASE WHEN p.views > 1000 THEN 1 ELSE 0 END) AS popular,
       ROUND(AVG(p.views), 1)            AS avg_views,
       MAX(p.created_at)                 AS last_post_at
FROM users u
JOIN posts p ON p.user_id = u.id
WHERE p.created_at >= '2026-01-01'      -- фильтр СТРОК, до группировки
GROUP BY u.id, u.name
HAVING COUNT(*) >= 5                     -- фильтр ГРУПП, после группировки
ORDER BY posts_total DESC
LIMIT 50;

-- FILTER (PostgreSQL) — читаемее, чем SUM(CASE WHEN ...)
SELECT user_id,
       COUNT(*) FILTER (WHERE status = 'published') AS published,
       COUNT(*) FILTER (WHERE status = 'draft')     AS drafts
FROM posts GROUP BY user_id;
ВажноCOUNT(*) считает строки, COUNT(col) — строки, где col IS NOT NULL, COUNT(DISTINCT col) — уникальные значения. Разница между первым и вторым — источник вечных расхождений в отчётах.
Типичная ошибкаСтавить условие по агрегату в WHERE (WHERE COUNT(*) > 5) — синтаксическая ошибка, потому что агрегат ещё не вычислен. И наоборот: тащить обычный фильтр строк в HAVING — работает, но лишает БД возможности отсечь строки до группировки, то есть медленнее.
Как диагностироватьМедленный GROUP BY в EXPLAIN виден как Using temporary; Using filesort (MySQL) или HashAggregate с большим объёмом (PostgreSQL). Обычно спасает индекс по колонкам группировки или предварительное сужение выборки по дате.
Типичный вопрос на собеседованииВ чём разница между WHERE и HAVING?
WHERE фильтрует строки до группировки и может использовать индекс. HAVING фильтрует результат агрегации после GROUP BY. Всё, что можно отфильтровать в WHERE, надо фильтровать там.
ПрактикаПостройте отчёт по авторам: число постов, число опубликованных, средние просмотры, дата последней публикации — только для авторов с 5+ постами за год.

middle / sql / подзапросы

Подзапросы: скалярные, IN, EXISTS, коррелированные

Средний
sqlЧетыре вида подзапросов
-- 1. Скалярный: возвращает одно значение
SELECT title, views,
       (SELECT AVG(views) FROM posts) AS avg_all
FROM posts;

-- 2. IN: список значений
SELECT * FROM users
WHERE id IN (SELECT user_id FROM orders WHERE total > 10000);

-- 3. EXISTS: проверка наличия, обычно быстрее IN на больших наборах
SELECT u.* FROM users u
WHERE EXISTS (SELECT 1 FROM orders o
              WHERE o.user_id = u.id AND o.total > 10000);

-- 4. NOT EXISTS вместо NOT IN — безопасно к NULL
SELECT u.* FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

-- Подзапрос в FROM (derived table)
SELECT c.name, s.cnt
FROM (SELECT city_id, COUNT(*) cnt FROM users GROUP BY city_id) s
JOIN cities c ON c.id = s.city_id;
ВажноNOT IN с подзапросом, который может вернуть NULL, вернёт пустой результат — потому что x NOT IN (1, NULL) вычисляется в NULL, а не в TRUE. Используйте NOT EXISTS или добавляйте WHERE col IS NOT NULL.
Типичная ошибкаКоррелированный подзапрос в SELECT, выполняющийся для каждой строки внешней выборки: на 100 000 строк это 100 000 запросов внутри одного SQL. Почти всегда переписывается в JOIN с предварительной агрегацией.
Как диагностироватьВ EXPLAIN MySQL ищите DEPENDENT SUBQUERY, в PostgreSQL — SubPlan с высоким loops в EXPLAIN ANALYZE. Оба говорят: подзапрос выполняется многократно.
Типичный вопрос на собеседованииЧто быстрее — IN или EXISTS?
Современные оптимизаторы часто приводят их к одному плану. Практическое правило: EXISTS предпочтителен, когда подзапрос большой и достаточно факта существования (он останавливается на первом совпадении); IN удобен на маленьком фиксированном списке. NOT EXISTS всегда предпочтительнее NOT IN из-за NULL.
ПрактикаНайдите пользователей без единого заказа тремя способами (NOT IN, NOT EXISTS, LEFT JOIN ... IS NULL) и сравните планы выполнения на таблице в 1 млн строк.

middle / sql / cte и оконные функции

CTE (WITH) и оконные функции

Средний

CTE — именованный подзапрос перед основным запросом. Он не делает запрос быстрее сам по себе, но радикально улучшает читаемость и позволяет рекурсию (деревья категорий, иерархии сотрудников). Оконные функции считают агрегат «вокруг» строки, не схлопывая её.

sqlCTE, включая рекурсивный
-- Обычный CTE: разбиваем сложный отчёт на шаги
WITH monthly AS (
    SELECT user_id,
           DATE_FORMAT(created_at, '%Y-%m') AS ym,
           SUM(total) AS revenue
    FROM orders
    WHERE status = 'paid'
    GROUP BY user_id, ym
),
top_users AS (
    SELECT user_id, SUM(revenue) AS total_revenue
    FROM monthly GROUP BY user_id
    HAVING SUM(revenue) > 100000
)
SELECT u.name, t.total_revenue
FROM top_users t JOIN users u ON u.id = t.user_id
ORDER BY t.total_revenue DESC;

-- Рекурсивный CTE: всё дерево категорий от корня
WITH RECURSIVE tree AS (
    SELECT id, parent_id, name, 1 AS depth
    FROM categories WHERE parent_id IS NULL
    UNION ALL
    SELECT c.id, c.parent_id, c.name, t.depth + 1
    FROM categories c JOIN tree t ON c.parent_id = t.id
)
SELECT * FROM tree ORDER BY depth, name;
sqlОконные функции
-- Место каждого поста внутри автора + доля от суммы просмотров
SELECT p.id, p.user_id, p.title, p.views,
       ROW_NUMBER() OVER (PARTITION BY p.user_id ORDER BY p.views DESC) AS rn,
       RANK()       OVER (PARTITION BY p.user_id ORDER BY p.views DESC) AS rnk,
       SUM(p.views) OVER (PARTITION BY p.user_id)                        AS user_views,
       LAG(p.views) OVER (PARTITION BY p.user_id ORDER BY p.created_at)  AS prev_views
FROM posts p;

-- Топ-3 поста каждого автора (классическая задача с собеседования)
WITH ranked AS (
    SELECT p.*, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY views DESC) rn
    FROM posts p
)
SELECT * FROM ranked WHERE rn <= 3;
ВажноВ MySQL 8+ и PostgreSQL CTE обычно инлайнится оптимизатором. Но в PostgreSQL до версии 12 CTE был барьером оптимизации (материализовался всегда) — если работаете со старой версией, помните об этом; управлять поведением можно через MATERIALIZED / NOT MATERIALIZED.
Типичная ошибкаРекурсивный CTE без ограничения глубины на данных с циклом (категория ссылается сама на себя через предка) — бесконечный цикл и падение. Добавляйте счётчик depth и условие WHERE depth < 20.
Как диагностироватьЕсли отчёт с CTE стал медленным, разверните его в EXPLAIN ANALYZE и посмотрите, какая часть материализуется. Иногда быстрее переписать CTE в подзапрос в FROM или во временную таблицу с индексом.
Типичный вопрос на собеседованииЗачем нужны оконные функции, если есть GROUP BY?
GROUP BY схлопывает строки, оконная функция сохраняет каждую строку и добавляет к ней агрегат по «окну». Это единственный вменяемый способ решить задачи вида «топ-N в каждой группе», «доля строки в сумме группы», «сравнение с предыдущим периодом».
ПрактикаВыведите для каждого клиента три последних заказа с их номером по счёту и суммой всех его заказов в той же строке — одним запросом без подзапросов в SELECT.

Индексы: как устроены и когда работают

СреднийСпрашивают всегда

Индекс — отдельная структура (обычно B+-дерево), хранящая значения колонок в отсортированном виде вместе со ссылкой на строку. Он превращает полный перебор O(n) в поиск O(log n). Плата: замедление INSERT/UPDATE/DELETE и дополнительное место на диске.

sqlСоздание индексов
CREATE INDEX idx_posts_user_created ON posts (user_id, created_at);
CREATE UNIQUE INDEX uniq_users_email ON users (email);
CREATE INDEX idx_orders_status ON orders (status) WHERE status <> 'done';  -- частичный, PostgreSQL
CREATE INDEX idx_users_lower_email ON users (LOWER(email));                    -- функциональный
CREATE FULLTEXT INDEX ft_posts_body ON posts (title, body);                    -- MySQL
CREATE INDEX idx_attrs ON products USING GIN (attributes);                     -- JSONB, PostgreSQL

Составной индекс и правило левого префикса

Индекс (user_id, created_at, status) работает для условий по user_id; по user_id + created_at; по всем трём. Он не работает для поиска только по created_at или только по status. Порядок колонок — самое важное решение при создании составного индекса.

sqlКогда индекс не используется
-- Функция над колонкой убивает индекс
WHERE YEAR(created_at) = 2026                     -- индекс не работает
WHERE created_at >= '2026-01-01'
  AND created_at <  '2027-01-01'              -- работает

-- Неявное приведение типов
WHERE phone = 79991234567                          -- phone VARCHAR → приведение, индекс не работает
WHERE phone = '79991234567'                      -- работает

-- Ведущий % в LIKE
WHERE email LIKE '%@mail.ru'                    -- не работает
WHERE email LIKE 'ivan%'                        -- работает

-- OR по разным колонкам часто хуже, чем UNION двух индексных выборок
WHERE user_id = 10 OR editor_id = 10
ВажноПокрывающий индекс (covering index) содержит все колонки, нужные запросу, — тогда БД вообще не обращается к таблице. В MySQL это видно как Using index, в PostgreSQL — Index Only Scan. Часто это ускорение в 5–20 раз.
Типичная ошибкаСоздать по индексу на каждую колонку «на всякий случай». Оптимизатор в большинстве случаев использует один индекс на таблицу в запросе, а десять индексов на горячей таблице замедляют запись в разы и раздувают базу.
Как диагностироватьНайдите неиспользуемые индексы: в PostgreSQL — pg_stat_user_indexes с idx_scan = 0; в MySQL — sys.schema_unused_indexes. Дубликаты (индекс (a) при наличии (a, b)) удаляйте: левый префикс уже покрывает первый.
Типичный вопрос на собеседованииЕсть индекс (a, b, c). Какие запросы его используют?
Условия по a; по a и b; по a, b, c; а также a = ? AND b > ? (диапазон по b останавливает дальнейшее использование c для поиска). Не используют: только b, только c, b + c.
ПрактикаСгенерируйте таблицу на 2 млн строк, замерьте запрос по неиндексированной колонке, добавьте индекс и замерьте снова. Затем добавьте составной индекс и сделайте запрос покрывающим — сравните три плана.

Транзакции и уровни изоляции

СреднийСпрашивают всегда

Транзакция — группа операций, которая выполняется целиком или не выполняется вовсе. Свойства ACID: атомарность, согласованность, изолированность, долговечность.

sqlТранзакция и точки сохранения
START TRANSACTION;
    UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
    UPDATE accounts SET balance = balance + 1000 WHERE id = 2;
    INSERT INTO transfers (from_id, to_id, amount) VALUES (1, 2, 1000);
COMMIT;   -- или ROLLBACK при ошибке

-- SAVEPOINT: частичный откат внутри транзакции
START TRANSACTION;
    INSERT INTO orders (...) VALUES (...);
    SAVEPOINT after_order;
    INSERT INTO order_items (...) VALUES (...);
    ROLLBACK TO SAVEPOINT after_order;   -- заказ остался, позиции откатились
COMMIT;
phpТранзакция в PDO с корректной обработкой ошибок
<?php
function transfer(PDO $pdo, int $from, int $to, string $amount): void
{
    $pdo->beginTransaction();
    try {
        // Условие в самом UPDATE защищает от ухода в минус
        $debit = $pdo->prepare(
            'UPDATE accounts SET balance = balance - :amt
              WHERE id = :id AND balance >= :amt'
        );
        $debit->execute([':amt' => $amount, ':id' => $from]);

        if ($debit->rowCount() === 0) {
            throw new RuntimeException('Недостаточно средств');
        }

        $pdo->prepare('UPDATE accounts SET balance = balance + :amt WHERE id = :id')
            ->execute([':amt' => $amount, ':id' => $to]);

        $pdo->prepare(
            'INSERT INTO transfers (from_id, to_id, amount) VALUES (:f, :t, :a)'
        )->execute([':f' => $from, ':t' => $to, ':a' => $amount]);

        $pdo->commit();
    } catch (Throwable $e) {
        if ($pdo->inTransaction()) {
            $pdo->rollBack();
        }
        throw $e;
    }
}

  • Неповторяющееся чтение — дважды прочитали одну строку и получили разные значения.

ВажноИзоляция не спасает от логических гонок в приложении. Классика: прочитали остаток на складе, проверили в PHP, списали. Между чтением и записью успел вклиниться другой процесс. Решение — атомарный UPDATE ... WHERE qty >= :n, SELECT ... FOR UPDATE или версионность.
Типичная ошибкаДержать транзакцию открытой во время HTTP-запроса к платёжному шлюзу или отправки письма. Внешний сервис отвечает 5 секунд — 5 секунд держатся блокировки, и пул соединений заканчивается. Транзакция должна быть максимально короткой и содержать только работу с БД.
Как диагностироватьДолгие транзакции видны в information_schema.innodb_trx (MySQL) и pg_stat_activity с состоянием idle in transaction (PostgreSQL). Последнее — прямой признак того, что код открыл транзакцию и ушёл делать что-то постороннее.
Типичный вопрос на собеседованииЧто такое ACID и какой уровень изоляции по умолчанию в MySQL?
Atomicity, Consistency, Isolation, Durability. По умолчанию InnoDB работает в REPEATABLE READ, PostgreSQL — в READ COMMITTED. Разница важна при миграции проекта между СУБД: код, рассчитанный на снимок данных внутри транзакции, в PostgreSQL начнёт видеть чужие коммиты.
ПрактикаОткройте две консоли к MySQL. В первой начните транзакцию и обновите строку без коммита, во второй прочитайте её. Повторите на READ COMMITTED и REPEATABLE READ, зафиксируйте разницу.

Блокировки и deadlock

Средний

Блокировки — механизм, которым СУБД разводит конкурирующие транзакции. В InnoDB и PostgreSQL блокировки строчные, а не табличные, и берутся автоматически при UPDATE/DELETE. Явно их берут через SELECT ... FOR UPDATE (эксклюзивно) и FOR SHARE (разделяемо).

sqlЯвные блокировки
START TRANSACTION;
    SELECT qty FROM stock WHERE product_id = 7 FOR UPDATE;   -- строка заблокирована
    -- ... проверка в приложении ...
    UPDATE stock SET qty = qty - 1 WHERE product_id = 7;
COMMIT;

-- Не ждать блокировку, а сразу упасть / пропустить строку
SELECT * FROM jobs WHERE status = 'new' LIMIT 1 FOR UPDATE NOWAIT;
SELECT * FROM jobs WHERE status = 'new' LIMIT 1 FOR UPDATE SKIP LOCKED;  -- очередь задач

Deadlock — взаимная блокировка: транзакция A держит строку 1 и ждёт строку 2, транзакция B держит строку 2 и ждёт строку 1. СУБД обнаруживает цикл и убивает одну из транзакций с ошибкой (MySQL: 1213, PostgreSQL: 40P01).

phpРетрай при deadlock
<?php
function withDeadlockRetry(PDO $pdo, callable $work, int $attempts = 3): mixed
{
    for ($i = 1; ; $i++) {
        $pdo->beginTransaction();
        try {
            $result = $work($pdo);
            $pdo->commit();
            return $result;
        } catch (PDOException $e) {
            $pdo->rollBack();
            // 40001 — сбой сериализации, 1213/1205 — deadlock и lock wait timeout
            $retryable = in_array($e->getCode(), ['40001', '40P01', 'HY000'], true);
            if (!$retryable || $i >= $attempts) {
                throw $e;
            }
            usleep(random_int(50_000, 200_000) * $i);  // backoff + jitter
        }
    }
}
ВажноDeadlock — не баг базы, а нормальное явление конкурентной среды. Два обязательных приёма: всегда обновляйте строки в одном и том же порядке (например, по возрастанию id) и всегда имейте ретрай на уровне сервиса.
Типичная ошибкаSELECT ... FOR UPDATE по колонке без индекса. InnoDB заблокирует не одну строку, а фактически просканированный диапазон — и вы получите блокировку половины таблицы.
Как диагностироватьMySQL: SHOW ENGINE INNODB STATUS, секция LATEST DETECTED DEADLOCK — там видны обе транзакции и конкретные запросы. PostgreSQL: сообщение о deadlock пишется в лог с обоими процессами; текущие ожидания видны в pg_locks + pg_stat_activity.
Типичный вопрос на собеседованииКак бороться с deadlock-ами?
Единый порядок захвата ресурсов, короткие транзакции, точечные условия по индексированным колонкам, автоматический ретрай с экспоненциальной задержкой. Для очередей — FOR UPDATE SKIP LOCKED, чтобы воркеры не конкурировали за одну строку.
ПрактикаВоспроизведите deadlock в двух консолях (обновите строки 1 и 2 в противоположном порядке), поймайте ошибку, затем реализуйте воркер очереди на SKIP LOCKED и запустите 5 копий параллельно — убедитесь, что задачи не дублируются.

CREATE TABLE post_tag (
    post_id BIGINT UNSIGNED NOT NULL,
    tag_id  BIGINT UNSIGNED NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (post_id, tag_id),
    KEY idx_post_tag_tag (tag_id),       -- для обратного поиска "посты по тегу"
    CONSTRAINT fk_pt_post FOREIGN KEY (post_id) REFERENCES posts(id) ON DELETE CASCADE,
    CONSTRAINT fk_pt_tag  FOREIGN KEY (tag_id)  REFERENCES tags(id)  ON DELETE CASCADE

ВажноВ таблице связи порядок колонок в составном PK определяет, какой поиск быстрый. PRIMARY KEY (post_id, tag_id) отлично отвечает на «теги поста», но для «постов по тегу» нужен отдельный индекс по (tag_id, post_id). Это две разные точки входа — обе нужны.

Отдельный сюжет — полиморфные связи (комментарии к постам, товарам и видео одновременно) вида commentable_type + commentable_id. Они популярны в Laravel, но ломают внешние ключи: база не может проверить, что commentable_id ссылается на существующую запись. Альтернатива — отдельные таблицы post_comments, product_comments либо общая таблица commentables с реальным FK.

Типичная ошибкаEAV-схема «на всякий случай»: таблица attributes(entity_id, key, value VARCHAR) для всех сущностей. Любой отчёт превращается в 8 самосоединений, типы теряются, индексы не помогают. Если атрибуты действительно динамические — используйте JSONB с GIN-индексом (PostgreSQL) или JSON + сгенерированные колонки (MySQL).
Как диагностироватьПризнак плохой схемы: чтобы получить одну карточку сущности, нужно 6+ джойнов, а условия постоянно содержат type = '...'. Второй признак — запросы вида «а посчитай теперь по-другому» требуют не нового запроса, а миграции.
Типичный вопрос на собеседованииКак реализовать связь many-to-many и что хранить в промежуточной таблице?
Отдельная таблица с двумя FK и составным PK. В неё же кладут атрибуты самой связи: qty и price в order_items, role в project_user, created_at для истории. Как только у связи появляются свои атрибуты, она становится полноценной сущностью.
ПрактикаСпроектируйте схему интернет-магазина: товары, категории (дерево), варианты товара, склад, корзина, заказ, позиции заказа, платежи, адреса доставки. Отметьте все три типа связей и обоснуйте каждый индекс.

    public function findById(int $id): ?Post
    {
        $stmt = $this->pdo->prepare(
            'SELECT id, user_id, title, body, status, created_at
               FROM posts WHERE id = :id AND deleted_at IS NULL'
        );
        $stmt->execute([':id' => $id]);
        $row = $stmt->fetch();

        return $row ? Post::fromRow($row) : null;
    }

    public function findPublishedByAuthor(int $authorId, int $limit, int $offset): array
    {
        $stmt = $this->pdo->prepare(
            'SELECT id, user_id, title, body, status, created_at
               FROM posts
              WHERE user_id = :author AND status = :status AND deleted_at IS NULL
              ORDER BY created_at DESC, id DESC
              LIMIT :lim OFFSET :off'
        );
        $stmt->bindValue(':author', $authorId, PDO::PARAM_INT);
        $stmt->bindValue(':status', 'published');
        $stmt->bindValue(':lim', $limit, PDO::PARAM_INT);
        $stmt->bindValue(':off', $offset, PDO::PARAM_INT);
        $stmt->execute();

        return array_map([Post::class, 'fromRow'], $stmt->fetchAll());
    }
}
ВажноРепозиторий возвращает объекты домена, а не массивы и не PDOStatement. Его ценность в том, что SQL не растекается по контроллерам: когда придёт время добавить кэш, шардинг или заменить запрос, вы правите одно место.
Типичная ошибкаМиграция, которая одновременно меняет структуру и переливает 20 млн строк одним UPDATE. Деплой встаёт, таблица блокируется. Данные надо переносить отдельным фоновым backfill-ом пачками (см. senior-раздел).
Как диагностироватьПризнак проблем с миграциями: расхождение схемы между стендами. Проверяется генерацией diff-миграции на чистой базе (doctrine:migrations:diff) — если она непустая, схема «уехала» от кода.
Типичный вопрос на собеседованииПочему нельзя редактировать уже применённую миграцию?
Потому что у коллег и на проде она уже выполнена и записана в таблицу версий — изменения просто не применятся, и схемы разойдутся. Нужна новая миграция поверх.
ПрактикаНастройте Phinx или Doctrine Migrations в учебном проекте. Сделайте 5 миграций (включая добавление индекса и переименование колонки), откатите три и накатите заново.

ORM и Query Builder: плюсы, минусы, проблема N+1

СреднийСпрашивают всегда

ORM отображает строки на объекты (Doctrine — Data Mapper, Eloquent — Active Record). Query Builder — программный конструктор SQL без объектного отображения. Оба ускоряют разработку и убирают ручную конкатенацию, но прячут стоимость запроса.

N+1 — самая частая проблема производительности в PHP-проектах: 1 запрос за списком и по 1 запросу за связью для каждого элемента.

phpN+1 и его лечение
<?php
// ПЛОХО: 1 + N запросов
$posts = Post::limit(50)->get();              // 1 запрос
foreach ($posts as $post) {
    echo $post->author->name;                  // +1 запрос на каждый пост = 51
}

// ХОРОШО: eager loading — 2 запроса
$posts = Post::with(['author', 'tags'])->limit(50)->get();

// ХОРОШО: агрегат без загрузки коллекции
$posts = Post::withCount('comments')->limit(50)->get();  // подзапрос вместо N запросов

// Doctrine: JOIN FETCH в DQL
$posts = $em->createQuery(
    'SELECT p, a FROM App\Entity\Post p JOIN p.author a ORDER BY p.createdAt DESC'
)->setMaxResults(50)->getResult();
phpРучной eager loading на чистом PDO
<?php
// 1. Достаём посты
$posts = $pdo->query('SELECT id, user_id, title FROM posts ORDER BY id DESC LIMIT 50')
             ->fetchAll();

// 2. Собираем уникальные id авторов и достаём их одним запросом
$authorIds = array_values(array_unique(array_column($posts, 'user_id')));
$in    = implode(',', array_fill(0, count($authorIds), '?'));
$stmt  = $pdo->prepare("SELECT id, name FROM users WHERE id IN ($in)");
$stmt->execute($authorIds);
$authors = array_column($stmt->fetchAll(), null, 'id');   // id => row

// 3. Склеиваем в памяти — итого 2 запроса вместо 51
foreach ($posts as &$post) {
    $post['author'] = $authors[$post['user_id']] ?? null;
}
unset($post);
ВажноEager loading не бесплатен: with() на пять уровней вложенности вытянет в память тысячи объектов. Для списков и отчётов часто правильнее не ORM, а плоский SQL-запрос, отдающий ровно нужные колонки в DTO.
Типичная ошибкаСчитать агрегаты обходом коллекции: $post->comments()->count() внутри цикла (запрос на итерацию) или count($post->comments) (загрузка всех комментариев в память). Правильно — withCount() или JOIN + GROUP BY.
Как диагностироватьПрофайлер Symfony / Laravel Debugbar показывает счётчик запросов и дубликаты. В проде — процент запросов вида SELECT ... WHERE id = ?, повторяющихся десятками за один HTTP-запрос. Можно поставить «предохранитель»: Model::preventLazyLoading() в Laravel, который в dev-режиме бросает исключение при ленивой подгрузке.
Типичный вопрос на собеседованииЧто такое N+1 и как его найти?
Это когда после одного запроса за списком делается по запросу за связью для каждого элемента. Ищется профайлером или логом запросов; лечится eager loading (with, JOIN FETCH), агрегатными подзапросами (withCount) либо ручной догрузкой связей одним IN-запросом.
ПрактикаВозьмите страницу со списком из 50 сущностей и связями, зафиксируйте число запросов, сократите его до 3–4, замерьте время до и после.

Оптимизация запросов и правильная пагинация

Средний

Чек-лист оптимизации запроса

  1. Сузить выборку по индексируемому условию (обычно дата или владелец) как можно раньше.
  2. Убрать функции и приведения типов с индексируемых колонок.
  3. Заменить SELECT * на список колонок и попробовать сделать индекс покрывающим.
  4. Вынести агрегацию в подзапрос/CTE, чтобы не размножать строки.
  5. OR по разным колонкам заменить на UNION ALL двух индексных выборок.
  6. Проверить статистику (ANALYZE) и актуальность плана.
  7. Если запрос всё ещё дорогой — денормализовать: счётчик, агрегатная таблица, материализованное представление.

Пагинация: OFFSET против keyset

sqlДве стратегии пагинации
-- OFFSET: простая, но деградирует. LIMIT 20 OFFSET 200000 заставит БД
-- прочитать и выбросить 200 000 строк.
SELECT id, title, created_at FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 200000;

-- KEYSET (cursor / seek): постоянное время на любой глубине
SELECT id, title, created_at FROM posts
WHERE (created_at, id) < (:last_created_at, :last_id)   -- курсор с прошлой страницы
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- Deferred join: если нужен именно OFFSET, сначала достаём id по узкому индексу
SELECT p.* FROM posts p
JOIN (SELECT id FROM posts ORDER BY created_at DESC, id DESC
      LIMIT 20 OFFSET 200000) x ON x.id = p.id;

-- Точное количество страниц дорого на больших таблицах. Варианты:
-- 1) не показывать общее число, только "есть ли следующая" (LIMIT 21);
-- 2) приблизительная оценка из статистики планировщика.
ВажноKeyset-пагинация требует детерминированной сортировки по уникальному «хвосту» (обычно id) и не умеет прыгать на произвольную страницу. Для бесконечной ленты и API это идеально; для админки с номерами страниц берут deferred join.
Типичная ошибкаSELECT COUNT(*) по всей таблице на каждой странице списка. На 50 млн строк это секунды. Считайте total только когда он действительно нужен, кэшируйте его или показывайте приблизительное значение.
Как диагностироватьПостройте график времени ответа списка в зависимости от номера страницы. Линейный рост — верный признак OFFSET-пагинации. Отдельно посмотрите, сколько времени уходит на COUNT относительно самой выборки.
Типичный вопрос на собеседованииПочему LIMIT/OFFSET плохо работает на больших смещениях?
Потому что база всё равно должна отсортировать и пройти OFFSET строк, прежде чем отдать нужные. Стоимость растёт линейно от глубины. Keyset-пагинация использует индекс для позиционирования и работает за постоянное время.
ПрактикаНа таблице в 5 млн строк замерьте OFFSET 0, OFFSET 100000, OFFSET 1000000, затем реализуйте keyset-пагинацию и повторите замеры.

Soft delete и audit fields

Средний

Soft delete — «удаление» через отметку deleted_at вместо физического DELETE. Нужен там, где данные восстанавливают, где на них ссылается история или где требуется аудит. Audit fields — created_at, updated_at, deleted_at, часто created_by, updated_by.

sqlСлужебные поля и работа с soft delete
ALTER TABLE posts
    ADD COLUMN created_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    ADD COLUMN updated_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP
                                       ON UPDATE CURRENT_TIMESTAMP,
    ADD COLUMN deleted_at DATETIME     NULL DEFAULT NULL,
    ADD COLUMN created_by BIGINT UNSIGNED NULL;

-- "Удаление"
UPDATE posts SET deleted_at = NOW() WHERE id = 10;

-- Каждый запрос обязан учитывать флаг
SELECT * FROM posts WHERE deleted_at IS NULL AND user_id = 42;

-- Частичный индекс (PostgreSQL): индексируем только живые строки
CREATE INDEX idx_posts_live_user ON posts (user_id, created_at)
WHERE deleted_at IS NULL;

-- Уникальность с учётом soft delete: удалённый email не должен блокировать новый
CREATE UNIQUE INDEX uniq_users_email_live ON users (email) WHERE deleted_at IS NULL;
ВажноSoft delete ломает UNIQUE-ограничения: удалённый пользователь с тем же email продолжает занимать значение. Решения: частичный уникальный индекс (PostgreSQL), уникальность по паре (email, deleted_at) или колонка deleted_token, куда при удалении пишется уникальный суффикс.
Типичная ошибкаЗабыть deleted_at IS NULL ровно в одном запросе — и удалённые записи всплывают в отчёте или в публичном API. Поэтому фильтр лучше держать в одном месте: глобальный скоуп ORM, view или репозиторий.
Как диагностироватьСравните COUNT(*) и COUNT(*) WHERE deleted_at IS NULL на горячих таблицах. Если удалённых больше 30–50%, индексы работают вхолостую — пора архивировать «мусор» в отдельную таблицу.
Типичный вопрос на собеседованииПлюсы и минусы soft delete?
Плюсы: восстановление, аудит, сохранность ссылочной целостности в истории. Минусы: раздувание таблиц и индексов, конфликт с UNIQUE, риск утечки «удалённых» данных, необходимость фильтра в каждом запросе, конфликт с требованиями GDPR о реальном удалении персональных данных.
ПрактикаДобавьте soft delete в блог: восстановление поста, частичный уникальный индекс на email, отдельная команда «жёсткой» очистки записей старше 90 дней.

Архитектурное проектирование БД

Senior

Проектирование схемы начинается не с таблиц, а с трёх вопросов: какие инварианты обязаны выполняться всегда (баланс не уходит в минус, у заказа не бывает двух оплат), какие запросы будут горячими и с какой частотой, и как данные будут расти через два года. Схема — это застывшая форма ответов на эти вопросы.

Практический порядок: список сущностей и их жизненные циклы → инварианты и границы транзакций (что обязано меняться атомарно) → точки входа в данные (по каким ключам ищем) → индексы под эти точки → оценка объёма и профиль роста → решение о денормализации.

Ситуация из проектаМаркетплейс. Изначально «остаток товара» хранился как поле products.qty. Через год появились склады, резервы под неоплаченные заказы и возвраты. Каждое изменение остатка стало гонкой за одну строку: на распродаже 400 запросов в секунду упирались в одну строку products, время ответа выросло до 3 секунд.
Архитектурное решениеОстаток перестал быть числом и стал журналом движений: таблица stock_movements(product_id, warehouse_id, delta, reason, order_id, created_at) только на вставку, плюс агрегатная таблица stock_balance с текущим остатком, обновляемая транзакционно. Резерв — отдельный тип движения с TTL. Конкуренция размазалась по складам, появился полный аудит «куда делся товар», а сверка стала возможной: SUM(delta) обязан совпадать с балансом.
РискиЖурнал растёт быстро — нужны партиционирование и архивация. Агрегат может разойтись с журналом при багах — нужен регулярный джоб сверки. Отчёты «остаток на дату» становятся дороже — решается снапшотами на конец суток.
Вопрос на собеседованииКак вы проектируете схему для новой предметной области?
От инвариантов и запросов, а не от «сущностей вообще». Формулирую, что должно быть атомарно (это границы агрегатов и транзакций), какие точки входа будут горячими, каков профиль роста. Затем нормализую до 3NF и осознанно денормализую там, где это подтверждено измерением, а не предчувствием.

senior / основы / acid

ACID на практическом уровне

Senior
  • Atomicity — транзакция применяется целиком либо не применяется. Реализуется undo-логом.
  • Consistency — после коммита выполнены все ограничения БД. Обратите внимание: это согласованность по ограничениям схемы, а не «бизнес-логика корректна».
  • Isolation — параллельные транзакции не видят промежуточных состояний друг друга; степень задаётся уровнем изоляции.
  • Durability — после COMMIT данные переживут падение процесса и сервера. Обеспечивается WAL / redo-логом и fsync.
sqlDurability стоит денег: настройки, которыми её торгуют
-- MySQL: 1 = fsync на каждый commit (безопасно), 2 и 0 — быстрее, но при сбое
-- сервера можно потерять последние транзакции
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
SHOW VARIABLES LIKE 'sync_binlog';

-- PostgreSQL: synchronous_commit = off даёт заметный прирост записи
-- ценой потери нескольких последних коммитов при аварии
SHOW synchronous_commit;
Ситуация из проектаСервис аналитики писал 30 000 событий в секунду и упирался в диск. Для этой таблицы включили групповой коммит и innodb_flush_log_at_trx_commit = 2: потеря секунды событий при падении узла была приемлемой. Для таблицы платежей в той же базе настройка осталась строгой — потеря даже одной транзакции недопустима.
Архитектурное решениеРазные требования к долговечности — разные хранилища. Платежи остались в основном кластере с полным ACID и синхронной репликой; события переехали в отдельный инстанс с ослабленной durability и последующей выгрузкой в аналитическое хранилище.
РискиОслабленный fsync означает, что реплика может уйти вперёд мастера после аварии; нужен корректный failover и понимание, какие данные допустимо потерять. Никогда не применяйте такие настройки «глобально ради скорости».
Вопрос на собеседованииЧто означает Durability и как она достигается?
Гарантия, что подтверждённая транзакция не пропадёт при сбое. Достигается журналом упреждающей записи (WAL/redo): изменения сначала попадают в лог и сбрасываются на диск, и только потом применяются к страницам данных. Скорость регулируется тем, как часто и насколько синхронно выполняется fsync.
Senior-заданиеОпишите для своего проекта матрицу «тип данных → допустимая потеря при аварии (RPO) → требуемые настройки durability и репликации».

MySQL vs PostgreSQL и CAP на практике

Senior

Практический ответ на «что выбрать» звучит скучно: берите то, что команда умеет эксплуатировать. Различия важны только когда есть конкретное требование, которое одна СУБД закрывает, а другая — нет.

  • PostgreSQL сильнее в сложной аналитике и нестандартных типах: JSONB с GIN, массивы, диапазонные типы, CHECK-ограничения, частичные и функциональные индексы, полнотекстовый поиск, расширения (PostGIS, pg_trgm), транзакционный DDL.
  • MySQL сильнее в простоте эксплуатации, зрелой асинхронной репликации, огромной экосистеме хостингов и предсказуемой скорости примитивных запросов по PK на очень высокой частоте.

CAP-теорема утверждает: при сетевом разделении (P) система вынуждена выбирать между согласованностью (C) и доступностью (A). Практическая ценность её ограничена: разделение случается редко, а большую часть времени вы выбираете между задержкой и согласованностью — это точнее описывает модель PACELC.

Ситуация из проектаКластер с одним мастером и двумя асинхронными репликами. Пользователь оформляет заказ (запись на мастер) и сразу открывает «Мои заказы» (чтение с реплики), а лаг репликации в момент пика — 800 мс. Заказа нет на экране, пользователь оформляет второй.
Архитектурное решениеВвели правило «read-your-own-writes»: после записи пользователь на N секунд помечается в Redis, и его чтения принудительно идут на мастер. Плюс на критичных операциях включили ожидание позиции реплики (MASTER_POS_WAIT в MySQL, pg_wal_lsn_diff в PostgreSQL). Плюс идемпотентность оформления, чтобы дубль всё равно не создал второй заказ.
РискиПринудительное чтение с мастера сводит на нет выигрыш от реплик, если правило применяется слишком широко. Ожидание позиции реплики увеличивает задержку и может таймаутиться при большом лаге.
Вопрос на собеседованииОбъясните CAP на примере вашего проекта.
При разрыве между мастером и репликой можно либо продолжать отдавать возможно устаревшие данные (AP), либо отказывать в обслуживании до восстановления (CP). Мы выбрали AP для чтения каталога и CP для операций с деньгами — платёжные запросы идут строго на мастер и падают явной ошибкой, если он недоступен.

senior / масштабирование / репликация

Репликация и read/write splitting

SeniorСпрашивают всегда

Репликация — поддержание копий данных на других серверах. Даёт масштабирование чтения, отказоустойчивость и площадку для тяжёлой аналитики.

  • Асинхронная — мастер не ждёт реплику. Быстро, но при аварии мастера часть транзакций теряется.
  • Полусинхронная — мастер ждёт подтверждения хотя бы от одной реплики. Компромисс, чаще всего оптимальный.
  • Синхронная — ждём все реплики. Максимальная надёжность, максимальная задержка записи.
phpМаршрутизация чтения и записи
<?php
final class ConnectionRouter
{
    private ?PDO $master = null;
    /** @var PDO[] */
    private array $replicas = [];
    private bool $stickyToMaster = false;

    public function write(): PDO
    {
        $this->stickyToMaster = true;     // после записи читаем с мастера
        return $this->master ??= $this->connect($this->masterDsn);
    }

    public function read(): PDO
    {
        if ($this->stickyToMaster || $this->replicas === []) {
            return $this->write();
        }
        return $this->replicas[array_rand($this->replicas)];
    }
}

// Важное правило: любой запрос внутри транзакции идёт только на мастер.
// Готовые решения: Doctrine PrimaryReadReplicaConnection, Laravel read/write в config/database.php,
// либо внешний прокси (ProxySQL, PgBouncer + HAProxy, Vitess).
Ситуация из проектаАналитический отчёт запускался на реплике и держал транзакцию 20 минут. На PostgreSQL это вызвало конфликт с очисткой старых версий строк: реплика начала отставать, а затем принудительно откатывать долгие запросы. Отчёты падали, лаг рос до десятков минут.
Архитектурное решениеРазделили реплики по назначению: «быстрые» реплики для пользовательских чтений с малым лагом и отдельная «аналитическая» реплика с включённым hot_standby_feedback и увеличенными задержками конфликтов. Тяжёлые отчёты уехали в отдельное хранилище с ночной выгрузкой.
РискиРеплики не масштабируют запись — она остаётся на одном мастере. Лаг репликации порождает баги «данные пропали». Failover без проверенного автоматического механизма (Orchestrator, Patroni) — это ручная работа под давлением в 3 часа ночи.
Вопрос на собеседованииКак обеспечить, чтобы пользователь сразу видел свои изменения при чтении с реплик?
Три приёма: sticky-сессия на мастер на короткое время после записи; ожидание достижения репликой нужной позиции лога; либо возврат клиенту уже записанного объекта из ответа на запись, без повторного чтения.

Шардирование и партиционирование

Senior

Партиционирование — разбиение одной таблицы на части внутри одного сервера (по диапазону дат, по хешу, по списку). Шардирование — разбиение данных между разными серверами. Первое решает проблему размера таблицы, второе — предела записи и объёма.

sqlПартиционирование по дате
-- PostgreSQL: декларативное партиционирование
CREATE TABLE events (
    id         BIGSERIAL,
    user_id    BIGINT NOT NULL,
    type       VARCHAR(50) NOT NULL,
    payload    JSONB,
    created_at TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_07 PARTITION OF events
    FOR VALUES FROM ('2026-07-01') TO ('2026-08-01');

-- Удаление старых данных за миллисекунды вместо часового DELETE:
DROP TABLE events_2026_01;

-- MySQL
ALTER TABLE events PARTITION BY RANGE (TO_DAYS(created_at)) (
    PARTITION p202607 VALUES LESS THAN (TO_DAYS('2026-08-01')),
    PARTITION pmax    VALUES LESS THAN MAXVALUE
);

Ключ шардирования — главное и почти необратимое решение. Для SaaS это обычно tenant_id, для соцсети — user_id, для маркетплейса — иногда seller_id. Правило: запрос должен уметь определить шард без обращения ко всем шардам.

Ситуация из проектаТаблица events выросла до 1,2 млрд строк. DELETE старых записей шёл 6 часов и забивал репликацию, ALTER TABLE стал невозможен, бэкап занимал ночь целиком.
Архитектурное решениеПомесячное партиционирование по created_at с автоматическим созданием партиций вперёд и отсоединением старых (DETACH PARTITION → выгрузка в S3 → DROP). Очистка стала мгновенной, запросы за последний месяц читают одну партицию, бэкап сократился втрое.
РискиПартиционирование помогает только если WHERE содержит ключ партиционирования — иначе БД сканирует все партиции и становится хуже, чем было. Уникальные индексы в партиционированной таблице обязаны включать ключ партиционирования. Шардирование ломает JOIN между шардами, кросс-шардовые транзакции и AUTO_INCREMENT — нужны глобальные id (UUIDv7, Snowflake) и агрегация результатов в приложении.
Вопрос на собеседованииЧем шардирование отличается от партиционирования и когда пора шардировать?
Партиционирование — внутри сервера, прозрачно для приложения. Шардирование — между серверами, требует логики роутинга. Шардировать стоит, когда исчерпаны вертикальное масштабирование, реплики для чтения, кэш, архивация и партиционирование, и упирается именно запись. Это последний шаг, а не первый.

Идемпотентность, outbox и eventual consistency

SeniorКритично

Идемпотентность — повторное выполнение операции даёт тот же результат, что и однократное. В распределённой системе повторы неизбежны: таймауты, ретраи очереди, двойной клик, webhook, доставленный дважды.

sqlИдемпотентность на уникальном ключе
CREATE TABLE payments (
    id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    order_id        BIGINT UNSIGNED NOT NULL,
    idempotency_key VARCHAR(64)     NOT NULL,
    amount          DECIMAL(12,2)   NOT NULL,
    status          VARCHAR(20)     NOT NULL,
    created_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uniq_payments_idem (idempotency_key)
);

-- Повторный запрос с тем же ключом не создаёт второй платёж
INSERT INTO payments (order_id, idempotency_key, amount, status)
VALUES (:order_id, :key, :amount, 'pending')
ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(id);
phpИдемпотентный обработчик платежа
<?php
public function charge(int $orderId, string $amount, string $idempotencyKey): Payment
{
    $this->pdo->beginTransaction();
    try {
        $stmt = $this->pdo->prepare(
            'INSERT INTO payments (order_id, idempotency_key, amount, status)
             VALUES (:o, :k, :a, \'pending\')'
        );
        $stmt->execute([':o' => $orderId, ':k' => $idempotencyKey, ':a' => $amount]);
        $paymentId = (int) $this->pdo->lastInsertId();
        $this->pdo->commit();
    } catch (PDOException $e) {
        $this->pdo->rollBack();
        // 23000 — нарушение уникальности: платёж уже создан, возвращаем существующий
        if ($e->getCode() !== '23000') {
            throw $e;
        }
        return $this->findByKey($idempotencyKey);
    }

    return $this->findById($paymentId);
}

Outbox pattern

Проблема двойной записи: нельзя атомарно записать в БД и отправить сообщение в очередь. Если сначала коммит, а затем publish — сообщение может не уйти. Если наоборот — событие уйдёт о том, чего не случилось. Outbox решает это: событие пишется в таблицу той же транзакцией, а отдельный процесс читает таблицу и публикует.

sqlOutbox: таблица и разбор
CREATE TABLE outbox_messages (
    id           BIGSERIAL PRIMARY KEY,
    aggregate    VARCHAR(50)  NOT NULL,
    aggregate_id VARCHAR(64)  NOT NULL,
    event_type   VARCHAR(100) NOT NULL,
    payload      JSONB        NOT NULL,
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    published_at TIMESTAMPTZ  NULL
);
CREATE INDEX idx_outbox_unpublished ON outbox_messages (id) WHERE published_at IS NULL;

-- Одна транзакция: бизнес-изменение + событие
BEGIN;
    UPDATE orders SET status = 'paid' WHERE id = 100;
    INSERT INTO outbox_messages (aggregate, aggregate_id, event_type, payload)
    VALUES ('order', '100', 'order.paid', '{"order_id":100,"amount":"1500.00"}');
COMMIT;

-- Воркер-публикатор: несколько экземпляров не мешают друг другу
BEGIN;
    SELECT * FROM outbox_messages
     WHERE published_at IS NULL
     ORDER BY id
     LIMIT 100
     FOR UPDATE SKIP LOCKED;
    -- ... публикация в брокер ...
    UPDATE outbox_messages SET published_at = NOW() WHERE id = ANY(:ids);
COMMIT;
ВажноOutbox даёт гарантию at-least-once: сообщение может уйти дважды, если воркер упал между публикацией и отметкой. Поэтому потребитель обязан быть идемпотентным — эти два паттерна всегда работают в паре.
Ситуация из проектаПлатёжный шлюз при таймауте отправлял webhook повторно. Обработчик создавал вторую запись оплаты, заказ помечался оплаченным дважды, и в бухгалтерии расходились цифры. Клиенты получали два письма «спасибо за покупку».
Архитектурное решениеКлюч идемпотентности от шлюза (или хеш от order_id + amount + provider_tx_id) в UNIQUE-индексе, ответ 200 на повтор без создания записи, все внешние события — через outbox, отправка писем — в очередь с дедупликацией по ключу события.
РискиТаблица outbox быстро растёт — нужны чистка опубликованных и мониторинг «возраста» самого старого неопубликованного сообщения. Порядок событий между агрегатами не гарантирован — потребители не должны на него полагаться.
Вопрос на собеседованииКак гарантировать, что платёж не пройдёт дважды?
Ключ идемпотентности с уникальным индексом в БД плюс транзакция: попытка вставки дубля падает на constraint, и мы возвращаем ранее созданный результат. Дополнительно — состояние платежа как конечный автомат с разрешёнными переходами и UPDATE ... WHERE status = 'pending', чтобы переход выполнялся ровно один раз.

Optimistic и pessimistic locking

Senior
sqlДве стратегии против потерянного обновления
-- ОПТИМИСТИЧНАЯ: версия строки, конфликт обнаруживается при записи
ALTER TABLE documents ADD COLUMN version INT NOT NULL DEFAULT 1;

UPDATE documents
   SET title = :title, body = :body, version = version + 1
 WHERE id = :id AND version = :expected_version;
-- rowCount() === 0 → кто-то изменил документ раньше нас → конфликт

-- ПЕССИМИСТИЧНАЯ: блокируем строку до конца транзакции
BEGIN;
    SELECT * FROM documents WHERE id = :id FOR UPDATE;
    -- ... расчёты ...
    UPDATE documents SET title = :title WHERE id = :id;
COMMIT;
phpОбработка конфликта версий
<?php
public function update(int $id, string $title, int $expectedVersion): void
{
    $stmt = $this->pdo->prepare(
        'UPDATE documents
            SET title = :title, version = version + 1, updated_at = NOW()
          WHERE id = :id AND version = :version'
    );
    $stmt->execute([':title' => $title, ':id' => $id, ':version' => $expectedVersion]);

    if ($stmt->rowCount() === 0) {
        // Отдаём 409 Conflict и текущую версию, чтобы UI показал diff
        throw new ConcurrentModificationException($id, $expectedVersion);
    }
}
ВажноПравило выбора: оптимистичная — когда конфликты редки, а пользователь может разрешить их вручную (редактирование карточки товара, профиля, документа). Пессимистичная — когда конфликт вероятен и дорог, а операция короткая (списание остатка, резерв места, начисление баланса).
Ситуация из проектаДва менеджера одновременно правили карточку товара в админке. Тот, кто сохранял вторым, молча затирал чужие изменения цены. Проблему обнаружили только по жалобам на «самовольно откатывающуюся цену».
Архитектурное решениеКолонка version, скрытое поле версии в форме, HTTP 409 с показом изменений и кнопкой «перезаписать». Для остатков склада — пессимистичная схема с FOR UPDATE и коротким критическим участком.
РискиОптимистичная блокировка при частых конфликтах превращается в бесконечные ретраи. Пессимистичная — в очередь ожидания и потенциальный deadlock; обязательны таймаут ожидания и порядок захвата.
Вопрос на собеседованииОптимистичная или пессимистичная блокировка — что выберете и почему?
Зависит от вероятности и цены конфликта плюс длительности операции. Долгая пользовательская правка — только оптимистичная, иначе строка будет заблокирована всё время, пока человек думает. Короткое списание остатка под высокой конкуренцией — пессимистичная или атомарный UPDATE ... WHERE qty >= :n.

CQRS и event sourcing

Senior

CQRS — разделение модели записи и модели чтения. Запись идёт в нормализованную схему с инвариантами, чтение — в подготовленные денормализованные проекции (отдельные таблицы, материализованные представления, Elasticsearch). Это не обязательно две базы: чаще всего это две модели над одной.

Event sourcing — состояние не хранится, а выводится из неизменяемого журнала событий. Даёт полный аудит, возможность «отмотать» состояние на любой момент и построить новую проекцию задним числом.

sqlХранилище событий и проекция для чтения
-- Журнал событий: только вставка, никаких UPDATE
CREATE TABLE event_store (
    id            BIGSERIAL PRIMARY KEY,
    aggregate_id  UUID        NOT NULL,
    aggregate_type VARCHAR(50) NOT NULL,
    version       INT         NOT NULL,
    event_type    VARCHAR(100) NOT NULL,
    payload       JSONB       NOT NULL,
    occurred_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (aggregate_id, version)   -- оптимистичная блокировка агрегата
);

-- Проекция для чтения: денормализована под конкретный экран
CREATE TABLE order_list_view (
    order_id     UUID PRIMARY KEY,
    customer_name VARCHAR(200) NOT NULL,
    status       VARCHAR(30)  NOT NULL,
    items_count  INT          NOT NULL,
    total        NUMERIC(12,2) NOT NULL,
    updated_at   TIMESTAMPTZ  NOT NULL
);
CREATE INDEX idx_olv_status_updated ON order_list_view (status, updated_at DESC);

-- Более лёгкий вариант CQRS без event sourcing: материализованное представление
CREATE MATERIALIZED VIEW seller_daily_stats AS
SELECT seller_id, DATE(created_at) AS d, COUNT(*) AS orders, SUM(total) AS revenue
FROM orders WHERE status = 'paid' GROUP BY seller_id, DATE(created_at);

REFRESH MATERIALIZED VIEW CONCURRENTLY seller_daily_stats;
Ситуация из проектаЭкран списка заказов в админке собирался из 9 таблиц с фильтрами по статусу, продавцу, дате и поиском по клиенту. Запрос занимал 4–8 секунд, и любая новая колонка в фильтре ломала план.
Архитектурное решениеВвели проекцию order_list_view, обновляемую подписчиком на события заказа (через outbox). Экран стал читать одну таблицу с двумя индексами: 40 мс вместо 6 секунд. Модель записи осталась строго нормализованной, инварианты не пострадали.
РискиПроекция отстаёт — нужны мониторинг лага и явная индикация в UI, если это критично. Восстановление проекции с нуля на большом журнале может занять часы — нужны снапшоты. Event sourcing резко повышает сложность: миграции схемы событий, версионирование, отладка. Применять только там, где аудит и история — это бизнес-требование (финансы, склад, медицина), а не «чтобы красиво».
Вопрос на собеседованииКогда CQRS оправдан, а когда это оверинжиниринг?
Оправдан, когда профили нагрузки чтения и записи расходятся кардинально: редкая запись со сложными инвариантами и массовое чтение по десятку разных срезов. Оверинжиниринг — когда команда маленькая, нагрузка умеренная, а согласованность «здесь и сейчас» дороже скорости. Начинать почти всегда стоит с одной модели и материализованных представлений.

senior / эксплуатация / миграции без downtime

Миграции без downtime, backfill и большие таблицы

SeniorСпрашивают всегда

Базовый принцип: схема и код должны быть совместимы в обе стороны на время выката. Во время деплоя одновременно работают старые и новые инстансы приложения, поэтому любое изменение раскладывается на несколько безопасных шагов.

Expand / Migrate / Contract

  1. Expand. Добавляем новое, ничего не ломая: новая колонка NULL без DEFAULT, новая таблица, новый индекс CONCURRENTLY.
  2. Двойная запись. Код пишет и в старое, и в новое поле; читает пока из старого.
  3. Backfill. Фоновый перенос исторических данных пачками.
  4. Переключение чтения. Код читает из нового поля; старое остаётся нетронутым.
  5. Contract. Через несколько релизов (когда откат уже не нужен) удаляем старую колонку и двойную запись.

ALTER TABLE users RENAME COLUMN phone TO phone_number;

-- БЕЗОПАСНО: добавить новую колонку, дублировать запись, потом удалить старую
ALTER TABLE users ADD COLUMN phone_number VARCHAR(20) NULL;

-- PostgreSQL: индекс без блокировки записи (нельзя внутри транзакции)
CREATE INDEX CONCURRENTLY idx_orders_user_created ON orders (user_id, created_at);
DROP INDEX CONCURRENTLY idx_old;

-- MySQL 8: онлайн-DDL, если алгоритм поддерживается

    ALGORITHM=INPLACE, LOCK=NONE;
-- Если сервер отказывается — pt-online-schema-change или gh-ost

ALTER TABLE orders VALIDATE CONSTRAINT chk_note_nn;   -- проверка без ACCESS EXCLUSIVE
phpBackfill пачками с контролем нагрузки
<?php
// Идём по PK, а не по OFFSET: постоянное время на любой глубине
$lastId    = 0;
$batchSize = 1000;

do {
    $stmt = $pdo->prepare(
        'SELECT id, phone FROM users
          WHERE id > :last AND phone_number IS NULL AND phone IS NOT NULL
          ORDER BY id LIMIT :lim'
    );
    $stmt->bindValue(':last', $lastId, PDO::PARAM_INT);
    $stmt->bindValue(':lim', $batchSize, PDO::PARAM_INT);
    $stmt->execute();
    $rows = $stmt->fetchAll();

    if ($rows === []) {
        break;
    }

    $pdo->beginTransaction();
    $update = $pdo->prepare('UPDATE users SET phone_number = :v WHERE id = :id');
    foreach ($rows as $row) {
        $update->execute([':v' => normalizePhone($row['phone']), ':id' => $row['id']]);
        $lastId = (int) $row['id'];
    }
    $pdo->commit();

    // Пауза + проверка лага реплики: не топим прод фоновой задачей
    usleep(100_000);
    waitForReplicationLagBelow($pdo, seconds: 1);
} while (true);
ВажноBackfill должен быть возобновляемым (хранит позицию), идемпотентным (условие WHERE new_col IS NULL) и управляемым (можно остановить и снизить скорость). Запускать его надо как обычный фоновый процесс, а не как шаг миграции в деплой-пайплайне.
Ситуация из проектаALTER TABLE orders ADD COLUMN на таблице в 80 млн строк в MySQL 5.7 заблокировал запись на 40 минут в час пик. Откатить было нельзя — операция уже шла.
Архитектурное решениеВсе DDL на таблицах свыше ~10 млн строк выполняются через gh-ost (копия таблицы + применение binlog + атомарная подмена) с ограничением по лагу реплики и возможностью паузы. В CI появилась проверка миграций: запрещены RENAME, DROP COLUMN в одном релизе с кодом и CREATE INDEX без CONCURRENTLY на PostgreSQL.
РискиДвойная запись усложняет код и обязана быть удалена — иначе через год никто не помнит, какая колонка настоящая. Долгий backfill раздувает WAL/binlog и может переполнить диск. Онлайн-инструменты требуют места под копию таблицы (примерно ×2).
Вопрос на собеседованииКак переименовать колонку в таблице на 100 млн строк без простоя?
Не переименовывать. Добавить новую колонку, включить двойную запись, выполнить фоновый backfill пачками по PK с контролем лага, переключить чтение, выждать несколько релизов ради возможности отката и только затем удалить старую колонку.

Мониторинг, slow query log и connection pooling

Senior

Что мониторить

  • Задержки запросов — p50/p95/p99, а не среднее: среднее прячет именно те запросы, которые ломают пользователям опыт.
  • QPS по типам запросов и топ по суммарному времени (не по единичному — 10 мс × 100 000 вызовов хуже, чем 2 с × 5).
  • Соединения: активные/лимит, ожидающие, idle in transaction.
  • Лаг репликации в секундах и байтах.
  • Буферный кэш: hit ratio, объём чтения с диска.
  • Блокировки и deadlock-и в единицу времени.
  • Место на диске и рост крупнейших таблиц и индексов.
  • Bloat и вакуум (PostgreSQL): возраст транзакций, автовакуум, «раздутость» таблиц.
sqlЗапросы для ежедневной эксплуатации
-- PostgreSQL: топ запросов по суммарному времени
SELECT calls, round(total_exec_time) AS total_ms,
       round(mean_exec_time, 2) AS mean_ms, rows, query
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 20;

-- PostgreSQL: кто держит транзакцию открытой
SELECT pid, state, now() - xact_start AS xact_age, wait_event_type, left(query, 120)
FROM pg_stat_activity
WHERE state <> 'idle' ORDER BY xact_start;

-- PostgreSQL: неиспользуемые индексы и размер таблиц
SELECT relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes WHERE idx_scan = 0 ORDER BY pg_relation_size(indexrelid) DESC;

-- MySQL: включить лог медленных запросов
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 0.5;
SET GLOBAL log_queries_not_using_indexes = 'ON';
-- Разбор: pt-query-digest /var/log/mysql/slow.log

-- MySQL: текущие транзакции и блокировки
SELECT trx_id, trx_started, trx_state, trx_rows_locked, trx_query
FROM information_schema.innodb_trx ORDER BY trx_started;

Connection pooling

PHP по природе не держит пул: каждый воркер FPM открывает своё соединение и закрывает после запроса. 100 воркеров × 5 серверов = 500 соединений, что для PostgreSQL уже много (каждое соединение — процесс с собственной памятью).

phpВарианты пулинга в PHP
<?php
// 1. Persistent-соединения PDO: живут между запросами внутри воркера.
//    Осторожно: незакрытая транзакция или временная таблица «переезжает»
//    в следующий запрос. Всегда проверяйте состояние.
$pdo = new PDO($dsn, $user, $pass, [
    PDO::ATTR_PERSISTENT => true,
    PDO::ATTR_ERRMODE    => PDO::ERRMODE_EXCEPTION,
]);

// 2. Внешний пулер — правильный путь для PostgreSQL:
//    PgBouncer в режиме transaction pooling между PHP и базой.
//    Ограничение: в transaction-режиме нельзя использовать серверные
//    prepared statements между транзакциями, advisory-локи и LISTEN/NOTIFY.

// 3. Для MySQL — ProxySQL: пулинг, роутинг read/write, зеркалирование, кэш.

// 4. Долгоживущие рантаймы (Swoole, RoadRunner, FrankenPHP) дают
//    настоящий пул внутри процесса — но требуют аккуратности с состоянием.
Ситуация из проектаПик трафика → автоскейлинг поднял 20 подов PHP-FPM → каждый по 40 воркеров → 800 соединений при max_connections = 500. База начала отклонять подключения, приложение — отдавать 500-е ошибки. Причём сама БД была почти не загружена: проблема была в количестве соединений, а не в запросах.
Архитектурное решениеPgBouncer в transaction-режиме перед базой: 800 клиентских соединений схлопнулись в 40 серверных. Дополнительно ограничили число воркеров на под и вынесли долгие задачи в отдельный пул с собственным лимитом соединений.
РискиTransaction pooling несовместим с сессионными фичами; часть ORM требует настройки (отключение серверных prepared statements). Persistent-соединения без дисциплины приводят к «залипшим» транзакциям и трудноуловимым багам.
Вопрос на собеседованииПочему в PHP нужен внешний пулер соединений?
Потому что модель «процесс на запрос» не позволяет переиспользовать соединения между запросами, а каждое соединение к PostgreSQL — отдельный серверный процесс со своей памятью. Внешний пулер мультиплексирует сотни клиентских соединений в десятки серверных.

senior / архитектура / очереди и нагрузка

Очереди, проектирование под нагрузку и денормализация

Senior

БД можно использовать как очередь — и это нормально для умеренных объёмов: SELECT ... FOR UPDATE SKIP LOCKED даёт корректную конкурентную выборку задач без брокера, а транзакционность позволяет ставить задачу тем же коммитом, что и бизнес-изменение.

sqlОчередь на таблице
CREATE TABLE jobs (
    id            BIGSERIAL PRIMARY KEY,
    queue         VARCHAR(50) NOT NULL DEFAULT 'default',
    payload       JSONB       NOT NULL,
    attempts      SMALLINT    NOT NULL DEFAULT 0,
    available_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    reserved_at   TIMESTAMPTZ NULL
);
CREATE INDEX idx_jobs_ready ON jobs (queue, available_at) WHERE reserved_at IS NULL;

-- Воркер забирает пачку, не конфликтуя с соседями
BEGIN;
    SELECT id, payload FROM jobs
     WHERE queue = 'emails' AND reserved_at IS NULL AND available_at <= NOW()
     ORDER BY id LIMIT 10
     FOR UPDATE SKIP LOCKED;
    UPDATE jobs SET reserved_at = NOW(), attempts = attempts + 1 WHERE id = ANY(:ids);
COMMIT;

Нормализация против денормализации

Нормализация защищает корректность, денормализация покупает скорость чтения ценой сложности поддержания согласованности. Правило: нормализуйте по умолчанию, денормализуйте по измерению.

sqlТри уровня денормализации
-- 1. Счётчик-кэш: самое дешёвое и самое частое
ALTER TABLE posts ADD COLUMN comments_count INT NOT NULL DEFAULT 0;
-- обновляется той же транзакцией, что и вставка комментария,
-- и периодически сверяется фоновым джобом

-- 2. Продублированное поле ради индекса без JOIN
ALTER TABLE order_items ADD COLUMN seller_id BIGINT UNSIGNED NOT NULL;
CREATE INDEX idx_oi_seller ON order_items (seller_id, created_at);

-- 3. Агрегатная таблица, обновляемая по расписанию или по событиям
CREATE TABLE daily_sales (
    d          DATE NOT NULL,
    seller_id  BIGINT NOT NULL,
    orders     INT NOT NULL,
    revenue    NUMERIC(14,2) NOT NULL,
    PRIMARY KEY (d, seller_id)
);
Ситуация из проектаГлавная страница считала COUNT(*) комментариев для 30 постов на каждый заход. При 2000 rps это давало 60 000 агрегирующих запросов в секунду и съедало весь CPU базы, хотя данные менялись раз в минуту.
Архитектурное решениеСчётчик comments_count в posts, обновляемый той же транзакцией, что и вставка комментария, плюс ночная сверка с фактическим COUNT и алерт при расхождении. Нагрузка на CPU базы упала в 6 раз, страница перестала зависеть от размера таблицы комментариев.
РискиЛюбая денормализация — это второй источник истины, который однажды разойдётся с первым. Обязательны: обновление в одной транзакции с исходным изменением (или через outbox), регулярная сверка, алерт на расхождение и документированный способ пересчёта.
Вопрос на собеседованииКогда вы пойдёте на денормализацию?
Когда измерение показало, что конкретный горячий запрос дорог, а нормализованное решение исчерпано (индексы, переписанный запрос, кэш). Начинаю с самого дешёвого варианта — счётчика или агрегатной таблицы, — и всегда добавляю сверку. Денормализация «на будущее», до появления нагрузки, — это чистый технический долг.

Сводный блок по работе с базой из PHP. Всё, что здесь есть, спрашивают на собеседованиях любого уровня — и почти всё пригождается в первый же рабочий день.

<?php
declare(strict_types=1);

final class ConnectionFactory
{
    public function __construct(
        private string $host,
        private string $db,
        private string $user,
        private string $password,
        private int $port = 3306,
    ) {}

    public function create(): PDO
    {
        $dsn = sprintf(
            'mysql:host=%s;port=%d;dbname=%s;charset=utf8mb4',
            $this->host, $this->port, $this->db

        $pdo = new PDO($dsn, $this->user, $this->password, [
            PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
            PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,

            PDO::ATTR_STRINGIFY_FETCHES  => false,
            PDO::ATTR_TIMEOUT            => 5,

        $pdo->exec("SET time_zone = '+00:00'");
        $pdo->exec("SET SESSION sql_mode = 'STRICT_ALL_TABLES,NO_ENGINE_SUBSTITUTION'");

        return $pdo;
    }

phpВложенные транзакции через SAVEPOINT
<?php
// PDO::beginTransaction() не поддерживает вложенность: второй вызов бросит
// исключение. Стандартное решение — счётчик уровней + SAVEPOINT.
final class TransactionManager
{
    private int $level = 0;

    public function __construct(private PDO $pdo) {}

    public function transactional(callable $fn): mixed
    {
        $this->begin();
        try {
            $result = $fn();
            $this->commit();
            return $result;
        } catch (Throwable $e) {
            $this->rollback();
            throw $e;
        }
    }

    private function begin(): void
    {
        $this->level === 0
            ? $this->pdo->beginTransaction()
            : $this->pdo->exec('SAVEPOINT sp' . $this->level);
        $this->level++;
    }

    private function commit(): void
    {
        $this->level--;
        if ($this->level === 0) {
            $this->pdo->commit();
        } else {
            $this->pdo->exec('RELEASE SAVEPOINT sp' . $this->level);
        }
    }

    private function rollback(): void
    {
        $this->level--;
        if ($this->level === 0) {
            $this->pdo->rollBack();
        } else {
            $this->pdo->exec('ROLLBACK TO SAVEPOINT sp' . $this->level);
        }
    }
}
ВажноВ MySQL DDL-операции (CREATE TABLE, ALTER TABLE, TRUNCATE) вызывают неявный коммит и рвут открытую транзакцию. Никогда не смешивайте DDL и бизнес-транзакции.

<?php
declare(strict_types=1);

final class ProductSearch
{
    private const SORTABLE = ['name', 'price', 'created_at'];   // белый список
    private const PER_PAGE = 20;

    public function __construct(private PDO $pdo) {}

    /** @return array<int, array{id:int, name:string, price:string}> */
    public function search(string $query, string $sort, int $page): array
    {
        $sort  = in_array($sort, self::SORTABLE, true) ? $sort : 'created_at';
        $page  = max(1, $page);
        $offset = ($page - 1) * self::PER_PAGE;

        $sql = "SELECT id, name, price
                  FROM products
                 WHERE name LIKE :q AND deleted_at IS NULL
                 ORDER BY {$sort} DESC, id DESC
                 LIMIT :lim OFFSET :off";

        $stmt = $this->pdo->prepare($sql);
        // Экранируем спецсимволы LIKE, иначе '%' от пользователя сломает поиск
        $escaped = addcslashes($query, '%_\\');
        $stmt->bindValue(':q', '%' . $escaped . '%');
        $stmt->bindValue(':lim', self::PER_PAGE, PDO::PARAM_INT);
        $stmt->bindValue(':off', $offset, PDO::PARAM_INT);
        $stmt->execute();

        return $stmt->fetchAll();
    }
}

Ответы намеренно короткие — это каркас, а не пересказ. На собеседовании выигрывает не длина ответа, а структура: определение → как работает → пример из практики → компромисс.

Junior · 15 вопросов

Junior
  1. Что такое реляционная база данных?Хранилище, где данные организованы в таблицы со строками и колонками, связи выражаются через ключи, а доступ идёт через SQL. Целостность поддерживается ограничениями, параллельный доступ — транзакциями.
  2. Чем PRIMARY KEY отличается от UNIQUE?PK один на таблицу, не допускает NULL и в InnoDB задаёт кластерный индекс. UNIQUE может быть несколько, и NULL в них допустим, причём несколько NULL не конфликтуют.
  3. Зачем нужен внешний ключ?Он гарантирует ссылочную целостность: нельзя сослаться на несуществующую строку и нельзя оставить «висячие» ссылки при удалении. Работает для любого писателя в базу, а не только для вашего кода.
  4. Чем INNER JOIN отличается от LEFT JOIN?INNER возвращает только совпадения, LEFT — все строки левой таблицы плюс NULL там, где пары нет. Список пользователей с их заказами, включая тех, у кого заказов нет, требует LEFT JOIN.
  5. Почему WHERE deleted_at = NULL не работает?Любое сравнение с NULL даёт NULL, а не истину. Нужно IS NULL / IS NOT NULL.
  6. Что делает GROUP BY?Разбивает строки на группы по значениям указанных колонок; агрегатные функции считаются внутри каждой группы. Отфильтровать группы можно через HAVING.
  7. Разница между COUNT(*) и COUNT(column)?COUNT(*) считает все строки группы, COUNT(column) — только те, где значение не NULL. COUNT(DISTINCT column) — уникальные значения.
  8. Что такое SQL-инъекция и как от неё защититься?Подмена структуры запроса пользовательскими данными при конкатенации. Защита — подготовленные выражения с плейсхолдерами: запрос и данные передаются раздельно, поэтому значение не может стать синтаксисом. Для имён колонок — белый список.
  9. Зачем нужен PDO и как его правильно настроить?Единый интерфейс к разным СУБД с prepared statements и транзакциями. Обязательные опции: ERRMODE_EXCEPTION, FETCH_ASSOC, EMULATE_PREPARES = false, кодировка utf8mb4 в DSN.
  10. В каком типе хранить деньги?DECIMAL/NUMERIC с фиксированной точностью либо целое число минимальных единиц. FLOAT и DOUBLE нельзя: двоичная плавающая точка представляет десятичные дроби неточно.
  11. Что такое нормализация и зачем она нужна?Организация схемы так, чтобы каждый факт хранился один раз. Убирает аномалии вставки, обновления и удаления. Практический ориентир — 3NF: справочные данные выносим в отдельные таблицы и ссылаемся по id.
  12. Что такое индекс и почему он ускоряет запрос?Отсортированная структура (B+-дерево) со ссылками на строки: вместо полного перебора БД спускается по дереву. Плата — замедление записи и дополнительный объём.
  13. Чем DELETE отличается от TRUNCATE?DELETE — DML: удаляет строки по условию, транзакционен, вызывает триггеры и проверки FK. TRUNCATE — DDL: быстро очищает таблицу целиком, сбрасывает автоинкремент, в MySQL неявно коммитит транзакцию.
  14. Что такое транзакция? Приведите пример, где она обязательна.Группа операций «всё или ничего». Пример: перевод денег между счетами — списание и зачисление должны примениться вместе, иначе деньги исчезнут или удвоятся.
  15. Почему нельзя делать запросы в цикле?Каждый запрос — это сетевой round-trip, разбор и планирование. 200 итераций — 200 обращений вместо одного. Заменяется на WHERE id IN (...), JOIN или пакетную вставку.

Middle · 20 вопросов

Middle
  1. Есть индекс (a, b, c). Какие запросы его используют?Условия по a; a + b; a + b + c; а также a = ? AND b > ?. Не используют поиск только по b, только по c или по b + c — правило левого префикса.
  2. Что убивает использование индекса?Функция или арифметика над колонкой, неявное приведение типов, LIKE '%...' с ведущим процентом, OR по разным колонкам, а также низкая селективность, при которой оптимизатор сознательно выбирает полное сканирование.
  3. Что такое покрывающий индекс?Индекс, содержащий все колонки запроса, так что таблица не читается вовсе. В MySQL видно как Using index, в PostgreSQL — Index Only Scan.
  4. Как читать вывод EXPLAIN?Смотрю тип доступа (ALL/Seq Scan — тревога), использованный индекс, оценку строк против фактической, наличие Using filesort/Using temporary. В EXPLAIN ANALYZE ищу узел с наибольшим фактическим временем.
  5. Запрос стал медленным. Порядок действий?Воспроизвести и замерить → EXPLAIN ANALYZE → проверить индексы и статистику → переписать запрос → при необходимости изменить модель данных (счётчик, агрегат, кэш). Всё сравниваю по планам «до и после».
  6. Что такое ACID?Атомарность (всё или ничего), согласованность (ограничения выполнены), изолированность (транзакции не видят промежуточных состояний друг друга), долговечность (после коммита данные переживут сбой).
  7. Назовите уровни изоляции и аномалии.READ UNCOMMITTED (грязное чтение), READ COMMITTED (неповторяющееся чтение, фантомы), REPEATABLE READ (фантомы; в InnoDB подавлены), SERIALIZABLE (без аномалий). Дефолт: MySQL — REPEATABLE READ, PostgreSQL — READ COMMITTED.
  8. Что такое lost update и как его предотвратить?Два процесса прочитали значение, изменили и записали — одно изменение потеряно. Лечится атомарным UPDATE ... SET x = x + 1, версионностью (WHERE version = :v) или SELECT ... FOR UPDATE.
  9. Что такое deadlock и как с ним жить?Циклическое ожидание блокировок; СУБД обнаруживает его и убивает одну транзакцию. Профилактика — единый порядок обновления строк и короткие транзакции; обязательный элемент — ретрай с задержкой.
  10. Зачем нужен FOR UPDATE SKIP LOCKED?Чтобы несколько воркеров разбирали очередь из таблицы, не конкурируя за одну строку: заблокированные другими строки просто пропускаются.
  11. Чем WHERE отличается от HAVING?WHERE фильтрует строки до группировки и может использовать индекс, HAVING — уже сформированные группы. Всё, что можно, фильтруем в WHERE.
  12. Зачем нужны оконные функции?Они считают агрегат по «окну» вокруг строки, не схлопывая её. Единственное вменяемое решение задач «топ-N в каждой группе», «доля от суммы группы», «сравнение с предыдущим значением».
  13. Что такое CTE и когда он полезен?Именованный подзапрос в WITH. Делает сложный запрос читаемым и позволяет рекурсию для деревьев. Сам по себе производительности не добавляет; в старых версиях PostgreSQL был барьером оптимизации.
  14. Почему NOT IN с подзапросом опасен?Если подзапрос вернёт хоть один NULL, всё выражение станет NULL и результат окажется пустым. Используйте NOT EXISTS.
  15. Что такое N+1 и как его найти?Один запрос за списком плюс по запросу за связью для каждого элемента. Находится профайлером или логом запросов; лечится eager loading, агрегатными подзапросами или ручной догрузкой одним IN-запросом.
  16. Плюсы и минусы ORM?Плюсы: скорость разработки, безопасность по умолчанию, доменная модель, переносимость. Минусы: скрытая стоимость запросов, N+1, память на гидрацию, слабость в аналитике и пакетных операциях. Решение — сочетать ORM с чистым SQL в репозиториях.
  17. Почему LIMIT/OFFSET плохо работает на больших смещениях?База обязана отсортировать и пройти OFFSET строк, прежде чем отдать нужные, — стоимость растёт линейно. Keyset-пагинация по (created_at, id) работает за постоянное время.
  18. Как реализовать связь many-to-many?Промежуточная таблица с двумя FK и составным PK плюс отдельный индекс для обратного направления поиска. Атрибуты самой связи (qty, price, role) живут в ней же.
  19. Плюсы и минусы soft delete?Плюсы: восстановление и аудит, сохранность истории. Минусы: рост таблиц, конфликт с UNIQUE, необходимость фильтра в каждом запросе, риск утечки удалённых данных, противоречие требованиям о реальном удалении персональных данных.
  20. Почему нельзя править уже применённую миграцию?Она записана как выполненная в таблице версий на всех стендах и повторно не применится — схемы разойдутся. Изменение оформляется новой миграцией.

  1. Как вы проектируете схему для новой предметной области?От инвариантов и профиля запросов: что обязано меняться атомарно (границы транзакций), какие точки входа горячие, как данные растут. Нормализую до 3NF, денормализую только по измерению.
  2. MySQL или PostgreSQL для нового проекта?По умолчанию — то, что команда умеет эксплуатировать. PostgreSQL выигрывает при сложных типах, аналитике, частичных и функциональных индексах, транзакционном DDL. MySQL — при простой модели, огромном потоке точечных запросов и зрелой инфраструктуре вокруг него.
  3. Объясните CAP применительно к вашей системе.При разделении сети выбираем между доступностью и согласованностью. У нас каталог читается с реплик (AP, допустимо устаревание), операции с деньгами идут строго на мастер (CP, при недоступности — явная ошибка). Вне разделения реальный выбор — между задержкой и согласованностью (PACELC).
  4. Как обеспечить read-your-own-writes при чтении с реплик?Sticky-маршрутизация на мастер на короткое время после записи, ожидание достижения репликой позиции лога либо возврат клиенту записанного объекта без повторного чтения.
  5. Чем шардирование отличается от партиционирования?Партиционирование — разбиение таблицы внутри сервера, прозрачно для приложения. Шардирование — распределение по разным серверам с логикой роутинга. Первое лечит размер таблицы, второе — предел записи.
  6. Как выбрать ключ шардирования?Так, чтобы горячие запросы определяли шард без обращения ко всем, нагрузка распределялась равномерно и не появлялось «горячих» шардов. Обычно это tenant_id или user_id. Заранее продумывается решардинг: виртуальные бакеты вместо прямого id % N.
  7. Когда пора шардировать?Когда исчерпаны вертикальное масштабирование, реплики чтения, кэш, архивация и партиционирование, и упирается именно запись. Шардирование — последний шаг, потому что оно необратимо усложняет всё: JOIN, транзакции, миграции, отчёты.
  8. Как гарантировать, что платёж не пройдёт дважды?Ключ идемпотентности в уникальном индексе: повторная вставка падает на constraint, и мы возвращаем ранее созданный результат. Плюс статус как конечный автомат с переходом через UPDATE ... WHERE status = 'pending', который выполняется ровно один раз.
  9. Что такое outbox pattern и какую проблему он решает?Проблему двойной записи: нельзя атомарно закоммитить БД и опубликовать сообщение. Событие пишется в таблицу той же транзакцией, отдельный воркер публикует его и отмечает. Гарантия — at-least-once, поэтому потребитель обязан быть идемпотентным.
  10. Оптимистичная или пессимистичная блокировка?Оптимистичная при редких конфликтах и длинных пользовательских операциях (версия строки, 409 при расхождении). Пессимистичная при частых конфликтах и коротком критическом участке (FOR UPDATE). Иногда достаточно атомарного UPDATE ... WHERE qty >= :n.
  11. Что такое eventual consistency и где она допустима?Копии данных сходятся не мгновенно, а спустя время. Допустима для лент, счётчиков, поиска, аналитики, кэшей. Недопустима там, где нарушение инварианта стоит денег: остатки при списании, баланс, уникальность заказа.
  12. Когда CQRS оправдан?Когда профили чтения и записи расходятся: редкая запись со сложными инвариантами и массовое чтение по разным срезам. При маленькой команде и умеренной нагрузке начинают с одной модели и материализованных представлений.
  13. Плюсы и минусы event sourcing?Плюсы: полный аудит, восстановление состояния на любой момент, новые проекции задним числом. Минусы: версионирование событий, сложная отладка, дорогое восстановление проекций, высокий порог входа. Оправдан там, где история — бизнес-требование.
  14. Как переименовать колонку в таблице на 100 млн строк без простоя?Expand / migrate / contract: добавить новую колонку, включить двойную запись, выполнить фоновый backfill пачками по PK с контролем лага, переключить чтение, выждать несколько релизов ради отката, затем удалить старую.
  15. Как безопасно добавить индекс на горячую таблицу?В PostgreSQL — CREATE INDEX CONCURRENTLY вне транзакции, с проверкой на невалидный индекс после сбоя. В MySQL — онлайн-DDL с ALGORITHM=INPLACE, LOCK=NONE, а на очень больших таблицах — gh-ost или pt-online-schema-change с ограничением по лагу реплики.
  16. Как организовать backfill данных на десятках миллионов строк?Пачками по первичному ключу (не по OFFSET), возобновляемо (хранит позицию), идемпотентно (WHERE new_col IS NULL), с паузами и проверкой лага репликации, с возможностью остановки. Это фоновый процесс, а не шаг деплоя.
  17. Что мониторить в БД и какие алерты ставить?p95/p99 времени запросов, топ по суммарному времени, число соединений и idle in transaction, лаг репликации, deadlock-и, место на диске, рост крупнейших таблиц, автовакуум и bloat в PostgreSQL. Алерты — на лаг, на исчерпание соединений и на свободное место.
  18. Зачем PHP-приложению внешний пулер соединений?Модель «процесс на запрос» не переиспользует соединения, а каждое соединение к PostgreSQL — отдельный серверный процесс. PgBouncer в transaction-режиме схлопывает сотни клиентских соединений в десятки серверных; для MySQL аналогичную роль играет ProxySQL.
  19. Когда вы пойдёте на денормализацию?Когда измерение показало дорогой горячий запрос, а нормализованные способы исчерпаны. Начинаю с самого дешёвого: счётчик или агрегатная таблица, обновляемые в одной транзакции с изменением, плюс регулярная сверка и алерт на расхождение.

Как отвечать на собеседовании

Бонус
  • Структура ответа: определение в одну фразу → как это работает внутри → пример из вашей практики → компромисс или ограничение. Последний пункт отличает middle от senior.
  • Не знаете — скажите прямо и добавьте, как стали бы разбираться. Выдуманный ответ проверяется одним уточняющим вопросом.
  • Уточняйте вводные в задачах на проектирование: объём данных, соотношение чтения и записи, требования к согласованности, срок хранения. Кандидат, который сразу рисует таблицы, проигрывает тому, кто сначала спрашивает.
  • Говорите цифрами: «сократил с 4,2 с до 180 мс», «с 51 запроса до 3». Это запоминается и проверяемо.
  • Приносите артефакты: два плана EXPLAIN, схему, постмортем. Они превращают рассказ в доказательство.
