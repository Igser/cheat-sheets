Laravel для PHP-разработчиков

Laravel — это не «фреймворк с красивым синтаксисом», а набор готовых решений для задач, которые в любом веб-приложении всё равно придётся решать: маршрутизация, валидация, доступ к базе, аутентификация, очереди, кэш, планировщик, почта, тесты. Его сила в том, что всё это уже связано между собой и работает из коробки. Его же главная опасность в том, что писать плохо на нём так же удобно, как хорошо: три строки в контроллере превращаются в N+1 на 40 000 запросов, а пара «умных» фасадов — в код, который невозможно протестировать.

На собеседовании по Laravel почти никогда не спрашивают синтаксис — его подскажет IDE. Спрашивают, понимаете ли вы, что происходит под капотом: как запрос проходит через ядро и middleware, как контейнер разрешает зависимости, почему $posts->user->name в цикле — это катастрофа, чем джоб отличается от события, когда очередь обязательна и что случится с приложением, если Redis отвалится.

Конспект собирает то, что реально нужно в работе и что действительно спрашивают: от первого маршрута до архитектуры под нагрузкой, деплоя без простоя и обновления мажорных версий. Материал разбит по уровням — можно читать подряд или взять свой блок. Смежные темы вынесены в отдельные конспекты: базы данных, структуры данных, AI и LLM.

junior / основы / жизненный цикл

Жизненный цикл запроса

БазаСпрашивают всегда

Первое, что отличает человека, знающего Laravel, от человека, копирующего примеры, — понимание пути запроса. Всё приложение — это функция Request → Response, а фреймворк лишь организует, что происходит между ними.

текстПуть одного HTTP-запроса
public/index.php            ← единственная точка входа (веб-сервер шлёт всё сюда)
   │
   ├─ vendor/autoload.php   ← автозагрузка Composer
   ├─ bootstrap/app.php     ← сборка приложения: роуты, middleware, обработка ошибок
   │
   ▼
HTTP-ядро
   │
   ├─ глобальные middleware        (TrustProxies, обработка строк, размер тела)
   ├─ маршрутизация                (какой роут совпал; 404, если ни один)
   ├─ middleware группы и маршрута (web/api, auth, throttle, can, свои)
   │
   ▼
Контроллер / замыкание
   │  ← контейнер внедряет зависимости по типам аргументов
   │  ← Form Request валидирует вход ДО тела метода
   │  ← Route Model Binding подставляет модель вместо id
   │
   ├─ бизнес-логика: сервисы, Eloquent, очереди, события
   ▼
Response  →  обратный проход по middleware  →  браузер

После ответа: terminable middleware, отложенные задачи, запись логов.

Middleware — это слои-луковицы вокруг обработчика: каждый может отклонить запрос, изменить его или подправить ответ на обратном пути. Аутентификация, CSRF, ограничение частоты, локаль, логирование — всё это middleware, а не строчки в начале каждого контроллера.

phpСвоё middleware: до и после обработчика
<?php
namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Symfony\Component\HttpFoundation\Response;

final class LogSlowRequests
{
    public function handle(Request $request, Closure $next): Response
    {
        $start = microtime(true);

        // ↓ здесь запрос идёт дальше по цепочке в контроллер
        $response = $next($request);
        // ↑ а здесь мы уже на обратном пути, ответ сформирован

        $ms = (microtime(true) - $start) * 1000;

        if ($ms > 500) {
            logger()->warning('slow.request', [
                'route' => $request->route()?->getName(),
                'ms'    => round($ms),
            ]);
        }

        return $response;
    }
}
ВажноГруппа web и группа api — это разные наборы middleware, и разница принципиальна. web включает сессии, куки и CSRF-защиту; api — без состояния и обычно с ограничением частоты. Отсюда классическая ошибка новичка: «почему в API не работает auth()->user()» — потому что там нет сессии, и аутентификация идёт по токену.
Типичный вопрос на собеседованииЧто происходит от запроса пользователя до ответа?
Веб-сервер отправляет всё в public/index.php, тот подключает автозагрузку и собирает приложение. Запрос проходит глобальные middleware, попадает в маршрутизатор, затем — в middleware группы и маршрута, оттуда в контроллер, куда контейнер внедряет зависимости. Контроллер возвращает ответ, который проходит middleware в обратном порядке. После отправки ответа выполняются завершающие задачи.
ПрактикаНапишите middleware, добавляющее в каждый ответ заголовок с временем обработки и идентификатором запроса. Подключите его глобально и убедитесь, что заголовок появляется и на ошибочных ответах тоже.

Структура проекта и где что лежит

База

Начиная с Laravel 11 скелет приложения заметно похудел: исчезли app/Http/Kernel.php и большая часть провайдеров, а конфигурация маршрутов, middleware и обработки исключений переехала в один файл bootstrap/app.php. Файлы конфигурации тоже публикуются по необходимости, а не лежат все сразу.

phpbootstrap/app.php — точка сборки
<?php
use Illuminate\Foundation\Application;
use Illuminate\Foundation\Configuration\Exceptions;
use Illuminate\Foundation\Configuration\Middleware;

return Application::configure(basePath: dirname(__DIR__))
    ->withRouting(
        web: __DIR__ . '/../routes/web.php',
        api: __DIR__ . '/../routes/api.php',
        commands: __DIR__ . '/../routes/console.php',
        health: '/up',                      // готовый health-check для оркестратора
    )
    ->withMiddleware(function (Middleware $middleware) {
        $middleware->append(App\Http\Middleware\LogSlowRequests::class);

        $middleware->alias([
            'admin' => App\Http\Middleware\EnsureUserIsAdmin::class,
        ]);
    })
    ->withExceptions(function (Exceptions $exceptions) {
        // централизованная обработка: логирование, формат ответа, отчётность
        $exceptions->dontReport([App\Exceptions\BusinessRuleException::class]);
    })
    ->create();
ВажноФункцию env() можно вызывать только внутри файлов конфигурации. В коде приложения читайте config('services.foo.key'). Причина практическая: на проде конфигурация кэшируется, и после кэширования env() вне config-файлов вернёт null. Это одна из самых частых причин «на локали работает, на проде нет».
АнтипаттернСкладывать всё в контроллеры и модели, потому что «так в туториале». Контроллер — это адаптер HTTP: принять запрос, вызвать логику, вернуть ответ. Модель — доступ к данным и её собственное поведение. Всё, что не относится ни к тому, ни к другому, выносится в отдельные классы (см. блок про организацию кода).
Типичный вопрос на собеседованииЧем config() отличается от env()?
env() читает переменную окружения и допустима только в файлах config/. config() читает уже собранную конфигурацию и работает всегда, включая режим с закэшированным конфигом. На проде конфиг кэшируют ради скорости, и после этого env() в коде приложения перестаёт видеть значения.
ПрактикаДобавьте в проект собственный файл конфигурации config/billing.php, читающий значения из окружения, и используйте его в коде через config(). Затем выполните кэширование конфига и убедитесь, что всё продолжает работать.

Маршруты, контроллеры и привязка моделей

БазаСпрашивают всегда
phproutes/web.php — основные формы записи
<?php
use App\Http\Controllers\PostController;
use Illuminate\Support\Facades\Route;

// Базовые методы
Route::get('/posts', [PostController::class, 'index'])->name('posts.index');
Route::post('/posts', [PostController::class, 'store'])->name('posts.store');

// Семь маршрутов CRUD одной строкой
Route::resource('posts', PostController::class);
// Для API — без create/edit (там нет форм)
Route::apiResource('posts', PostController::class);

// Группы: общий префикс, middleware, имя
Route::middleware(['auth', 'admin'])
    ->prefix('admin')
    ->name('admin.')
    ->group(function () {
        Route::get('/orders', [OrderController::class, 'index'])->name('orders.index');
    });

// Ограничение параметра: только цифры
Route::get('/orders/{order}', ...)->whereNumber('order');

Route Model Binding — приём, который экономит десятки строк: если параметр маршрута назван так же, как аргумент метода с типом модели, Laravel сам найдёт запись и подставит её, а при отсутствии вернёт 404.

phpПривязка модели вместо ручного поиска
<?php
// БЫЛО: ручной поиск и проверка
public function show(int $id)
{
    $post = Post::find($id);
    if ($post === null) { abort(404); }

    return view('posts.show', ['post' => $post]);
}

// СТАЛО: модель приходит уже найденной, 404 — автоматически
public function show(Post $post)
{
    return view('posts.show', ['post' => $post]);
}

// Поиск по другому полю — прямо в маршруте:
// Route::get('/posts/{post:slug}', ...);

// Вложенная привязка: комментарий обязан принадлежать посту
Route::get('/posts/{post}/comments/{comment}', ...)->scopeBindings();
ВажноПривязка модели решает вопрос «существует ли запись», но не решает вопрос «имеет ли право этот пользователь её видеть». Проверка прав — отдельный шаг: политика, middleware can или явный вызов авторизации. Забытая проверка здесь — самая распространённая уязвимость в Laravel-приложениях: подставил чужой id в URL и получил чужие данные.
АнтипаттернТолстые контроллеры: запросы к базе, отправка почты, генерация PDF и бизнес-правила в одном методе на 150 строк. Такой код невозможно переиспользовать (например, из консольной команды) и тяжело тестировать. Контроллер должен читаться за десять секунд.
Типичный вопрос на собеседованииЧто такое Route Model Binding и в чём его подвох?
Автоматический поиск модели по параметру маршрута с возвратом 404, если её нет. Подвох в том, что это только поиск: авторизацию он не выполняет. Без политики или middleware can любой аутентифицированный пользователь получит доступ к чужой записи, просто поменяв id в адресе.
ПрактикаСделайте ресурсный контроллер для сущности проекта с привязкой моделей и именованными маршрутами. Затем напишите тест, который проверяет, что чужая запись отдаёт 403, а несуществующая — 404.

Валидация и Form Request

БазаСпрашивают всегда

Правило простое: в приложение не должны попадать невалидные данные. Валидация — это граница, и она должна стоять до бизнес-логики, а не внутри неё. Laravel даёт два способа: быстрый прямо в контроллере и вынесенный в отдельный класс.

phpБыстрый способ и правильный способ
<?php
// Быстро — годится для одного-двух полей
public function store(Request $request)
{
    $data = $request->validate([
        'title' => ['required', 'string', 'max:200'],
        'body'  => ['required', 'string'],
    ]);

    // При ошибке фреймворк сам вернёт 422 для API
    // или редирект с ошибками и старым вводом для формы.
    $post = Post::create($data + ['user_id' => $request->user()->id]);

    return redirect()->route('posts.show', $post);
}
phpForm Request: валидация и авторизация в одном месте
<?php
namespace App\Http\Requests;

use Illuminate\Foundation\Http\FormRequest;
use Illuminate\Validation\Rule;

final class StorePostRequest extends FormRequest
{
    // Выполняется ДО правил: false → 403 и тело метода не запустится
    public function authorize(): bool
    {
        return $this->user()?->can('create', Post::class) ?? false;
    }

    public function rules(): array
    {
        return [
            'title'       => ['required', 'string', 'max:200'],
            'slug'        => ['required', 'alpha_dash', Rule::unique('posts')],
            'body'        => ['required', 'string', 'min:10'],
            'status'      => ['required', Rule::in(['draft', 'published'])],
            'category_id' => ['required', 'exists:categories,id'],
            'tags'        => ['array', 'max:10'],
            'tags.*'      => ['integer', 'exists:tags,id'],
            'published_at' => ['nullable', 'date', 'after_or_equal:today'],
        ];
    }

    // Нормализация входа до проверки правил
    protected function prepareForValidation(): void
    {
        $this->merge(['slug' => str($this->input('title', ''))->slug()->value()]);
    }

    public function messages(): array
    {
        return ['title.required' => 'Укажите заголовок публикации.'];
    }
}

// Контроллер становится тривиальным
public function store(StorePostRequest $request)
{
    // validated() отдаёт ТОЛЬКО прошедшие проверку поля — это важно
    $post = $request->user()->posts()->create($request->validated());

    return redirect()->route('posts.show', $post);
}
ВажноИспользуйте validated(), а не all(). all() вернёт всё, что прислал клиент, включая поля, которых нет в правилах, — а дальше это уходит в create(). В связке с широким $fillable так и появляется классическая уязвимость: пользователь дописывает в форму is_admin=1, и оно сохраняется.
АнтипаттернПроверять данные в модели или в сервисе «на всякий случай» вместо валидации на входе. Получается двойная логика в двух местах, которая со временем расходится. Валидация формата и обязательности — на границе (Form Request), проверка бизнес-инвариантов («достаточно ли товара на складе») — в доменном коде и в БД.
Типичный вопрос на собеседованииЧем Form Request лучше валидации в контроллере?
Он выносит правила и авторизацию из контроллера в отдельный тестируемый класс, переиспользуется между методами, даёт места для нормализации входа и своих сообщений и гарантирует, что тело метода вообще не выполнится при неверных данных или отсутствии прав. Контроллер при этом остаётся тонким.
ПрактикаПереведите один «толстый» контроллер на Form Request с авторизацией, нормализацией входа и своими сообщениями. Напишите тесты на три случая: успешный запрос, невалидный (422) и без прав (403).

junior / данные / eloquent

Eloquent: модели, CRUD, связи

БазаСпрашивают всегда

Eloquent — реализация паттерна Active Record: модель одновременно и объект предметной области, и способ доступа к строке таблицы. Это делает простые вещи очень простыми, а сложные — требующими понимания того, какие SQL-запросы за этим стоят.

phpМодель: настройки, которые ставят всегда
<?php
namespace App\Models;

use Illuminate\Database\Eloquent\Factories\HasFactory;
use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\Relations\BelongsTo;
use Illuminate\Database\Eloquent\Relations\HasMany;

final class Post extends Model
{
    use HasFactory;

    // Что разрешено массово заполнять из запроса
    protected $fillable = ['title', 'slug', 'body', 'status', 'category_id', 'published_at'];

    // Приведение типов: из БД приходят строки, в PHP нужны типы
    protected function casts(): array
    {
        return [
            'published_at' => 'datetime',
            'is_featured'  => 'boolean',
            'meta'         => 'array',        // JSON-колонка ↔ массив PHP
            'price'        => 'decimal:2',
        ];
    }

    public function author(): BelongsTo
    {
        return $this->belongsTo(User::class, 'user_id');
    }

    public function comments(): HasMany
    {
        return $this->hasMany(Comment::class);
    }

    // Локальный скоуп: переиспользуемый кусок условия
    public function scopePublished($query)
    {
        return $query->where('status', 'published')
                     ->whereNotNull('published_at');
    }
}
phpОсновные операции и что за ними в SQL
<?php
// Чтение
Post::find(1);                       // SELECT ... WHERE id = 1 LIMIT 1, null если нет
Post::findOrFail(1);                 // то же, но 404 при отсутствии
Post::where('status', 'published')->first();

Типичный вопрос на собеседованииЧто такое mass assignment и чем он опасен?

Миграции, фабрики и сидеры

База

Миграции — это версионирование схемы БД в git. Правило, которое нарушают чаще всего: применённую и уехавшую в общую ветку миграцию не правят — изменения оформляются новой миграцией. У всех, кто её уже применил, она записана как выполненная и повторно не запустится, а схемы разойдутся.

<?php
// app/Console/Commands/PublishScheduledPosts.php
final class PublishScheduledPosts extends Command
{
    protected $signature = 'posts:publish-scheduled {--dry-run : Только показать}';
    protected $description = 'Публикует посты, у которых наступило время публикации';

    public function handle(PostPublisher $publisher): int
    {
        $due = Post::where('status', 'scheduled')
            ->where('published_at', '<=', now())
            ->get();

        foreach ($due as $post) {
            $this->line("Публикую: {$post->title}");

            if (!$this->option('dry-run')) {
                $publisher->publish($post);
            }
        }

        return self::SUCCESS;
    }
}

Типичный вопрос на собеседованииКак в Laravel устроены периодические задачи?

Service Container, провайдеры и фасады

Ключевая темаСпрашивают всегда

Service Container — сердце фреймворка: он умеет создавать объекты, автоматически подставляя их зависимости по типам аргументов конструктора. Именно поэтому в контроллере можно просто попросить нужный сервис — и он появится.

phpАвтоматическое разрешение зависимостей
<?php
final class OrderController extends Controller
{
    // Контейнер сам создаст OrderService, а для него — его зависимости,
    // и так далее по всей цепочке. Ничего вручную не new-им.
    public function __construct(
        private readonly OrderService $orders,
        private readonly PaymentGateway $payments,   // это интерфейс!
    ) {}

    public function store(StoreOrderRequest $request)
    {
        $order = $this->orders->place($request->user(), $request->validated());

        return OrderResource::make($order);
    }
}

Интерфейс контейнер создать не может — ему нужно сказать, какую реализацию подставлять. Это делается в сервис-провайдере: register() только регистрирует привязки, boot() выполняется после регистрации всех провайдеров и годится для остальной загрузочной логики.

phpПривязки в провайдере
<?php
final class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        // Интерфейс → реализация. Новый объект на каждое разрешение.
        $this->app->bind(PaymentGateway::class, StripeGateway::class);

        // Singleton: один экземпляр на весь запрос
        $this->app->singleton(ExchangeRates::class, function ($app) {
            return new CachedExchangeRates(
                $app->make(HttpExchangeRates::class),
                $app->make('cache.store'),
            );
        });

        // Контекстная привязка: разным потребителям — разные реализации
        $this->app->when(ReportExporter::class)
                  ->needs(Filesystem::class)
                  ->giveConfig('filesystems.disks.reports');
    }

    public function boot(): void
    {
        // Здесь всё, что требует уже собранного приложения
        Model::shouldBeStrict(!$this->app->isProduction());

        RateLimiter::for('api', fn (Request $r) =>
            Limit::perMinute(60)->by($r->user()?->id ?: $r->ip()));
    }
}

Практическая выгода: подмена реализации в тестах, единая точка конфигурации сервисов и отсутствие ручного связывания объектов по всему коду.

Связи и проблема N+1

Ключевая темаСпрашивают всегда

Самая частая проблема производительности в Laravel и самый частый вопрос на собеседовании. Суть: один запрос за списком плюс по запросу за связью для каждого элемента.

phpКак выглядит N+1 и как его убрать
<?php
// ПЛОХО: 1 запрос за постами + 100 за авторами + 100 за счётчиками = 201
$posts = Post::latest()->take(100)->get();
foreach ($posts as $post) {
    echo $post->author->name;              // +1 запрос на каждой итерации
    echo $post->comments->count();          // +1 запрос и вся выборка в память
}

// ХОРОШО: 3 запроса независимо от числа постов
$posts = Post::with('author')            // подгрузить авторов одним IN-запросом
    ->withCount('comments')                 // счётчик подзапросом, без загрузки строк
    ->latest()->take(100)->get();

foreach ($posts as $post) {
    echo $post->author->name;
    echo $post->comments_count;             // уже посчитано
}
phpИнструменты жадной загрузки
<?php
// Вложенные связи через точку
Post::with('comments.author')->get();

// Только нужные колонки: меньше трафика, работают покрывающие индексы
Post::with(['author:id,name,avatar'])->get();

// Условие внутри связи
Post::with(['comments' => fn ($q) => $q->where('approved', true)->latest()->limit(3)])
    ->get();

// Догрузка для уже полученной коллекции
$posts->load('tags');
$posts->loadMissing('author');       // не перезагружает уже загруженное

Post::whereHas('comments', fn ($q) => $q->where('approved', true))->get();

// Агрегаты по связи
Post::withSum('orderItems', 'total')->get();
phpЛовим N+1 автоматически, а не на проде
<?php
// AppServiceProvider::boot()
// Вне продакшена ленивая загрузка бросает исключение —
// N+1 находится на этапе разработки и в тестах, а не в инциденте.
Model::preventLazyLoading(!$this->app->isProduction());

// shouldBeStrict включает сразу три проверки:
// запрет ленивой загрузки, запрет присвоения незаполняемых атрибутов
// и обращение к отсутствующим атрибутам.
Model::shouldBeStrict(!$this->app->isProduction());
ВажноЖадная загрузка — не всегда решение. Загрузить связь у 10 000 записей означает выбрать десятки тысяч строк в память. На больших объёмах правильнее агрегаты (withCount, withSum), джоины с выборкой нужных колонок или отдельный запрос по чанкам. «Просто добавь with» — рефлекс, который иногда меняет проблему запросов на проблему памяти.
Антипаттерн$user->posts->count() вместо $user->posts()->count(). Первое загружает все посты в память и считает их в PHP; второе выполняет SELECT COUNT(*) в базе. Разница — одна пара скобок и вся выборка в памяти.
Типичный вопрос на собеседованииЧто такое N+1 и как его найти?
Один запрос за списком и по запросу за связью на каждый элемент. Находится профайлером (Telescope, Debugbar, лог запросов), а лучше — включённым запретом ленивой загрузки вне прода, тогда он падает тестом. Лечится жадной загрузкой with(), агрегатами withCount()/withSum() или переписыванием на джоин.
ПрактикаВключите запрет ленивой загрузки и прогоните тесты — они начнут падать в местах с N+1. Исправьте их, затем замерьте число запросов на главной странице до и после (например, счётчиком в тесте).

middle / данные / запросы

Запросы, транзакции и большие объёмы

Инженерия

Eloquent удобен, но за удобством стоит SQL, и на объёмах это становится заметно. Три темы, которые отличают middle: осознанный выбор между Eloquent и Query Builder, транзакции и обработка данных, не помещающихся в память.

phpОбработка больших выборок без переполнения памяти
<?php
// ПЛОХО: 2 млн моделей в памяти — гарантированный memory_limit
foreach (Order::all() as $order) { /* ... */ }

// chunkById: пачками по первичному ключу, устойчиво к изменению данных
Order::where('status', 'pending')->chunkById(1000, function ($orders) {
    foreach ($orders as $order) {
        $this->process($order);
    }
});

// lazy(): удобный синтаксис foreach, под капотом те же чанки
foreach (Order::lazyById(1000) as $order) {
    $this->process($order);
}

// cursor(): один запрос, строки по одной из курсора БД.
// Память ниже, но соединение занято на всё время обхода.
foreach (Order::where('status', 'pending')->cursor() as $order) {
    $this->process($order);
}

// Когда объекты не нужны — вообще не создаём модели
$ids = Order::where('status', 'pending')->pluck('id');
DB::table('orders')->whereIn('id', $ids)->update(['status' => 'archived']);

<?php
// Транзакция с автоматическим повтором при deadlock (5 попыток)
$order = DB::transaction(function () use ($user, $items) {
    foreach ($items as $item) {
        // Блокируем строку остатка до конца транзакции
        $stock = Stock::where('product_id', $item['product_id'])
            ->lockForUpdate()
            ->firstOrFail();

        if ($stock->quantity < $item['qty']) {
            // Исключение = откат всей транзакции
            throw new OutOfStockException($item['product_id']);
        }

        $stock->decrement('quantity', $item['qty']);
    }

ВажноВнутри транзакции не должно быть обращений к внешним сервисам: HTTP-запросов к платёжному шлюзу, отправки почты, публикации в очередь без отложенной диспетчеризации. Внешний вызов может длиться секунды, всё это время держатся блокировки, а при откате отменить уже отправленное невозможно. Правило: транзакция короткая и только про базу.
АнтипаттернЧитать значение, менять его в PHP и записывать обратно ($post->views = $post->views + 1; $post->save();). Два параллельных запроса потеряют одно обновление. Правильно — атомарный increment() или условный UPDATE ... WHERE.
Типичный вопрос на собеседованииКак обработать миллион записей, не упав по памяти?
Пачками: chunkById() или lazyById() — они идут по первичному ключу и устойчивы к изменению данных по ходу обработки. cursor() экономит память ещё сильнее, но держит соединение и курсор на весь проход. Если объекты моделей не нужны, работать через Query Builder и pluck(), а массовые изменения делать одним UPDATE, а не построчно.
ПрактикаСгенерируйте 500 000 записей и напишите команду пересчёта, замерив память и время для трёх вариантов: all(), chunkById(), cursor(). Затем добавьте оформление заказа с блокировкой остатка и проверьте его 50 параллельными запросами.

middle / http / api

API: ресурсы, пагинация, версии

Прикладное

Возвращать модели напрямую (return $posts;) — быстро и опасно: в JSON уедет всё, включая поля, которые не предназначены клиенту, а любое изменение схемы БД молча изменит контракт API. API Resource — слой преобразования между моделью и её представлением.

phpРесурс: явный контракт ответа
<?php
namespace App\Http\Resources;

use Illuminate\Http\Resources\Json\JsonResource;

final class PostResource extends JsonResource
{
    public function toArray($request): array
    {
        return [
            'id'        => $this->id,
            'title'     => $this->title,
            'excerpt'   => str($this->body)->limit(200)->value(),
            'status'    => $this->status,
            'published_at' => $this->published_at?->toIso8601String(),

            // Связь попадёт в ответ, только если была загружена.
            // Это защита от N+1 прямо в слое представления.
            'author'    => UserResource::make($this->whenLoaded('author')),
            'comments_count' => $this->whenCounted('comments'),

            // Поле только для тех, кто имеет право его видеть
            'internal_note' => $this->when(
                $request->user()?->can('viewInternal', $this->resource()),
                fn () => $this->internal_note,
            ),
        ];
    }
}

// В контроллере
public function index(Request $request)
{
    $posts = Post::with('author:id,name')
        ->withCount('comments')
        ->published()
        ->latest()
        ->paginate(min((int) $request->integer('per_page', 20), 100));

    // Пагинация сама добавит meta и links в ответ
    return PostResource::collection($posts);
}

middle / доступ / auth

Аутентификация и авторизация

Ключевая темаСпрашивают всегда

Два разных вопроса, которые часто путают. Аутентификация — «кто ты» (сессия, токен). Авторизация — «что тебе можно» (гейты и политики). Первое решает пакет, второе пишете вы.

phpПолитика: правила доступа к модели
<?php
namespace App\Policies;

final class PostPolicy
{
    public function view(?User $user, Post $post): bool
    {
        return $post->status === 'published' || $user?->id === $post->user_id;
    }

    public function update(User $user, Post $post): bool
    {
        return $user->id === $post->user_id;
    }

    public function delete(User $user, Post $post): bool
    {
        return $user->id === $post->user_id
            && $post->created_at->gt(now()->subHours(24));
    }
}

Типичный вопрос на собеседованииЧем гейт отличается от политики?

middle / фон / очереди

Очереди и джобы

Ключевая темаСпрашивают всегда

Правило: всё, что дольше пары сотен миллисекунд и не нужно пользователю немедленно, уходит в очередь. Отправка почты, генерация PDF, обращение к внешнему API, обработка загруженного файла, рассылка уведомлений. Пользователь получает быстрый ответ, а работа выполняется воркером.

phpДжоб с настройками, которые ставят в проде
<?php
namespace App\Jobs;

use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Contracts\Queue\ShouldBeUnique;
use Illuminate\Foundation\Queue\Queueable;

final class GenerateInvoice implements ShouldQueue, ShouldBeUnique
{
    use Queueable;

    public int $tries = 3;                 // сколько всего попыток
    public int $timeout = 120;             // секунд на одну попытку
    public int $maxExceptions = 2;         // хватит и двух исключений

    // Растущая задержка между попытками
    public function backoff(): array { return [10, 60, 300]; }

    // Уникальность: второй такой же джоб не поставится, пока этот в работе
    public function uniqueId(): string { return (string) $this->order->id; }
    public int $uniqueFor = 600;

    // Модель сериализуется как id и заново достаётся при выполнении
    public function __construct(public readonly Order $order) {}

    public function handle(InvoiceBuilder $builder): void
    {
        // Идемпотентность: джоб может выполниться повторно после сбоя
        if ($this->order->hasInvoice()) {
            return;
        }

        $builder->build($this->order);
    }

    // Вызывается, когда все попытки исчерпаны
    public function failed(\Throwable $e): void
    {
        logger()->error('invoice.failed', ['order' => $this->order->id, 'e' => $e->getMessage()]);
        $this->order->markInvoiceFailed();
    }
}

ВажноДжоб обязан быть идемпотентным. Он может выполниться дважды: воркер упал после работы, но до подтверждения; сработал таймаут и джоб вернулся в очередь; кто-то перезапустил упавшие задачи. Проверка «уже сделано?» в начале handle() — обязательный элемент, а не перестраховка.

Типичный вопрос на собеседованииЧто произойдёт, если джоб упадёт?
Он вернётся в очередь и будет повторён до исчерпания $tries (с задержкой из backoff()). После этого попадёт в таблицу проваленных задач, и вызовется метод failed(). Оттуда его можно перезапустить вручную. Поэтому джоб должен быть идемпотентным, а важные сбои — попадать в мониторинг, а не только в таблицу.
ПрактикаВынесите отправку уведомлений в очередь с ретраями, backoff и уникальностью. Сымитируйте падение внешнего сервиса и проследите путь джоба: повторы, попадание в проваленные, перезапуск. Проверьте, что двойное выполнение не создаёт дублей.

Типичный вопрос на собеседованииКогда событие, а когда просто вызов метода?
Событие — когда реакций несколько, они не обязательны для основного сценария и источник не должен о них знать (уведомления, аналитика, интеграции). Прямой вызов — когда действие обязательно, результат нужен здесь и порядок важен. Если «событие» слушает ровно один слушатель и без него сценарий сломан — это замаскированный вызов метода.
ПрактикаРазнесите оформление заказа: основной сценарий в сервисе, а уведомление, аналитику и начисление бонусов — в слушателей события. Убедитесь тестом, что при падении слушателя заказ всё равно создаётся.

Типичный вопрос на собеседованииКак защититься от одновременного пересчёта тяжёлого кэша?

ПрактикаНайдите самый тяжёлый запрос на главной странице, закэшируйте его с TTL и инвалидацией по событию, добавьте блокировку от одновременного пересчёта. Замерьте время ответа до и после и проверьте поведение при выключенном Redis.

Тестирование

Ключевая темаСпрашивают всегда

В Laravel-проектах основную ценность дают feature-тесты: они проходят через маршрут, middleware, валидацию, авторизацию и базу — то есть проверяют поведение, а не реализацию. Unit-тесты остаются для чистой логики: расчёты, правила, преобразования.

Типичный вопрос на собеседованииЧто и как вы тестируете в Laravel-приложении?
Основа — feature-тесты на HTTP-уровне: успешный сценарий, валидация, авторизация, граничные случаи. Unit-тесты — для чистой логики без фреймворка. Отдельно полезно проверять число запросов, чтобы N+1 падал в CI.
ПрактикаПокройте один ресурс полным набором feature-тестов: список, создание, обновление, удаление, права, валидация. Добавьте проверку числа SQL-запросов и подмену внешнего API. Запустите набор в CI.

Организация кода: куда класть логику

Инженерия

Вопрос, на котором ломается большинство проектов на третий год жизни. Laravel не навязывает архитектуру, поэтому решение принимаете вы — и чаще всего слишком поздно.

текстЭволюция по мере роста
1. КОНТРОЛЛЕР + МОДЕЛЬ            небольшой проект, CRUD
   Нормально. Не усложняйте раньше времени.

2. + FORM REQUEST, RESOURCE, POLICY   появились правила и API
   Валидация, представление и права уехали из контроллера.

3. + ACTION / SERVICE              логика переиспользуется
   «Оформить заказ» вызывается из контроллера, консоли и джоба —

4. + DTO, QUERY-ОБЪЕКТЫ, СОБЫТИЯ   логика стала сложной

5. + МОДУЛИ / ГРАНИЦЫ КОНТЕКСТОВ   большая команда, много доменов

<?php
final class PlaceOrder
{
    public function __construct(
        private readonly StockManager $stock,
        private readonly PriceCalculator $prices,
    ) {}

    public function execute(User $user, OrderData $data): Order
    {
        $order = DB::transaction(function () use ($user, $data) {
            $this->stock->reserve($data->items);

            return Order::create([
                'user_id' => $user->id,
                'total'   => $this->prices->total($data->items),
            ]);
        });

        // Побочные эффекты — после коммита и через событие
        OrderPlaced::dispatch($order);

        return $order;
    }
}

// Контроллер снова тонкий
public function store(StoreOrderRequest $request, PlaceOrder $placeOrder)
{
    $order = $placeOrder->execute($request->user(), OrderData::from($request->validated()));

    return OrderResource::make($order);
}
ВажноОтдельно про репозитории. В Laravel Eloquent уже является слоем доступа к данным, и обёртка вокруг него ради «абстракции от БД» обычно приносит только лишние интерфейсы: сменить Eloquent на другой ORM всё равно не выйдет, потому что модели протекают повсюду. Репозиторий оправдан, когда источников данных несколько (БД плюс внешний API), когда нужны сложные переиспользуемые выборки или когда важно подменять доступ к данным в тестах без базы.
АнтипаттернСтроить многослойную архитектуру с интерфейсами на каждый класс в проекте из десяти таблиц. Абстракция, у которой одна реализация и не предвидится второй, — это не гибкость, а лишний файл и лишний переход при чтении кода. Слои добавляются, когда появляется конкретная боль, а не заранее.
Типичный вопрос на собеседованииКуда вы кладёте бизнес-логику в Laravel?
Валидация — в Form Request, права — в политики, представление — в ресурсы и шаблоны. Логика, специфичная для сущности, живёт в модели. Сценарий, затрагивающий несколько сущностей и переиспользуемый из контроллера, консоли и джоба, выносится в action или сервис. Контроллер остаётся адаптером HTTP. Репозитории — только по конкретной необходимости, а не по умолчанию.
ПрактикаВозьмите самый большой контроллер в проекте и разложите его: валидацию в Form Request, права в политику, сценарий в action, ответ в ресурс. Убедитесь, что тесты не изменились — они проверяют поведение, а не структуру.

Масштабирование и Octane

Архитектура

Классическая модель PHP — «процесс на запрос»: всё создаётся заново и умирает после ответа. Это дорого по загрузке фреймворка, но невероятно устойчиво: утечка памяти живёт один запрос. Octane меняет модель — приложение загружается один раз и обслуживает множество запросов в долгоживущем процессе.

текстЧто ломается при переходе на Octane
СОСТОЯНИЕ МЕЖДУ ЗАПРОСАМИ — главный источник багов:

  • статические свойства классов живут между запросами;
  • синглтоны, в которые положили текущего пользователя или Request,
    начнут отдавать чужие данные другим пользователям;
  • «глобальные» настройки, выставленные по ходу запроса
    (локаль, часовой пояс, конфиг), протекают дальше;
  • утечка памяти больше не лечится концом запроса —
    процесс постепенно распухает.

ЧТО ДЕЛАТЬ:
  • не хранить данные запроса в синглтонах и статике;
  • зависимости, привязанные к запросу, разрешать через контейнер
    в момент обработки, а не сохранять в свойствах;
  • ограничивать число обработанных запросов на воркер (перезапуск);
  • нагрузочно тестировать долгий прогон, а не один запрос.

КОГДА ОКУПАЕТСЯ: когда узкое место — загрузка фреймворка,
а не база. Если 80% времени — SQL, выигрыш будет скромным.

ВажноРазделяйте очереди по критичности. Одна общая очередь означает, что ночная переиндексация каталога на 200 000 товаров задержит отправку письма с кодом подтверждения. Минимум: быстрая очередь для пользовательских сценариев и медленная для массовых операций, с разными воркерами.
Типичный вопрос на собеседованииЧто нужно изменить, чтобы приложение работало на нескольких серверах?
Убрать локальное состояние: сессии и кэш — в Redis, загруженные файлы — в объектное хранилище, очереди — в общий брокер, планировщик — с блокировкой на одном сервере, логи — в централизованный сбор. Плюс проверить, что деплой обновляет все узлы согласованно и воркеры перезапускаются.
ПрактикаРазверните проект на двух узлах за балансировщиком и найдите всё, что сломается: вход в систему, загрузка аватара, кэш, планировщик. Исправьте и проверьте, что выключение одного узла не ломает сценарии.

senior / архитектура / границы

Границы модулей и когда усложнять

Архитектура

Через два-три года проект на 300 таблиц и 15 разработчиков упирается не в производительность, а в связность: изменение в биллинге ломает каталог, никто не знает, кто вызывает этот метод, а тесты идут сорок минут. Решение — явные границы внутри монолита.

текстМодульный монолит
app/                          Modules/
  Http/                         Catalog/
  Models/          вместо         Domain/       модели, правила, события
  Services/        этого          Application/  сценарии (actions)
  ...                             Infrastructure/ репозитории, интеграции
                                  Http/         контроллеры, ресурсы, роуты
                                Billing/
                                Shipping/

Правила, ради которых всё затевалось:
  • модуль общается с другим ТОЛЬКО через публичный контракт
    (сервис-фасад модуля или доменное событие);
  • нельзя тянуть модель чужого модуля напрямую в свой код;
  • у каждого модуля свои тесты, их можно гонять отдельно;
  • нарушения границ ловятся линтером архитектуры в CI,
    иначе договорённость проживёт ровно до ближайшего дедлайна.

Типичный вопрос на собеседованииКогда стоит распиливать монолит на сервисы?
Когда есть конкретная причина, которую монолит не решает: часть системы нужно масштабировать независимо, у неё другой цикл релизов или другой стек, либо команды физически мешают друг другу в одном репозитории. Проблемы связности сначала решаются границами внутри монолита — это дешевле и обратимо. Распил ради моды даёт сетевые отказы, распределённые транзакции и общую боль без выигрыша.
ПрактикаВыделите в своём проекте один домен в модуль с явным публичным контрактом и запретом на прямое обращение к его моделям снаружи. Добавьте в CI проверку, которая падает при нарушении границы.

Минимальный набор, который должен быть на проде:

  • Трекер ошибок с группировкой и оповещением. Логи в файле, которые никто не читает, — это не мониторинг.
  • Метрики приложения: время ответа по перцентилям, частота ошибок, число запросов в БД на обращение.
  • Метрики очередей: длина, время ожидания, доля проваленных, возраст самой старой задачи. Растущая очередь — предвестник инцидента.
  • Метрики БД: медленные запросы, соединения, лаг реплик.
  • Health-check для оркестратора и внешнего мониторинга.
  • Алерты по симптомам, а не по всему подряд: рост ошибок, деградация p95, очередь выше порога, свободное место на диске.
ВажноЛоги не должны содержать секретов и персональных данных сверх необходимого: токены, пароли, номера карт, содержимое запросов с ПДн. Маскирование настраивается один раз в форматтере, иначе через год у вас база персональных данных в файлах логов, о которой никто не помнит.

Дальше — по сквозному идентификатору запроса собрать полную картину в логах. Если единственный сигнал «пользователь написал в поддержку» — наблюдаемости нет.
ПрактикаДобавьте сквозной идентификатор запроса во все логи и во внешние вызовы, переведите три ключевых места на структурированные события и настройте один алерт на рост доли ошибок. Проверьте срабатывание, намеренно сломав фичу на стенде.

senior / поддержка / версии

Обновление версий и жизнь с легаси

Архитектура

Мажорные версии Laravel выходят регулярно, а окно поддержки исправлений и безопасности у каждой ограничено. Проект, который «пока не до обновлений», через три года оказывается на неподдерживаемой версии фреймворка и старом PHP, а обновление превращается в отдельный квартальный проект.

текстСтратегия, которая работает
ПОСТОЯННО
  • обновлять минорные версии и зависимости регулярно (раз в спринт),
    а не копить на год;
  • держать тесты зелёными — это единственная реальная страховка
    при обновлении фреймворка;
  • следить за предупреждениями об устаревании в логах.

ПРИ МАЖОРНОМ ОБНОВЛЕНИИ
  1. Прочитать руководство по обновлению целиком — там перечислены
     ломающие изменения, а не только новинки.
  2. Поднять PHP до требуемой версии отдельным шагом, до фреймворка.
  3. Обновлять в ветке, прогонять полный набор тестов.
  4. Разобраться с пакетами: часть может не поддерживать новую версию —
     это обычная причина застрять.
  5. Выкатывать отдельным релизом, без функциональных изменений,
     чтобы при проблемах было понятно, что откатывать.

ЕСЛИ ПРОЕКТ СИЛЬНО ОТСТАЛ
  Идти по версиям последовательно, а не прыгать через две-три:
  каждый шаг проверяется тестами и выкатывается отдельно.
ВажноГлавный технический долг при обновлении — не сам фреймворк, а сторонние пакеты и код, который лезет во внутренности. Чем больше вы полагаетесь на недокументированное поведение и заброшенные пакеты, тем дороже каждое обновление. При выборе пакета смотрите на активность репозитория и число зависимостей — это решение на годы.
Типичный вопрос на собеседованииКак вы обновляете мажорную версию фреймворка на большом проекте?
Сначала убеждаюсь, что есть покрытие тестами ключевых сценариев — без него обновление вслепую. Затем читаю руководство по обновлению, поднимаю версию PHP отдельным шагом, обновляю в отдельной ветке, разбираюсь с несовместимыми пакетами и выкатываю отдельным релизом без функциональных изменений. Если проект отстал на несколько версий — иду последовательно, а не одним прыжком.
ПрактикаПроверьте, на какой версии фреймворка и PHP работает ваш проект и в каком состоянии её поддержка. Составьте план обновления с оценкой: какие пакеты мешают, какие тесты нужно дописать заранее, сколько релизов потребуется.

60 вопросов с эталонными ответами

Ответы намеренно короткие — это каркас, а не пересказ документации. Структура сильного ответа: определение → как работает → пример из практики → компромисс.

Junior · 20 вопросов

Junior
  1. Что происходит от запроса пользователя до ответа?Веб-сервер направляет всё в единую точку входа, подключается автозагрузка, собирается приложение. Запрос проходит глобальные middleware, маршрутизацию, middleware группы и маршрута, попадает в контроллер с внедрёнными зависимостями и возвращается ответом через те же слои в обратном порядке.
  2. Что такое middleware и зачем оно?Слой вокруг обработчика, который может отклонить запрос, изменить его или подправить ответ. Аутентификация, CSRF, ограничение частоты, локаль, логирование — типичные примеры. Позволяет не дублировать эти проверки в каждом контроллере.
  3. Чем группа web отличается от api?web включает сессии, куки и CSRF-защиту, api — без состояния, обычно с ограничением частоты и аутентификацией по токену. Отсюда типичная ошибка: ожидать работы сессии в API-маршруте.
  4. Чем config() отличается от env()?env() допустима только в файлах конфигурации; в коде читают config(). После кэширования конфигурации на проде env() вне config/ вернёт null. Это самая частая причина «локально работает, на проде нет».
  5. Что такое Route Model Binding?Автоматический поиск модели по параметру маршрута: в метод приходит уже найденный объект, при отсутствии — 404. Можно искать по другому полю и ограничивать вложенные привязки. Прав доступа не проверяет.
  6. Как работает валидация и что возвращается при ошибке?Правила проверяются до тела метода. Для обычных запросов — редирект назад с ошибками и старым вводом; для JSON-запросов — статус 422 с перечнем ошибок по полям.
  7. Зачем Form Request, если есть $request->validate()?Он выносит правила и авторизацию в отдельный тестируемый класс, переиспользуется между методами, даёт место для нормализации входа и своих сообщений, и гарантирует, что метод контроллера не выполнится при неверных данных.
  8. Почему нужно брать validated(), а не all()?Потому что all() вернёт всё, что прислал клиент, включая поля вне правил. В связке с массовым заполнением это позволяет дописать в форму служебное поле и сохранить его.
  9. Что такое mass assignment и как защититься?Заполнение модели массивом. Защита — явный список разрешённых полей в $fillable и передача только проверенных данных. Пустой $guarded вместе с all() — прямой путь к уязвимости.
  10. Какие типы связей вы знаете?Один к одному, один ко многим и обратные к ним, многие ко многим через промежуточную таблицу, связь через посредника и полиморфные связи. Отличаются тем, где лежит внешний ключ.
  11. Что делает casts() в модели?Приводит атрибуты к нужным типам при чтении и записи: даты в объекты, JSON-колонки в массивы, флаги в булевы значения, деньги в десятичные. Из базы всё приходит строками, приведение избавляет от ручных преобразований.
  12. Чем find() отличается от findOrFail()?Первый вернёт null, второй бросит исключение, которое превращается в 404. В контроллерах обычно нужен второй вариант или привязка модели.
  13. Что такое скоуп модели?Переиспользуемый кусок условия запроса, оформленный методом модели: Post::published(). Избавляет от копирования одних и тех же where по всему коду.
  14. Зачем нужны миграции?Чтобы схема БД версионировалась вместе с кодом и одинаково разворачивалась у всех. Схема воспроизводится с нуля одной командой, изменения проходят ревью, релиз можно откатить.
  15. Почему нельзя менять уже применённую миграцию?Она отмечена как выполненная на всех стендах и повторно не запустится, поэтому схемы разойдутся. Любое изменение оформляется новой миграцией.
  16. Зачем фабрики и сидеры?Фабрики создают правдоподобные объекты для тестов и разработки, включая связанные сущности и именованные состояния. Сидеры наполняют базу набором данных. Вместе дают воспроизводимое окружение одной командой.
  17. Чем {{ }} отличается от {!! !!} в Blade?Первое экранирует HTML и защищает от XSS, второе выводит как есть. Второе допустимо только для разметки, которую вы сформировали сами и в которой уверены.
  18. Зачем в форме @csrf?Это скрытое поле с токеном, подтверждающим, что форма отправлена с вашего сайта. Без него middleware отклонит запрос. Защита от того, что сторонняя страница отправит запрос от имени залогиненного пользователя.
  19. Как в Laravel устроены задачи по расписанию?Расписание описывается в коде, а система раз в минуту запускает одну команду планировщика, которая решает, что пора выполнить. Есть защита от наложений и запуск только на одном сервере в кластере.
  20. Что такое Artisan и какие команды вы используете чаще всего?Консольный интерфейс приложения: генерация классов, миграции, запуск воркеров и планировщика, кэши, диагностика. Ежедневно — генераторы, migrate, route:list, tinker, optimize:clear.

Middle · 20 вопросов

Middle
  1. Что такое Service Container?Механизм создания объектов с автоматическим разрешением зависимостей по типам аргументов. Позволяет писать код против интерфейсов, а выбор реализации держать в одном месте — провайдере.
  2. Чем bind отличается от singleton?bind создаёт новый объект на каждое разрешение, singleton — один на весь жизненный цикл приложения. В обычном запросе разница невелика, а в долгоживущем процессе синглтон с состоянием запроса приводит к утечке данных между запросами.
  3. Чем register() отличается от boot() в провайдере?В register() только регистрируют привязки — в этот момент другие сервисы могут быть ещё не зарегистрированы. boot() выполняется после регистрации всех провайдеров, туда идёт остальная загрузочная логика.
  4. Что такое фасад и мешает ли он тестированию?Статический прокси к объекту в контейнере: вызов уходит в обычный метод реального сервиса. Тестированию не мешает — фасады подменяются фейками. Проблема не в фасадах, а в скрытых зависимостях, когда по сигнатуре класса непонятно, чем он пользуется.
  5. Что такое N+1 и как его находить?Один запрос за списком плюс по запросу за связью на каждый элемент. Находится профайлером или логом запросов, а надёжнее — включённым запретом ленивой загрузки вне прода: тогда проблема падает тестом, а не всплывает в инциденте.
  6. Чем with() отличается от load()?with() задаёт жадную загрузку до выполнения запроса, load() догружает связь для уже полученных моделей. Есть также loadMissing(), который не перезагружает то, что уже загружено.
  7. Как посчитать связанные записи, не загружая их?withCount() — счётчик приходит подзапросом. Для одной модели — $model->relation()->count() со скобками: это SELECT COUNT(*). Без скобок коллекция загрузится в память целиком.
  8. Как обработать миллион записей?Пачками через chunkById() или lazyById() — по первичному ключу, устойчиво к изменению данных. cursor() экономит память сильнее, но держит соединение. Если объекты не нужны — Query Builder и массовые операции одним запросом.
  9. Когда нужна транзакция и что нельзя делать внутри?Когда несколько изменений должны примениться вместе. Внутри нельзя обращаться к внешним сервисам: HTTP, почта, публикация в очередь без отложенной отправки. Внешний вызов держит блокировки и не откатывается вместе с транзакцией.
  10. Как избежать потерянного обновления при конкурентном доступе?Не читать-менять-писать, а выполнять атомарный UPDATE (increment, условный where) либо блокировать строку на время транзакции. Уровень изоляции сам по себе от этого не спасает.
  11. Почему нельзя возвращать модель напрямую из API?Ответ становится зеркалом схемы БД: любое изменение колонок меняет контракт, служебные поля утекают клиенту. Ресурс задаёт явный список полей, позволяет скрывать данные по правам и форматировать значения.
  12. Чем гейт отличается от политики?Гейт — замыкание для действия, не привязанного к модели. Политика — класс с методами под конкретную модель, автоматически связываемый с ней. CRUD над сущностью — политика, всё остальное — гейт.
  13. Где проверять права доступа?На сервере, на каждом эндпоинте: в контроллере, middleware маршрута или в Form Request. В шаблоне — только чтобы скрыть элемент интерфейса. Самое надёжное — сразу выбирать только доступные пользователю записи.
  14. Что должно уходить в очередь?Всё, что долго и не нужно пользователю немедленно: письма, отчёты, обращения к внешним API, обработка файлов, массовые операции. Пользователь получает быстрый ответ, а работа выполняется воркером с ретраями.
  15. Что произойдёт, если джоб упадёт?Он повторится до исчерпания числа попыток с задержкой из backoff, затем попадёт в проваленные и вызовется его метод failed(). Оттуда возможен ручной перезапуск. Поэтому джоб обязан быть идемпотентным.
  16. Почему после деплоя воркеры выполняют старый код?Потому что это долгоживущие процессы, загрузившие код при старте. Нужен queue:restart в деплое, чтобы они корректно завершили текущую задачу и перезапустились с новой версией.
  17. Когда событие, а когда прямой вызов?Событие — когда реакций несколько, они не обязательны для основного сценария и источник не должен о них знать. Прямой вызов — когда действие обязательно и важен порядок. Событие с единственным слушателем, без которого сценарий сломан, — замаскированный вызов метода.
  18. В чём ограничение обсерверов?События модели не срабатывают на массовых операциях через построитель запросов: обновление и удаление по условию идут прямо в SQL. Логика, обязанная выполняться всегда, должна жить в явном сервисе или в самой базе.
  19. Как защититься от одновременного пересчёта тяжёлого кэша?Атомарной блокировкой: первый запрос считает, остальные ждут или получают старое значение. Иначе при истечении TTL под нагрузкой десятки запросов одновременно бросаются пересчитывать одно и то же.
  20. Что и как вы тестируете?Основа — feature-тесты через HTTP: успех, валидация, права, граничные случаи. Unit — для чистой логики. Внешние сервисы, очереди, почта и файлы подменяются фейками, база пересоздаётся, данные готовят фабрики. Полезно проверять и число SQL-запросов.

  1. Страница отвечает 4 секунды. Порядок действий?Измерить: сколько запросов в БД и какие. Обычно N+1 или отсутствующий индекс. Дальше — объём выбираемых данных, вынос синхронных внешних вызовов в очередь, кэш тяжёлых агрегатов. Инфраструктура — в последнюю очередь, с замером на каждом шаге.
  2. Что даёт php artisan optimize и чем он опасен?Кэширует конфигурацию, маршруты, события и шаблоны — заметно ускоряет старт приложения. Опасность в том, что после кэширования конфигурации env() вне config/ возвращает null, а маршруты-замыкания кэшировать нельзя.
  3. Что ломается при переходе на Octane?Состояние между запросами: статические свойства, синглтоны с данными запроса, глобально выставленные настройки, утечки памяти. Приложение перестаёт «обнуляться» после ответа, поэтому данные одного пользователя могут утечь другому.
  4. Что нужно, чтобы приложение работало на нескольких серверах?Убрать локальное состояние: сессии и кэш в Redis, файлы в объектное хранилище, очереди в общий брокер, планировщик с блокировкой на одном сервере, логи в централизованный сбор. Плюс согласованный деплой всех узлов.
  5. Зачем разделять очереди?Чтобы массовая фоновая работа не задерживала пользовательские сценарии. Минимум — быстрая очередь для писем и уведомлений и медленная для пересчётов, с отдельными воркерами и приоритетами.
  6. Как настроить чтение с реплик?В конфигурации соединения задаются отдельные хосты для чтения и записи. Важен режим «липкости»: после записи в рамках того же запроса читать нужно с мастера, иначе пользователь не увидит только что сохранённые данные из-за задержки репликации.
  7. Как выкатить миграцию на таблице в 40 млн строк?По схеме «расширить → перенести → сузить»: добавить новое, включить двойную запись, перенести данные фоном пачками по ключу с контролем лага, переключить чтение, выждать несколько релизов и только потом удалить старое. Это несколько релизов, а не одна миграция.
  8. Почему разрушающая миграция в одном релизе с кодом опасна?Потому что во время выкатки одновременно работают старая и новая версии приложения. Удалённая колонка ломает старые процессы, а откат релиза становится невозможным без потери данных.
  9. Когда выделять модули, а когда сервисы?Модули внутри монолита — когда мешает связность: команды правят одни и те же файлы, изменения расходятся волной. Отдельный сервис — когда нужны независимое масштабирование, свой цикл релизов или другой стек. Распил без такой причины даёт распределённый монолит.
  10. Как удержать границы модулей?Сделать их нарушение невозможным незаметно: публичные контракты модулей, запрет обращаться к чужим моделям и проверка зависимостей в CI. Договорённость без автоматической проверки не переживает первый срочный релиз.
  11. Какие уязвимости чаще всего находят в Laravel-проектах?Забытая проверка прав на эндпоинте (доступ по чужому id), массовое заполнение с пустым $guarded, инъекции в «сырых» выражениях и сортировке по полю из запроса, XSS через невыключенное экранирование, включённая отладка на проде и устаревшие зависимости.
  12. Как безопасно сортировать по полю из запроса?Только по белому списку допустимых колонок и направлений. Передача значения из запроса в «сырое» выражение сортировки — это SQL-инъекция, которую не закрывают подготовленные выражения.
  13. Как дать временный доступ к файлу без авторизации?Подписанной ссылкой с ограниченным сроком: маршрут проверяет подпись middleware. Самодельные токены в базе обычно приводят к тому, что их забывают инвалидировать.
  14. Что должно быть в логах и чего в них быть не должно?Должно: имя события, идентификаторы сущностей и пользователя, длительность, сквозной идентификатор запроса — в структурированном виде. Не должно: паролей, токенов, номеров карт и лишних персональных данных. Маскирование настраивается один раз централизованно.
  15. Как вы узнаете о поломке на проде?Из алертов: рост доли ошибок, деградация p95, всплеск проваленных джобов, рост длины и возраста очереди. Дальше — сборка картины по сквозному идентификатору запроса. Если единственный источник — обращения пользователей, наблюдаемости нет.
  16. Опишите деплой без простоя.Сборка релиза отдельно, применение только совместимых миграций, сборка кэшей, атомарное переключение симлинка, перезагрузка FPM, перезапуск воркеров, проверка health-check и метрик. Откат — переключение симлинка обратно.
  17. Что делать, если после деплоя работает старый код?Проверить три вещи: перезагружен ли FPM (и сброшен ли opcache), перезапущены ли воркеры очередей, пересобраны ли кэши конфигурации и маршрутов для нового релиза. Почти всегда причина в одном из них.
  18. Как обновляете мажорную версию фреймворка?Сначала обеспечиваю покрытие тестами ключевых сценариев, затем читаю руководство по обновлению, поднимаю версию PHP отдельным шагом, обновляю в ветке, разбираюсь с несовместимыми пакетами и выкатываю отдельным релизом без функциональных изменений.
  19. Нужны ли репозитории поверх Eloquent?По умолчанию нет: Eloquent сам является слоем доступа к данным, а «абстракция от БД» обычно иллюзорна — модели протекают повсюду. Репозиторий оправдан при нескольких источниках данных, сложных переиспользуемых выборках или необходимости подменять доступ в тестах без базы.
  20. Спроектируйте систему заказов под 5000 запросов в секунду на чтение.Ожидается разговор о компромиссах: индексы под горячие запросы и денормализация после измерения; чтение с реплик с осознанным решением по устареванию; кэш карточек и агрегатов с блокировкой от одновременного пересчёта; очереди с разделением по критичности; идемпотентность оформления заказа; лимиты частоты; наблюдаемость и алерты; план деградации при отказе Redis и реплик.

Как отвечать на собеседовании

Бонус
  • Структура ответа: определение в одну фразу → как работает внутри → пример из вашей практики → компромисс или ограничение. Последний пункт отличает middle от senior.
  • Говорите про SQL под фреймворком. Вопрос «как работает with()» на самом деле про то, понимаете ли вы, что происходит в базе. Ответ «загружает связь» слабый; «делает второй запрос с IN и раскладывает результат по моделям» — сильный.
  • Говорите цифрами: «сократил страницу с 201 запроса до 3», «время ответа с 4,2 с до 180 мс», «очередь разгружалась 40 минут, стало 4». Это запоминается и проверяемо.
  • Не бойтесь сказать «здесь это лишнее». Отказ от репозиториев, микросервисов или Octane с внятным обоснованием — сильный ответ: он показывает, что вы считаете стоимость сложности.
  • Уточняйте вводные в задачах на проектирование: объём данных, соотношение чтения и записи, требования к задержке, цена ошибки. Кандидат, который сразу пишет код, проигрывает тому, кто сначала спрашивает.
  • Приносите артефакты: отчёт по оптимизации, план миграции без простоя, набор тестов, документ готовности к проду. Они превращают рассказ в доказательство.
