Конспект · объекты · типы · проектирование классов

ООП в PHP

Объектно-ориентированный код оценивают не по количеству классов и не по наличию интерфейсов, а по одному признаку: сколько состояний объекта возможно и сколько из них корректны. Класс, который можно создать наполовину заполненным, изменить в любом порядке и оставить в противоречивом виде, не является абстракцией — это структура данных с методами, и все проверки корректности рано или поздно расползутся по всему приложению.

Отсюда практический критерий, к которому сводится большая часть темы: объект отвечает за свои инварианты сам. Конструктор не даёт создать некорректный экземпляр, публичные методы переводят объект только между допустимыми состояниями, а всё, что не должно меняться, физически не меняется. Такой класс невозможно использовать неправильно — и именно это, а не количество слоёв абстракции, отличает хороший объектный дизайн.

Конспект идёт от механики к проектированию: инкапсуляция, интерфейсы против абстрактных классов, наследование и композиция, трейты → типизация и вариантность, иммутабельность, идентичность и клонирование, магические методы, исключения, стандартные интерфейсы → инварианты, связанность, рефлексия и атрибуты, эволюция публичного API. Смежные темы: паттерны и архитектура кода (SOLID, каталог паттернов, DDD), PHP (синтаксис и рантайм), новые версии языка, тестирование.

Уровень 01 · механика объектов

Junior: из чего состоит класс и зачем это нужно

Первый уровень — не про синтаксис, а про смысл конструкций. Модификатор доступа, интерфейс, наследование и трейт решают конкретные задачи, и умение сказать, какую именно, отличает понимание от заученных определений.

junior / инкапсуляция

Инкапсуляция и состояние

База

Инкапсуляция — это не «сделать свойства приватными и написать геттеры». Это обещание класса: снаружи известно, что он умеет, но не известно, как он это хранит. Класс с приватными свойствами и полным набором геттеров и сеттеров ничего не инкапсулирует — его внутреннее устройство видно целиком, просто через методы.

PHPДанные с методами против объекта
// НЕ инкапсуляция: структура данных, притворяющаяся объектом
class Order
{
    private array $items = [];
    private string $status = 'new';

    public function getItems(): array { return $this->items; }
    public function setItems(array $i): void { $this->items = $i; }
    public function setStatus(string $s): void { $this->status = $s; }
}
// Правила живут в вызывающем коде и дублируются в пяти местах:
// if ($order->getStatus() === 'new') { $order->setStatus('paid'); }

// Инкапсуляция: наружу — операции, внутрь — правила
final class Order
{
    private array $items = [];

    public function __construct(private OrderStatus $status = OrderStatus::New) {}

    public function addItem(Sku $sku, int $qty): void
    {
        if (!$this->status->allowsEditing()) {
            throw new OrderIsLocked($this->status);
        }
        $this->items[] = new OrderItem($sku, $qty);
    }

    public function pay(Money $amount): void
    {
        // правило живёт ровно в одном месте — здесь
        if ($this->status !== OrderStatus::New) {
            throw new OrderAlreadyPaid();
        }
        if (!$amount->equals($this->total())) {
            throw new AmountMismatch($amount, $this->total());
        }
        $this->status = OrderStatus::Paid;
    }

    // наружу отдаём копию, а не внутренний массив
    public function items(): array { return [...$this->items]; }
}

ВажноВозврат внутреннего массива — самая частая незаметная дыра. В PHP массивы копируются при присваивании, поэтому return $this->items для массива относительно безопасен, но массив объектов копируется поверхностно: элементы остаются теми же экземплярами, и вызывающий код может изменить их состояние в обход всех правил класса. С объектами это уже полноценная утечка инкапсуляции.
Типичный вопрос на собеседованииЧто такое инкапсуляция и зачем она нужна?
Это сокрытие внутреннего устройства объекта за набором операций: снаружи известно, что объект умеет, но не известно, как он хранит данные. Практическая ценность в двух вещах: правила корректности живут в одном месте, а не размазаны по вызывающему коду, и внутреннее устройство можно менять, не ломая пользователей класса. Приватные свойства с полным набором геттеров и сеттеров инкапсуляцией не являются — они просто дают доступ к тем же данным другим синтаксисом.

junior / контракты

Интерфейсы и абстрактные классы

Контракт

Интерфейс говорит, что объект умеет; абстрактный класс говорит, чем объект является, и приносит с собой часть реализации. Различие не в синтаксисе, а в отношении: интерфейс описывает роль, абстрактный класс — общее устройство семейства.

СмыслРоль: «умеет делать X»Природа: «является разновидностью Y»

Практическое правило. Начинайте с интерфейса, если нужна подмена реализации или граница между слоями. Абстрактный класс берите, когда у нескольких классов действительно есть общая реализация и они образуют одно семейство. Часто правильный ответ — интерфейс плюс отдельный класс с общей логикой, который реализации используют композицией, а не наследуют.

АнтипаттернИнтерфейс на каждый класс «на всякий случай»: UserService и UserServiceInterface с одной реализацией навсегда. Такой интерфейс ничего не абстрагирует и удваивает количество файлов: любое изменение приходится делать дважды. Интерфейс оправдан, когда реализаций больше одной, когда он проходит по границе слоя или когда его подменяют в тестах, — а не потому, что «так принято».
ОриентирХороший интерфейс узкий: два-три метода, связанных одной ролью. Интерфейс с пятнадцатью методами почти наверняка описывает не роль, а целый класс, и его реализация всегда будет наполовину состоять из заглушек. Если у половины реализаций часть методов выбрасывает исключение «не поддерживается» — интерфейс нужно разделить.

junior / наследование

Наследование и композиция

Выбор

Наследование — самая соблазнительная и самая дорогая связь в объектном коде. Оно даёт переиспользование одной строчкой и взамен намертво привязывает потомка к родителю: наследник видит защищённые свойства, зависит от порядка вызовов внутри родительских методов и ломается от изменений, которые формально ничего не нарушают.

PHPКогда наследование ломается
// Классическая ловушка: квадрат «является» прямоугольником
class Rectangle
{
    public function setWidth(int $w): void  { $this->w = $w; }
    public function setHeight(int $h): void { $this->h = $h; }
    public function area(): int { return $this->w * $this->h; }
}

class Square extends Rectangle
{
    public function setWidth(int $w): void { $this->w = $this->h = $w; }
    public function setHeight(int $h): void { $this->w = $this->h = $h; }
}

// Код, корректный для Rectangle, ломается на Square:
function resize(Rectangle $r): int
{
    $r->setWidth(5);
    $r->setHeight(4);
    return $r->area();   // ожидали 20, для Square получим 16
}
// Наследование корректно, только если наследника можно
// подставить всюду вместо родителя, ничего не сломав.

// Композиция решает это без иерархии вовсе:
final class Square
{
    public function __construct(private readonly int $side) {}
    public function area(): int { return $this->side ** 2; }
}

Проверочный вопрос перед наследованием: можно ли подставить наследника всюду, где ожидается родитель, и весь существующий код останется корректным? Если хотя бы в одном сценарии нет — это не наследование, а попытка переиспользовать код через иерархию, и решается композицией.

ВажноКлючевое слово final по умолчанию — хорошая привычка. Класс, от которого нельзя наследоваться, можно свободно менять внутри: никто не завязан на порядок вызовов внутренних методов. Открывать класс для наследования стоит осознанно, спроектировав, какие именно методы предназначены для переопределения, — а это отдельная работа, а не свойство, возникающее само собой.

junior / трейты и статика

Трейты, статика, константы

Инструменты

Трейт — механическая вставка кода в класс на этапе компиляции. Он не создаёт типа: класс с трейтом нельзя передать туда, где ожидается «что-то, использующее этот трейт». Из-за этого трейт удобен для технических мелочей и плох для предметного поведения.

Статические методы удобны и опасны по одной причине: их нельзя подменить. Статический вызов внутри класса — жёсткая зависимость от конкретной реализации, невидимая в конструкторе и непроверяемая в тестах. Разумное применение статики — именованные конструкторы и чистые функции без зависимостей.

PHPИменованные конструкторы и константы
final class Money
{
    // приватный конструктор: создание только через понятные имена
    private function __construct(
        public readonly int $amount,     // в минимальных единицах
        public readonly Currency $currency,
    ) {}

    // имя объясняет, что именно означает число
    public static function fromMinorUnits(int $m, Currency $c): self
    {
        return new self($m, $c);
    }

    public static function zero(Currency $c): self
    {
        return new self(0, $c);
    }

    // статика здесь безопасна: нет зависимостей и нет состояния
}

// Константы класса вместо разбросанных строк и чисел
final class RetryPolicy
{
    public const int MAX_ATTEMPTS = 5;
    public const int BASE_DELAY_MS = 200;
}

// Набор связанных значений — это enum, а не набор констант:
enum OrderStatus: string
{
    case New     = 'new';
    case Paid    = 'paid';
    case Shipped = 'shipped';

    // поведение живёт рядом со значением, а не в switch по коду
    public function allowsEditing(): bool
    {
        return $this === self::New;
    }
}
ОриентирПеречисление почти всегда лучше набора строковых констант: невозможные значения перестают существовать на уровне типов, а поведение, зависящее от варианта, переезжает в методы перечисления вместо ветвлений по строке, разбросанных по коду. Проверка «а что если сюда придёт неизвестный статус» исчезает сама.

middle / типы

Типы и вариантность

Проверки

Типы в PHP проверяются в рантайме, но настоящую пользу приносят раньше — в анализаторе и в редакторе. Строгий режим превращает молчаливое приведение в явную ошибку, а это разница между багом, найденным при разработке, и багом, найденным пользователем.

PHPЧто даёт strict_types
declare(strict_types=1);

function discount(int $percent): int { return $percent; }

// без strict_types: тихое приведение, ошибка уезжает дальше
discount('15');     // 15
discount(15.9);      // 15 — дробная часть потеряна молча
discount(true);      // 1

// со strict_types: TypeError сразу, в точке ошибки
discount('15');     // TypeError

// объявление действует на ВЫЗОВЫ из этого файла,
// а не на объявленные в нём функции — поэтому строка
// нужна в каждом файле, а не один раз в проекте

Вариантность описывает, как разрешено менять типы при переопределении метода. Правило вытекает из подстановки: наследник должен уметь всё, что умеет родитель, поэтому принимать он может больше, а возвращать — меньше.

middle / обобщения

Обобщённые типы

Анализатор

Обобщённых типов в самом языке нет: array ничего не сообщает о содержимом, а типизированная коллекция в рантайме проверяет элементы вручную. Но статические анализаторы понимают обобщения из аннотаций и ловят ошибки до запуска — на практике это закрывает большую часть потребности.

PHPТипизированная коллекция с аннотациями
/**
 * Обобщение существует только для анализатора,
 * но этого достаточно: ошибка видна в редакторе.
 *
 * @template T of object
 * @implements \IteratorAggregate<int, T>
 */
final class TypedCollection implements \IteratorAggregate, \Countable
{
    /** @var list<T> */
    private array $items;

    /**
     * @param class-string<T> $type
     * @param list<T>         $items
     */
    public function __construct(private readonly string $type, array $items = [])
    {
        foreach ($items as $item) {
            // рантайм-проверка нужна на границе: данные извне
            $item instanceof $this->type
                || throw new \InvalidArgumentException($type);
        }
        $this->items = array_values($items);
    }

    /**
     * @param callable(T): bool $predicate
     * @return self<T>
     */
    public function filter(callable $predicate): self
    {
        return new self($this->type, array_filter($this->items, $predicate));
    }

    /** @return \Traversable<int, T> */
    public function getIterator(): \Traversable
    {
        return new \ArrayIterator($this->items);
    }

    public function count(): int { return count($this->items); }
}

middle / неизменяемость

Иммутабельность и значения

Надёжность

Неизменяемый объект нельзя испортить: после создания его состояние не меняется никогда. Отсюда всё остальное — его можно свободно передавать, кэшировать, сравнивать и использовать как ключ, не опасаясь, что кто-то изменит его за спиной вызывающего кода.

PHPОбъект-значение и методы порождения
final class DateRange
{
    public function __construct(
        public readonly \DateTimeImmutable $from,
        public readonly \DateTimeImmutable $to,
    ) {
        // инвариант проверяется один раз — при создании
        if ($from > $to) {
            throw new \InvalidArgumentException('Начало позже конца');
        }
    }

    // изменение = новый объект, старый остаётся валидным
    public function withTo(\DateTimeImmutable $to): self
    {
        return new self($this->from, $to);   // проверка снова сработает
    }

    public function overlaps(self $other): bool
    {
        return $this->from <= $other->to && $other->from <= $this->to;
    }
}

// ОСТОРОЖНО: readonly запрещает переприсваивание свойства,
// но не делает объект внутри неизменяемым
final class Report
{
    public function __construct(public readonly \ArrayObject $rows) {}
}

Типичный вопрос на собеседованииДелает ли readonly объект неизменяемым?
Нет, только само свойство: его нельзя переприсвоить после инициализации. Если в свойстве лежит изменяемый объект или коллекция, их внутреннее состояние прекрасно меняется — $obj->list[] = $x для объекта-коллекции сработает. Настоящая неизменяемость требует, чтобы всё содержимое тоже было неизменяемым: скалярные значения, перечисления, DateTimeImmutable и такие же неизменяемые объекты, а массивы отдавались копией.

middle / равенство

Идентичность и клонирование

Копии

Два вопроса, на которые каждый класс отвечает — явно или молчаливым поведением по умолчанию: когда два экземпляра считаются одинаковыми и что происходит при копировании. Умолчания редко совпадают с тем, что нужно.

PHPСравнение и копирование объектов
$a = new Money(100, Currency::RUB);
$b = new Money(100, Currency::RUB);

$a == $b;    // true:  тот же класс и равные свойства (рекурсивно)
$a === $b;   // false: это разные экземпляры

// Для сущности сравнение по всем полям неверно:
// два объекта одного заказа с разным набором загруженных связей
// не равны по ==, хотя это один и тот же заказ.
// Поэтому равенство объявляют явно:
public function equals(self $other): bool
{
    return $this->id->equals($other->id);   // сущность: по идентификатору
}

// ---------- клонирование ----------
final class Basket
{
    /** @var list<Item> */
    private array $items = [];
    private \DateTimeImmutable $createdAt;

    // clone копирует свойства ПОВЕРХНОСТНО:
    // массив копируется, но объекты внутри остаются общими
    public function __clone(): void
    {
        // без этого изменение позиции в копии заденет оригинал
        $this->items = array_map(
            static fn(Item $i): Item => clone $i,
            $this->items,
        );
        // DateTimeImmutable клонировать не нужно: он неизменяем
    }
}

Цена

Обещания

Публичный метод — это обещание: при таких входных данных произойдёт то-то, а при таких будет ошибка определённого вида. Исключения — часть этого обещания наравне с типами, и проектировать их нужно так же осознанно.

PHPИерархия исключений предметной области
// Базовый маркер модуля: позволяет ловить всё своё разом
interface BillingException extends \Throwable {}

// Конкретные ситуации — с данными, а не только с текстом
final class InsufficientFunds extends \DomainException implements BillingException
{
    public function __construct(
        public readonly Money $required,
        public readonly Money $available,
    ) {
        parent::__construct(sprintf(
            'Требуется %s, доступно %s',
            $required, $available,
        ));
    }

    // вызывающий код принимает решение по данным, а не парсит текст
    public function shortage(): Money
    {
        return $this->required->minus($this->available);
    }
}

// Именованные конструкторы делают выброс читаемым
final class OrderNotFound extends \RuntimeException implements BillingException
{
    public static function withId(OrderId $id): self
    {
        return new self("Заказ {$id} не найден");
    }
}

// Использование: ловим то, что умеем обработать, остальное — наверх
try {
    $this->billing->charge($order);
} catch (InsufficientFunds $e) {
    return $this->offerTopUp($e->shortage());
}
ВажноЛовить нужно то, что вы действительно умеете обработать. Блок catch (\Throwable $e) в середине бизнес-логики превращает падение в тишину: ошибка программиста маскируется под нормальную работу, а данные тихо портятся. Общий перехват уместен на границе приложения — в обработчике HTTP-запроса или воркере, — где он логирует и превращает исключение в ответ или в повтор задачи.
Типичный вопрос на собеседованииВозвращать null или бросать исключение, если объект не найден?
Зависит от того, нормальна ли эта ситуация для вызывающего кода. Метод findByEmail в поиске по фильтру возвращает null: отсутствие — ожидаемый результат. Метод getById с идентификатором, полученным из системы, бросает исключение: отсутствие означает нарушенную целостность. Плохо только смешивать — когда один и тот же метод иногда возвращает null, иногда бросает, а иногда отдаёт пустой массив, вызывающий код обрастает проверками на все случаи сразу.

Если после получения объекта приходится выяснять, заполнены ли поля, в каком он состоянии и можно ли вызывать метод, — инварианты не инкапсулированы. Идеал — объект, у которого любой публичный метод можно вызвать в любой момент, и он либо сделает работу, либо бросит осмысленное исключение.
Типичный вопрос на собеседованииКак избавиться от проверок на null, разбросанных по коду?
Обычно они означают, что один класс описывает несколько разных состояний сразу. Вместо объекта с шестью опциональными полями делают несколько типов, у каждого из которых обязательные поля действительно обязательны, и общий интерфейс с нужной операцией. Проверки исчезают не потому, что их спрятали, а потому, что невозможных комбинаций больше нет. Там, где отсутствие значения действительно осмысленно, помогает явный тип отсутствия или значение по умолчанию, заданное в конструкторе.

senior / метапрограммирование

Рефлексия и атрибуты

Инструменты каркасов

Рефлексия позволяет коду изучать самого себя: получить список свойств, прочитать типы, создать объект в обход конструктора. На этом построены контейнеры зависимостей, ORM, сериализаторы и валидаторы. В прикладном коде она нужна редко и почти всегда является признаком того, что задачу решают не с той стороны.

PHPАтрибут и его обработка
// Атрибут — это обычный класс, помеченный как атрибут
#[\Attribute(\Attribute::TARGET_METHOD)]
final class Retry
{
    public function __construct(
        public readonly int $attempts = 3,
        public readonly int $delayMs = 200,
    ) {}
}

final class PaymentGateway
{
    #[Retry(attempts: 5, delayMs: 500)]
    public function charge(Money $amount): Receipt { /* ... */ }
}

// Чтение атрибута: объект создаётся только при newInstance()
final class RetryPolicyReader
{
    public function read(string $class, string $method): ?Retry
    {
        $ref   = new \ReflectionMethod($class, $method);
        $attrs = $ref->getAttributes(Retry::class);

        return $attrs === [] ? null : $attrs[0]->newInstance();
    }
}

ВажноАтрибуты — это данные, а не поведение: они ничего не делают сами, пока кто-то их не прочитает. Отсюда два следствия. Второе: логика в атрибутах распределена между объявлением и обработчиком, поэтому её труднее проследить, чем явный вызов. Для каркасов это оправданная цена, для прикладного кода — редко.

senior / эволюция

Эволюция публичного API

Совместимость

Всё публичное — это обещание, которое придётся поддерживать. Внутри библиотеки или модуля, которым пользуются другие команды, каждое публичное имя становится обязательством, а каждое изменение — потенциальной поломкой чужого кода. Отсюда правило: публичной должна быть минимальная поверхность, достаточная для работы.

Senior checklist

Проверка

Что должно быть в арсенале.

  • Сформулировать инварианты класса и обеспечить их конструктором и операциями, а не проверками снаружи.
  • Превратить объект с шестью опциональными полями в несколько типов состояний.
  • Оценить класс по критерию «сколько проверок вынуждены писать его пользователи».

  • Перечислить признаки чрезмерной связанности, включая пары классов, которые всегда правятся вместе.
  • Объяснить, где рефлексия оправдана, и почему её результат кэшируют.
  • Назвать, что атрибут ничего не делает без обработчика, и вытекающие из этого риски.

            throw new \InvalidArgumentException('Продление в прошлое');
        }

        $this->paidUntil = $until;
        $this->status    = SubscriptionStatus::Active;
    }

    public function cancel(\DateTimeImmutable $at): void
    {
        if ($this->status === SubscriptionStatus::Cancelled) {
            return;   // идемпотентно: повтор не ошибка
        }
        $this->status      = SubscriptionStatus::Cancelled;
        $this->cancelledAt = $at;
    }

    // Вопросы вместо выдачи внутренностей наружу
    public function isActiveAt(\DateTimeImmutable $moment): bool
    {
        return $this->status === SubscriptionStatus::Active
            && $moment <= $this->paidUntil;
    }
}

ООП — тема, где легко отвечать определениями из учебника. Сильный ответ всегда содержит следствие: что именно этот механизм даёт и чего стоит.

Junior · 20 вопросов

База
  1. Что такое инкапсуляция?Сокрытие внутреннего устройства объекта за набором операций: снаружи известно, что объект умеет, но не то, как он хранит данные. Даёт две вещи: правила корректности живут в одном месте и внутреннее устройство можно менять, не ломая пользователей класса.
  2. Является ли инкапсуляцией набор приватных свойств с геттерами и сеттерами?Нет. Внутреннее устройство при этом видно целиком, просто доступ идёт через методы, а правила корректности остаются в вызывающем коде. Настоящая инкапсуляция начинается там, где вместо установки полей есть операции предметной области.
  3. Чем опасно возвращать внутреннюю коллекцию объектов?Массив в PHP копируется при возврате, но объекты внутри остаются теми же экземплярами: вызывающий код может изменить их состояние в обход всех правил класса. Отдавать нужно копию с клонированными элементами или неизменяемое представление.
  4. Что такое полиморфизм и зачем он?Возможность вызвать одну и ту же операцию у разных типов и получить поведение, соответствующее конкретному типу. Практическая ценность в том, что ветвление по типу исчезает из вызывающего кода: добавление нового варианта не требует править существующие места.
  5. Чем интерфейс отличается от абстрактного класса?Интерфейс описывает роль — что объект умеет — и не несёт ни реализации, ни состояния; их можно реализовать сколько угодно. Абстрактный класс описывает природу, приносит реализацию и состояние, но он один и жёстко связывает наследников.
  6. Когда выбирать интерфейс, а когда абстрактный класс?Интерфейс — когда нужна подмена реализации или граница между слоями. Абстрактный класс — когда у нескольких классов действительно есть общая реализация и они образуют одно семейство. Часто лучший вариант — интерфейс плюс отдельный класс с общей логикой, используемый композицией.
  7. Нужен ли интерфейс для класса с одной реализацией?Обычно нет. Такой интерфейс ничего не абстрагирует и удваивает работу при каждом изменении. Он оправдан, если реализаций больше одной, если он проходит по границе слоя или если его подменяют в тестах.
  8. Каким должен быть хороший интерфейс?Узким: два-три метода, связанных одной ролью. Интерфейс с пятнадцатью методами описывает не роль, а целый класс, и его реализации всегда наполовину состоят из заглушек. Если часть методов выбрасывает «не поддерживается», интерфейс пора разделить.
  9. Почему композицию предпочитают наследованию?Наследование создаёт очень сильную связь: наследник зависит от внутреннего устройства родителя и ломается от изменений, которые формально ничего не нарушают. Композиция связывает через интерфейс, позволяет комбинировать несколько источников поведения и менять его в рантайме.
  10. Как понять, что наследование здесь неуместно?Проверить подстановку: можно ли использовать наследника всюду, где ожидается родитель, не сломав существующий код. Классический контрпример — квадрат, унаследованный от прямоугольника: код, который задаёт ширину и высоту, начинает давать неверную площадь.
  11. Зачем помечать классы final?Чтобы сохранить свободу менять внутренности: никто не завязан на порядок вызовов внутренних методов и на защищённые свойства. Открывать класс для наследования стоит осознанно, спроектировав точки расширения, — это отдельная работа, а не свойство, возникающее само.
  12. Что такое трейт и когда он уместен?Механическая вставка кода в класс на этапе компиляции. Он не создаёт типа, поэтому подставлять объекты по трейту нельзя. Уместен для одинаковой технической мелочи в неродственных классах; для предметного поведения нужен интерфейс или композиция.
  13. Чем опасны трейты?Скрытыми связями: трейт может обращаться к свойствам класса-хозяина, и эта зависимость нигде не объявлена. Плюс конфликты при подключении нескольких трейтов с одинаковыми методами, которые приходится разрешать вручную.
  14. Чем плохи статические методы?Их нельзя подменить: статический вызов внутри класса — жёсткая зависимость от конкретной реализации, невидимая в конструкторе и непроверяемая в тестах. Безопасные применения — именованные конструкторы и чистые функции без зависимостей и состояния.
  15. Что такое именованный конструктор и зачем он?Статический метод создания с говорящим именем вместо публичного __construct. Он объясняет, что означают аргументы, позволяет иметь несколько способов создания и оставляет свободу менять сигнатуру конструктора, не ломая вызывающий код.
  16. Почему перечисление лучше набора строковых констант?Невозможные значения перестают существовать на уровне типов: функция, принимающая перечисление, не может получить неизвестный статус. Плюс поведение, зависящее от варианта, переезжает в методы перечисления вместо ветвлений по строке, разбросанных по коду.
  17. Зачем нужны константы класса?Чтобы связанное с классом значение имело имя и одно место определения. Если значений несколько и они образуют закрытый набор, вместо констант нужно перечисление: оно даёт и тип, и возможность повесить на варианты поведение.
  18. Что означает модификатор protected и когда он нужен?Доступ для самого класса и его наследников. Нужен только там, где наследование спроектировано осознанно как точка расширения. В классе, помеченном final, защищённые члены смысла не имеют, и их наличие обычно означает, что наследование когда-то предполагалось, а потом о нём забыли.
  19. Что такое абстрактный метод?Объявление без реализации в абстрактном классе: наследник обязан его реализовать. Это способ зафиксировать каркас алгоритма в родителе, оставив наследникам конкретные шаги. Но каждый такой метод — точка жёсткой связи, поэтому их должно быть мало.
  20. С чего начинать проектирование класса?С вопроса, какие операции он должен предоставлять и какие утверждения о его состоянии обязаны быть истинны всегда. Список полей появляется потом, из этих ответов. Обратный порядок — сначала поля, потом методы доступа к ним — и даёт класс-мешок данных.

Механика
  1. Что даёт strict_types?Отключает тихое приведение скалярных типов в вызовах: передача строки туда, где объявлен int, становится ошибкой сразу, а не превращается в неверное значение где-то дальше. Объявление действует на вызовы из файла, где оно написано, поэтому нужно в каждом файле.
  2. Что такое ковариантность и контравариантность?Правила изменения типов при переопределении, вытекающие из подстановки. Возвращаемый тип можно сузить до наследника: наследник обещает не меньше родителя. Тип параметра можно расширить: наследник принимает не меньше. Тип свойства менять нельзя, потому что его и читают, и пишут.
  3. Почему array в сигнатуре — слабая типизация?Он не говорит ничего о содержимом: ни о типе элементов, ни о ключах, ни о том, может ли массив быть пустым. Заменяется объектом, типизированной коллекцией или хотя бы аннотацией вида list<Order>, которую понимает анализатор.
  4. Есть ли в PHP обобщённые типы?В самом языке нет: array ничего не знает о содержимом, а типизированная коллекция проверяет элементы вручную. Но статические анализаторы понимают обобщения из аннотаций и ловят ошибки до запуска, что на практике закрывает большую часть потребности.
  5. Где нужны рантайм-проверки, а где хватит аннотаций?На границе системы — данные из запроса, очереди, внешнего API — нужна настоящая проверка, потому что аннотации ничего не гарантируют. Внутри, где данные уже прошли границу, достаточно аннотаций: дублирующие проверки в каждом методе ничего не ловят и замедляют код.
  6. Зачем заменять примитивы отдельными типами?Чтобы сделать невозможными целые классы ошибок. Сигнатура с тремя int позволяет переставить аргументы местами, и этого не заметит ни анализатор, ни ревью. Отдельные типы счёта, суммы и идентификатора превращают такую ошибку в ошибку типов.
  7. Что такое объект-значение?Объект, который определяется своими значениями, а не идентификатором: две тысячи рублей равны двум тысячам рублей. Он неизменяем, проверяет свои инварианты при создании и несёт рядом поведение — сложение, сравнение, форматирование.
  8. Чем сущность отличается от объекта-значения?Сущность имеет идентификатор, меняется со временем и остаётся собой; равенство у неё по идентификатору. Объект-значение определяется набором полей, не меняется и заменяется целиком; равенство по всем полям. Из этого следуют разные способы хранения и сравнения.
  9. Делает ли readonly объект неизменяемым?Нет, только запрещает переприсваивание свойства. Если внутри лежит изменяемый объект или коллекция, их состояние прекрасно меняется. Настоящая неизменяемость требует, чтобы всё содержимое тоже было неизменяемым, а массивы отдавались копией.
  10. Что даёт неизменяемость?Проверка нужна ровно в одном месте — в конструкторе; переданный объект не изменится у вас за спиной; экземпляр можно свободно разделять и кэшировать; тесты не требуют подготовки состояния; клонирование теряет смысл. Плата — больше создаваемых объектов и методы порождения вместо сеттеров.
  11. Как изменить неизменяемый объект?Создать новый на основе старого методом вида withX(), который возвращает новый экземпляр через конструктор — значит, все инварианты проверятся заново. Исходный объект остаётся валидным, и код, который его держал, не заметит изменения.
  12. Чем == отличается от === для объектов?Первое проверяет, что это объекты одного класса с равными свойствами, сравнивая их рекурсивно. Второе — что это один и тот же экземпляр. Для объектов-значений == часто уместно, для сущностей опасно: два объекта одного заказа с разным набором подгруженных связей окажутся неравными.
  13. Как правильно объявлять равенство?Явным методом. Для объекта-значения — сравнение всех значащих полей, для сущности — сравнение идентификаторов. Это делает правило видимым и защищает от сюрпризов встроенного сравнения, особенно при циклических ссылках и ленивой загрузке.
  14. Что делает clone и когда нужен __clone?Копирует свойства поверхностно: скаляры копируются, а вложенные объекты остаются общими для оригинала и копии. Метод __clone нужен, когда внутри есть изменяемые объекты или массив объектов: их клонируют вручную, иначе изменение копии заденет оригинал.
  15. Чем плохи __get и __set?У объекта нет ни известного набора свойств, ни типов, ни подсказок в редакторе; опечатка возвращает null вместо ошибки; анализатор не может ничего проверить; поиск использований свойства по проекту перестаёт работать. Гибкость не стоит потери всех этих гарантий.
  16. Какие магические методы использовать нормально?__toString вместе с интерфейсом Stringable, __invoke для объектов с одной операцией, __clone при изменяемом содержимом, __serialize и __unserialize при несериализуемых полях. __call — только в прокси и обёртках, с описанием в аннотациях.
  17. Зачем реализовывать IteratorAggregate вместо возврата массива?Коллекция остаётся объектом со своим поведением и инвариантами, но её можно обойти в foreach, и внутренний массив не утекает наружу. Вместе с Countable это даёт привычный интерфейс без превращения объекта в массив.
  18. Как проектировать исключения?Как часть контракта метода: отдельный тип на каждую осмысленную ситуацию, данные внутри исключения вместо текста, который придётся разбирать, и общий интерфейс-маркер модуля, чтобы можно было поймать всё своё разом. Именованные конструкторы делают выброс читаемым.
  19. Где уместен перехват \Throwable?На границе приложения — в обработчике HTTP-запроса, в воркере, в консольной команде, — где он логирует и превращает исключение в ответ или в повтор задачи. В середине бизнес-логики он маскирует ошибку программиста под нормальную работу и позволяет данным тихо портиться.
  20. Возвращать null или бросать исключение, если объект не найден?Зависит от того, нормальна ли ситуация для вызывающего кода. Поиск по фильтру возвращает null: отсутствие ожидаемо. Получение по идентификатору, взятому из системы, бросает исключение: отсутствие означает нарушенную целостность. Плохо смешивать оба поведения в одном методе.

Senior · 20 вопросов

Проектирование
  1. Что такое инвариант класса?Утверждение о состоянии объекта, истинное всё время его жизни: начало диапазона не позже конца, сумма неотрицательна, у оплаченного заказа есть платёж. Задача проектирования — сделать нарушение невозможным, а не проверять его во всех местах использования.
  2. Как избавиться от проверок на null, разбросанных по коду?Обычно они означают, что один класс описывает несколько состояний сразу. Вместо объекта с шестью опциональными полями делают несколько типов с обязательными полями и общим интерфейсом. Проверки исчезают потому, что невозможных комбинаций больше не существует.
  3. Как оценить качество класса?По количеству проверок, которые вынуждены писать его пользователи. Если после получения объекта нужно выяснять, заполнены ли поля и можно ли вызывать метод, инварианты не инкапсулированы. Идеал — любой публичный метод можно вызвать в любой момент, и он либо работает, либо бросает осмысленное исключение.
  4. Почему объект не должен создаваться пустым?Потому что между созданием и заполнением существует некорректное состояние, и любой код, получивший объект в этот момент, работает с мусором. Все обязательные данные передаются в конструктор; если их слишком много, это признак, что класс описывает несколько сущностей.
  5. Назовите виды связанности от худшей к лучшей.Через внутреннее устройство другого класса; через глобальное состояние; через конкретный класс, создаваемый внутри; через флаг поведения; через интерфейс; через переданные данные. Последние два приемлемы, первые три делают изменения дорогими и непредсказуемыми.
  6. Что означает «просить сделать, а не спрашивать»?Если код достаёт данные из объекта, принимает по ним решение и кладёт результат обратно, это решение принадлежит самому объекту. Перенос логики внутрь убирает цепочки вызовов и дублирование: правило оказывается в одном месте вместо каждого вызывающего.
  7. Чем плохи длинные цепочки вызовов через точку?Класс начинает знать устройство трёх чужих объектов сразу, и переименование поля в дальнем конце цепочки ломает код, который формально с ним не связан. Лечится тем, что объект сам отвечает на нужный вопрос, или тем, что методу передают ровно те данные, которые ему нужны.
  8. О чём говорит конструктор с восемью зависимостями?О том, что класс делает несколько разных дел. Обычно его можно разделить по операциям: каждая нуждается в двух-трёх зависимостях, а вместе они собираются только потому, что оказались в одном файле. Побочный признак — тест, который требует построить полсистемы.
  9. Чем плох логический флаг в аргументах метода?Он означает, что внутри два разных сценария, и вызывающий код выбирает поведение вместо объекта. Читаемость страдает сразу: save($order, true) ничего не говорит. Решается двумя методами с говорящими именами или отдельными типами.
  10. Что такое анемичная модель и всегда ли она плоха?Объекты без поведения плюс сервисы, содержащие всю логику. Плоха, когда предметная область содержательна: правила размазываются по сервисам и дублируются. Приемлема для простых сценариев чтения и передачи данных, где никаких правил нет, — навязывать поведение там, где его нет, тоже не нужно.
  11. Где уместна рефлексия?В каркасах: контейнер зависимостей, сериализаторы, восстановление объекта из базы в обход конструктора, чтение атрибутов. Всегда с кэшированием результата, потому что рефлексия дорога. В прикладном коде она обычно означает, что задачу решают не с той стороны.
  12. Что такое атрибуты и в чём их особенность?Это данные, прикреплённые к элементам кода, а не поведение: атрибут ничего не делает, пока кто-то его не прочитает. Отсюда риски — помеченный метод без подключённого обработчика молча ничего не даёт, а логика оказывается распределена между объявлением и обработчиком.
  13. Какие изменения ломают обратную совместимость?Удаление и переименование публичного метода, добавление обязательного параметра, сужение типа параметра, расширение типа возврата, добавление метода в интерфейс, новое исключение вне объявленной иерархии, добавление final к существующему классу. Безопасны изменения приватной реализации и необязательный параметр в конец.
  14. Как уменьшить поверхность публичного API?final по умолчанию, пометка служебных классов как внутренних, интерфейс для потребителей при скрытой реализации, именованные конструкторы вместо публичного конструктора и привычка спрашивать перед добавлением метода, готовы ли вы поддерживать его два года.
  15. Когда вводить абстракцию?При втором реальном случае, а не при первом воображаемом. Абстракция, добавленная заранее, платится ежедневно: каждое изменение проходит через лишние файлы, а понимание кода требует держать в голове конструкции, ничего не решающие. Второй случай к тому же показывает, какая именно абстракция нужна.
  16. Как понять, что граница между классами проведена неверно?По тому, что они всегда правятся вместе: изменение в одном требует изменения в другом. Это означает, что они разделяют знание, которое должно жить в одном месте. Решение — либо объединить, либо перенести это знание внутрь одного из них.
  17. Как подойти к рефакторингу класса на две тысячи строк?Не переписывать целиком. Найти в нём группы методов, работающих с одним подмножеством полей: это будущие отдельные классы. Выделять по одной группе, покрывая тестами интерфейс перед выделением. Ключевой критерий готовности шага — старый код продолжает работать без изменений в вызывающих местах.
  18. Как объектный дизайн влияет на тестируемость?Напрямую: класс с зависимостями через конструктор и без статических вызовов тестируется подстановкой, а класс, создающий зависимости внутри и лезущий в глобальное состояние, требует поднимать окружение. Трудность написания теста — самый честный индикатор проблем с дизайном.
  19. Когда объектный подход не нужен?Там, где нет ни правил, ни состояния: чтение данных для отображения, простые преобразования, скрипты. Оборачивать структуру из трёх полей в класс с интерфейсом и фабрикой — расход без выигрыша. ООП оправдывает себя там, где есть инварианты, которые надо защищать, и поведение, которое надо держать рядом с данными.
  20. Какой главный признак зрелого объектного дизайна?Класс, который невозможно использовать неправильно: некорректный экземпляр не создаётся, недопустимый переход состояния не выполняется, а пользователю не приходится помнить правила. Второй признак — понимание цены: зрелый инженер умеет объяснить не только зачем нужна абстракция, но и почему в этом месте её не будет.

15 практических заданий

Задания рассчитаны на реальный код: почти каждое начинается с того, что вы находите нужный класс у себя в проекте.

Junior · 5 заданий

Основы

1. Убрать сеттеры

Найдите класс с набором сеттеров, выпишите все места, где вызывающий код проверяет условия перед их вызовом. Замените сеттеры операциями предметной области, перенеся проверки внутрь.

РезультатПравила в одном месте вместо пяти и понимание, что инкапсуляция — не про модификаторы доступа.

2. Найти утечку внутренностей

Найдите метод, возвращающий внутреннюю коллекцию объектов. Напишите код, который меняет элемент снаружи в обход правил класса. Затем закройте дыру.

РезультатНаглядная демонстрация того, почему возврат массива объектов не безопасен.

3. Строковый статус в перечисление

Найдите строковое поле статуса и все ветвления по нему. Замените перечислением, перенеся поведение в его методы. Проверьте, сколько ветвлений исчезло.

РезультатМеньше ветвлений и невозможность передать несуществующий статус.

4. Разобрать иерархию

Возьмите класс, наследующийся от другого, и проверьте подстановку: можно ли использовать наследника всюду вместо родителя. Если нет — перепишите на композицию.

РезультатЛичный пример того, где наследование не работает, вместо учебного про квадрат и прямоугольник.

5. Интерфейс или абстрактный класс

Найдите в проекте абстрактный класс и интерфейс. Для каждого ответьте: сколько реализаций, что общего они несут, что сломается при добавлении метода. Решите, правильный ли механизм выбран.

РезультатОсознанный выбор вместо привычки и, возможно, пара лишних интерфейсов на удаление.

Middle · 6 заданий

Механика

6. Объект-значение целиком

Напишите объект-значение с приватным конструктором, именованным создателем, проверкой инварианта, методом равенства, поведением и приведением к строке. Покройте тестами создание с неверными данными.

РезультатШаблон, который дальше применяется к деньгам, идентификаторам, телефонам и адресам.

7. Примитивы в типы

Найдите метод с двумя-тремя одинаковыми примитивами в аргументах. Заведите отдельные типы, перепишите сигнатуру. Попробуйте переставить аргументы местами и убедитесь, что теперь это ошибка.

РезультатЦелый класс ошибок, ставший невозможным, ценой двух маленьких классов.

8. Сломать readonly

Создайте класс с readonly свойством, содержащим изменяемый объект. Измените его состояние снаружи. Затем сделайте объект по-настоящему неизменяемым.

РезультатПонимание глубины неизменяемости и готовый ответ на частый вопрос собеседования.

9. Клонирование с вложенными объектами

Возьмите класс с коллекцией изменяемых объектов, склонируйте, измените элемент в копии и убедитесь, что оригинал тоже изменился. Реализуйте __clone и проверьте снова.

РезультатПрактическое различие поверхностного и глубокого копирования на своём коде.

10. Типизированная коллекция

Замените возврат array на коллекцию с IteratorAggregate, Countable и аннотациями обобщений. Прогоните статический анализатор и посмотрите, что он теперь находит.

РезультатАнализатор начинает ловить ошибки, которые раньше были невидимы.

11. Иерархия исключений

Замените выброс общих исключений с текстовым сообщением на типы предметной области с данными и общим интерфейсом-маркером. Найдите места, где текст разбирали строковыми функциями.

РезультатОбработка ошибок по данным вместо разбора сообщений.

Senior · 4 задания

Проектирование

12. Убрать невозможные состояния

Найдите класс, где половина полей опциональна. Выпишите все комбинации и отметьте корректные. Разделите на отдельные типы состояний с общим интерфейсом и посчитайте, сколько проверок на null исчезло из проекта.

РезультатЧисло удалённых проверок — самая наглядная метрика этой темы.

13. Аудит инвариантов

Возьмите три ключевых класса и выпишите для каждого инварианты. Проверьте, где они обеспечиваются: в конструкторе, в операциях или в вызывающем коде. Перенесите всё, что можно, внутрь.

РезультатКлассы, которые нельзя привести в некорректное состояние снаружи.

14. Разбор связанности

Найдите класс с конструктором на шесть и более зависимостей. Сгруппируйте методы по тому, какие зависимости они используют. Выделите группы в отдельные классы и проверьте, упростились ли тесты.

РезультатНесколько классов с двумя-тремя зависимостями и тесты, которые пишутся без подготовки половины системы.

15. Ревизия публичной поверхности

Возьмите модуль и выпишите все публичные классы и методы. Для каждого ответьте, используется ли он снаружи модуля. Всё лишнее сделайте внутренним, классы — final. Посмотрите, что сломалось.

РезультатМеньшая поверхность обязательств и понимание, что на самом деле держит модуль связанным с остальным кодом.

Финал · подготовка

План подготовки на 4 недели

Расчёт на час-полтора в будний день. Вся практика — на собственном коде: учебные примеры в этой теме дают меньше, чем один разобранный класс из своего проекта.

Неделя 1 · Механика

База

Задачи недели

Разобраться, какую задачу решает каждая конструкция языка, и перестать выбирать их по привычке.

Что сделать

  • Переписать класс с сеттерами в класс с операциями предметной области (задание 1).
  • Найти утечку внутренней коллекции и закрыть её (задание 2).
  • Заменить строковый статус перечислением с поведением (задание 3).
  • Проверить одну иерархию наследования на подстановку и переписать на композицию (задание 4).
  • Разобрать имеющиеся интерфейсы и абстрактные классы: сколько реализаций, что они дают (задание 5).

Результат недели

Умение объяснить выбор между интерфейсом, абстрактным классом, трейтом и композицией на своём коде.

Неделя 2 · Типы и значения

Точность

Задачи недели

Научиться делать ошибки невозможными через типы и вынести правила из процедурного кода в объекты-значения.

Что сделать

  • Написать полноценный объект-значение с проверкой, равенством и поведением (задание 6).
  • Заменить одинаковые примитивы в сигнатуре отдельными типами (задание 7).
  • Разобраться с ковариантностью и контравариантностью на своём коде.
  • Заменить возврат array типизированной коллекцией и прогнать анализатор (задание 10).
  • Включить strict_types там, где его нет, и разобрать возникшие ошибки.

Результат недели

Анализатор начинает находить то, что раньше находили пользователи, и часть проверок из кода исчезает.

Неделя 3 · Состояние и ошибки

Механика

Задачи недели

Закрыть вопросы, которые обычно решаются поведением по умолчанию: изменяемость, равенство, копирование, ошибки.

Что сделать

  • Сломать readonly изменяемым содержимым и сделать объект по-настоящему неизменяемым (задание 8).
  • Реализовать __clone для класса с коллекцией объектов (задание 9).
  • Объявить явное равенство для одной сущности и одного объекта-значения.
  • Построить иерархию исключений с данными вместо текстовых сообщений (задание 11).
  • Найти в коде перехват \Throwable в середине логики и решить, что с ним делать.

Результат недели

Явные ответы на вопросы о равенстве, копировании и ошибках вместо умолчаний, о которых никто не думал.

Неделя 4 · Проектирование

Финиш

Задачи недели

Перейти от отдельных классов к дизайну: инварианты, связанность, границы, стоимость изменений.

Что сделать

  • Убрать невозможные состояния из класса с опциональными полями и посчитать удалённые проверки (задание 12).
  • Провести аудит инвариантов трёх ключевых классов (задание 13).
  • Разобрать класс с шестью зависимостями на несколько (задание 14).
  • Провести ревизию публичной поверхности модуля (задание 15).
  • Пройтись по чек-листу вопросов к классу на ближайшем ревью и записать, что нашли.

Результат недели

Готовность обсуждать дизайн в терминах инвариантов, связанности и стоимости изменений, а не определений.

Что помогает на собеседовании

Бонус
  • Не отвечайте определениями. «Инкапсуляция — это сокрытие данных» — ответ уровня учебника. Сильный ответ добавляет следствие: правила живут в одном месте, внутреннее устройство можно менять, не ломая пользователей.
  • Приводите пример из своего кода. Классический пример про квадрат и прямоугольник знают все. Собственная история, где наследование пришлось разобрать на композицию, звучит принципиально иначе.
  • Называйте цену. Любой механизм — компромисс: неизменяемость создаёт больше объектов, интерфейсы удваивают файлы, атрибуты распределяют логику. Умение назвать обратную сторону отличает опыт от начитанности.
  • Умейте не вводить абстракцию. На вопрос «как бы вы это спроектировали» сильный ход — сказать, что здесь достаточно одного класса, и объяснить, при каком условии появится второй. Кандидаты чаще перепроектируют, чем недопроектируют.
  • Считайте проверки у пользователя класса. Формулировка «сколько условий вынужден помнить тот, кто им пользуется» — быстрый и убедительный критерий качества, который редко звучит на интервью.
  • Различайте ошибку программиста и ситуацию предметной области. Это одна из немногих тем про исключения, где сразу видно наличие продового опыта.
  • Будьте готовы к вопросу про рефакторинг легаси. Ответ «переписать» слабый. Сильный — выделять по одной группе методов, работающих с общим подмножеством полей, покрывая интерфейс тестами перед каждым шагом.
