Паттерны проектирования

Паттерн — не рецепт и не украшение кода, а название для повторяющегося решения, у которого есть известная область применимости и известная цена. Практическая ценность каталога в двух вещах: он даёт словарь, на котором двое разработчиков договариваются за одну фразу вместо получаса объяснений, и он избавляет от изобретения заново конструкции, чьи слабые места уже описаны за тридцать лет до вас.

Обратная сторона видна в любом проекте, где каталог прочитали слишком рано: фабрика фабрик, интерфейс на каждый класс, семь уровней декораторов вокруг одного HTTP-клиента. Паттерн не делает код лучше сам по себе — он обменивает простоту на возможность менять одну конкретную вещь дешевле. Если эта вещь не меняется, обмен убыточен. Поэтому весь конспект построен вокруг вопроса «какая ось изменения здесь настоящая», а не вокруг заучивания диаграмм.

Маршрут: зачем паттерны и когда они вредят, классификация, порождающие, одиночка и его цена, структурные → поведенческие, паттерн против возможности языка, паттерны внутри фреймворков → выбор по оси изменения, цена абстракции, рефакторинг к паттернам и обратно, корпоративные и инфраструктурные паттерны, антипаттерны. Смежные темы: паттерны и архитектура кода (SOLID, слои, DDD, работа с легаси), ООП в PHP (интерфейсы, композиция, объекты-значения), ORM и Doctrine, system design, тестирование.

junior / зачем

Зачем каталог паттернов

Мотивация

Паттерн — это описание пары «повторяющаяся проблема и проверенное решение» с именем. Имя и есть главная ценность: фраза «здесь стратегия» передаёт коллеге структуру, точки расширения и ожидаемое поведение за секунду. Без общего словаря то же самое объясняется абзацем текста, и половина смысла теряется.

Вторая ценность — предупреждения. Каталог описывает не только устройство решения, но и его слабые места: сколько классов появится, что станет труднее читать, какая гибкость окажется невостребованной. Разработчик, который изобретает конструкцию сам, получает её сильные стороны сразу, а слабые — через полгода.

Практический критерий, к которому сводится большая часть темы: паттерн вводится тогда, когда без него изменение требует правки нескольких мест сразу. Если очередная задача каждый раз заставляет добавить условие в три разных метода — ось изменения найдена и паттерн окупится. Если такого опыта ещё нет, введение паттерна — это ставка на предположение, а не решение проблемы.

АнтипаттернПроектирование «по каталогу»: разработчик прочитал книгу и раскладывает задачу по знакомым именам ещё до того, как понял, что в ней меняется. Симптом — интерфейс с одной реализацией у каждого класса, фабрика, создающая единственный тип, и стратегия с единственным вариантом. Такой код выглядит грамотным на ревью и стоит вдвое дороже в поддержке, потому что каждое изменение проходит через лишние слои.
Типичный вопрос на собеседованииЗачем нужны паттерны проектирования?
Для двух вещей: общего словаря в команде и готового знания о цене решения. Имя паттерна передаёт структуру и точки расширения одной фразой, а описание предупреждает о слабых местах, которые иначе обнаруживаются через полгода эксплуатации. При этом паттерн — не цель: он оправдан, когда есть реальная ось изменения, и вреден, когда вводится «на будущее».

Классификация и карта GoF

Каталог

ВажноКаталог написан для языков, где нет замыканий, перечислений и первоклассных функций. Часть паттернов в современном PHP сжимается до нескольких строк: стратегия часто становится замыканием, итератор — генератором, состояние — перечислением с методами. Это не отменяет паттерн, а меняет его форму: важно узнавать замысел, а не искать в коде диаграмму из книги.
Типичный вопрос на собеседованииКакие бывают группы паттернов и чем они отличаются?
Порождающие изолируют способ создания объекта, структурные — способ соединения объектов, поведенческие — распределение обязанностей и поток управления. Практическая польза деления в том, что оно сужает поиск: сначала понимаешь, что именно тебе мешает — создание, соединение или ветвление поведения, — и дальше выбираешь внутри группы.

Порождающие паттерны

Создание

Все порождающие паттерны решают одну проблему: код, который использует объект, не должен знать, как этот объект собирается. Как только создание становится сложным — зависит от условий, требует нескольких шагов, тянет за собой зависимости, — оно расползается по вызывающим местам и дублируется.

abstract class ReportJob

Строитель оправдан там, где объект собирается из многих необязательных частей и порядок сборки имеет значение: запрос к внешнему API, конфигурация отчёта, письмо с вложениями и условным содержимым. Признак, по которому его вводят, — конструктор, у которого больше пяти параметров и половина из них null в большинстве вызовов.

PHPСтроитель: собрать сложный объект и проверить инвариант один раз
final class ReportRequestBuilder
{
    private ?Period $period = null;
    private array $filters = [];
    private Format $format = Format::Csv;

    public function for(Period $period): static
    {
        $clone = clone $this;      // неизменяемый строитель: безопасно переиспользовать
        $clone->period = $period;

        return $clone;
    }

    public function filterBy(string $field, mixed $value): static
    {
        $clone = clone $this;
        $clone->filters[$field] = $value;

        return $clone;
    }

    // Инвариант проверяется в одной точке, а не в каждом сеттере
    public function build(): ReportRequest
    {
        if ($this->period === null) {
            throw new \LogicException("Период обязателен");
        }

        return new ReportRequest($this->period, $this->filters, $this->format);
    }
}
ОриентирВ PHP большая часть потребности в порождающих паттернах закрывается двумя вещами: именованными конструкторами и контейнером внедрения зависимостей. Контейнер — это и есть промышленная фабрика: он умеет собирать графы объектов, разрешать зависимости и отдавать разные реализации по конфигурации. Своя фабрика нужна, когда выбор зависит от данных времени выполнения, а не от конфигурации приложения.
Типичный вопрос на собеседованииЧем фабричный метод отличается от абстрактной фабрики?
Фабричный метод — один метод создания, который переопределяет наследник: варьируется один продукт внутри иерархии создателей. Абстрактная фабрика — интерфейс с несколькими методами, создающий семейство согласованных между собой объектов, чтобы нельзя было смешать части разных семейств. На практике в PHP первый встречается регулярно, вторая — редко и обычно там, где приложение работает с несколькими взаимоисключающими наборами реализаций.

junior / одиночка

Одиночка и его цена

Разбор

Одиночка гарантирует единственный экземпляр класса и даёт к нему глобальный доступ. Первая половина обещания иногда полезна, вторая — источник почти всех проблем: глобальный доступ означает, что зависимость не видна в сигнатурах, не подменяется в тестах и может использоваться откуда угодно.

PHPОдиночка и то, чем его заменяют
// Классическая реализация: экземпляр один, доступ отовсюду
final class Config
{
    private static ?self $instance = null;

    private function __construct(private array $values) {}

    public static function getInstance(): self
    {
        return self::$instance ??= new self(require "config.php");
    }
}

// Проблема видна в вызывающем коде:
final class InvoiceService
{
    public function issue(Order $order): Invoice
    {
        // Зависимость от конфигурации спрятана внутри метода:
        // её не видно в конструкторе и нельзя подменить в тесте.
        $vat = Config::getInstance()->get("vat_rate");

        return new Invoice($order, $vat);
    }
}

// Замена: единственность обеспечивает контейнер,
// а зависимость становится явной и подменяемой.
final class InvoiceService
{
    public function __construct(
        private readonly TaxPolicy $taxPolicy,
    ) {}

    public function issue(Order $order): Invoice
    {
        return new Invoice($order, $this->taxPolicy->rateFor($order));
    }
}

ВажноЕдинственность экземпляра и глобальная точка доступа — разные требования, и почти всегда нужно только первое. Контейнер внедрения зависимостей по умолчанию отдаёт один и тот же экземпляр сервиса, то есть даёт единственность без глобального доступа: зависимость остаётся видимой в конструкторе и подменяемой в тестах. Отдельно стоит помнить про долгоживущие процессы — там любой хранимый в статике объект живёт между запросами со всем накопленным состоянием, о чём подробнее в конспекте по асинхронному PHP.
Типичный вопрос на собеседованииПочему одиночку считают антипаттерном?
Не за единственность, а за глобальный доступ. Класс, вызывающий getInstance внутри метода, скрывает свою зависимость: её не видно в конструкторе, её нельзя подменить в тесте, и она превращается в общее изменяемое состояние, из-за которого тесты начинают влиять друг на друга. Единственность экземпляра при этом прекрасно обеспечивается контейнером, поэтому от паттерна остаётся только его цена.

Структурные паттерны

Обёртки

Четыре самых частых структурных паттерна снаружи выглядят одинаково — объект, который держит внутри другой объект. Различаются они замыслом, и путаница между ними — классический источник вопросов на собеседовании.

PHPДекоратор: поведение добавляется без правки класса
interface ExchangeRates
{
    public function rateFor(Currency $from, Currency $to): Rate;
}

// Базовая реализация ничего не знает ни о кэше, ни о логах
final class HttpExchangeRates implements ExchangeRates { /* ... */ }

final class CachedExchangeRates implements ExchangeRates
{
    public function __construct(
        private readonly ExchangeRates $inner,   // тот же интерфейс — ключ паттерна
        private readonly CacheInterface $cache,
    ) {}

    public function rateFor(Currency $from, Currency $to): Rate
    {
        return $this->cache->get(
            "rate.{$from->code}.{$to->code}",
            fn() => $this->inner->rateFor($from, $to),
        );
    }
}

$rates = new LoggedExchangeRates(

Заместитель отличается от декоратора намерением: он не добавляет новое поведение, а управляет доступом к настоящему объекту. Отсюда его разновидности, каждая из которых встречается в реальных проектах чаще, чем кажется.

Фасад — единственный из четырёх, кто меняет интерфейс на более простой и не обязан ничего сохранять. Он полезен на границе с чужой подсистемой и вреден внутри своего кода, если превращается в класс на тридцать методов, через который проходит вообще всё: тогда это уже не фасад, а точка сцепления всего со всем.

Типичный вопрос на собеседованииЧем декоратор отличается от адаптера и заместителя?
Интерфейсом и замыслом. Адаптер меняет интерфейс: приспосабливает чужой контракт к нужному. Декоратор сохраняет интерфейс и добавляет поведение — кэш, логирование, повторы, — поэтому декораторы складываются друг на друга. Заместитель тоже сохраняет интерфейс, но не добавляет функциональности, а управляет доступом: откладывает создание, проверяет права, скрывает сетевой вызов.

Поведенческие: варианты алгоритма

Ядро

PHPСтратегия: от match по типу к набору реализаций
// Было: метод растёт при каждом новом способе доставки
public function cost(Order $order, string $method): Money
{
    return match ($method) {
        "pickup"  => Money::zero(),
        "courier" => $this->courierCost($order),
        "post"    => $this->postCost($order),
        // ...и такой же match ещё в трёх местах: сроки, доступность, текст
    };
}

// Стало: вариант — это объект, знающий про свой способ всё
interface ShippingMethod
{
    public function supports(Order $order): bool;
    public function cost(Order $order): Money;
    public function estimate(Order $order): \DateInterval;
}

final class CourierShipping implements ShippingMethod { /* ... */ }

final class ShippingCalculator
{
    // Реализации собирает контейнер: новый способ — новый класс,
    // существующие файлы не трогаются.
    public function __construct(
        private readonly iterable $methods,
    ) {}

    public function cheapestFor(Order $order): Money
    {
        $costs = [];

        foreach ($this->methods as $method) {
            if ($method->supports($order)) {
                $costs[] = $method->cost($order);
            }
        }

        return Money::min(...$costs);
    }
}

Стратегия окупается не первым вариантом, а вторым использованием того же различия. Пока способ доставки влияет только на цену, хватает match в одном методе. Как только он влияет ещё и на сроки, доступность и текст в письме, ветвления начинают расходиться: где-то забыли добавить новый вариант, где-то условие сформулировано иначе. Именно этот момент — сигнал, а не появление второго варианта как такового.

PHPСостояние: поведение переезжает из условий в перечисление
// Классическая форма паттерна — класс на каждое состояние.
// В PHP роль диспетчера часто берёт перечисление с методами:
// невозможных значений не существует, а поведение лежит рядом.
enum OrderStatus: string
{
    case Draft     = "draft";
    case Confirmed = "confirmed";
    case Shipped   = "shipped";
    case Canceled  = "canceled";

    public function allowsEditing(): bool
    {
        return $this === self::Draft;
    }

    public function canTransitionTo(self $next): bool
    {
        return in_array($next, match ($this) {
            self::Draft     => [self::Confirmed, self::Canceled],
            self::Confirmed => [self::Shipped, self::Canceled],
            self::Shipped, self::Canceled => [],
        }, true);
    }
}

// собственные данные и зависимости: тогда перечисление не тянет.

    public function charge(Subscription $s): ChargeResult;

Команда превращает вызов в объект: у действия появляются имя, данные и возможность быть отложенным. В PHP-проектах паттерн живёт под другими названиями — сообщение в шине, задача в очереди, объект запроса в обработчике. Типичный вопрос на собеседованииЧем стратегия отличается от состояния?
Структура похожа — объект с подставляемой реализацией, — но различается управление. Стратегию выбирает вызывающий код или конфигурация, и варианты друг о друге не знают. Состояние объект меняет сам в зависимости от своего статуса, и состояния обычно знают о допустимых переходах между собой. Отсюда разные риски: у стратегии — разрастание точки выбора, у состояния — размазанная логика переходов.

PHPЦепочка обязанностей в форме middleware
interface Middleware
{
    // Каждое звено решает: обработать, передать дальше или прервать
    public function process(Request $request, callable $next): Response;
}

final class RateLimiter implements Middleware
{
    public function process(Request $request, callable $next): Response
    {
        if ($this->limiter->exceeded($request->clientId())) {
            return new Response(status: 429);   // прерываем цепочку
        }

        return $next($request);
    }
}

final class Pipeline
{
    public function __construct(private readonly array $middlewares) {}

    public function handle(Request $request, callable $handler): Response
    {
        // Сворачиваем список в матрёшку замыканий: последнее звено
        // вызывается первым, поэтому массив разворачивается с конца.
        $next = array_reduce(
            array_reverse($this->middlewares),
            fn(callable $next, Middleware $m) => fn(Request $r) => $m->process($r, $next),
            $handler,
        );

        return $next($request);
    }
}

Наблюдатель в чистом виде — объект со списком подписчиков и методом уведомления — в прикладном коде почти не пишут: его роль играет диспетчер событий фреймворка. Замысел от этого не меняется: источник публикует факт, не зная, кто на него отреагирует. Отсюда и главный риск — поток управления перестаёт читаться по коду, потому что список реакций собирается конфигурацией.

ВажноСобытие описывает уже случившийся факт, а не команду. Слушатель, который отменяет заказ внутри обработчика события «заказ создан», превращает оповещение в скрытый поток управления: по коду создания заказа невозможно понять, что произойдёт дальше. Практическое правило: если действие обязательно и его результат важен вызывающему коду — это вызов сервиса или команда, а не событие; события остаются для необязательных побочных эффектов.
АнтипаттернПосредник, который начинал с развязки трёх объектов, а через год знает про пятнадцать сервисов и содержит половину бизнес-логики. Формально связей «каждый с каждым» больше нет, фактически появился единственный класс, который правится в каждой задаче и который невозможно протестировать по частям. Признак вырождения — методы посредника перестали быть про координацию и начали содержать правила предметной области.
Типичный вопрос на собеседованииКогда событие, а когда прямой вызов?
Прямой вызов — когда действие обязательно, его результат нужен вызывающему коду и порядок важен: списать деньги, зарезервировать товар. Событие — когда факт уже произошёл и реакции необязательны и независимы: отправить письмо, обновить статистику, начислить бонусы. Ошибка в обе стороны заметна: обязательное действие в слушателе тихо теряется, а необязательное в основном потоке роняет операцию из-за недоступности почты.

PHPИтератор и компоновщик: обход дерева без знания устройства
// Компоновщик: лист и узел реализуют один интерфейс,
// поэтому вызывающий код не различает «элемент» и «группу».
interface CatalogNode
{
    public function title(): string;
    public function productCount(): int;
}

final class Product implements CatalogNode
{
    public function productCount(): int { return 1; }
}

final class Category implements CatalogNode, \IteratorAggregate
{
    /** @param list<CatalogNode> $children */
    public function __construct(
        private readonly string $title,
        private readonly array $children,
    ) {}

    public function productCount(): int
    {
        // Рекурсия по одному интерфейсу: ветвления по типу нет
        return array_sum(
            array_map(fn(CatalogNode $n) => $n->productCount(), $this->children),
        );
    }

    // Итератор в современном PHP — это генератор: обход описан
    // как последовательность, память под всё дерево не выделяется.
    public function getIterator(): \Generator
    {
        foreach ($this->children as $child) {
            yield $child;

            if ($child instanceof \Traversable) {
                yield from $child;
            }
        }
    }
}

Посетитель заслуживает отдельного предупреждения. Он дёшев, когда набор типов стабилен, а операций над ними много: отчёты, экспорт в разные форматы, вычисления по дереву. Но он обменивает лёгкость добавления операции на тяжесть добавления типа: новый узел заставляет править каждого посетителя. В прикладном коде, где типы предметной области как раз добавляются регулярно, эта сделка чаще всего невыгодна.

ОриентирПрежде чем вводить компоновщик или посетителя, проверьте, не решается ли задача одним рекурсивным методом. Дерево категорий с подсчётом товаров не требует иерархии классов, если группа и элемент по-настоящему различаются: match по двум типам читается лучше, чем интерфейс с методом, который у листа всегда возвращает единицу. Паттерн окупается с третьей-четвёртой операцией над структурой, а не с первой.

Когда над устойчивым набором типов нужно много разных операций и не хочется добавлять их в сами классы: вычисления по дереву, экспорт в разные форматы. Недостаток зеркальный: добавление операции дёшево, а добавление типа заставляет править всех посетителей сразу. Поэтому он уместен для стабильных структур вроде дерева выражений и плохо подходит для растущей доменной модели.

Типичный вопрос на собеседованииНужны ли паттерны в языке с замыканиями и перечислениями?

Экономика

У каждого паттерна есть постоянные издержки: больше файлов, больше косвенности, длиннее путь от точки входа до реальной логики. Эти издержки платятся всегда, а выгода приходит только при изменении. Рефакторинг к паттернам и обратно

Техника

В работающем проекте паттерны не проектируют заранее — к ним приходят, когда очередная задача упирается в одно и то же место. Важна техника: переход должен состоять из мелких шагов, каждый из которых оставляет код работающим и проверяемым тестами.

PHPЗамена условий полиморфизмом: четыре безопасных шага
// Шаг 0. Исходное состояние: правила в условиях, тесты есть только
// на публичный метод — этого достаточно, чтобы начать.
public function discountFor(Customer $c, Cart $cart): Money
{
    if ($c->isVip()) {
        return $cart->total()->percent(15);
    }

    if ($c->isEmployee()) {
        return $cart->total()->percent(30);
    }

    return Money::zero();
}

// Шаг 1. Каждая ветка становится отдельным приватным методом.
// Поведение не меняется, тесты остаются зелёными.

// Шаг 2. Методы переезжают в классы с общим интерфейсом.
interface DiscountPolicy
{
    public function appliesTo(Customer $c): bool;
    public function amount(Cart $cart): Money;
}

// Шаг 3. Условия заменяются перебором политик. Старый метод
// остаётся на месте и делегирует — вызывающий код не трогаем.
public function discountFor(Customer $c, Cart $cart): Money
{
    foreach ($this->policies as $policy) {
        if ($policy->appliesTo($c)) {
            return $policy->amount($cart);
        }
    }

    return Money::zero();
}

// Шаг 4. Только теперь — тесты на каждую политику отдельно
// и удаление тестов, которые проверяли ветвление изнутри.

Набор тестов, где каждая стратегия проверяется отдельно, а сценария целиком нет, превращает любой обратный рефакторинг в переписывание тестов — и потому в аргумент «трогать нельзя». Правильная опора для перехода — тесты, которые не знают, есть внутри паттерн или нет. Подробнее о таком разделении — в конспекте по тестированию.
Типичный вопрос на собеседованииКак ввести паттерн в работающий код, не сломав его?
Мелкими шагами с зелёными тестами после каждого. Сначала выделяю ветки в отдельные методы, потом переношу их в классы с общим интерфейсом, потом заменяю условие перебором реализаций, оставляя старый метод как точку входа. Вызывающий код не трогается до самого конца, а тесты пишутся на поведение через публичную границу — тогда и обратный ход, если абстракция не оправдается, остаётся дешёвым.

Выбор между Data Mapper и Active Record — самое заметное архитектурное решение этого слоя, и оно не сводится к «Doctrine лучше». Active Record выигрывает на CRUD-приложениях: меньше кода, быстрее разработка, всё под рукой. Data Mapper выигрывает там, где есть настоящая предметная логика с инвариантами, которую хочется тестировать без базы. Ошибка обычно не в выборе, а в попытке построить сложный домен поверх Active Record и потом удивляться, что модель знает про хранение.

ВажноРепозиторий — не «класс с запросами», а коллекция сущностей с точки зрения домена. Признак вырождения — методы вида findActiveByCategoryAndPriceRangeOrderedByRating, которые множатся с каждым экраном интерфейса. Лечится двумя способами: спецификациями для отбора внутри домена и отдельными объектами-запросами для чтения на экраны, что заодно разводит модель записи и модель чтения. Подробнее о репозиториях и связанных ловушках — в конспекте по ORM и Doctrine.
Типичный вопрос на собеседованииЧем Data Mapper отличается от Active Record?
Тем, кто знает про хранение. В Active Record сущность сама умеет сохраняться и наследуется от базового класса ORM — быстро для CRUD, но домен становится зависим от базы, а тесты требуют хранилища. В Data Mapper объект предметной области ничего не знает о базе, отображением занимается отдельный слой — больше кода, зато инварианты и логика тестируются без инфраструктуры. Выбор определяется тем, есть ли в приложении настоящая доменная логика.

Общее у всей группы — они описывают поведение при отказе, а не структуру классов. Поэтому и вводят их не по каталогу, а по инциденту: предохранитель появляется после первого раза, когда лежащий провайдер выел пул воркеров, идемпотентный обработчик — после первого двойного списания. Это редкий случай, когда «преждевременное» применение оправдано: у некоторых из них цена ошибки такова, что закладывать их лучше сразу.

ОриентирКлассические и инфраструктурные паттерны хорошо сочетаются: предохранитель, повторы и кэш естественно оформляются декораторами поверх одного порта. Это даёт полезное свойство — базовая реализация остаётся чистой и тестируется без инфраструктуры, а поведение при отказах собирается конфигурацией контейнера и меняется без правки бизнес-кода.
Типичный вопрос на собеседованииКакие паттерны вы применяете при интеграции с внешним сервисом?
Со стороны структуры — порт с адаптером, чтобы чужое API не протекало в домен, и декораторы поверх него для повторов, предохранителя, кэша и метрик. Со стороны поведения — идемпотентность операций и явная обработка неизвестного результата при таймауте. Такое разделение оставляет базовую реализацию тестируемой без сети, а политику отказов — настраиваемой без правки кода.

АнтипаттернОтдельно стоит культ каталога на ревью: комментарий «здесь нужен паттерн X» без объяснения, какая ось изменения его оправдывает. Типичный вопрос на собеседованииПриведите пример, когда паттерн навредил.
Сильный ответ — из собственного опыта и с числами: сколько файлов приходилось открывать, чтобы понять поведение, сколько правок требовало изменение, ради которого абстракция и заводилась. Типичный сюжет: интерфейс и фабрика заведены под будущего второго поставщика, второй поставщик пришёл через два года и потребовал другого контракта, так что абстракцию всё равно переписали, а два года её просто обходили.

Проверка

Что должно быть в арсенале.

  • Выводить паттерн из оси изменения, а не подбирать из каталога.
  • Назвать по запаху кода подходящее решение и случаи, где паттерн не поможет.
  • Перечислить издержки абстракции и сказать, кто именно их платит.

  • Найти признаки неудачной абстракции и предложить сворачивание.
  • Провести замену условий полиморфизмом мелкими шагами с зелёными тестами.

Стратегия через контейнер

Шаблон

Ключевая деталь — точка выбора не должна знать список реализаций. Иначе новый вариант всё равно требует правки старого файла, и половина смысла паттерна теряется.

PHP + YAMLНабор реализаций собирается автоматически
// Реализации помечаются атрибутом — регистрация не требуется
#[AutoconfigureTag("app.discount_policy")]
interface DiscountPolicy
{
    public function appliesTo(Customer $customer): bool;
    public function amount(Cart $cart): Money;
}

final class DiscountCalculator
{
    /** @param iterable<DiscountPolicy> $policies */
    public function __construct(
        #[AutowireIterator("app.discount_policy")]
        private readonly iterable $policies,
    ) {}

    public function bestFor(Customer $customer, Cart $cart): Money
    {
        $best = Money::zero();

        foreach ($this->policies as $policy) {
            if (!$policy->appliesTo($customer)) {
                continue;
            }

            $amount = $policy->amount($cart);
            $best = $amount->greaterThan($best) ? $amount : $best;
        }

        return $best;
    }
}

#[AsDecorator(decorates: ExchangeRates::class, priority: 10)]
final class CachedExchangeRates implements ExchangeRates
{
    public function __construct(
        #[AutowireDecorated] private readonly ExchangeRates $inner,
        private readonly CacheInterface $cache,
    ) {}

    public function rateFor(Currency $from, Currency $to): Rate
    {
        return $this->cache->get(
            "rate.{$from->code}.{$to->code}",
            fn() => $this->inner->rateFor($from, $to),
        );
    }
}

// приоритетов проходит ревью незаметно и меняет поведение.

Спецификация

Шаблон

Правило отбора получает имя и перестаёт дублироваться между проверкой в коде и условием в запросе. Второй метод — перевод в критерий базы — и есть то, ради чего паттерн обычно вводят.

interface Specification
{
    public function isSatisfiedBy(Customer $customer): bool;
    public function toCriteria(): Criteria;
}

final class LoyalCustomer implements Specification
{
    public function __construct(
        private readonly int $minOrders = 5,
    ) {}

    public function isSatisfiedBy(Customer $customer): bool
    {
        return $customer->completedOrders() >= $this->minOrders;
    }

    // Та же логика в терминах хранилища: правило одно,
    // поэтому список на экране и проверка в домене не разъезжаются.
    public function toCriteria(): Criteria
    {
        return Criteria::create()->andWhere(
            Criteria::expr()->gte("completedOrders", $this->minOrders),
        );
    }
}

        private readonly OrderRepository $orders,

Чек-лист перед введением паттерна

Проверка
  • Сформулирована ось изменения: «чтобы дёшево менять ___».
  • Есть подтверждение из истории задач, что эта ось действительно меняется.
  • Вариантов уже три или второй-третий на подходе, а не «может быть».
  • Понятно, кто выбирает вариант: вызывающий код, конфигурация или сам объект.
  • Точка выбора не требует правки при добавлении нового варианта.
  • Проверено, не решает ли задачу возможность языка: замыкание, перечисление, генератор.
  • Проверено, не реализован ли паттерн уже во фреймворке.
  • Названо, что станет труднее: сколько файлов открывать, чтобы понять поведение.
  • Тесты пишутся на поведение через публичную границу, а не на устройство паттерна.
  • Есть представление, как свернуть абстракцию обратно, если она не оправдается.
  • Имя в коде отражает предметную область, а не название паттерна из книги.
  • Решение объяснимо коллеге одной фразой без ссылки на авторитет каталога.

60 вопросов с эталонными ответами

Паттерны — тема, где легко отвечать пересказом книги. Сильный ответ содержит две вещи, которых в книге нет: форму паттерна в современном PHP и его цену.

Junior · 20 вопросов

База
  1. Что такое паттерн проектирования?Описание повторяющейся проблемы и проверенного решения с именем и известной областью применимости. Ценность в общем словаре: фраза «здесь стратегия» передаёт структуру и точки расширения за секунду. Вторая ценность — готовое знание о слабых местах решения.
  2. Зачем нужны паттерны, если код и так работает?Чтобы изменения стоили дешевле там, где они действительно происходят. Паттерн выделяет ось изменения, чтобы добавление варианта требовало одной правки, а не пяти. Если ось изменения не найдена, паттерн только добавляет косвенности и не окупается.
  3. Какие есть группы паттернов?Порождающие изолируют создание объектов, структурные — их соединение, поведенческие — распределение обязанностей и поток управления. Деление помогает искать решение: сначала понимаешь, что мешает — создание, соединение или ветвление, — потом выбираешь внутри группы.
  4. Назовите порождающие паттерны.Фабричный метод, абстрактная фабрика, строитель, прототип, одиночка. В PHP к ним примыкают именованные конструкторы и контейнер внедрения зависимостей, который фактически выполняет роль промышленной фабрики для всего приложения.
  5. Чем фабричный метод отличается от абстрактной фабрики?Фабричный метод — один метод создания, переопределяемый наследником: варьируется один продукт. Абстрактная фабрика — интерфейс с несколькими методами, создающий семейство согласованных объектов, чтобы нельзя было смешать части из разных семейств. В PHP первое встречается регулярно, второе редко.
  6. Что такое именованный конструктор?Статический метод создания с говорящим именем вместо публичного конструктора: Money::fromDecimalString, Email::fromString. Он объясняет смысл аргументов, позволяет иметь несколько способов создания и оставляет свободу менять сигнатуру конструктора, не ломая вызывающий код.
  7. Когда нужен строитель?Когда объект собирается из многих необязательных частей и порядок сборки важен: запрос к API, конфигурация отчёта, письмо с вложениями. Практический признак — конструктор с шестью параметрами, половина из которых в большинстве вызовов равна null. Инвариант при этом проверяется один раз в методе сборки.
  8. Что такое прототип?Создание нового объекта копированием готового, когда конструирование дороже копирования. В PHP это clone, и главная тонкость — поверхностность копирования: вложенные объекты остаются общими, поэтому при наличии изменяемого состояния нужно реализовать __clone.
  9. Почему одиночку считают проблемой?Из-за глобального доступа, а не из-за единственности. Класс, вызывающий getInstance внутри метода, скрывает зависимость: её не видно в конструкторе, нельзя подменить в тесте, и она превращается в общее изменяемое состояние. Единственность прекрасно обеспечивает контейнер.
  10. Чем заменить одиночку?Внедрением зависимости через конструктор: контейнер по умолчанию отдаёт один и тот же экземпляр сервиса, то есть даёт единственность без глобального доступа. Зависимость остаётся видимой и подменяемой, а в долгоживущих процессах не превращается в состояние, протекающее между запросами.
  11. Что такое адаптер?Обёртка, приводящая чужой интерфейс к нужному вам. Типичное применение — SDK внешнего сервиса за собственным доменным контрактом: тогда замена поставщика затрагивает один класс, а не двадцать файлов, где раньше упоминалась библиотека.
  12. Что такое декоратор?Обёртка с тем же интерфейсом, добавляющая поведение вокруг вызова: кэш, логирование, повторы, метрики. Поскольку интерфейс сохраняется, декораторы складываются друг на друга, а базовая реализация остаётся чистой и ничего о них не знает.
  13. Что такое заместитель и какие у него виды?Объект с тем же интерфейсом, управляющий доступом к настоящему. Виды: ленивый — откладывает создание, как прокси-объекты Doctrine; защитный — проверяет права; удалённый — прячет сетевой вызов; кэширующий и измеряющий. Новой функциональности он не добавляет, в этом отличие от декоратора.
  14. Чем декоратор отличается от адаптера и заместителя?Интерфейсом и замыслом. Адаптер меняет интерфейс, декоратор его сохраняет и добавляет поведение, заместитель сохраняет и управляет доступом. Структурно все трое — объект внутри объекта, поэтому на собеседовании ждут именно объяснения через намерение.
  15. Что такое фасад?Простой вход в сложную подсистему: один метод вместо пяти вызовов подряд. Он не обязан сохранять исходный интерфейс и полезен на границе с чужим кодом. Вырождается, когда превращается в класс на тридцать методов, через который проходит вообще всё.
  16. Что такое компоновщик?Единый интерфейс для отдельного элемента и группы элементов, благодаря чему вызывающий код обходит дерево, не различая узел и лист. Классические примеры — дерево категорий, вложенные правила валидации, составные фильтры.
  17. Что такое стратегия?Взаимозаменяемые варианты алгоритма за общим интерфейсом: способ доставки, расчёт скидки, формат экспорта. Вводится, когда одинаковое ветвление появляется в нескольких методах: тогда новый вариант становится новым классом вместо правки трёх существующих файлов.
  18. Что такое наблюдатель?Оповещение подписчиков о произошедшем факте без знания о том, кто на него отреагирует. В PHP-проектах его роль почти всегда играет диспетчер событий фреймворка. Цена — поток управления перестаёт читаться по коду, потому что список реакций собирается конфигурацией.
  19. Что такое шаблонный метод?Общий каркас алгоритма в базовом классе, где отдельные шаги переопределяются наследниками: три почти одинаковых импорта, различающихся разбором строки. Отличие от стратегии — механизм наследования вместо композиции, поэтому вариант нельзя подменить в рантайме.
  20. Когда паттерн применять не нужно?Когда ось изменения не подтверждена опытом: вариант один, код не менялся год, а обоснование звучит как «вдруг понадобится». Признаки преждевременности — интерфейс с единственной реализацией, фабрика для одного класса, стратегия с одним вариантом. Цена косвенности платится сразу, а выгода может не наступить никогда.

Механика
  1. Чем стратегия отличается от состояния?Управлением. Стратегию выбирает вызывающий код или конфигурация, варианты друг о друге не знают. Состояние объект меняет сам по своему статусу, и состояния обычно знают о допустимых переходах. Риски тоже разные: у стратегии разрастается точка выбора, у состояния — логика переходов.
  2. Чем стратегия отличается от шаблонного метода?Механизмом. Стратегия — композиция: реализация подставляется и меняется в рантайме. Шаблонный метод — наследование: варианты фиксируются на этапе написания и жёстко связаны с базовым классом, поэтому его изменение задевает всех наследников. При прочих равных предпочтительна композиция.

Полноценные классы состояний нужны, когда у состояния есть собственные данные или зависимости, которые в перечисление не помещаются.
  4. Зачем превращать действие в объект?Чтобы его можно было отложить, поставить в очередь, повторить после сбоя, залогировать или отменить. В PHP это сообщение шины, задача очереди или объект запроса с обработчиком. Обязательное условие — обработчик идемпотентен, потому что доставка «как минимум один раз» означает повторы.
  5. Как устроена цепочка обязанностей в вебе?Как middleware: каждое звено получает запрос и функцию перехода к следующему, может обработать, передать дальше или прервать цепочку. Порядок регистрации определяет поведение, а самая частая ошибка — звено, забывшее вызвать следующий обработчик: запрос исчезает молча.
  6. Когда использовать событие, а когда прямой вызов?Прямой вызов — когда действие обязательно, его результат нужен вызывающему коду и порядок важен. Событие — когда факт уже случился, а реакции необязательны и независимы. Ошибка в любую сторону заметна: обязательное действие в слушателе тихо теряется, а необязательное в основном потоке роняет операцию.
  7. Чем наблюдатель отличается от посредника?Наблюдатель рассылает факт всем подписчикам и не управляет ими. Посредник знает участников и координирует их взаимодействие, заменяя связи «каждый с каждым». Отсюда и разные риски: у наблюдателя — неявный поток управления, у посредника — вырождение в божественный объект с бизнес-логикой.
  8. В чём недостаток посетителя?Он делает дешёвым добавление операции и дорогим добавление типа: новый узел структуры требует правки всех посетителей. Поэтому он хорош для стабильных структур — дерево выражений, разбор формата — и плох для доменной модели, куда типы добавляются регулярно.
  9. Всегда ли нужен компоновщик для дерева?Нет. Если операций над структурой одна-две, обычный рекурсивный метод с match по двум типам читается лучше, чем интерфейс, у которого лист возвращает константу. Паттерн окупается с третьей-четвёртой операцией или когда клиентский код действительно не должен различать узел и лист.
  10. Когда замыкание вместо класса, а когда наоборот?Замыкание — когда вариант это одна операция без зависимостей, живущая в конфигурации: сравнение для сортировки, простое преобразование. Класс — когда у варианта есть зависимости, ему нужно предметное имя и отдельные тесты. Замыкание на сорок строк, захватывающее пять переменных, — это класс, который постеснялись создать.

Замысел при этом сохраняется: важно узнавать решаемую проблему, а не искать в коде диаграмму из книги.
  12. Какие паттерны вы видите в своём фреймворке?Контейнер — фабрика и заместитель, middleware — цепочка обязанностей, диспетчер событий — наблюдатель, шина сообщений — команда, прокси-объекты ORM — ленивый заместитель, PSR-совместимые кэш и логгер — адаптеры. Сильный ответ добавляет следствие: например, порядок middleware определяет, увидит ли ограничитель уже аутентифицированного пользователя.
  13. Фасады Laravel — это паттерн фасад?Нет, это локатор служб со статическим доступом к контейнеру. Классический фасад упрощает интерфейс подсистемы и остаётся обычным объектом с явными зависимостями. Локатор же скрывает зависимость класса, и в тестах это проявляется так же, как с одиночкой.
  14. Какой паттерн стоит за прокси-объектами Doctrine?Ленивый заместитель: вместо связанной сущности подставляется объект того же типа, который загружает данные при первом обращении к полю. Практическое следствие — обращение к свойству может выполнить запрос, и именно отсюда берётся N+1 при обходе коллекции.
  15. Зачем нужен репозиторий, если есть ORM?Чтобы домен говорил о коллекции сущностей, а не о запросах: findActiveSubscribers вместо построителя запроса в сервисе. Плюс это точка подмены в тестах. Вырождается он в класс с сорока методами findByXAndY, что лечится спецификациями и отдельными объектами-запросами для чтения.
  16. Что такое Unit of Work?Паттерн, при котором изменения накапливаются и сохраняются одной атомарной пачкой. В Doctrine это происходит при flush: менеджер отслеживает изменённые сущности и генерирует запросы сам. Следствие — забытый flush теряет изменения, а неожиданный сохраняет то, что править не собирались.
  17. Что такое спецификация и зачем она?Правило отбора, оформленное объектом с именем: проверка объекта в памяти и то же условие для запроса к базе живут в одном месте и не разъезжаются. Правила комбинируются логическими операциями, поэтому вместо копирования условий появляется композиция.
  18. Когда уместен пустой объект?Когда отсутствие поведения — нормальный режим: отключённый канал уведомлений, пустой сборщик метрик в тестах. Неуместен как заглушка вместо отсутствующих данных: пустой клиент с нулевым балансом скрывает ошибку загрузки, и она всплывает далеко от места возникновения.
  19. Почему важен порядок декораторов?Потому что он определяет поведение: кэш поверх повторов сохраняет уже успешный результат, а повторы поверх кэша будут повторять и обращения к кэшу. При настройке через контейнер порядок задаётся приоритетами и молча меняется при правке конфигурации, поэтому его фиксируют тестом.
  20. Как тестировать код с паттернами?Через поведение на публичной границе, а не через устройство. Реализации стратегий проверяются по отдельности, но обязателен и тест сценария целиком, иначе любой обратный рефакторинг превращается в переписывание тестов. Проверки вида «был вызван такой-то класс» привязывают тесты к структуре и мешают её менять.

Senior · 20 вопросов

Решения
  1. Как вы выбираете паттерн?От оси изменения, а не перебором каталога. Сначала формулирую, что именно здесь меняется и как часто, потом ищу точку подстановки, которая делает изменение локальным, и только в конце появляется имя паттерна — оно нужно для разговора с командой. Если ось изменения назвать не получается, любой выбор будет угадыванием.
  2. Что такое правило трёх?Первый случай пишется прямо, второй копируется с осознанием дублирования, на третьем выделяется абстракция. Смысл в том, что только к третьему разу видно, что действительно общее, а что различается. Абстракция из двух примеров почти всегда обобщает не по той оси и потом мешает.
  3. Сколько стоит абстракция?Косвенность при чтении, лишние сущности с их тестами, порог входа для новых людей, более длинные трассировки при отладке и сопротивление удалению — паттерн выглядит правильным, и его жалко убирать. Издержки платятся постоянно, а выгода приходит только при изменении по заложенной оси.
  4. Как понять, что абстракция неудачная?У интерфейса годами одна реализация; реализации выбрасывают «не поддерживается»; добавление варианта всё равно требует правок в нескольких файлах; в сигнатурах появляются детали одной конкретной реализации. Проверочная фраза — «этот интерфейс нужен, чтобы дёшево менять ___»; отсутствие ответа и есть диагноз.
  5. Как ввести паттерн в работающий код?Мелкими шагами с зелёными тестами: выделить ветки в методы, перенести их в классы с общим интерфейсом, заменить условие перебором реализаций, оставив прежний метод точкой входа. Вызывающий код трогается последним. Такая последовательность делает дешёвым и обратный ход.
  6. Как убрать паттерн, который не оправдался?Встроить единственную реализацию обратно в вызывающий класс, удалить интерфейс и точку выбора, затем убрать тесты, которые проверяли устройство, а не поведение. Главное препятствие обычно не техническое: конструкция выглядит «правильной», и её удаление приходится обосновывать так же, как введение.
  7. Почему тесты мешают убирать абстракции?Потому что часто написаны на устройство: моки конкретных интерфейсов, проверки «был вызван такой-то класс». Такие тесты фиксируют структуру, и любое её изменение выглядит как поломка. Опора для рефакторинга — тесты на поведение через публичную границу, которые не знают, есть внутри паттерн или нет.
  8. Data Mapper или Active Record?По характеру приложения. Active Record выигрывает на CRUD: меньше кода, быстрее разработка. Data Mapper выигрывает там, где есть настоящая доменная логика с инвариантами, которую нужно тестировать без базы. Типичная ошибка — строить сложный домен поверх Active Record и удивляться, что модель знает про хранение.
  9. Что такое анемичная модель и всегда ли это плохо?Сущности без поведения, вся логика в сервисах. Плохо, когда у домена есть инварианты: они перестают защищаться и дублируются по сервисам. Нормально, когда предметной логики почти нет и приложение по сути перекладывает данные, — тогда доменная модель была бы церемонией ради церемонии.
  10. Как не дать репозиторию выродиться?Разделить чтение и запись: репозиторий говорит о сущностях и их сохранении, а списки для экранов собираются отдельными объектами-запросами, которым не нужны сущности целиком. Правила отбора выносятся в спецификации, чтобы не плодить методы вида findActiveByCategoryAndPriceRange.
  11. Когда оправдан CQRS?Когда модель записи и модель чтения расходятся по-настоящему: запись защищает инварианты, чтение обслуживает десяток разных экранов с агрегатами. Начинать стоит с разделения в коде без отдельных хранилищ; отдельная база для чтения добавляет согласованность в конечном счёте и оправдана только при доказанной нагрузке.
  12. Зачем нужны порты и адаптеры?Чтобы контракт задавал домен, а инфраструктура его реализовывала, а не наоборот. Тогда чужое API не протекает внутрь, реализацию можно подменить в тестах, а поведение при отказах — повторы, предохранитель, кэш — добавляется декораторами поверх порта без правки бизнес-кода.
  13. Какие паттерны нужны при интеграции с внешним сервисом?Структурно — порт с адаптером и декораторы для повторов, предохранителя, кэша и метрик. Поведенчески — идемпотентность операций и явная обработка неизвестного результата при таймауте. Такое разделение оставляет базовую реализацию тестируемой без сети, а политику отказов — настраиваемой.
  14. Что делает предохранитель и когда его вводить?Размыкает вызовы к сервису после превышения доли ошибок, чтобы лежащая зависимость не съедала пул воркеров и не превращала частичный отказ в полный. Вводят обычно после первого такого инцидента, но для критичных внешних зависимостей разумно закладывать сразу — цена ошибки слишком высока.
  15. Что такое идемпотентный обработчик и зачем он?Обработчик, для которого повторная обработка того же сообщения ничего не меняет. Он необходим, потому что очереди дают доставку «как минимум один раз», а сеть — неизвестные результаты. Технически это ключ операции с уникальным индексом плюс проверка текущего состояния перед действием.
  16. Зачем сага, если есть транзакции?Потому что транзакции не пересекают границу сервиса или внешней системы: двухфазная фиксация с чужим провайдером невозможна. Сага заменяет откат компенсирующими действиями и требует упорядочить шаги по обратимости — необратимые последними. Остаточные расхождения ловит сверка.
  17. Приведите пример, когда паттерн навредил.Сильный ответ — из своего опыта с цифрами: сколько файлов нужно открыть, чтобы понять поведение, и сколько правок потребовало изменение, ради которого абстракция заводилась. Типичный сюжет — интерфейс под будущего второго поставщика, который через два года пришёл с другим контрактом, так что абстракцию всё равно переписали.
  18. Как вы относитесь к требованию «примени паттерн» на ревью?Принимаю его только вместе с осью изменения: «чтобы дёшево менять ___». Без этого комментарий опирается на авторитет каталога и не обсуждается по существу, а в код попадают абстракции, которых никто не заказывал. Обратное требование — обосновать удаление абстракции — работает по тем же правилам.
  19. Как называть классы: по паттерну или по домену?По домену, за редкими исключениями. PromoDiscount говорит, что делает класс, а DiscountStrategyImpl — только то, какую книгу читал автор. Имена паттернов уместны там, где они стали частью словаря инфраструктуры: CachedExchangeRates, OrderRepository, обработчик команды.
  20. Как понять, что проект переусложнён паттернами?По измеримым признакам: сколько файлов открывает разработчик, чтобы проследить простой сценарий; сколько абстракций имеют единственную реализацию; сколько времени занимает онбординг до первой самостоятельной задачи. Если типичное изменение всё равно задевает пять файлов, гибкость заложена не там, где она нужна.

Результат недели

Готовность обсуждать паттерны в терминах осей изменения, цены и обратимости, а не структуры из книги.

Что помогает на собеседовании

Бонус
  • Отвечайте задачей, а не структурой. «Стратегия — это интерфейс и несколько реализаций» — уровень учебника. Сильный ответ начинается с проблемы: одинаковое ветвление разошлось по трём методам, и каждый новый вариант забывали добавить в одном из них.
  • Называйте форму в современном PHP. Упоминание, что состояние часто становится перечислением с методами, а итератор — генератором, сразу отличает практика от человека, который читал книгу и не писал код.
  • Всегда называйте цену. У любого паттерна она есть: больше файлов, длиннее путь до логики, сложнее отладка. Кандидат, который сам говорит про издержки, выглядит убедительнее того, кто перечисляет одни достоинства.
  • Держите наготове историю про удаление. Ввести паттерн умеют все, рассказать, как убрали неоправдавшуюся абстракцию и что это дало, — единицы. Это один из самых сильных ответов на вопрос про архитектурный опыт.
  • Не путайте похожие пары. Декоратор и заместитель, стратегия и состояние, адаптер и фасад — самые частые уточняющие вопросы. Различие объясняется через замысел, а не через диаграмму.
  • Знайте паттерны своего фреймворка. Вопрос «какие паттерны вы видите в Symfony или Laravel» встречается постоянно, а хороший ответ добавляет следствие: порядок middleware, ленивые прокси и N+1, скрытые зависимости при статическом доступе.
  • Будьте готовы отказаться от паттерна. На задачу «спроектируйте это» сильный ход — сказать, что здесь достаточно одного класса, и назвать условие, при котором появится абстракция. Переусложняют на собеседованиях гораздо чаще, чем недоусложняют.
  • Помните про инфраструктурный слой. На уровне Senior повторы, предохранитель, идемпотентность и сага спрашивают чаще, чем посетителя и приспособленца. Их полезно уметь связать с конкретным инцидентом из своего опыта.
