Git и командная работа

Git выучивают дважды. Сначала как набор из шести команд, которых хватает, пока всё идёт по плану. Потом — по-настоящему, обычно после первого случая «я что-то сделал и потерял день работы». Разница между этими состояниями не в количестве заученных флагов, а в понимании модели: что такое коммит, куда указывает ветка и почему почти ничего в Git на самом деле не теряется.

Вторая половина темы — не про инструмент, а про людей. История коммитов, размер pull request и тон комментариев на ревью влияют на скорость команды сильнее, чем выбор между rebase и merge. Проект, где ревью идёт три дня, а ветки живут месяц, тормозит не из-за Git — Git лишь делает эту боль видимой.

Конспект идёт от модели данных к процессу: объекты и ветки → rebase, отмена изменений, стратегии ветвления, pull request → выбор процесса под команду, история как инструмент расследования, откаты в инцидентах и договорённости, которые держат всё это вместе. Смежные темы: инфраструктура и CI, тестирование, софт-скиллы, PHP.

junior / модель

Как устроен Git

База

Git хранит не изменения, а снимки: каждый коммит — это полное состояние дерева файлов плюс ссылка на родителя. Различия вычисляются на лету при показе. Отсюда следует всё остальное: коммит неизменяем, ветка — просто указатель, а история — граф, а не список.

bashЧто внутри: объекты, на которые всё опирается
# Коммит — это объект: дерево файлов, родитель, автор, сообщение
git cat-file -p HEAD
# tree   a1b2c3...        ← снимок дерева файлов
# parent 9f8e7d...        ← предыдущий коммит (у merge их два)
# author Ivan <i@e.com> 1770000000 +0300

# Ветка — это файл с одной строкой: хеш коммита. Всё.
cat .git/refs/heads/main
# 9f8e7d6c5b4a...

# HEAD — указатель на текущую ветку (или прямо на коммит в detached-состоянии)
cat .git/HEAD
# ref: refs/heads/main

# Отсюда следствие: переключение веток и создание веток — операции почти бесплатные,
# потому что это запись одного хеша в один файл, а не копирование кода.

ВажноГлавное практическое следствие модели: коммит, который вы сделали, почти невозможно потерять. Даже если ветка «пропала», а reset --hard увёл вас в прошлое, коммиты остаются в репозитории и находятся через git reflog в течение месяцев. По-настоящему теряются только незакоммиченные изменения — поэтому первое правило при страшной операции: сначала закоммитить или спрятать в stash.
Типичный вопрос на собеседованииЧто такое ветка в Git?
Подвижный указатель на коммит — буквально файл с одним хешем. Создание ветки не копирует код, поэтому это мгновенная операция, а переключение меняет рабочий каталог на состояние из соответствующего снимка. Каждый коммит знает своего родителя, поэтому история — это граф, и ветка «содержит» все коммиты, достижимые от неё по родителям.

junior / рутина

Ежедневный цикл

База

Девяносто процентов работы — это шесть команд. Важна не их зубрёжка, а привычка смотреть на состояние перед каждым действием: git status отвечает почти на все вопросы и подсказывает следующую команду.

bashРабочий цикл от задачи до пуша
# 1. Начинаем от свежего состояния основной ветки
git switch main
git pull --ff-only              # безопасный вариант: не создаст неожиданный merge

# 2. Своя ветка под задачу
git switch -c feature/PROJ-142-order-discount

# 3. Смотрим, что изменилось, ПЕРЕД добавлением
git status
git diff                        # изменения, ещё не добавленные в индекс
git diff --staged               # то, что уже уйдёт в коммит

# 4. Добавляем осознанно, а не «всё подряд»
git add src/Pricing/Discount.php
git add -p src/Order/Cart.php   # по кускам: отличный способ не тащить лишнее

# 5. Коммит с внятным сообщением
git commit -m "feat(pricing): процентная скидка на корзину"

# 6. Публикация с привязкой ветки к удалённой
git push -u origin feature/PROJ-142-order-discount

# Дальше в цикле хватает трёх команд
git status && git add -p && git commit

Типичный вопрос на собеседованииЗачем нужен индекс (staging area)?
Чтобы отделить «что я изменил» от «что я хочу зафиксировать». Это позволяет собрать атомарный коммит из части правок — например, закоммитить исправление бага отдельно от случайно затронутого форматирования. Основной инструмент здесь git add -p: он предлагает добавлять изменения кусками и почти всегда улучшает качество истории.

junior / ветвление

Ветки и слияние

База

Ветка отделяет вашу работу от общей, чтобы незаконченное не мешало остальным. Слияние возвращает её обратно. Понимать нужно два случая: когда история линейна и когда она разошлась.

bashДва вида слияния и почему они разные
# Случай 1: fast-forward — main не двигался, пока вы работали.
# Git просто передвигает указатель вперёд, нового коммита не появляется.
#   main:    A---B
#   feature:      \---C---D
#   после:   A---B---C---D   (main указывает на D)
git switch main && git merge feature

# Случай 2: истории разошлись — создаётся merge-коммит с двумя родителями
#   main:    A---B---E
#   feature:      \---C---D
#   после:   A---B---E---M   (M имеет родителей E и D)
git merge feature

# Явно запретить fast-forward: слияние ветки всегда видно в истории
git merge --no-ff feature      # типовая настройка для веток задач

# Посмотреть граф глазами — привычка, экономящая массу непонимания
git log --oneline --graph --all --decorate -20

ВажноВетка задачи должна жить дни, а не недели. Чем дольше она существует, тем сильнее расходится с основной, тем больнее слияние и тем выше шанс, что кто-то параллельно переписал те же файлы. Практическое правило: если ветка живёт больше недели — либо задача слишком крупная и её надо резать, либо изменения стоит вливать за флагом функциональности по частям.
Типичный вопрос на собеседованииЧто такое fast-forward и когда его лучше запретить?
Это слияние без создания коммита: основная ветка не двигалась, поэтому её указатель просто передвигается вперёд, история остаётся линейной. Запрещают его (--no-ff) для веток задач, когда важно видеть в истории сам факт вливания ветки — тогда группа коммитов остаётся выделенной и её можно откатить одним revert merge-коммита.

junior / конфликты

Конфликты

База

Конфликт возникает, когда две стороны изменили одни и те же строки, и Git не может решить за вас, какой вариант верный. Это не ошибка и не поломка — это вопрос, на который нужно ответить.

bashРазрешение конфликта по шагам
# Git останавливается и говорит, какие файлы конфликтуют
git status                       # «both modified: src/Order/Cart.php»

# В файле появляются маркеры:
#   <<<<<<< HEAD            ← ваша текущая ветка
#   $total = $sum * 1.2;
#   =======
#   $total = $sum * $rate;   ← то, что вливается
#   >>>>>>> feature/rates

# Показать три версии сразу: базовую, свою и чужую — так понятнее, что произошло
git checkout --conflict=diff3 src/Order/Cart.php

# Взять целиком одну из сторон, если правка тривиальна
git checkout --ours   config/services.yaml    # свою
git checkout --theirs composer.lock           # чужую

# После правки: убрать маркеры, проверить, что код собирается, и пометить решённым
git add src/Order/Cart.php
git commit                        # для merge сообщение подставится автоматически

# Передумали — откат в исходное состояние
git merge --abort                 # или git rebase --abort

Правило: после разрешения обязательно перечитать получившийся фрагмент целиком и прогнать тесты, а в сомнительных случаях спросить автора второй стороны — это две минуты против дня расследования.
Типичный вопрос на собеседованииКак вы разрешаете конфликты слияния?
Сначала смотрю, что именно конфликтует, и по возможности показываю три версии — базовую, свою и чужую: часто становится понятно, что стороны решали разные задачи и нужно объединить, а не выбрать. Правлю, убираю маркеры, прогоняю тесты, только потом фиксирую. Для файлов вроде composer.lock ручная правка не годится — беру версию основной ветки и переустанавливаю зависимости.

Хорошие коммиты

База

История коммитов — это документация, которую читают в двух ситуациях: когда разбираются, почему код такой, и когда ищут причину поломки. В обеих ситуациях сообщение вида «фиксы» бесполезно.

Типичный вопрос на собеседованииКаким должен быть коммит?
Атомарным: одно логическое изменение, проект собирается и тесты проходят. Сообщение — заголовок в повелительном наклонении о смысле изменения и тело с причиной: почему сделано именно так и какие варианты отвергнуты. Форматирование и переименования выносятся отдельными коммитами, иначе дифф с содержательной правкой становится нечитаемым.

junior / удалённый

Удалённый репозиторий

База

Локальный и удалённый репозитории независимы. Git не синхронизирует их автоматически — вы явно забираете и явно отправляете. Понимание, что origin/main — это ваше локальное представление о состоянии сервера, снимает большинство недоумений.

bashСинхронизация: что происходит на самом деле
# fetch: скачивает изменения, НО не трогает ваши ветки.
# Обновляется только origin/main — «моё знание о том, что на сервере».
git fetch origin

# Теперь можно посмотреть, что прилетело, ДО того как это на вас повлияет
git log --oneline HEAD..origin/main     # что есть у них, но нет у меня
git log --oneline origin/main..HEAD     # что есть у меня, но нет у них
git diff HEAD origin/main -- src/

# pull = fetch + слияние. Опасен тем, что делает второй шаг неявно.
git pull --ff-only        # влить только если можно без merge-коммита; иначе — ошибка
git pull --rebase         # перенести свои коммиты поверх чужих (линейная история)

# Состояние веток относительно удалённых
git branch -vv
# feature/x  9f8e7d6 [origin/feature/x: ahead 2, behind 1] ...

# Уборка ссылок на удалённые ветки, которых уже нет на сервере
git fetch --prune

# Публикация новой ветки с привязкой
git push -u origin feature/PROJ-142
ВажноПравило про push --force: никогда в общие ветки (main, develop, релизные) — вы перепишете историю, на которую опираются другие, и их работа окажется в подвешенном состоянии. Типичный вопрос на собеседованииЧем fetch отличается от pull?
fetch скачивает изменения с сервера и обновляет только ссылки вида origin/main, ваши ветки и рабочий каталог не трогает — это безопасная операция, после которой можно посмотреть, что прилетело. pull — это fetch плюс слияние в текущую ветку, и именно второй шаг делает неожиданности: неявный merge-коммит или конфликт посреди работы.

middle / история

Rebase против merge

Ключевое

Обе команды решают одну задачу — соединить разошедшиеся ветки, — но принципиально по-разному. merge сохраняет историю как было и добавляет коммит слияния. rebase переписывает ваши коммиты так, будто вы начали работу от актуального состояния основной ветки.

textОдна и та же ситуация, два результата
Исходное состояние:

  main:     A---B---E---F
                 \
  feature:        C---D


После git merge main (находясь в feature):

  main:     A---B---E---F
                 \       \
  feature:        C---D---M      ← merge-коммит с двумя родителями


После git rebase main (находясь в feature):

  main:     A---B---E---F
                         \
  feature:                C'--D'  ← НОВЫЕ коммиты с новыми хешами

# C' и D' — это копии C и D с другим родителем. Исходные C и D остаются
# в репозитории (их видно в reflog), но ветка на них больше не указывает.

Золотое правило rebase: не переписывайте историю, которую уже видят другие. В своей ветке задачи — сколько угодно; в main или в ветке, над которой работает коллега, — никогда. Практичная схема для большинства команд: свою ветку актуализируем через rebase и чистим интерактивно, а вливаем в основную через merge --no-ff или squash — так история остаётся читаемой, а факт вливания фичи виден.

bashИнтерактивный rebase: уборка ветки перед ревью
# Привести в порядок последние 5 коммитов перед отправкой на ревью
git rebase -i HEAD~5

# В открывшемся списке напротив каждого коммита ставится действие:
#   pick   — оставить как есть
#   reword — изменить сообщение
#   squash — объединить с предыдущим, объединив сообщения
#   fixup  — объединить с предыдущим, отбросив сообщение
#   edit   — остановиться и дать поправить коммит
#   drop   — выбросить коммит
#   reorder — просто переставить строки местами

# Типовая уборка: «fix опечатка», «ещё fix», «правка после ревью» → в исходный коммит

# Ещё удобнее — помечать правки сразу, а потом схлопнуть автоматически:
git commit --fixup=9f8e7d6          # коммит-правка к конкретному коммиту
git rebase -i --autosquash HEAD~5   # сам расставит fixup в нужные места

# После rebase ветку нужно перезалить — только с проверкой чужих изменений
git push --force-with-lease

# Если во время rebase всё пошло не так
git rebase --abort
Важно--force-with-lease вместо --force — привычка, которая однажды спасёт чужой день. Обычный --force затирает удалённую ветку безусловно, включая коммиты, которые кто-то запушил туда, пока вы делали rebase. Вариант с lease проверяет, что удалённая ветка находится там, где вы её видели в последний раз, и отказывается работать, если это не так.
Типичный вопрос на собеседованииЧем rebase отличается от merge и что вы используете?
Merge соединяет ветки, сохраняя историю и добавляя коммит слияния; rebase переписывает коммиты поверх новой базы, делая историю линейной, но меняя хеши. Правило одно: rebase только для своей ещё не общей ветки. У себя я актуализирую ветку rebase-ом и чищу её интерактивно перед ревью, а в основную вливаю merge-ом без fast-forward — тогда фича видна одним блоком и откатывается одним revert.

Типичный вопрос на собеседованииЧем reset отличается от revert?
reset сдвигает указатель ветки назад — история переписывается, коммиты перестают быть достижимыми. revert создаёт новый коммит, отменяющий изменения, история сохраняется. Практическое правило: пока коммиты только у вас — можно reset; как только они опубликованы и их кто-то забрал — только revert, иначе у коллег ломается ветка. И почти всё, что «пропало» после reset, возвращается через reflog.

Стратегии ветвления

Ключевое

Стратегия ветвления — это не вкусовщина, а следствие того, как часто вы выкатываетесь и сколько версий поддерживаете. Команда, релизящаяся десять раз в день, и команда с квартальными релизами коробочного продукта не могут работать одинаково.

Практический выбор. Для типичного веб-проекта с одной боевой версией правильный ответ почти всегда — GitHub flow: main всегда готова к выкатке, ветки задач живут пару дней, вливание через pull request с зелёным CI. Git flow с двумя долгоживущими ветками добавляет постоянную работу по синхронизации develop и main и оправдан, только если вы реально поддерживаете несколько версий одновременно. Trunk-based — следующий шаг для зрелой команды, но он требует хорошего покрытия тестами и работающих feature flags, иначе превращается в «выкатываем недоделанное».

АнтипаттернДолгоживущая ветка refactoring или new-version, которая существует месяцами параллельно с активной разработкой. Она гарантированно превращается в ад слияния: конфликты накапливаются экспоненциально, а ценность работы падает, потому что основная ветка ушла вперёд. Крупные изменения делаются в основной ветке маленькими совместимыми шагами — за флагом или по схеме «расширить, перенести, удалить».
Типичный вопрос на собеседованииКакую стратегию ветвления вы используете и почему?
Для веб-проекта с одной боевой версией — короткие ветки задач от main, вливание через pull request с зелёным CI, релиз из main. Git flow беру только когда нужно поддерживать несколько версий одновременно: две долгоживущие ветки стоят постоянной синхронизации. Ключевой критерий не название схемы, а время жизни ветки: если ветки живут неделями, любая схема превратится в проблему слияний.

middle / релизы

Релизы, теги, версии

Ключевое

Тег — неподвижная метка на коммите: он отвечает на вопрос «какой именно код сейчас в проде». Без тегов ответ приходится восстанавливать по датам деплоя, а во время инцидента это лишние минуты.

bashТеги и семантическое версионирование
# Аннотированный тег (с автором, датой и сообщением) — для релизов только такой
git tag -a v2.4.0 -m "Скидки на корзину, ускорение выгрузки"
git push origin v2.4.0

# Семантическое версионирование: MAJOR.MINOR.PATCH
#   MAJOR — несовместимые изменения (сломается у потребителей)
#   MINOR — новая функциональность, совместимая назад
#   PATCH — исправления без изменения поведения

# Что сейчас в проде и насколько мы ушли вперёд
git describe --tags                     # v2.4.0-17-g9f8e7d6: 17 коммитов после тега
git log --oneline v2.3.0..v2.4.0        # что вошло в релиз
git log --oneline v2.4.0..HEAD          # что накопилось после релиза

# Changelog по conventional commits собирается автоматически
git log v2.3.0..v2.4.0 --pretty=format:'%s' | grep -E '^(feat|fix)' | sort

# Найти, в какой релиз попал коммит (частый вопрос от поддержки)
git tag --contains 9f8e7d6
git describe --contains 9f8e7d6
bashСрочное исправление в проде, пока main ушла вперёд
# Ситуация: в проде тег v2.4.0, а в main уже 30 коммитов недорелизной работы.
# Выкатывать main нельзя — там незаконченное. Нужен точечный фикс.

# 1. Ветка от тега, который сейчас в проде, — а не от main
git switch -c hotfix/v2.4.1 v2.4.0

# 2. Минимальное исправление и тест на него
git commit -am "fix(orders): не терять валюту при частичном возврате"

# 3. Тег и выкатка
git tag -a v2.4.1 -m "Hotfix: валюта при частичном возврате"
git push origin hotfix/v2.4.1 v2.4.1

# 4. ОБЯЗАТЕЛЬНО: вернуть исправление в основную ветку, иначе следующий релиз
#    вернёт баг обратно. Это самая частая ошибка при hotfix.
git switch main
git cherry-pick <hash-фикса>      # или merge ветки hotfix
ВажноРегрессия «баг починили в hotfix, а через неделю он вернулся» — классика, и причина всегда одна: исправление не попало в основную ветку. Защита процессная: ветка hotfix закрывается только после того, как фикс влит и в релиз, и в main; в шаблоне pull request для hotfix стоит галочка «портирование в main выполнено».
Типичный вопрос на собеседованииКак выкатить срочное исправление, если в основной ветке незаконченная работа?
Ветка от тега, который сейчас в проде, минимальное исправление, новый patch-тег, выкатка. Затем обязательный перенос фикса в основную ветку через cherry-pick или merge — без этого следующий релиз вернёт баг. Отдельно проверяю, что на исправление есть тест: hotfix без теста имеет свойство повторяться.

Сначала читаю описание и понимаю задачу, потом смотрю на архитектурный уровень: решает ли код проблему, нет ли пропущенных случаев, что с правами и данными. Стиль не комментирую — это работа линтера. Замечания делю на обязательные и необязательные, спорные формулирую вопросом. Если PR больше пятисот строк, прошу разбить: честно прочитать такой объём невозможно, а «LGTM» на нём — это отсутствие ревью.

middle / автоматизация

Хуки и защита веток

Ключевое

Всё, что можно проверить автоматически, не должно проверять человек. Задача ревьюера — думать о логике, а не считать пробелы; задача правил репозитория — сделать невозможными опасные действия.

senior / расследование

История как инструмент

Архитектура

История коммитов — это база данных о том, как система пришла в текущее состояние. Умение задавать ей вопросы превращает расследования из «читаем весь код и гадаем» в направленный поиск за минуты.

# Ситуация: «месяц назад работало, сейчас нет». Между релизами 400 коммитов.

# Что происходило в конкретный период и кем
git log --since='2026-01-01' --until='2026-02-01' --author='Ivan' --oneline

Культура ревью

Архитектура

Ревью — самый дорогой процесс в команде по человеко-часам и самый недооценённый по влиянию. Оно одновременно ловит ошибки, распространяет знания о коде и формирует стандарты. Оно же способно испортить отношения в команде за месяц.

Кто обязан ревьюить: один человек, двое, владелец модуля. Что блокирует вливание, а что остаётся пожеланием — это самый ценный пункт: без него любой комментарий воспринимается как блокирующий. И правило разрешения споров, чтобы обсуждение не зацикливалось.

ВажноРевью не заменяет обсуждение подхода. Если человек два дня писал код по решению, которое ревьюер считает неверным, любой исход плох: переделывать дорого, соглашаться — накапливать долг. Дешёвое решение — короткое согласование подхода до реализации: пять минут разговора или три строки в задаче. Правило простое: чем крупнее изменение, тем раньше нужно обсуждение.
Типичный вопрос на собеседованииЧто делать, если ревьюер требует переделать то, с чем вы не согласны?
Сначала понять аргумент — часто за замечанием стоит контекст, которого я не знал. Если после этого не согласен, отвечаю по существу: чем обосновано моё решение, какие есть компромиссы. Если расхождение остаётся, не спорю в комментариях по кругу: перевожу в разговор голосом на пять минут или зову третьего человека. И отдельно фиксирую итог в описании PR или в решении — чтобы через полгода не проходить это заново.

Если вернуться нельзя из-за миграции, чиню вперёд hotfix-ом от тега прода. Когда виновата вся влитая ветка, делаю revert -m 1 merge-коммита, помня, что повторное вливание потребует отмены этого revert. И обязательно фиксирую хронологию по ходу: потом её не восстановить.

# 7. Публикация событий через outbox

Статус: принято · Дата: 2026-02-11 · Заменяет: —

## Контекст
Заказы отправляют события в брокер. Иногда транзакция коммитится,
а событие теряется: склад не узнаёт об оплате. За квартал 4 инцидента.

## Решение
Событие пишется в таблицу outbox в той же транзакции, отдельный
процесс переносит его в брокер.

## Последствия
+ Событие не теряется при падении между коммитом и отправкой.
− Доставка «хотя бы один раз»: потребители обязаны дедуплицировать.
− Появляется процесс-релей, за которым нужно следить (метрика возраста).

## Отвергнутые варианты
- Отправка после коммита: не решает проблему, она ровно про этот промежуток.
- Двухфазный коммит: доступность становится произведением доступностей.

Ответы короткие — это каркас. Вопросы про Git на собеседовании почти всегда проверяют не знание флагов, а понимание модели и умение работать в команде: что вы делаете, когда что-то пошло не так, и как договариваетесь с людьми.

Junior
  1. Что такое коммит?Снимок всего дерева файлов плюс ссылка на родителя, автора и сообщение. Git хранит именно снимки, а различия вычисляет при показе. Коммит неизменяем: любая «правка» коммита создаёт новый объект с новым хешем.
  2. Что такое ветка?Подвижный указатель на коммит — буквально файл с одним хешем. Поэтому создание и переключение веток почти бесплатны: копирования кода не происходит. Ветка «содержит» все коммиты, достижимые от неё по цепочке родителей.
  3. Что такое HEAD?Указатель на текущее положение: обычно на ветку, в которой вы работаете. Если переключиться прямо на коммит, HEAD оказывается «отсоединённым» — коммиты в этом состоянии не принадлежат ни одной ветке и легко теряются из виду, хотя и находятся через reflog.
  4. Зачем нужен индекс?Чтобы отделить «что изменено» от «что попадёт в коммит». Это позволяет собрать атомарный коммит из части правок — например, отделить исправление бага от случайно затронутого форматирования. Основной инструмент — git add -p.
  5. Какие три состояния бывают у файла?Изменён (правки в рабочем каталоге), подготовлен (добавлен в индекс), зафиксирован (в репозитории). Отдельно стоит неотслеживаемый файл — Git о нём ничего не знает, и git clean удалит его безвозвратно.
  6. Как отменить правки в файле до коммита?git restore <file> — вернёт содержимое из индекса или последнего коммита, правки пропадут безвозвратно. Если файл уже добавлен в индекс, сначала git restore --staged <file>. Это одна из немногих действительно необратимых операций, поэтому в сомнительных случаях лучше stash.
  7. Зачем нужен .gitignore и почему он иногда не работает?Он исключает файлы из отслеживания: зависимости, кэш, локальные настройки, секреты. Не работает он в одном случае — если файл уже отслеживается: правила касаются только новых файлов. Нужно убрать файл из индекса командой git rm --cached, и помнить, что из истории он при этом не исчезает.
  8. Что такое fast-forward?Слияние без создания коммита: основная ветка не двигалась, пока вы работали, поэтому её указатель просто передвигается вперёд и история остаётся линейной. Для веток задач часто запрещают его флагом --no-ff, чтобы факт вливания ветки был виден в истории.
  9. Почему возникает конфликт слияния?Потому что обе стороны изменили одни и те же строки, и Git не может решить, какой вариант верный. Это не поломка, а вопрос к человеку. Важно после разрешения не просто убрать маркеры, а перечитать фрагмент целиком и прогнать тесты: механическое «оставлю своё» молча удаляет чужую работу.
  10. Как отменить начатое слияние?git merge --abort — возвращает репозиторий в состояние до начала слияния. Аналогично работает git rebase --abort. Знание этих двух команд убирает страх начинать слияние: любой эксперимент обратим.
  11. Каким должно быть сообщение коммита?Заголовок в повелительном наклонении о смысле изменения, до примерно 72 символов, и тело с причиной: почему сделано так и какие варианты отвергнуты. Пересказывать дифф не нужно — он и так виден. Тест качества: поймёт ли человек через год по git blame, почему строка такая.
  12. Что такое conventional commits?Соглашение о формате заголовка: тип, область и описание — feat(pricing): ..., fix(orders): .... Смысл не в красоте: по типам автоматически собирается changelog и определяется следующая версия по семантическому версионированию, а пометка о несовместимом изменении становится машиночитаемой.
  13. Что значит «атомарный коммит»?Одно логическое изменение, после которого проект собирается и тесты проходят. Это не про размер: правка в одну строку и рефакторинг на двести могут быть одинаково атомарными. Практическая ценность в расследованиях: по атомарной истории работает bisect и читается blame.
  14. Чем fetch отличается от pull?fetch скачивает изменения и обновляет только ссылки вида origin/main — ваши ветки не трогаются, это безопасно. pull дополнительно сливает изменения в текущую ветку, и именно второй шаг приносит неожиданности: неявный merge-коммит или конфликт посреди работы.
  15. Что такое origin?Имя удалённого репозитория по умолчанию — просто псевдоним для адреса. Их может быть несколько: например, origin для своего форка и upstream для исходного проекта. origin/main — это ваше локальное представление о состоянии ветки на сервере, обновляемое при fetch.
  16. Почему нельзя делать push --force в общую ветку?Потому что вы перепишете историю, которую другие уже забрали: их локальные ветки разойдутся с сервером, а чужие коммиты могут быть просто затёрты. В своей ветке задачи после rebase force-push нормален, но и там стоит использовать --force-with-lease, который откажется работать, если кто-то успел запушить туда изменения.
  17. Как временно отложить незаконченную работу?git stash push -u -m "описание" — прячет правки, включая неотслеживаемые файлы, и очищает рабочий каталог. Вернуть — git stash pop. Полезно при срочном переключении, но не стоит копить: stash легко забыть, и он не виден в обычной истории. Для долгого хранения лучше сделать коммит в отдельной ветке.
  18. Как посмотреть, что изменилось в ветке относительно основной?git diff main...HEAD с тремя точками — покажет только ваши изменения, не примешивая то, что появилось в main после ответвления. С двумя точками сравниваются текущие состояния веток, и это почти всегда не то, что нужно при подготовке к ревью.
  19. Что делать, если случайно закоммитили не в ту ветку?Если не запушено: создать правильную ветку из текущего состояния — коммиты «уедут» с вами, — затем вернуть исходную ветку назад через reset --hard к состоянию сервера. Если уже запушено, переносить через cherry-pick и отменять в неправильной ветке через revert.
  20. Правда ли, что в Git можно потерять работу?Закоммиченную — почти нет: даже «пропавшие» коммиты остаются в репозитории и находятся через git reflog в течение месяцев. По-настоящему теряются только незакоммиченные изменения — от reset --hard, restore и clean. Отсюда практическое правило: перед страшной операцией сделать коммит или stash.

Middle · 20 вопросов

Middle
  1. Чем rebase отличается от merge?Merge соединяет ветки, сохраняя историю и добавляя коммит слияния с двумя родителями. Rebase переносит ваши коммиты поверх новой базы, создавая их копии с новыми хешами, — история становится линейной. Отсюда и разница в применении: merge безопасен всегда, rebase — только для ещё не общей ветки.
  2. В чём золотое правило rebase?Не переписывать историю, которую уже видят другие. Как только ветку кто-то забрал, rebase в ней ломает чужие репозитории. Внутри своей ветки задачи rebase и интерактивная уборка — нормальная практика вплоть до момента, когда её начали ревьюить и на неё ссылаться.
  3. Зачем нужен интерактивный rebase?Чтобы привести ветку в порядок перед ревью: объединить коммиты-правки с исходными, переписать сообщения, поменять порядок, выбросить лишнее. Удобный приём — помечать правки через commit --fixup и затем схлопывать автоматически с --autosquash: ревьюер видит чистую последовательность логических изменений.
  4. Чем reset отличается от revert?reset сдвигает указатель ветки назад, переписывая историю; revert создаёт новый коммит, отменяющий изменения, история сохраняется. Пока коммиты только у вас — можно reset; как только опубликованы — только revert, иначе у коллег ломается ветка.
  5. Чем отличаются reset --soft, --mixed и --hard?--soft убирает коммит, оставляя изменения в индексе — удобно пересобрать коммит заново. --mixed (по умолчанию) оставляет изменения в рабочем каталоге, но убирает из индекса. --hard выбрасывает изменения совсем — единственный по-настоящему опасный вариант, потому что незакоммиченное не восстановить.
  6. Что такое reflog и когда он спасает?Локальный журнал перемещений HEAD и веток за последние примерно 90 дней. Он спасает после неудачного reset --hard, потерянной ветки, испорченного rebase: находите нужный хеш и создаёте от него ветку. Не спасает от потери незакоммиченных изменений — их в журнале никогда не было.
  7. Как отменить уже влитую ветку?git revert -m 1 <merge-commit>, где единица означает «считать основным первого родителя», то есть ветку, в которую вливали. Важный нюанс: чтобы влить эту ветку заново после исправления, придётся сначала отменить сам revert, иначе Git будет считать изменения уже применёнными.
  8. Что такое cherry-pick и когда он уместен?Перенос отдельного коммита в другую ветку — создаётся копия с новым хешем. Уместен для точечных случаев: перенести hotfix в релизную ветку или в main. Систематическое использование вместо слияний плодит дубликаты изменений в истории и усложняет понимание того, что где применено.
  9. Какие бывают стратегии ветвления и как выбрать?Trunk-based — только основная ветка, всё за флагами, требует сильных тестов. GitHub flow — короткие ветки задач от main, подходит большинству веб-проектов. Git flow — несколько долгоживущих веток, оправдан при поддержке нескольких версий. Выбор определяется частотой релизов и числом поддерживаемых версий, а не модой.
  10. Чем плохи долгоживущие ветки?Расхождение с основной растёт нелинейно: чем дольше ветка живёт, тем больше конфликтов и тем выше шанс, что кто-то параллельно переписал те же места. Плюс работа месяцами не проверяется в интеграции. Крупные изменения лучше делать в основной ветке маленькими совместимыми шагами за флагом.
  11. Зачем нужны теги и какими они бывают?Тег — неподвижная метка на коммите, отвечающая на вопрос «какой код сейчас в проде». Лёгкий тег — просто ссылка; аннотированный содержит автора, дату и сообщение и является полноценным объектом — для релизов используют его. По тегам собирается changelog и определяется, в какую версию попал фикс.
  12. Как выкатить hotfix, если в main незаконченная работа?Создать ветку от тега, который сейчас в проде, внести минимальное исправление с тестом, поставить новый patch-тег и выкатить. Затем обязательно перенести фикс в основную ветку через cherry-pick или merge — без этого следующий релиз вернёт баг. Это самая частая ошибка в работе с hotfix.
  13. Каким должен быть размер pull request?До 200–400 строк изменений. Дальше внимание ревьюера падает, а после тысячи строк честно прочитать код невозможно — появляется «LGTM», то есть отсутствие ревью при формальном его наличии. Если задача крупная, её режут по смыслу: отдельно рефакторинг, отдельно новая логика, отдельно миграции.
  14. Что должно быть в описании pull request?Что и зачем сделано, как проверить, какие приняты решения и что отвергнуто, какие есть риски. Это экономит время ревьюеру сейчас и человеку, который через год будет разбираться, почему код такой. Описание из одной строки «PROJ-142» перекладывает всю работу на читателя.
  15. На что вы смотрите при код-ревью?Сначала на правильность и полноту: решает ли код задачу, какие случаи пропущены. Затем безопасность (права на объект, экранирование), работа с данными (совместимость миграции, N+1, поведение при повторе), качество тестов и читаемость. Стиль не комментирую — это работа линтера, а не человека.
  16. Как формулировать замечания на ревью?О коде, а не об авторе. Явно разделять обязательное и желательное — иначе любое замечание читается как блокирующее. Там, где не уверен, задавать вопрос, а не утверждать. И отмечать удачные решения: это ничего не стоит и заметно меняет отношение к ревью в команде.
  17. Что автоматизировать хуками, а что в CI?В хуках — быстрое: синтаксис, форматирование с автоисправлением, проверка формата сообщения коммита, поиск отладочного вывода. В CI — долгое: статический анализ, тесты, аудит зависимостей, сканер секретов. Хук должен занимать секунды, иначе его начнут обходить ключом --no-verify.
  18. Почему хуков недостаточно и нужна защита веток?Потому что любой локальный хук отключается одним ключом, а хуки к тому же не копируются при клонировании. Гарантии дают только настройки репозитория: запрет прямого пуша в основную ветку, обязательный зелёный пайплайн, минимум одно одобрение, запрет force-push и удаления ветки.
  19. Что делать с конфликтом в composer.lock?Не править вручную: файл машинный и его ручное слияние приводит к несогласованному состоянию зависимостей. Взять версию основной ветки, затем заново применить своё изменение состава зависимостей и пересобрать lock. Аналогично с любыми сгенерированными файлами.
  20. Как вы поддерживаете чистую историю?Атомарные коммиты с осмысленными сообщениями, отдельные коммиты на форматирование и переименования, уборка ветки интерактивным rebase перед ревью, запрет неожиданных merge-коммитов от pull через pull.ff only. Цель не эстетика: по чистой истории работают bisect и blame, то есть расследование инцидентов.

Senior · 20 вопросов

Senior
  1. Баг появился где-то за последние 400 коммитов. Как найдёте?Свожу воспроизведение к скрипту или тесту, возвращающему код возврата, и запускаю git bisect run между заведомо рабочим тегом и текущим состоянием — это примерно девять проверок вместо четырёхсот. Найденный коммит смотрю целиком: дифф, сообщение, связанную задачу. Дальше при необходимости blame и log -S для контекста.
  2. От чего зависит эффективность bisect?От качества истории. Если коммиты неатомарны, половина не собирается, а в одном коммите смешаны фича и рефакторинг, двоичный поиск буксует и приводит к «виноват коммит на 2000 строк». Это главный практический аргумент за атомарные коммиты — не эстетика, а скорость расследования.
  3. Как найти, когда в коде появилась конкретная строка или вызов?git log -S '<строка>' ищет коммиты, где число вхождений изменилось, -G — то же по регулярному выражению. С флагом -p сразу видно контекст изменения. Это гораздо точнее, чем blame, когда строку несколько раз перемещали или переформатировали.
  4. Как найти проблемные места в проекте по истории?Посчитать частоту изменений файлов за период: файлы из верха списка — кандидаты в горячие точки. Пересечение высокой частоты изменений и высокой сложности почти всегда даёт места, где рождается большинство багов. Это хороший объективный аргумент при планировании рефакторинга.
  5. Как выбрать процесс работы с репозиторием для команды?От условий: частота релизов, число поддерживаемых версий, размер команды, зрелость тестов, наличие feature flags, требования к прослеживаемости. Для типичного веб-продукта — короткие ветки от main, PR с зелёным CI и одобрением, защита основной ветки, релиз по тегу. Дальше смотрю на метрики процесса, а не на соответствие схеме из статьи.
  6. Какие метрики процесса разработки вы бы отслеживали?Время жизни ветки, время от открытия PR до вливания, размер PR, частоту релизов, долю релизов с откатом и время восстановления. Они показывают, где именно затык: крупные задачи, медленное ревью или хрупкий релиз. Метрики про людей (число коммитов, строк) вредны — они поощряют имитацию.
  7. Монорепозиторий или отдельные репозитории?Монорепо выигрывает, когда изменения часто затрагивают несколько компонентов сразу: одно атомарное изменение вместо согласования нескольких PR и порядка выкатки. Платите размером клона, необходимостью собирать только изменённое и более сложным разграничением доступа. Отдельные репозитории естественны для продуктов с независимым жизненным циклом и разными командами.
  8. Как ускорить ревью в команде?Тремя вещами: уменьшить PR (это главное — режем задачи), договориться о сроке ответа и сделать ревью приоритетнее своей задачи, автоматизировать всё, что проверяет линтер. Плюс явно разделять блокирующие замечания и пожелания, иначе каждый комментарий останавливает вливание.
  9. Что делать, если ревью превращается в конфликт?Переводить из письменного в устный формат: пять минут разговора обычно закрывают то, что в комментариях идёт третий круг. Договориться заранее о тоне и о том, кто принимает решение при расхождении — владелец модуля или обсуждение с третьим человеком. И отделять вопросы вкуса от вопросов последствий: первые не стоят конфликта.
  10. Что делать, если PR слишком большой?Просить разделить и помогать это сделать: отдельно рефакторинг, отдельно новая логика, отдельно миграции и переименования. Если разделить действительно нельзя, менять формат: разбор голосом с автором вместо комментариев по диффу. Читать тысячу строк по диагонали и ставить одобрение — худший вариант из всех.
  11. Как выглядит порядок действий при откате релиза?Сначала восстановление: выкатка предыдущего тега образа или выключение функции флагом — это быстрее любой Git-операции. Если вернуться нельзя из-за применённой миграции, чиню вперёд hotfix-ом от тега прода. Когда виновата вся ветка — revert -m 1 merge-коммита. Хронология фиксируется по ходу, разбор — после восстановления.
  12. Почему совместимые миграции важны для отката?Потому что откат кода не откатывает схему. Если миграция удалила колонку, предыдущая версия приложения на новой схеме не запустится, и быстрый откат становится невозможен — придётся чинить вперёд под давлением. Совместимые изменения схемы превращают откат из спецоперации в одну команду.
  13. Кто-то сделал force push и затёр коммиты. Что делать?Найти потерянные коммиты в reflog у того, кто забирал ветку до этого, или через поиск недостижимых объектов на сервере, и восстановить ветку по хешу. Затем закрыть возможность повторения: запрет force-push на защищённых ветках. Быстрая реакция важна — недостижимые объекты со временем удаляются сборкой мусора.
  14. Как обеспечить прослеживаемость «задача → коммит → релиз»?Идентификатор задачи в названии ветки и в сообщениях коммитов, аннотированные теги на релизы, changelog по conventional commits. Тогда на вопрос «в какой версии этот фикс» отвечает одна команда, а на вопрос «что вошло в релиз» — сравнение тегов. Для аудита этого обычно достаточно, а для поддержки — критично.
  15. Как заходить в проект, где история — сплошные «фиксы»?Не переписывать прошлое — это бессмысленно и опасно. Договориться о правилах с текущего момента: формат сообщений, атомарность, отдельные коммиты на форматирование. Подкрепить автоматикой: проверка формата сообщения хуком, шаблон описания PR. История выправляется за пару месяцев, а старая часть остаётся как есть.
  16. Как фиксируются знания о принятых решениях?Короткими записями решений в репозитории рядом с кодом: контекст, решение, последствия и отвергнутые варианты с причинами. Они ревьюются вместе с кодом и потому не устаревают отдельно. Плюс сообщения коммитов с причиной и комментарии со ссылкой на решение в неочевидных местах — они спасают от «оптимизаций», ломающих систему.
  17. Как вы оцениваете качество онбординга?По времени до первого осмысленного pull request. Если это первый день — проект поднимается по инструкции, правила описаны, задачи нарезаны понятно. Если неделя, проблема не в человеке: часть знаний живёт только в головах. Полезно, чтобы новичок правил документацию по ходу — он единственный видит пробелы свежим взглядом.
  18. Что делать с веткой, которая живёт три месяца?Признать, что дальше будет только хуже, и разбирать: выделить из неё части, совместимые с основной веткой, и вливать по одной, при необходимости за флагом функциональности. Регулярно подтягивать основную ветку в неё, чтобы конфликты решались порциями. И параллельно разбираться с причиной — обычно это слишком крупно нарезанная задача.
  19. Нужны ли правила именования веток?Минимальные и работающие на автоматику: тип и идентификатор задачи — feature/PROJ-142-краткое-описание. Это даёт связь с задачей, читаемый список веток и возможность автоматизировать привязку к тикету. Развёрнутые регламенты именования обычно не окупаются: их всё равно нарушают, а пользы сверх этого нет.
  20. Как понять, что процесс работы с репозиторием не подходит команде?По тому, что его регулярно обходят: прямые пуши «в порядке исключения», одобрения без чтения, ветки, висящие месяцами. Правильная реакция — не усиливать контроль, а выяснить причину: обычно это слишком крупные задачи, медленный CI или отсутствие договорённости о сроке ревью. Неудобный процесс всегда проигрывает срокам.

Git осваивается только руками, и лучше всего — на учебном репозитории, который не жалко сломать. Половина заданий выполняется именно там, вторая половина — на рабочем проекте.

Junior

1. Учебный репозиторий и пять поломок

Создайте репозиторий с несколькими коммитами и намеренно сломайте его пятью способами: reset --hard с потерей коммитов, удаление ветки, испорченный rebase, коммит не в ту ветку, затёртый файл. Каждый раз восстанавливайтесь.

РезультатИсчезновение страха: вы знаете, что почти всё восстанавливается, и знаете как.

2. Атомарные коммиты через add -p

Сделайте в файле три несвязанных изменения и разложите их на три коммита, не откатывая ничего. Затем напишите каждому сообщение с причиной, а не пересказом диффа.

РезультатНавык, который сразу улучшает историю и делает ревью в разы проще.

3. Конфликт от начала до конца

Смоделируйте конфликт: две ветки правят одни строки. Разрешите его, включив показ базовой версии, затем повторите с merge --abort и снова разрешите иначе.

Как отвечать на вопросы про Git и командную работу

Бонус
  • Отвечайте моделью, а не командой. «Rebase — это git rebase» ничего не показывает. «Rebase создаёт копии коммитов с новыми хешами поверх новой базы, поэтому в общей ветке он ломает чужие репозитории» — показывает понимание.
  • Про Git спрашивают, чтобы проверить командную работу. Вопрос «что вы делаете при конфликте» — на самом деле про то, разберётесь ли вы сами и пойдёте ли уточнять у автора второй стороны. Отвечайте и про технику, и про взаимодействие.
  • Называйте числа процесса. Сколько живут ветки, какого размера PR, за сколько отвечают на ревью, как часто релизите, сколько занимает откат. Это самый быстрый способ показать, что вы работали в живом процессе.
  • Не защищайте догмы. «Только rebase» или «только merge» — слабые позиции. Сильная: «внутри своей ветки rebase, вливание merge без fast-forward, потому что так фича видна одним блоком и откатывается одним revert».
  • Держите наготове историю спасения. Как восстановили потерянную работу, как откатывали релиз, как нашли причину через bisect. Такие истории отвечают сразу на несколько вопросов и запоминаются.
  • Говорите о ревью как о процессе, а не о вкусах. Размер PR, срок ответа, разделение блокирующего и желательного, что автоматизировано. Это признак человека, который отвечал за скорость команды, а не только за свой код.
  • Признавайте несовершенство процесса честно. «У нас ветки жили по две недели, я начал с разбиения задач и договорённости о сроке ревью, стало три дня» — гораздо сильнее, чем описание идеального процесса, которого не было.
