Финтех и платёжные системы

Финтех отличается от остальной разработки одним свойством: здесь у ошибки есть сумма. Потерянный запрос в интернет-магазине — это не показанная карточка товара; потерянный запрос в платёжном сервисе — это списанные и не зачисленные деньги, о которых узнают не из мониторинга, а из обращения клиента. Поэтому в предметной области почти всё устроено вокруг одного вопроса: что произойдёт, если операция прервалась в середине и мы не знаем её результата.

Из этого вопроса вырастает весь набор практик темы. Сумма хранится в целых минимальных единицах, потому что дробная арифметика не сходится при сверке. Платёжный запрос идемпотентен, потому что его придётся повторить. Состояние платежа меняется по явной статусной машине, потому что «обновить статус» из двух мест приводит к двойному зачислению. Движение денег пишется двойной записью, потому что баланс должен выводиться из проводок, а не храниться отдельным числом, которое кто-то однажды поправит руками. Каждое из этих правил — не догма, а следствие конкретной аварии, которая случается без него.

Конспект идёт от денег к контуру: представление сумм, участники платежа, жизненный цикл, идемпотентность, вебхуки → двойная запись, гонки и блокировки, статусная машина, сверка, возвраты и споры, рекуррентные платежи, интеграция с провайдером → архитектура платёжного контура, антифрод, KYC и AML, PCI DSS, аудит и отчётность, эксплуатация денег. Смежные темы: HTTP и дизайн API (идемпотентность, вебхуки, коды ответов), брокеры сообщений (outbox, DLQ, семантика доставки), базы данных (транзакции, уровни изоляции, блокировки), безопасность, system design, наблюдаемость.

Уровень 01 · деньги и платёжный поток

Junior: как устроены деньги и как проходит платёж

Первый уровень закрывает то, на чём спотыкаются почти все, кто пришёл в финтех из обычного веба: представление суммы в коде, кто на самом деле переводит деньги при оплате картой, из каких стадий состоит платёж и почему любой платёжный запрос обязан переживать повтор.

junior / деньги

Деньги в коде

Обязательно

Деньги — не число. Это пара «сумма и валюта» с фиксированной точностью, набором правил округления и запретом на молчаливое смешивание валют. Первая же попытка положить сумму в float заканчивается тем, что 0.1 + 0.2 даёт 0.30000000000000004, а сверка с банком расходится на копейки, которые невозможно объяснить.

Минимальная единица — копейка, цент, филс. Сумма 199,90 ₽ хранится как целое 19990. Масштаб зависит от валюты: у рубля и доллара две цифры после запятой, у японской иены — ноль, у динара Кувейта — три. Поэтому «умножить на 100» не универсальное правило, а частный случай; масштаб берут из справочника валют ISO 4217.

PHPОбъект-значение Money: точность, валюта, распределение остатка
final class Money
{
    // amount — всегда целое в минимальных единицах валюты
    private function __construct(
        public readonly int $amount,
        public readonly Currency $currency,
    ) {}

    public static function of(int $minorUnits, Currency $currency): self
    {
        return new self($minorUnits, $currency);
    }

    // Единственная точка входа для «человеческих» строк вида 199.90
    public static function fromDecimalString(string $value, Currency $currency): self
    {
        $scale  = $currency->exponent();          // RUB и USD — 2, JPY — 0, KWD — 3
        $scaled = bcmul($value, bcpow("10", (string) $scale), 0);

        return new self((int) $scaled, $currency);
    }

    public function add(self $other): self
    {
        $this->assertSameCurrency($other);

        return new self($this->amount + $other->amount, $this->currency);
    }

    // Деление денег без потери копеек: остаток раздаётся по одной единице
    // Money::of(10000, RUB)->allocate([1, 1, 1]) => 33.34 + 33.33 + 33.33
    public function allocate(array $ratios): array
    {
        $total       = array_sum($ratios);
        $shares      = [];
        $distributed = 0;

        foreach ($ratios as $ratio) {
            $share = intdiv($this->amount * $ratio, $total);  // всегда вниз
            $shares[]   = $share;
            $distributed += $share;
        }

        // Остаток от округления вниз раздаём по копейке, начиная с первой доли
        for ($i = 0; $i < $this->amount - $distributed; $i++) {
            $shares[$i % count($shares)]++;
        }

        return array_map(fn(int $a) => new self($a, $this->currency), $shares);
    }

    private function assertSameCurrency(self $other): void
    {
        if ($this->currency !== $other->currency) {
            throw new CurrencyMismatch($this->currency, $other->currency);
        }
    }
}

Распределение остатка — отдельная задача, всплывающая при делении суммы на части: комиссия маркетплейса, разбиение платежа между продавцами, рассрочка на три месяца. Сумма частей обязана точно равняться исходной сумме, поэтому округлять каждую часть отдельно нельзя: 100,00 ₽ на троих дадут 33,33 × 3 = 99,99 и потерянную копейку, которая через месяц станет расхождением в отчёте.

ВажноВалюта — часть типа, а не подпись рядом. Если сложение Money в рублях и Money в долларах не выбрасывает исключение, однажды оно даст «сумму» из 500 рублей и 20 долларов, равную 520 чего-то. Конвертация — всегда явная операция с указанием курса и его источника, и её результат сохраняется вместе с курсом и меткой времени: через полгода придётся объяснить, откуда взялась именно эта сумма.
Типичный вопрос на собеседованииПочему деньги нельзя хранить во float?
Потому что двоичная плавающая точка не представляет большинство десятичных дробей точно: 0,1 и 0,2 хранятся приближённо, и их сумма не равна 0,3. На одной операции ошибка невидима, на миллионе — это расхождение с банковской выпиской, которое нельзя ни объяснить, ни списать. Стандартное решение — целое число минимальных единиц валюты, обёрнутое в объект Money, который знает свою валюту и не даёт смешивать разные.

Карта рынка

«Оплата картой» выглядит как один HTTP-запрос, а на деле это цепочка из пяти-шести организаций, у каждой из которых свои сроки, комиссии и правила отказа. Понимание этой цепочки объясняет вещи, которые иначе выглядят абсурдом: почему деньги списались, а магазин их ещё не получил, почему возврат идёт пять дней и почему отказ по операции приходит без внятной причины.

Отдельно стоят небанковские способы оплаты: платёжные ссылки и QR по системе быстрых платежей, электронные кошельки, оплата по счёту для юридических лиц, рассрочка от партнёра. У каждого своя механика подтверждения и свои сроки: у карточного платежа результат известен за секунды, у счёта для юрлица — на следующий рабочий день, а у части кошельков подтверждение приходит только вебхуком и никак иначе.

ВажноОтказ эмитента почти никогда не содержит настоящей причины: коды вида «отказ без объяснения» покрывают и недостаток средств, и срабатывание антифрода, и блокировку карты. Показывать пользователю технический код бессмысленно, а строить на нём логику повторов опасно. Работать нужно с крупными категориями: «недостаточно средств» — предложить другую карту, «отказ эмитента» — предложить связаться с банком, «техническая ошибка» — повторить.
Типичный вопрос на собеседованииЧем эквайер отличается от PSP?
Эквайер — банк, который заключил договор с мерчантом, проводит расчёты и физически перечисляет выручку на его счёт. PSP — технологическая прослойка: единое API, форма оплаты, токенизация карт, вебхуки, часто маршрутизация между несколькими эквайерами. Мерчант обычно интегрируется с PSP, но деньги и сроки зачисления определяет эквайер, и при разборе расхождений разговаривать приходится с обоими.

Жизненный цикл платежа

Механика

Платёж — не событие, а процесс с несколькими точками невозврата. Между «клиент нажал оплатить» и «деньги на счёте компании» проходит от нескольких секунд до нескольких дней, и на каждой стадии деньги находятся в разном состоянии. Путаница между стадиями — источник классических багов: заказ отгружают по факту авторизации, которая потом не подтвердилась, или считают выручку по списанию, не дождавшись расчётов.

Одностадийная и двухстадийная схема. В одностадийной авторизация и списание происходят одним запросом — это подходит для цифровых товаров и всего, что отдаётся мгновенно. В двухстадийной сначала делается холд, а списание выполняется отдельным вызовом, когда товар собран и отгружен. Двухстадийная схема нужна везде, где между оплатой и отгрузкой есть время и возможность не выполнить заказ.

ВажноСрок жизни холда — не бесконечный и не одинаковый: у разных схем и эмитентов он составляет от нескольких дней до месяца, после чего сумма разблокируется автоматически, и списать по этой авторизации уже нельзя. Отсюда практическое правило: если заказ висит дольше срока холда, его нужно либо списать, либо отменить явно и уведомить клиента, а не оставлять «до выяснения». Отдельная неприятность — клиент видит замороженную сумму как списание и приходит с вопросом, почему деньги сняли дважды.
Типичный вопрос на собеседованииЧем авторизация отличается от списания?
Авторизация — проверка и заморозка суммы на стороне эмитента: деньги ещё у клиента, но потратить их он не может. Списание — подтверждение операции мерчантом, после которого сумма уходит в расчёты. Разделение даёт возможность не брать деньги, если заказ не может быть выполнен: отмена холда дешевле и быстрее возврата, а для клиента выглядит гораздо лучше.

junior / идемпотентность

Идемпотентность и повторы

Обязательно

Любой сетевой вызов имеет три исхода, а не два: успех, явная ошибка и неизвестность. Третий — самый важный: таймаут, обрыв соединения, ответ 502 от промежуточного прокси. В этом случае операция могла выполниться полностью, а могла не начаться, и определить это по коду ответа невозможно. Всё устройство платёжных API вращается вокруг того, чтобы повтор такого запроса не создал вторую операцию.

Ключ идемпотентности — строка, которую клиент генерирует до запроса и повторяет при каждой попытке. Провайдер по ней узнаёт повтор и возвращает результат первой операции вместо создания новой. Ключ должен быть детерминированным относительно намерения: один ключ на одну попытку оплаты заказа, а не случайный на каждый вызов, иначе смысл теряется.

PHPИдемпотентное создание платежа: ключ, уникальный индекс, повтор
final class CreatePaymentHandler
{
    public function __construct(
        private readonly PaymentRepository $payments,
        private readonly PaymentGateway $gateway,
    ) {}

    public function handle(CreatePayment $command): Payment
    {
        // 1. Ключ пришёл от клиента и одинаков во всех его повторах.
        //    В базе на него стоит UNIQUE — это и есть защита от гонки.
        $existing = $this->payments->findByIdempotencyKey($command->idempotencyKey);

        if ($existing !== null) {
            // 2. Повтор с теми же параметрами — отдаём прежний результат.
            //    Другая сумма под тем же ключом — ошибка вызывающего, а не новый платёж.
            if (!$existing->matches($command)) {
                throw new IdempotencyKeyReused($command->idempotencyKey);
            }

            return $existing;
        }

        // 3. Сначала фиксируем намерение у себя, потом идём в сеть.
        //    Платёж в статусе pending уже существует, даже если вызов не вернётся.
        $payment = Payment::pending(
            $command->orderId,
            $command->amount,
            $command->idempotencyKey,
        );
        $this->payments->save($payment);

        try {
            $result = $this->gateway->authorize(
                $payment,
                idempotencyKey: $command->idempotencyKey,
            );
        } catch (GatewayUnknownState $e) {
            // 4. Таймаут: НЕ считаем платёж неудавшимся.
            //    Статус выяснит фоновая задача, опрашивая провайдера.
            $payment->markUnknown($e->getMessage());
            $this->payments->save($payment);

            return $payment;
        }

        $payment->applyGatewayResult($result);
        $this->payments->save($payment);

        return $payment;
    }
}
АнтипаттернПовтор запроса на списание без ключа идемпотентности «потому что первый упал по таймауту». Это самый прямой способ списать с клиента дважды: первая операция дошла до эмитента и прошла, ответ потерялся по дороге, повтор создал вторую независимую операцию. Второй вариант той же ошибки — генерировать ключ внутри цикла повторов, из-за чего каждая попытка получает новый ключ и перестаёт быть повтором.
ОриентирЗаписывайте намерение в свою базу до сетевого вызова и всегда передавайте провайдеру собственный идентификатор платежа. Тогда после любого сбоя есть две опоры: своя запись, по которой видно, что операция начиналась, и возможность найти её у провайдера по своему идентификатору, даже если его ответ до вас не дошёл.
Типичный вопрос на собеседованииЗапрос на списание завершился таймаутом. Ваши действия?
Не считать операцию неуспешной. Платёж переводится в состояние «результат неизвестен», а дальше — повтор с тем же ключом идемпотентности либо явный запрос статуса по своему идентификатору. Клиенту показывается «платёж обрабатывается», а не ошибка с кнопкой «попробовать снова», которая создаст вторую операцию. Окончательный статус выставляет фоновая проверка или вебхук провайдера.

junior / вебхуки

Вебхуки провайдера

Интеграция

Вебхук — способ провайдера сообщить об изменении статуса: платёж подтверждён, возврат исполнен, спор открыт. Он приходит в произвольный момент, может прийти дважды, может прийти не по порядку и может не прийти вовсе. Обработчик, написанный в предположении «пришло один раз и вовремя», ломается на первой же неделе продакшена.

PHPОбработчик вебхука: подпись, дедупликация, быстрый ответ
final class WebhookController
{
    public function __invoke(Request $request): Response
    {
        $raw = $request->getContent();

        // 1. Подпись считается по сырому телу, до любого декодирования.
        //    Сравнение — только hash_equals: обычное === уязвимо к тайминг-атаке.
        $expected = hash_hmac("sha256", $raw, $this->secret);

        if (!hash_equals($expected, $request->headers->get("X-Signature", ""))) {
            return new Response(status: 401);
        }

        $event = $this->serializer->decode($raw);

        // 2. Дедупликация по идентификатору события провайдера.
        //    UNIQUE на event_id: повтор упирается в базу, а не в проверку в коде.
        if (!$this->inbox->register($event->id)) {
            return new Response(status: 200);   // уже обработан — молча подтверждаем
        }

        // 3. Тяжёлую работу — в очередь. Ответ провайдеру нужен быстро,
        //    иначе он посчитает доставку неуспешной и повторит её.
        $this->bus->dispatch(new ProcessGatewayEvent($event->id));

        return new Response(status: 200);
    }
}

// В обработчике очереди статус применяется через статусную машину,
// а не присваиванием: событие «оплачен» после «возвращён» игнорируется.
final class ProcessGatewayEventHandler
{
    public function __invoke(ProcessGatewayEvent $message): void
    {
        $event   = $this->inbox->get($message->eventId);
        $payment = $this->payments->lockByGatewayId($event->paymentId);

        // Вебхук — сигнал, а не источник истины. Для операций с деньгами
        // статус подтверждается запросом к API провайдера.
        $actual = $this->gateway->fetchStatus($event->paymentId);

        $payment->transitionTo($actual->status, $actual->amount);
        $this->payments->save($payment);
    }
}

middle / учёт

Двойная запись и ledger

Обязательно

Соблазнительный вариант учёта — колонка balance в таблице пользователей и запросы вида UPDATE users SET balance = balance - 500. Он работает ровно до первого вопроса «почему у клиента 1 320 ₽, откуда эта сумма». Ответа нет: история движений не хранится, восстановить её невозможно, а любая ошибка кода навсегда остаётся в числе.

Двойная запись решает это структурно: денег не появляется и не исчезает, они только перемещаются между счетами. Каждая операция порождает минимум две проводки — списание с одного счёта и зачисление на другой, — и их сумма по операции всегда равна нулю. Баланс перестаёт быть хранимым числом и становится вычисляемым: это сумма проводок по счёту.

SQLМинимальная схема ledger: счета, операции, проводки
-- Счёт: и клиентский кошелёк, и технический счёт эквайера, и доходы
CREATE TABLE accounts (
    id          BIGSERIAL PRIMARY KEY,
    code        TEXT NOT NULL UNIQUE,        -- user:42:wallet, revenue:fee
    currency    CHAR(3) NOT NULL,
    kind        TEXT NOT NULL,               -- liability, asset, revenue
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Операция: то, что произошло в предметной области
CREATE TABLE ledger_transactions (
    id              BIGSERIAL PRIMARY KEY,
    idempotency_key TEXT NOT NULL UNIQUE,    -- защита от двойного проведения
    kind            TEXT NOT NULL,           -- payment, refund, fee, payout
    reference       TEXT NOT NULL,           -- ссылка на платёж или заказ
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Проводка: неизменяемая строка. UPDATE и DELETE здесь запрещены.
CREATE TABLE ledger_entries (
    id             BIGSERIAL PRIMARY KEY,
    transaction_id BIGINT NOT NULL REFERENCES ledger_transactions(id),
    account_id     BIGINT NOT NULL REFERENCES accounts(id),
    amount         BIGINT NOT NULL,        -- минимальные единицы, знак = направление
    currency       CHAR(3) NOT NULL,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_entries_account ON ledger_entries (account_id, id);

-- Баланс не хранится, а выводится из проводок
SELECT COALESCE(SUM(amount), 0) AS balance
FROM ledger_entries
WHERE account_id = :account_id;

-- Ежедневная проверка инварианта: сумма всех проводок операции равна нулю
SELECT transaction_id, SUM(amount) AS imbalance
FROM ledger_entries
GROUP BY transaction_id
HAVING SUM(amount) <> 0;

Цена подхода — рост таблицы проводок и стоимость вычисления баланса. Обе проблемы решаются одинаково: периодические снимки. Раз в сутки на каждый счёт пишется строка с балансом на конец дня, и текущий баланс считается как «последний снимок плюс проводки после него». Снимок при этом остаётся производной величиной: его всегда можно пересчитать заново из проводок, поэтому он не создаёт второго источника истины.

Типичный вопрос на собеседованииЗачем двойная запись, если можно хранить баланс числом?
Потому что баланс — производная величина, а истина — история движений. Двойная запись даёт три вещи, которых нет у колонки: ответ на вопрос «из чего сложилась сумма», встроенный инвариант, по которому расхождение обнаруживается автоматически, и возможность сверки с банком по техническим счетам. Хранимый баланс допустим как кэш или снимок, но не как источник истины.

middle / согласованность

Гонки, транзакции, блокировки

Механика

Списание средств — учебный пример состояния гонки, только с деньгами. Два параллельных запроса читают баланс 1 000 ₽, оба видят, что 800 ₽ списать можно, оба списывают. Итог — минус 600 ₽ на счёте, который по бизнес-правилам не может уходить в минус. Проверка в коде здесь не помогает вообще: между чтением и записью есть окно, и на нагрузке в него попадают регулярно.

PHP + SQLСписание с блокировкой строки и проверкой инварианта
// Неправильно: проверка и запись разнесены во времени
$balance = $this->balanceOf($accountId);          // 1 000
if ($balance >= $amount) {                          // оба запроса проходят
    $this->insertEntry($accountId, -$amount);       // оба списывают
}

// Правильно: конкуренты выстраиваются в очередь на строке счёта
public function withdraw(int $accountId, Money $amount, string $key): void
{
    $this->connection->transactional(function ($db) use ($accountId, $amount, $key) {
        // 1. Блокируем счёт: параллельная транзакция ждёт здесь.
        //    Порядок блокировки счетов фиксирован (по id) — иначе взаимоблокировка.
        $db->executeStatement(
            "SELECT id FROM accounts WHERE id = ? FOR UPDATE",
            [$accountId],
        );

        // 2. Баланс читается уже под блокировкой — значение актуально.
        $balance = (int) $db->fetchOne(
            "SELECT COALESCE(SUM(amount), 0) FROM ledger_entries WHERE account_id = ?",
            [$accountId],
        );

        if ($balance < $amount->amount) {
            throw new InsufficientFunds($accountId, $balance, $amount);
        }

        // 3. Ключ идемпотентности с UNIQUE — вторая попытка того же
        //    списания упрётся в ограничение и не создаст вторую операцию.
        $txId = $this->insertTransaction($db, $key, "withdrawal");

        $this->insertEntry($db, $txId, $accountId, -$amount->amount);
        $this->insertEntry($db, $txId, $this->payoutAccountId, +$amount->amount);
    });
}

Порядок блокировок — источник взаимоблокировок при переводах. Транзакция A блокирует счёт 1, затем счёт 2; транзакция B — в обратном порядке; обе ждут вечно, пока база не убьёт одну из них по таймауту. Лечится соглашением: счета всегда блокируются в порядке возрастания идентификатора, независимо от того, кто кому переводит.

АнтипаттернТранзакция базы, внутри которой делается HTTP-вызов провайдера. Блокировки держатся всё время сетевого ожидания, при таймауте в десять секунд счёт заблокирован десять секунд, а при откате транзакции запрос к провайдеру всё равно уже ушёл, и деньги списаны, хотя у нас записи нет. Правильный порядок: короткая транзакция фиксирует намерение, сетевой вызов идёт вне транзакции, результат применяется отдельной короткой транзакцией.
Типичный вопрос на собеседованииДва запроса одновременно списывают деньги с одного счёта. Как не уйти в минус?
Проверка в коде не помогает: между чтением баланса и вставкой проводки есть окно. Нужна блокировка строки счёта FOR UPDATE внутри транзакции — второй запрос ждёт и читает уже актуальный баланс. Дополнительно ставится ограничение уровня базы, чтобы даже ошибка в коде не смогла создать отрицательный остаток, а ключ идемпотентности с уникальным индексом защищает от повторного проведения той же операции.

middle / состояние

Статусная машина и события

Дисциплина

Платёж меняет статус под влиянием четырёх независимых источников: действий пользователя, ответов API провайдера, вебхуков и фоновых задач. Если каждый из них присваивает статус напрямую, порядок событий определяет случай, и рано или поздно возврат перезатирается пришедшим позже подтверждением оплаты. Единственное лекарство — явная статусная машина, через которую проходят все изменения.

enum PaymentStatus: string
{
    case Created    = "created";
    case Pending    = "pending";
    case Unknown    = "unknown";
    case Authorized = "authorized";
    case Captured   = "captured";
    case Failed     = "failed";
    case Refunded   = "refunded";
    case Disputed   = "disputed";

    // Разрешённые переходы описаны данными, а не разбросанными if-ами
    public function canTransitionTo(self $next): bool
    {
        return in_array($next, match ($this) {
            self::Created    => [self::Pending, self::Failed],
            self::Pending    => [self::Authorized, self::Captured, self::Failed, self::Unknown],
            self::Unknown    => [self::Authorized, self::Captured, self::Failed],
            self::Authorized => [self::Captured, self::Failed],
            self::Captured   => [self::Refunded, self::Disputed],
            self::Refunded   => [self::Disputed],
            self::Failed, self::Disputed => [],
        }, true);
    }
}

final class Payment
{
    public function transitionTo(PaymentStatus $next, Money $amount): void
    {
        // Повторное применение того же статуса — не ошибка, а обычное дело:
        // вебхук пришёл дважды. Просто ничего не делаем.
        if ($this->status === $next) {
            return;
        }

        // Запоздавшее событие «оплачен» после возврата не откатывает статус
        if (!$this->status->canTransitionTo($next)) {
            throw new IllegalTransition($this->id, $this->status, $next);
        }

        $this->status = $next;

        // Событие пишется в ту же транзакцию, что и смена статуса (outbox):
        // либо есть и статус, и событие, либо нет ни того, ни другого.
        $this->recordEvent(new PaymentStatusChanged($this->id, $next, $amount));
    }
}

Почему outbox обязателен именно здесь. Смена статуса на «оплачен» и отправка события в очередь — две операции в разных системах. Если сначала публиковать в брокер, а потом фиксировать транзакцию, откат оставит миру событие о платеже, которого нет. Если наоборот — падение между фиксацией и публикацией потеряет событие, и заказ никогда не уедет в отгрузку. Запись события в таблицу той же транзакцией снимает вопрос: отдельный процесс потом дочитывает таблицу и публикует. Подробности — в конспекте по брокерам сообщений.

ОриентирДержите историю переходов отдельной таблицей: платёж, старый статус, новый статус, источник, метка времени, идентификатор входящего события. Это стоит одной вставки на переход и окупается при первом же разборе — «почему платёж стал возвращённым в 3:40 ночи» превращается из расследования по логам в один запрос.
Типичный вопрос на собеседованииВебхуки приходят не в том порядке. Как не сломать статус?
Через статусную машину с явным списком допустимых переходов: запоздавшее «оплачен» после «возвращён» не проходит проверку и отбрасывается, а не перезаписывает статус. Повтор того же статуса при этом считается нормой и обрабатывается без ошибки. Дополнительно у событий сравнивается версия или метка времени провайдера, чтобы отличить старое событие от нового.

Обязательно

Сверка отвечает на вопрос, который нельзя решить внутри системы: совпадает ли наша картина мира с картиной банка. Система без сверки не «работает без ошибок», она просто не знает о них.

-- Полное внешнее соединение показывает все три вида расхождений сразу.
SELECT
    COALESCE(p.gateway_id, s.gateway_id) AS gateway_id,
    p.amount      AS our_amount,
    s.amount      AS their_amount,
    p.status      AS our_status,
    s.status      AS their_status,
    CASE
        WHEN p.gateway_id IS NULL            THEN "missing_locally"
        WHEN s.gateway_id IS NULL            THEN "missing_remotely"
        WHEN p.amount <> s.amount          THEN "amount_mismatch"
        WHEN p.status <> s.status          THEN "status_mismatch"
    END AS discrepancy
FROM payments p
FULL OUTER JOIN settlement_rows s ON s.gateway_id = p.gateway_id
-- Окно с перекрытием: операции около полуночи попадают в соседний реестр
WHERE COALESCE(p.created_at, s.created_at)
      BETWEEN :from - INTERVAL "2 hours" AND :to + INTERVAL "2 hours"
  AND (

     OR s.gateway_id IS NULL
     OR p.amount <> s.amount
     OR p.status <> s.status
      );

Три уровня сверки. Первый — операционный: наши платежи против реестра провайдера, ежедневно. Второй — учётный: технические счета ledger против сумм в реестре, включая комиссии. Третий — банковский: сумма выплат провайдера против поступлений на расчётный счёт компании. Расхождение на каждом уровне означает разное, и склеивать их в один отчёт бесполезно: непонятно, где именно потерялись деньги.

ВажноСверка бессмысленна без процесса разбора. Отчёт, который никто не открывает, отличается от отсутствия сверки только потраченным временем. Работающая схема: расхождения попадают в очередь задач с ответственным и сроком, автоматические правила закрывают типовые случаи вроде «платёж около полуночи», а всё остальное разбирает человек. Количество нерасследованных расхождений старше суток — хорошая метрика здоровья финансового контура.
Типичный вопрос на собеседованииКак понять, что в платёжном контуре что-то потерялось?
Только сверкой с внешним источником: реестр провайдера против наших операций, наши технические счета против реестра, выплаты против выписки по расчётному счёту. Внутренние проверки покажут только внутреннюю несогласованность, а типичная потеря — платёж, который прошёл у провайдера и не дошёл до нас, — по нашим данным вообще не существует и обнаруживается исключительно снаружи.

middle / деньги назад

Возвраты, chargeback и споры

Обратный поток

Деньги в финтехе двигаются в обе стороны, и обратный поток устроен сложнее прямого. Возврат инициирует мерчант, спор — клиент через свой банк, и от того, какой это случай, зависит и стоимость, и сроки, и то, кто в итоге платит. Система, где возврат реализован как «списание с обратным знаком», ломается на первом же частичном возврате и первом же споре.

PHPЧастичный возврат: инварианты и идемпотентность
final class RefundPaymentHandler
{
    public function handle(RefundPayment $command): Refund
    {
        return $this->connection->transactional(function () use ($command) {
            // Блокируем платёж: параллельные возвраты — обычное дело,
            // когда клиент нажимает кнопку дважды или менеджер дублирует заявку.
            $payment = $this->payments->lockById($command->paymentId);

            if ($payment->status !== PaymentStatus::Captured) {
                throw new RefundNotAllowed($payment->status);
            }

            // Ключевой инвариант: возвращено не больше, чем списано
            $alreadyRefunded = $this->refunds->totalFor($payment->id);

            if ($alreadyRefunded->add($command->amount)->greaterThan($payment->amount)) {
                throw new RefundExceedsPayment($payment->id, $command->amount);
            }

            // Ключ идемпотентности возврата строится из намерения,
            // а не генерируется случайно на каждый клик.
            $refund = Refund::requested(
                $payment->id,
                $command->amount,
                $command->reason,
                $command->idempotencyKey,
            );

            $this->refunds->save($refund);   // UNIQUE (payment_id, idempotency_key)

            // Вызов провайдера — за пределами транзакции, из обработчика очереди
            $refund->recordEvent(new RefundRequested($refund->id));

            return $refund;
        });
    }
}

Типичный вопрос на собеседованииЧем возврат отличается от chargeback?
Возврат инициирует мерчант добровольно, он проходит по обычному платёжному каналу и обходится в комиссию. Chargeback инициирует клиент через свой банк: деньги удерживаются принудительно, мерчант платит штраф за спор и обязан доказывать правоту документами в жёсткий срок. Высокая доля споров ведёт к повышенным тарифам и вплоть до отказа в обслуживании, поэтому дешевле вернуть деньги самому, чем доводить до спора.

middle / подписки

Рекуррентные платежи и токены

Подписки

Подписка означает списание без участия клиента, а значит — сохранённый способ оплаты. Карту при этом хранит не мерчант, а провайдер: наружу отдаётся токен, бесполезный для кого-либо ещё. Это и требование стандарта безопасности, и практическое удобство: смена провайдера превращается в отдельный проект по переносу токенов, но хотя бы не в утечку.

Дальнейшие списания идут по токену как операции по инициативе мерчанта, с сохранённым согласием клиента. Мерчант хранит только токен, маску номера и срок действия, что оставляет его вне зоны действия требований к хранению карточных данных.

Интеграция с провайдером

Надёжность

Платёжный провайдер — внешняя система, которая тормозит, отвечает ошибками и иногда лежит целиком. Разница с обычной интеграцией в том, что здесь неверная реакция на сбой стоит денег: лишний повтор создаёт второе списание, а преждевременный отказ — потерянную продажу и клиента, у которого деньги заморожены.

        try {
            $response = $this->http->request("POST", "/payments", [
                // Разные таймауты: на соединение — короткий, на ответ — щедрый.
                // Общий бюджет запроса меньше таймаута воркера, иначе процесс
                // убьют раньше, чем он успеет записать результат.
                "timeout"         => 25,
                "connect_timeout" => 3,
                "headers"         => ["Idempotency-Key" => $idempotencyKey],
                "json"            => [
                    "amount"      => $payment->amount->amount,
                    "currency"    => $payment->amount->currency->code,
                    // Свой идентификатор — единственный способ найти операцию,
                    // если ответ провайдера до нас не дошёл.
                    "merchant_id" => $payment->id->toString(),
                ],
            ]);
        } catch (ConnectException $e) {
            // Соединение не установлено — запрос точно не выполнен.
            // Это безопасная ошибка: повторять можно сразу.
            throw new GatewayUnavailable(previous: $e);
        } catch (TransferException $e) {
            // Таймаут ответа: операция могла выполниться. Опасное состояние,
            // повтор допустим только с тем же ключом идемпотентности.
            throw new GatewayUnknownState(previous: $e);
        }

        return match (true) {
            $response->getStatusCode() >= 500 => throw new GatewayUnknownState(),
            $response->getStatusCode() === 409 => $this->fetchByMerchantId($payment->id),
            default => GatewayResult::fromResponse($response),
        };
    }
}

На этом уровне решения принимаются не про код, а про контур целиком: где проходят границы сервисов, что делать при отказе половины цепочки, сколько мошенничества компания готова терпеть ради конверсии, что требует регулятор и как всё это доказывается через полгода при проверке.

senior / архитектура

Архитектура платёжного контура

Дизайн

Главное архитектурное решение в финтехе — отделить учёт от процессинга. Учётный контур знает только о счетах и проводках, ничего не знает о картах и провайдерах и обязан быть строго согласованным. Процессинг работает с внешним миром, живёт в условиях таймаутов и неизвестных состояний и по определению согласован в конечном счёте. Смешение этих двух миров в одном сервисе даёт систему, которая не может быть ни надёжной, ни быстрой.

Не распределённой транзакцией, а сагой с явными компенсациями и жёстким порядком шагов: обратимые впереди, необратимые в конце. Внутри учётного сервиса согласованность строгая — проводки пишутся одной транзакцией с проверкой инварианта. Между сервисами — согласованность в конечном счёте: события через outbox, идемпотентные обработчики и сверка, которая ловит то, что всё-таки разошлось.

Антифрод и риск

Риск

Антифрод — не задача «поймать всех мошенников», а задача найти точку, где сумма потерь от мошенничества и потерь от отклонённых честных операций минимальна. Ноль мошенничества достигается отклонением всех платежей и стоит бизнесу дороже любого мошенника, поэтому разговор всегда идёт о пороге, а не о наличии защиты.

потери = ущерб от пропущенного мошенничества + упущенная выручка от ложных отказовзадача — минимум суммы, а не минимум первого слагаемого

PHPПравила скорости и решение с тремя исходами
final class RiskEngine
{
    // Решение всегда одно из трёх, а не «да или нет»:
    // пропустить, потребовать подтверждения, отклонить.
    public function assess(PaymentAttempt $attempt): RiskDecision
    {
        $score  = 0;
        $hits   = [];

        // Скоростные правила считаются по окну, а не за всё время.
        // Счётчики живут в Redis: обращение к базе тут не уложится в бюджет.
        foreach ($this->velocityRules as $rule) {
            $count = $this->counters->countInWindow(
                $rule->keyFor($attempt),   // card:hash, device:id, ip:subnet
                $rule->window,
            );

            if ($count > $rule->threshold) {
                $score += $rule->weight;
                $hits[] = $rule->name;
            }
        }

        // Жёсткие блокировки не участвуют в скоринге: санкционный список
        // и подтверждённое мошенничество отклоняют операцию сразу.
        if ($this->denyList->contains($attempt)) {
            return RiskDecision::deny("deny_list");
        }

        // Средняя зона — не отказ, а усиленное подтверждение: 3-D Secure
        // переносит ответственность на эмитента и сохраняет конверсию.
        return match (true) {
            $score >= $this->denyThreshold      => RiskDecision::deny(...$hits),
            $score >= $this->challengeThreshold => RiskDecision::challenge(...$hits),
            default                            => RiskDecision::allow(),
        };
    }
}

Работающее решение — разделение хранилищ: учётные записи о движении денег остаются с обезличенным идентификатором, а персональные сведения живут отдельно и удаляются или обезличиваются по истечении срока. Проектировать это нужно заранее: разделить сущности в работающей системе гораздо дороже.

Типичный вопрос на собеседованииКлиент требует удалить свои данные, а операции хранить обязаны. Как быть?
Разнести хранение: движение денег фиксируется по внутреннему идентификатору без персональных сведений, а персональные данные хранятся отдельно и обезличиваются по требованию или по истечении установленного срока. Тогда удаление профиля не разрушает историю операций и не нарушает обязанность её хранить. Отдельно фиксируется сам факт обращения и что именно было обезличено.

senior / карточные данные

PCI DSS и карточные данные

Обязательно

Стандарт PCI DSS описывает требования к тем, кто хранит, обрабатывает или передаёт данные карт. Главная инженерная мысль здесь простая: самый дешёвый способ соответствовать требованиям — не прикасаться к карточным данным вообще. Каждый компонент, через который проходит номер карты, попадает в зону соответствия вместе со всей инфраструктурой вокруг него.

Что нельзя хранить никогда: код проверки подлинности карты и содержимое магнитной полосы или чипа — даже в зашифрованном виде, даже временно, даже «для отладки». Номер карты, если он всё-таки хранится, маскируется при показе и защищается криптографически при хранении. На практике для мерчанта достаточно токена провайдера, маски вида «первые шесть и последние четыре» и срока действия — этого хватает и для интерфейса, и для поддержки.

АнтипаттернПолный номер карты в логах, в теле исключения, в сохранённом запросе для отладки или в системе отслеживания ошибок. Обычно это происходит не намеренно: логируется всё тело запроса, а карта оказалась внутри. Защита — фильтр по маске на уровне логгера и обработчика ошибок плюс тест, который прогоняет типичные полезные нагрузки через журналирование и проверяет, что номера не осталось нигде. Один такой лог превращает соответствие требованиям в фикцию и создаёт полноценную утечку.
ВажноЗона соответствия — это не только код приёма платежа, но и всё, что имеет к нему сетевой доступ: контейнеры на той же машине, база, резервные копии, скрипты аналитики на странице оплаты, сотрудники с доступом. Отсюда практический вывод: сокращение зоны почти всегда выгоднее её защиты. Замена собственной формы на поля провайдера обходится в несколько недель работы, тогда как поддержание полного соответствия — в постоянные расходы и регулярные аудиты.
Типичный вопрос на собеседованииКак принимать оплату картой, не попадая в дорогую зону PCI DSS?
Не пропускать карточные данные через свои серверы: форма провайдера во фрейме, его поля внутри своей вёрстки или переадресация на его страницу. Мерчант получает токен и работает дальше с ним, а у себя хранит только маску и срок действия. Дополнительно проверяется, что номер карты не попадает в логи, трассировки и системы отслеживания ошибок, — это самая частая незаметная утечка данных за пределы зоны.

senior / аудит

Аудит и закрытие периода

Отчётность

Финансовая система должна уметь отвечать на вопрос «что произошло с этими деньгами» через год, с точностью до операции и с указанием, кто её инициировал. Это меняет требования к хранению: журнал операций перестаёт быть отладочным средством и становится частью продукта, а «почистить старые записи» превращается из оптимизации в нарушение.

Дата операции и дата учёта — разные вещи. Платёж, прошедший в 23:58 последнего дня месяца, попадает в отчёт этого месяца, даже если наш обработчик записал его в 00:03 следующего. Поэтому у операции хранятся обе метки: техническая, когда запись создана, и учётная, к какому периоду она относится. Без этого разделения ежемесячная отчётность расходится с данными провайдера каждый раз на границе месяца, и каждый раз это выясняется заново.

Закрытие периода — момент, после которого проводки за период считаются окончательными. Всё, что обнаружено позже, оформляется корректирующими операциями текущего периода со ссылкой на исходную, а не правкой закрытых записей. Технически это означает запрет на вставку проводок с учётной датой в закрытом периоде — проверку удобно держать на уровне базы, чтобы её нельзя было обойти из кода.

ОриентирХороший признак зрелости финансового контура — возможность в любой момент воспроизвести баланс любого счёта на произвольную дату в прошлом, повторив расчёт из проводок. Если такой запрос требует восстановления резервной копии или ручных выкладок, значит, где-то в системе баланс всё-таки хранится как самостоятельная величина и однажды разойдётся с историей.
Типичный вопрос на собеседованииОбнаружилась ошибочная проводка недельной давности. Что с ней делать?
Не исправлять и не удалять. Создаётся сторнирующая операция, отменяющая эффект ошибочной, затем корректная операция — обе с текущей датой и ссылкой на исходную. История остаётся полной: видно, что произошла ошибка, когда её нашли и как исправили. Правка задним числом лишает журнал доказательной силы и почти всегда всплывает при сверке, только позже и дороже.

senior / эксплуатация

Эксплуатация денег

Продакшен

В платёжном контуре обычного технического мониторинга недостаточно. Сервис может отвечать за 50 мс с нулевым процентом ошибок и при этом не проводить ни одного платежа: провайдер отклоняет всё подряд, а с точки зрения инфраструктуры всё прекрасно. Поэтому основные метрики здесь — денежные и продуктовые, а не только технические.

ВажноРучные корректировки — необходимая часть эксплуатации денег: без них некоторые ситуации не разрешить. Опасны не они, а их отсутствие в системе. Правильная форма — операция того же типа, что и обычная, с обязательным указанием автора, причины и основания, проходящая через тот же ledger и те же инварианты. Прямой доступ к базе с UPDATE по балансу — самое дорогое, что может случиться с финансовым контуром: следов не остаётся, а разошедшийся баланс обнаруживается спустя месяцы.
Типичный вопрос на собеседованииКакие алерты вы поставите на платёжный сервис?
Помимо технических — денежные: падение доли успешных операций относительно того же часа неделей ранее, всплеск конкретной причины отказа, платежи в неизвестном состоянии старше установленного срока, нерасследованные расхождения сверки старше суток и любое нарушение инварианта двойной записи. Технические метрики показывают, что сервис жив, но не показывают, что он перестал зарабатывать деньги.

Senior checklist

Проверка

Что должно быть в арсенале.

  • Развести учётный контур и процессинг и объяснить, почему у них разные требования к согласованности.
  • Спроектировать сагу оформления заказа с компенсациями и объяснить порядок необратимых шагов.
  • Обосновать выбор оркестрации для денежных процессов.
  • Назвать критерии маршрутизации между провайдерами и опасность каскада после таймаута.
  • Сформулировать задачу антифрода как минимизацию суммы двух видов потерь.
  • Описать решение с тремя исходами и роль 3-D Secure в переносе ответственности.
  • Перечислить требования KYC и AML, влияющие на архитектуру системы.
  • Развести хранение персональных данных и истории операций.
  • Назвать способы сократить зону соответствия PCI DSS и то, что нельзя хранить никогда.

  • Перечислить денежные метрики и алерты, которых нет в обычном мониторинге.

Досмотр зависших платежей

Шаблон

Задача, которая закрывает главную дыру любой интеграции: платежи, по которым мы не получили ни ответа, ни вебхука. Без неё такие операции живут в базе вечно и всплывают только при сверке или обращении клиента.

PHPПериодический опрос статусов у провайдера
final class ResolveStuckPayments
{
    public function __invoke(): void
    {
        // Берём платежи, застрявшие дольше разумного времени.
        // Порог больше типичного времени ответа провайдера, но меньше
        // срока, за который клиент успеет пожаловаться.
        $stuck = $this->payments->findStuck(
            statuses: [PaymentStatus::Pending, PaymentStatus::Unknown],
            olderThan: new \DateInterval("PT5M"),
            limit: 200,
        );

        foreach ($stuck as $payment) {
            try {
                // Ищем по СВОЕМУ идентификатору: идентификатора провайдера
                // может не быть — ответ до нас не дошёл.
                $state = $this->gateways
                    ->for($payment->gateway)
                    ->findByMerchantId($payment->id);
            } catch (GatewayUnavailable) {
                continue;   // провайдер лежит — вернёмся на следующем запуске
            }

            if ($state === null) {
                // Операции нет у провайдера и прошло достаточно времени:
                // платёж не состоялся, закрываем и освобождаем заказ.
                if ($payment->olderThan(new \DateInterval("PT1H"))) {
                    $this->apply($payment, PaymentStatus::Failed);
                }

                continue;
            }

            // Статус провайдера — истина. Применяем через статусную машину:
            // запрещённый переход означает, что вебхук нас уже опередил.
            $this->apply($payment, $state->status);
        }
    }
}

Чек-лист ревью платёжного кода

Проверка
  • Сумма — целое в минимальных единицах, валюта рядом и проверяется при операциях.
  • Округление происходит один раз, а остаток при делении распределяется явно.
  • У каждой операции есть ключ идемпотентности с уникальным индексом в базе.
  • Намерение записывается в базу до сетевого вызова, свой идентификатор уходит провайдеру.
  • Таймаут не приводит к статусу «отказ»: есть состояние «результат неизвестен» и его разбор.
  • Ошибки провайдера классифицированы: что повторять, что нет, когда размыкать предохранитель.
  • Внутри транзакции базы нет сетевых вызовов.
  • Статус меняется только через статусную машину, запрещённые переходы отбрасываются.
  • События публикуются через outbox в той же транзакции.
  • Вебхуки проверяются по подписи от сырого тела, дедуплицируются по идентификатору события.
  • Решения на сумму принимаются по ответу API, а не по телу вебхука.
  • Проводки только вставляются, исправления оформляются сторно.
  • Сумма возвратов не может превысить сумму платежа, и это проверяется под блокировкой.
  • Номер карты, код проверки и полные ответы с карточными данными не попадают в логи.
  • Есть ежедневная сверка и очередь разбора расхождений с ответственным.
  • Есть фоновая задача, закрывающая зависшие платежи и просроченные холды.

60 вопросов с эталонными ответами

Финтех — тема, где проверяют не знание терминов, а понимание того, что произойдёт с деньгами при сбое. Сильный ответ почти всегда содержит сценарий отказа и цену ошибки.

Junior · 20 вопросов

База
  1. Почему деньги не хранят во float?Двоичная плавающая точка не представляет десятичные дроби точно: 0,1 плюс 0,2 не равно 0,3. Ошибка накапливается и превращается в расхождение при сверке с банком, которое невозможно объяснить. Хранят целое число минимальных единиц валюты, обёрнутое в объект Money.
  2. Что такое минимальная единица валюты?Наименьшая неделимая часть: копейка, цент, филс. Сумма 199,90 ₽ хранится как 19990. Масштаб зависит от валюты: у рубля и доллара две цифры после запятой, у иены — ноль, у кувейтского динара — три, поэтому умножение на сто не универсально и берётся из справочника валют.
  3. Можно ли использовать DECIMAL в базе?Да, для хранения и отчётности это корректный тип с точной десятичной арифметикой. Осторожность нужна на границе: драйвер отдаёт значение строкой, и случайное приведение к float в PHP возвращает исходную проблему. В домене всё равно удобнее целое в минимальных единицах.
  4. Как разделить 100 ₽ на троих?Не округлением каждой доли — так получится 33,33 три раза и потерянная копейка. Каждая доля считается делением вниз, затем остаток раздаётся по одной минимальной единице: 33,34 плюс 33,33 плюс 33,33. Инвариант — сумма частей строго равна исходной сумме.
  5. Что такое банковское округление и зачем оно?Округление ровной половины к ближайшей чётной цифре. На массовых начислениях процентов обычное округление половины вверх даёт систематическое смещение в одну сторону, банковское его убирает. В прикладных расчётах чаще применяется половина вверх — важно, чтобы правило было одно на систему и зафиксировано.
  6. Почему валюта — часть типа суммы?Иначе появится сложение рублей с долларами, которое ничего не заметит. Объект Money хранит валюту рядом с числом и выбрасывает исключение при попытке сложить разные. Конвертация — отдельная явная операция, результат которой сохраняется вместе с курсом и его источником.
  7. Кто такой эквайер?Банк, обслуживающий мерчанта: он принимает платёж, участвует в расчётах и перечисляет выручку на счёт компании. От него зависят сроки зачисления, комиссии, лимиты и реестры для сверки. С провайдером его путают потому, что мерчант обычно общается с провайдером, а деньги идут через эквайера.
  8. Чем PSP отличается от эквайера?PSP — технологический слой: единое API, форма оплаты, токенизация карт, вебхуки, иногда маршрутизация между несколькими эквайерами. Эквайер — банк, который проводит расчёты. Один PSP может работать с несколькими эквайерами, и наоборот.
  9. Кто принимает окончательное решение по операции?Банк-эмитент, выпустивший карту клиента: он проверяет средства, лимиты и собственный антифрод. Мерчант и провайдер могут отклонить операцию раньше, но одобрение всегда за эмитентом. Причину отказа он обычно не раскрывает.
  10. Чем авторизация отличается от списания?Авторизация — проверка и заморозка суммы у эмитента: деньги ещё у клиента, но недоступны. Списание — подтверждение операции мерчантом, после которого сумма уходит в расчёты. Разделение позволяет не брать деньги, если заказ не может быть выполнен.
  11. Когда нужна двухстадийная схема?Когда между оплатой и исполнением есть время и возможность не выполнить заказ: товар со склада, доставка, аренда, депозит. Тогда сначала делается холд, а списание — по факту отгрузки, возможно на меньшую сумму. Для цифровых товаров и подписок хватает одностадийной.
  12. Что происходит с холдом, если его не списать?Он сгорает: срок жизни ограничен и зависит от схемы и эмитента, обычно от нескольких дней до месяца. После этого сумма разблокируется, а списать по этой авторизации уже нельзя. Поэтому заказы, висящие дольше срока холда, нужно либо списывать, либо явно отменять.
  13. Клиент говорит, что деньги списались дважды. С чего начать?Проверить, не является ли одна из сумм холдом: замороженная сумма в приложении банка выглядит как списание. Затем найти операции по своему идентификатору заказа и сверить с провайдером. Настоящий дубль обычно означает повтор запроса без ключа идемпотентности или переключение на другого провайдера после таймаута.
  14. Что такое ключ идемпотентности?Строка, генерируемая до первой попытки и повторяемая во всех повторах запроса. Провайдер по ней узнаёт повтор и возвращает результат первой операции вместо создания второй. Ключ соответствует намерению — одной попытке оплаты заказа, — а не отдельному вызову, иначе он бесполезен.
  15. Запрос к провайдеру завершился таймаутом. Платёж прошёл?Неизвестно — и это отдельное состояние, а не отказ. Операция могла выполниться полностью. Правильные действия: повтор с тем же ключом идемпотентности либо запрос статуса по своему идентификатору, а клиенту показывается «платёж обрабатывается». Считать такой платёж неуспешным — прямой путь к двойному списанию.
  16. Зачем передавать провайдеру собственный идентификатор платежа?Чтобы найти операцию, если его ответ до нас не дошёл. Без своего идентификатора поиск возможен только по сумме и времени, что при потоке платежей ненадёжно. Это самая дешёвая страховка от потерянных операций.
  17. Что такое вебхук и зачем проверять его подпись?Уведомление провайдера об изменении статуса, приходящее на публичный адрес. Публичный адрес доступен всем, поэтому без проверки подписи любой может прислать «платёж оплачен». Подпись считается по сырому телу до разбора и сравнивается через hash_equals, а не обычным сравнением строк.
  18. Вебхук пришёл дважды. Что делать?Дедуплицировать по идентификатору события через таблицу с уникальным индексом: вторая вставка не проходит, обработчик отвечает 200. Проверки «есть ли такая запись» в коде недостаточно — две параллельные доставки пройдут её одновременно. Сам переход статуса тоже делается идемпотентным.
  19. Можно ли доверять сумме из тела вебхука?Нет, вебхук — сигнал «посмотри на операцию», а не документ. Тело может быть устаревшим, урезанным, а при ошибке в проверке подписи — вообще чужим. Решения на сумму принимаются по ответу API провайдера, полученному собственным запросом.
  20. Почему обработчик вебхука должен отвечать быстро?Провайдер считает медленный ответ неуспешной доставкой и повторяет её, умножая нагрузку и создавая дубли в обработке. Правильная схема: проверить подпись, записать событие, поставить задачу в очередь, ответить 200. Вся тяжёлая работа делается в фоне.

Middle · 20 вопросов

Механика
  1. Что такое двойная запись?Способ учёта, при котором каждая операция порождает минимум две проводки: списание с одного счёта и зачисление на другой, а их сумма равна нулю. Деньги не появляются и не исчезают, они перемещаются. Отсюда встроенная проверка целостности и полная история движений.
  2. Почему баланс не хранят числом?Потому что баланс — производная от истории, а не самостоятельная величина. Хранимое число не отвечает на вопрос «из чего оно сложилось», навсегда впитывает любую ошибку кода и не с чем сверяться. Допустимо хранить снимок баланса как кэш, если он в любой момент пересчитывается из проводок.
  3. Как быстро считать баланс на большом объёме проводок?Периодическими снимками: раз в сутки на счёт пишется баланс на конец дня, текущий считается как снимок плюс проводки после него. Ключевое условие — снимок остаётся производной величиной и пересчитывается из истории, иначе появляется второй источник истины со всеми его проблемами.
  4. Как обнаружить нарушение целостности ledger?Регулярным запросом, который группирует проводки по операции и ищет те, где сумма не равна нулю. Это дешёвая проверка, которая ловит ошибки кода и последствия ручных вмешательств. Ненулевой перекос — всегда повод для алерта, а не для строки в отчёте.
  5. Почему проводки нельзя изменять?Потому что восстанавливаемая история — единственное доказательство того, что произошло с деньгами. Ошибка исправляется сторнирующей операцией и последующей корректной, обе с текущей датой и ссылкой на исходную. Разрешение на UPDATE обесценивает весь учётный контур.
  6. Два параллельных списания с одного счёта. Как не уйти в минус?Блокировкой строки счёта FOR UPDATE внутри транзакции: второй запрос ждёт и читает актуальный баланс. Проверка в коде не спасает — между чтением и записью есть окно. Дополнительно ставится ограничение на уровне базы, чтобы даже ошибка в коде не создала отрицательный остаток.
  7. Откуда берутся взаимоблокировки при переводах?Из разного порядка захвата блокировок: одна транзакция блокирует счёт A, потом B, другая — наоборот, и обе ждут. Лечится соглашением блокировать счета в фиксированном порядке, например по возрастанию идентификатора, независимо от направления перевода.
  8. Почему нельзя вызывать API провайдера внутри транзакции базы?Блокировки держатся всё время сетевого ожидания, и при таймауте в десять секунд строка заблокирована десять секунд. Хуже другое: при откате транзакции запрос уже ушёл, деньги списаны, а записи у нас нет. Правильный порядок — короткая транзакция, сетевой вызов вне её, ещё одна короткая транзакция для результата.
  9. Что такое outbox и зачем он в платежах?Таблица исходящих событий, куда событие пишется той же транзакцией, что и изменение состояния, а отдельный процесс публикует его в брокер. Это снимает выбор между «опубликовать до фиксации» — событие о том, чего не произошло — и «после» — потерянное событие при падении между операциями.
  10. Как обработать вебхуки, приходящие не по порядку?Статусной машиной с явным списком допустимых переходов: запоздавшее «оплачен» после «возвращён» не проходит проверку и отбрасывается. Повтор того же статуса считается нормой и обрабатывается без ошибки. При наличии версии или метки времени события они сравниваются дополнительно.
  11. Зачем хранить историю переходов статуса?Чтобы отвечать на вопрос «почему платёж оказался в этом состоянии». Строка с прежним статусом, новым, источником изменения и меткой времени превращает расследование по логам в один запрос. Стоит одной вставки на переход и окупается при первом же разборе.
  12. Что такое сверка и зачем она нужна?Сравнение наших данных с внешним источником: реестром провайдера, а затем и с выпиской по расчётному счёту. Внутренние проверки не видят самой опасной ситуации — платёж прошёл у провайдера и не дошёл до нас. Такая операция по нашим данным просто не существует, и найти её можно только снаружи.
  13. Какие бывают расхождения при сверке?Операция есть у провайдера и нет у нас — дописываем по его данным; есть у нас и нет у него — запрашиваем статус, при отсутствии закрываем как несостоявшуюся; разные суммы — обычно комиссия, частичное списание или конвертация; разные статусы — принимаем статус провайдера через статусную машину. Отдельный случай — операции у границы суток.
  14. Почему сверку делают с перекрытием по времени?Потому что операция, прошедшая в 23:59, может попасть в реестр следующего дня, а у нас записана в текущий. Строгое деление по календарным суткам даёт ложные расхождения каждый день. Окно берётся с запасом в обе стороны, а совпадения ищутся по идентификатору операции.
  15. Какие инварианты у частичного возврата?Сумма всех возвратов по платежу не превышает сумму списания; возврат возможен только по списанному платежу; повтор с тем же ключом не создаёт второй возврат; позиция заказа не возвращается дважды. Проверка суммы делается под блокировкой платежа, иначе два параллельных возврата пройдут вместе.
  16. Чем chargeback отличается от возврата?Возврат инициирует мерчант через обычный платёжный канал. Chargeback инициирует клиент через свой банк: деньги удерживаются принудительно, мерчант платит штраф и обязан представить доказательства в жёсткий срок. Высокая доля споров ведёт к повышенным тарифам и вплоть до отказа в обслуживании.
  17. Что нужно сохранить, чтобы выиграть спор?Всё, что доказывает исполнение и участие клиента: детали заказа, результат проверки 3-D Secure, адрес и устройство, факт и время доставки, подтверждение получения, переписку. Собирать это надо в момент операции, а не через два месяца при запросе — иначе спор проигрывается независимо от правоты.
  18. Как устроено ежемесячное списание по подписке?Карта сохраняется у провайдера при первой операции, мерчанту возвращается токен. Дальнейшие списания идут по токену как операции по инициативе мерчанта на основании ранее данного согласия. Мерчант хранит только токен, маску и срок действия, оставаясь вне зоны хранения карточных данных.
  19. Что делать при отказе по подписке?Смотреть на причину. Недостаточно средств — несколько повторов с растущими интервалами; истёкшая карта — запрос новых реквизитов; подозрение на мошенничество или блокировка карты — повторять нельзя. Число попыток ограничено правилами платёжных систем, а бесконечные повторы штрафуются и портят репутацию мерчанта.
  20. Какие ошибки провайдера можно повторять?Ошибку соединения — безопасно, запрос не выполнялся. Ответ 5xx и 429 — с задержкой и разбросом. Таймаут — только с тем же ключом идемпотентности и с последующей проверкой статуса. Ошибку валидации и отказ эмитента повторять нельзя: первая даст тот же результат, вторая ухудшит статистику мерчанта.

Архитектура
  1. Как разделить платёжную систему на сервисы?Главная граница — между учётом и процессингом. Учёт знает счета и проводки, требует строгой согласованности и живёт в одной базе. Процессинг работает с провайдерами, живёт в мире таймаутов и согласован в конечном счёте. Смешение делает систему одновременно медленной и ненадёжной.
  2. Как обеспечить согласованность между заказом, платежом и учётом?Сагой с явными компенсациями, а не распределённой транзакцией: двухфазная фиксация через границу организации невозможна, провайдер в вашем протоколе не участвует. Шаги упорядочиваются по обратимости — необратимые последними, — события идут через outbox, обработчики идемпотентны, а остаточные расхождения ловит сверка.
  3. Что такое компенсация в саге и чем она отличается от отката?Компенсация — не откат, а обратное действие: отмена холда, сторнирующая проводка, возврат. Она видима снаружи и иногда стоит денег, поэтому шаги выстраивают так, чтобы дешёвые компенсации шли раньше, а необратимые действия вроде отгрузки — в самом конце.
  4. Оркестрация или хореография для платёжного процесса?Для денег — оркестрация. Процесс живёт в явном координаторе с видимым состоянием, компенсации описаны по шагам, а при инциденте сразу понятно, где встал процесс. Хореография на событиях уместна для побочных эффектов: уведомлений, аналитики, начисления бонусов.
  5. Зачем нужны несколько провайдеров и чем это опасно?Нужны ради доступности, конверсии, стоимости и покрытия способов оплаты. Опасны удвоением работы: своя сверка на каждого, разные форматы вебхуков, разные правила возвратов. Главный технический риск — каскад после таймаута: операция могла пройти у первого провайдера, и попытка у второго создаст второе списание.
  6. Когда каскадное переключение допустимо?Только при подтверждённой неудаче: явный отказ провайдера по технической причине или недоступность соединения. При неизвестном состоянии сначала выясняется исход у первого провайдера — опросом статуса по своему идентификатору, — и лишь потом принимается решение. При отказе эмитента каскад бесполезен: другой канал получит тот же ответ.
  7. Как измерять эффективность антифрода?Суммой двух потерь: ущерб от пропущенного мошенничества плюс упущенная выручка от ложных отказов. Оптимум — минимум суммы, а не минимум первого слагаемого: нулевое мошенничество достигается отклонением всех операций и стоит дороже любого мошенника. Нужны и обратная связь по подтверждённым случаям, и регулярный пересчёт порогов.
  8. Почему у решения антифрода три исхода, а не два?Потому что средняя зона риска — самая массовая, и отклонять её дорого. Третий исход — усиленное подтверждение через 3-D Secure: операция сохраняется, а ответственность за мошенничество переходит к эмитенту. Отказ остаётся для явных случаев и списков блокировки.
  9. Почему решения антифрода должны быть объяснимыми?Потому что их придётся объяснять поддержке, клиенту и регулятору, а модель без объяснений даёт ответ «система так решила». Хранятся сработавшие правила и их значения, версия модели и итоговая оценка. Плюс обязателен процесс ручного пересмотра со сроком: ошибки будут, и клиент не должен попадать в тупик.
  10. Как KYC влияет на архитектуру?Появляются уровни идентификации, от которых зависят лимиты и доступные операции, а значит — проверки на каждом денежном пути, а не только в профиле. Добавляются хранение и защита персональных данных, журнал доступа к ним, сроки хранения и процессы перепроверки. Всё это дешевле заложить сразу, чем встроить потом.
  11. Какие требования AML доходят до кода?Проверка по санкционным и иным спискам до проведения операции, лимиты по суммам и периодам, правила на серии операций для выявления дробления, связь операции с подтверждающими документами, регулярная отчётность в заданном формате и техническая возможность заморозить операции клиента. Ключевое — «до», а не «после»: проверка после списания бесполезна.
  12. Клиент требует удалить данные, а операции хранить обязаны. Как быть?Разделить хранилища: движение денег фиксируется по внутреннему идентификатору без персональных сведений, персональные данные лежат отдельно и обезличиваются по требованию или по истечении срока. История операций остаётся полной, обязанность хранения не нарушается, а факт обращения и объём обезличивания фиксируются.
  13. Как сократить зону соответствия PCI DSS?Не пропускать карточные данные через свои серверы: форма провайдера во фрейме, его поля внутри своей вёрстки или переадресация на его страницу, а дальше работа по токену. У себя хранятся только маска, срок действия и токен. Отдельно проверяется, что номер карты не утекает в логи, трассировки и системы отслеживания ошибок.
  14. Что нельзя хранить никогда?Код проверки подлинности карты и содержимое магнитной полосы или чипа — ни в каком виде, включая зашифрованный и временный. Номер карты, если он хранится, маскируется при отображении и защищается криптографически. Самая частая утечка — не база, а логи и сохранённые тела запросов при отладке.
  15. Какие требования предъявляются к финансовому журналу?Неизменяемость записей, полнота, включая ручные действия, авторство каждой операции, точное время и учётный период, связи с операцией провайдера и документом-основанием, срок хранения в годы. Это не отладочный лог, а часть продукта: по нему отвечают на вопросы клиента, аудитора и регулятора.
  16. Чем дата операции отличается от даты учёта?Дата операции — когда она фактически произошла, дата учёта — к какому периоду она относится. Платёж в 23:58 последнего дня месяца учитывается в этом месяце, даже если запись создана в 00:03 следующего. Без разделения ежемесячные отчёты расходятся с данными провайдера на каждой границе периода.
  17. Что такое закрытие периода?Момент, после которого проводки периода считаются окончательными и не меняются. Всё найденное позже оформляется корректирующими операциями текущего периода со ссылкой на исходную. Технически это запрет на вставку проводок с учётной датой в закрытом периоде, который лучше держать на уровне базы, а не только в коде.
  18. Какие метрики нужны платёжному сервису сверх технических?Доля успешных операций в сравнении с тем же часом прошлой недели, распределение причин отказа, платежи в неизвестном состоянии старше порога, возраст незакрытых холдов, нерасследованные расхождения сверки, перекос в ledger, задержка вебхуков, доля споров и очередь возвратов. Сервис может отвечать за 50 мс без ошибок и при этом не проводить ни одного платежа.
  19. Как правильно делать ручные корректировки?Как обычную операцию системы: через тот же ledger, с теми же инвариантами, с обязательным указанием автора, причины и основания, желательно с подтверждением второго человека при крупных суммах. Прямой UPDATE по балансу не оставляет следов, и расхождение обнаруживается спустя месяцы, когда причину уже не восстановить.
  20. Обнаружены массовые двойные списания. Порядок действий?Сначала остановить источник: отключить повторы или каскад, чтобы дубли перестали появляться. Затем найти их по своему идентификатору операции и данным провайдера, а не по жалобам клиентов. Вернуть деньги проактивно и сообщить клиентам самим — это дешевле волны споров. После стабилизации — постмортем: почему повтор был без ключа идемпотентности и почему сверка не поймала это раньше.

Возьмите один реальный платёж в своём проекте и выпишите его путь: когда создан, когда авторизован, когда списан, когда деньги пришли на счёт компании. Найдите, где в системе фиксируется каждый момент.

РезультатПонимание, какие стадии система вообще различает, и обнаружение тех, что склеены в одну.

4. Ключ идемпотентности

РезультатЗащита от двойного списания на уровне базы, а не на уровне надежды.

5. Вебхук под обстрелом

Отправьте своему обработчику вебхука: правильный запрос, запрос с испорченной подписью, дубль правильного и запрос с событием более старым, чем текущее состояние. Проверьте, что система реагирует правильно на все четыре случая.

РезультатЧетыре сценария, которые в продакшене приходят в первую же неделю, проверены заранее.

6. Мини-ledger

РезультатРабочее понимание двойной записи и готовая проверка целостности.

7. Воспроизвести гонку

РезультатЛичный пример гонки на деньгах и тест, который её ловит.

8. Убрать сеть из транзакции

9. Статусная машина

Финал · подготовка

План подготовки на 4 недели

Расчёт на час-полтора в будний день. Тема плохо учится по определениям: почти каждый пункт полезно проверять на реальной интеграции или хотя бы на песочнице провайдера, где сбои можно вызвать намеренно.

Неделя 1 · Деньги и поток

База

Задачи недели

Перестать думать о платеже как об одном запросе и научиться обращаться с суммами так, чтобы они сходились.

Что сделать

  • Воспроизвести накопление ошибки во float и найти такое место у себя (задание 1).
  • Написать объект Money с распределением остатка и тестами (задание 2).
  • Разобрать путь одного реального платежа по стадиям и найти, где фиксируется каждая (задание 3).
  • Выписать, какие участники задействованы в вашей схеме оплаты и за что отвечает каждый.
  • Проверить, есть ли в системе двухстадийная схема и что происходит с просроченными холдами.

Результат недели

Умение объяснить на своём примере, где находятся деньги в каждый момент и почему сумма хранится именно так.

Неделя 2 · Надёжность

Механика

Задачи недели

Закрыть сценарии сбоя, из-за которых деньги списываются дважды или теряются между системами.

Что сделать

  • Ввести ключ идемпотентности с уникальным индексом и тестом на повтор (задание 4).
  • Обстрелять обработчик вебхука четырьмя сценариями и починить найденное (задание 5).
  • Убрать сетевые вызовы из транзакций базы и измерить время блокировок (задание 8).
  • Свести присваивание статуса в единственный метод перехода (задание 9).
  • Разобраться, что происходит в вашей системе при таймауте провайдера, и завести состояние «результат неизвестен».

Результат недели

Ни один сбой сети больше не приводит к двойному списанию или потерянному платежу, и это подтверждено тестами.

Неделя 3 · Учёт и сверка

Точность

Задачи недели

Научиться отвечать на вопрос «откуда взялась эта сумма» и обнаруживать расхождения раньше клиентов.

Что сделать

  • Собрать мини-ledger и провести через него оплату с комиссией (задание 6).
  • Воспроизвести гонку на списании и закрыть её блокировкой (задание 7).
  • Сделать сверку за сутки и разобрать каждое расхождение вручную (задание 10).
  • Реализовать частичный возврат с проверкой инварианта под блокировкой (задание 11).
  • Написать запрос проверки инварианта двойной записи и поставить его в расписание.

Результат недели

Баланс выводится из истории, расхождения находятся автоматически, а возврат больше не может превысить платёж.

Неделя 4 · Контур целиком

Финиш

Задачи недели

Подняться с уровня отдельных операций до контура: отказы, риски, требования извне и эксплуатация.

Что сделать

  • Составить карту отказов платёжного пути и найти слепые зоны (задание 12).
  • Описать сагу оформления заказа с компенсациями и переставить шаги по обратимости (задание 13).
  • Проверить, не утекают ли карточные данные в логи и системы ошибок (задание 14).
  • Завести денежные метрики и проверить алерты искусственными условиями (задание 15).
  • Прочитать требования провайдера к спорам и проверить, что доказательства действительно сохраняются.

Результат недели

Готовность обсуждать платёжный контур целиком: границы сервисов, поведение при отказах, риски и то, как всё это наблюдается в продакшене.

Что помогает на собеседовании

Бонус
  • Начинайте со сценария отказа. На любой вопрос про платежи сильный ответ содержит фразу «а если запрос прервался здесь». Это моментально отличает человека, который видел продакшен, от того, кто читал документацию провайдера.
  • Называйте цену ошибки в деньгах. «Двойное списание» звучит абстрактно, «двойное списание на тысяче клиентов плюс волна споров плюс повышенный тариф от платёжной системы» — конкретно. Финтех — область, где технические решения принято обосновывать суммами.
  • Различайте бизнес-отказ и технический сбой. Отказ эмитента повторять нельзя, таймаут — можно и нужно, но только с ключом идемпотентности. Эта пара различений всплывает почти на каждом интервью и сразу показывает уровень.
  • Помните про третий исход. На вопросы о надёжности отвечайте не «успех или ошибка», а «успех, ошибка и неизвестность». Обработка третьего случая — суть всей темы.
  • Не обещайте распределённую транзакцию. Предложение использовать двухфазную фиксацию с внешним провайдером — заметный красный флаг. Правильный ответ — сага, идемпотентность и сверка.
  • Упоминайте сверку без напоминания. Кандидатов, которые сами говорят «а ещё это поймает ежедневная сверка», заметно меньше, чем тех, кто помнит про идемпотентность. Это дешёвый способ выделиться.
  • Будьте готовы к вопросу про легаси. «Переписать платежи с нуля» — слабый ответ: миграция денежных данных дороже и рискованнее любой другой. Сильный — двойная запись параллельно старому механизму, сверка двух контуров и переключение после схождения.
  • Знайте границы своей ответственности. Требования регулятора и правила платёжных систем меняются, и никто не ждёт, что разработчик помнит их наизусть. Ждут другого: что вы понимаете, какие из них влияют на архитектуру, и умеете задать вопрос комплаенсу до, а не после реализации.
